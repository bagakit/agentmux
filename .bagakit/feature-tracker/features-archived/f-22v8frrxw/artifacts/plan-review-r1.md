## 用户原话

> 「还是应该弄个能渲染 markdown 的组件, tracker 里头说清楚吧. 现在的支持不好」

## 现状的四个短板（对着真实内容实测，非感觉）

拿用户截图里的内容跑现有解析器，输出是：

| 构造 | 现状 |
| --- | --- |
| **表格** | 整块变成一个 paragraph，`\|---\|---\|` 原样显示——**这正是截图里最刺眼的那处** |
| **嵌套列表** | `- 顶层 / ␠␠- 嵌套 / - 又一项` 被压成 3 个平级项，层级丢失 |
| **引用块** | `> 引用` 当普通文本 |
| **水平线** | `---` 当普通文本 |

表格最要紧，因为 Agent 特别爱用表格陈述对照关系。

## 换成成熟解析器，而不是继续自己写

项目原则：「优先用成熟的、有人维护的库。没有明确理由别自己重写」「先翻项目里已有的依赖能做什么」。

**已翻过**：仓库现有依赖中没有任何 markdown 解析能力（monaco 只带语法高亮，不是渲染器）。

**候选与体积**（`npm view dist.unpackedSize`）：

| 包 | 版本 | 解包体积 |
| --- | --- | --- |
| `remark-parse` | 11.0.0 | **19 KB** |
| `react-markdown` | 10.1.0 | 51 KB |
| `micromark` | 4.0.2 | 204 KB |
| `marked` | 18.0.11 | 468 KB |
| `markdown-it` | 15.0.1 | 1916 KB |

**选 `remark-parse`**：它只做「文本 → mdast 语法树」，**不产出 HTML**。这恰好保住我们已经确立的安全
性质——Agent 输出是不可信文本，我们把 mdast 节点映射成 React 元素，`dangerouslySetInnerHTML` 仍然
从不出现，因此仍然**没有东西需要 sanitise**（风险面为零而非"已被过滤"）。GFM 表格经
`remark-gfm` 扩展获得，同属 unified 生态。

不选 `marked` / `markdown-it`：它们的产物是 HTML 字符串，采用即等于同时接下"必须永久正确过滤它"的
责任——这是我们此前刻意避开的。`react-markdown` 会连带一整条 rehype 渲染链，而我们只需要语法树。

## 删掉手写解析器，不留兼容层

按「不保留向后兼容，过时的直接删」：`agent-markdown.ts` 的手写解析器**整个删除**，不保留为 fallback。
它的测试（`agent-markdown.test.ts` 中针对解析器内部的部分）随之替换为针对新管线的断言；
**渲染层的行为断言必须保留**——标题不靠字号、链接走出网 seam、raw HTML 不被解释、纯文本原样呈现。

## 不变的约束（沿用既有决定）

- **多级标题不得有字号差别**：body 13px，所有层级继承，靠字重与留白分级（用户原始要求 + 密度合同）
- **只在 turn register 渲染**，机器行保持纯文本
- **链接是 button 不是 `<a href>`**：不可信输出里的 `<a>` 是导航逃逸口，由 Main 裁决并归一化
- **纯文本不进解析器**：避免把从来不是 markdown 的句子重排
