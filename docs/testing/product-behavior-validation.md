# 从产品需求到行为验证

本文说明怎样从已确认的产品需求／设计推导可证伪行为、枚举关键场景并验证实际结果。适用于功能与缺陷修复，也适用于 Agent 上下文调整；按本次影响选择范围，不要求穷举所有组合。实现验收、变异与真实产品调用链仍归[测试策略](strategy.md#任务验收与假绿防护)，本文不增加发布门禁或评测框架。

## 从需求写出可证伪行为

先定位 owning 需求／设计及适用版本，区分已确认约束、当前实现和待讨论预期。每项行为写清：谁在什么条件下，凭什么权限，对哪个准确对象做什么，外部能观察到什么结果；失败、未知与恢复时保留什么。尚未确认的产品选择可先探索，但不冒称既定 GT。

把“Agent 理解启动知识”改写成可观察的问题，例如：实际收到哪些输入、是否按当前任务读取所需模块、实际执行了哪个动作、是否保住原身份和授权。提示里出现一句规则、Agent 复述正确或声称会执行，分别只能证明对应观察，不能直接证明行为已发生。

预期行为（GT）先于查看候选结果确定，引用已确认设计、准确对象上的权威协议或原始回执。当前代码和模型答案不能单独为自己提供预期；存在冲突时保留原来源，指出待裁定的问题，不为当前结果倒改答案。

## 枚举有区分力的场景

从受影响的业务分支与风险选择场景，逐项问哪些条件会改变预期：

- 角色、任务阶段和入口：新任务、等待、恢复或继续；不同入口是否真的走同一行为。
- 对象、来源与授权：准确目标、合法多处绑定、错误目标、来源缺失或未经授权。
- 状态与时序：正常、失败、观察未知、并发、回执丢失，以及原身份上的重试／恢复。
- 消费与成本：实际消费者、必要后续读取，以及无关对象增长是否放大本次工作。

这些是选场景的维度，不是每项改动都要执行的全量清单。相同输入与相同行为的入口可以合并，但记录等价依据和覆盖入口；会改变授权、输入、恢复或消费路径的差异不能合并。保留最小而有区分力的集合，注明未覆盖范围。

以下以[启动握手与自命名](../design/behavior/agent-capabilities-and-messaging.md#启动握手与自命名)及[渐进加载](../design/behavior/public-control.md#基础-skill模块发现与渐进加载)为例；以下均为推导示例，不表示本轮已执行，也不是固定题库或完整验收清单。

| 场景差异 | 要区分的预期 | 对应观察 |
| --- | --- | --- |
| 新任务已知业务域 | 能辨认当前任务与第一步，按需读取相关模块 | 实际输入、原只读身份初始化及后续模块读取／动作回执 |
| 无具体任务的新启动 | 不虚构任务，等待不延后原只读身份初始化 | 原输入、身份读取及实际等待行为 |
| 身份或空间观察缺失 | 缺失保持未知，已有健康能力不因观察缺口消失 | 同次缺失事实、已有能力和后续操作结果 |
| 恢复时原操作结果未知 | 保原来源与操作身份，不自动重复副作用 | 原保存输入、operation 及恢复后的真实回执 |

## 验证实际行为

为每项预期选择能观察该结果的最小真实消费链。纯组合测试可证明生成内容，实际 CLI／公共接口调用可证明发现与回执，隔离产品场景可证明操作及结果；需要模型选择行为时，记录模型实际可见的输入、读取和动作。沿原测试策略选择变异、产品调用链或视觉等证据，不用另一层通过替代。

冻结本轮场景、输入与预期后执行，记录源码／构建候选、实际输入、操作顺序、原结果及证据引用。上下文样本沿实际生产 composer／guide 生成，明确合成身份、任务、文件和外部内容的边界；不靠手写一个理想 prompt 代替生产输入。测试使用隔离资源，不向用户健康 Run 注入探测输入。

比较预期与实际观察，区分产品缺陷、fixture 错误、预期错误与评审分歧。修正后重验相关场景，保留原结果；若题目、设计或输入发生变化，记录新版本，不将旧通过或旧确认自动沿用。历史样本可作回归素材，不自动成为每次改动的全量硬 gate。

## Agent 上下文的两种默认诊断

Agent 上下文变更默认只对受影响的场景分别准备以下两类评价；可复用未变的有效证据，不要求每次全量、多轮或跨模型评审，普通功能修复不因此增加模型评价义务。两类材料与评审上下文隔离，先冻结实际输入，再分发给独立评价者，不把已看过答案的重试称为盲测或独立留出。

| 评价 | 提供什么 | 观察什么 |
| --- | --- | --- |
| 知情评价 | 当前需求、任务及实际输入 | 职责、任务与第一步是否清楚；有无重复、歧义、无关负担或遗漏 |
| input-only 盲读 | 仅实际允许 Agent 看见的输入；不附角色／场景标签、设计或 GT | 评价者能复述哪些职责、任务边界与下一步，哪些仍无法判断 |

可直接使用的盲读提问：“只根据以下输入，说明你认为自己的职责、当前任务、边界和下一步；指出无法判断的部分。只复述，不执行任务。”评价核对预期行为的理解，不要求逐字复述全部事实。知情评价则要求指出具体输入及其影响，判断哪些可安全后置或合并，保留当前阶段必要的信息。

信息负担按完成当前阶段所需的输入和必要后续读取总量判断，不只比较首包字数。若场景依赖原历史、等待后续任务或允许按需查模块，盲读只能说明本次材料可知的范围，不能把缺少未提供历史直接判为产品缺陷。发现误解后回到需求、实际输入、GT 和评审条件核对，允许按当前需求修订或删除失效题目，不为提高分数向提示塞答案。

两类诊断可发现清晰度和负担问题，不证明实际送达、权限、模型采用或操作成功；这些结论仍需上一节对应的行为证据。无需合成总分，用具体观察说明有效、部分有效或未知的范围，并保留已观察到的不符合预期。

## 仅在需要时记录人类 GT 裁定

事实型预期引用原设计、协议或真实记录即可。只有预期涉及尚未确认的产品判断、证据冲突或人类独有事实时，才预留人类确认栏；允许为空并明确未确认，普通测试不要求逐题人工审批。尚未裁定的预期标未知／待确认，不据此判产品失败，也不影响已有独立事实的验证。

确认绑定具体 case、实际题目／输入的版本及内容 digest、适用设计版本、确认的实际内容和原始人类证据。署名用于归属记录，本身不是身份认证或新增授权；Agent 不得代签，不能仅因模板已生成、模型赞同或存在署名就声称人已确认。人类确认预期也不代表实现通过或用户验收。

```text
结论：符合／不符合／未知；有效范围、未覆盖及下一步：

```
