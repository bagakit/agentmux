## 我先前的判断，以及它为什么错

第一份采样：2461 样本全在主线程、调用图 6696 行、嵌套 **344** 层深。
我据此判为「主线程跑飞的同步递归」。**这个判断是错的**，两条实测把它推翻：

**(1) 两份采样的热点地址几乎不重合。** 第一份 top 热点 `0x1505afcfc`×215、`0x150ef4f98`×147、
`0x1503ddc14`×110；第二份只有 `0x150ef4f98` 是共有的（×117），其余全不同。
**同一个死循环在两次采样里应当高度重合**——不重合说明它不是在原地转，而是在**持续做新工作**。

**(2) CPU 与 RSS 都在波动，不是单调。** CPU 108.5% → 23.0%；RSS 970MB → 773MB → 919MB。
死循环不会自己降下来；内存回落说明是**周期性分配+回收**，不是无界泄漏。

教训：**深度大 ≠ 死循环。** 344 层深只说明调用栈深（JS 框架 + 深组件树足以做到），
要判「是不是同一个循环」得看**两次采样的热点地址是否重合**，而不是看深度。
我拿一份快照的形状当成了稳态的证据。

## 现场真实形状

- **主进程也在烧 44.3% CPU**，而它的栈是正常的 `__CFRunLoopRun` / `CFRunLoopServiceMachPort`——
  **不是死循环**。所以这不是渲染进程单方面失控，是**两端一起在持续工作**。
- 渲染进程时间分布：Electron Framework 4875 帧、`<unknown binary>` 1297 帧（JIT 出来的 JS）。
  **CoreText 只有 26 帧**——字体/文本测量是噪声，先前顺着它推理会走偏。
- **四个文件系统观察者子进程未释放**：pid 77061–77064，父进程均为主进程 72361，
  **同一秒（14:40:20）启动，存活 9h29m**。命令行确证是 `--input-type=module --eval` 里
  `import { watch } from 'node:fs'` 的观察者。

这正是 `store.ts` 注释记载过的那一族（#559）：workspace 记录消失后，
`state.tabs` 里的文件 Tab 仍各自攥着一个 Main 侧观察者子进程，不可达却不释放，**一直活到 app 退出**。

## 观测能力的缺口（用户点名要查的那件事）

- `~/Library/Application Support/dev.agentmux.desktop/crash-log.ndjson` 最新一条是 **09-13/09-14**。
  一个持续 9 小时、吃满一个核的异常状态，**在崩溃日志里一个字都没留下**——因为它不崩溃。
  只记 crash 的日志，对「不崩但坏了」这一类**结构性失明**。
- 全仓没有任何**计数类**判据（渲染次数 / 调用次数上界，实测零命中）。现有"性能"测试全是结构契约
  （合批、让出、死区、内存预算协调）。**结构判据只问「有没有这条边」，不问「这条边被走了多少次」。**
  一个持续重入在结构上完全合法，所以测试全绿。
- 没有「长命子进程数量」的判据。四个观察者活 9 小时无人报警，只能靠人手动 `ps` 发现。

## 下一步判据（按可得性排序）

1. **渲染进程 devtools console**——唯一能定名的证据。看 `Maximum call stack size exceeded`（成环那支）、
   `getSnapshot should be cached` / React #185（selector 那支）、或反复出现的同一条 `reportError` 文本。
2. **观察者子进程计数**：关掉若干文件 Tab / 移除 workspace 后，`ps` 数那四个 eval 子进程是否减少。
   不减少即证实泄漏仍在，且这条判据可自动化（进程数上界）。
3. 不要再用「深度」当死循环判据；要用**跨采样热点地址重合度**。
