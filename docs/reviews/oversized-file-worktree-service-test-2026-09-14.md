# 超大文件评审：worktree-service.test.ts（以及那次评审真正找到的东西）

Status: decided — 不拆

日期：2026-09-14。触发：`apps/desktop/test/worktree-service.test.ts` 越过 1000 行（1297 行），
由本人提交 a9aa6ffa 加的 106 行推过阈值，按「一旦发现单个超大的文件，立刻分析是否应该结构化」
就地评审。

## 结论

**不拆。** 重开条件写在最后一节。

## 评审过程中改变结论的那件事

一开始要拆的理由有两条：1297 行，且整份文件跑 **65.4 秒**。第二条是主要理由——vitest 按**文件**
并行，把 28 条真 git 用例切出去，理论上能把这条关键路径砍短。

于是先去量这 65 秒花在哪，而不是直接动刀。逐步计时的结果：

| 夹具步骤 | 耗时 |
| --- | --- |
| `mkdtemp` + `mkdir` | 0ms |
| `git init` | 22ms |
| `git add` | 16ms |
| **`git commit`** | **2057ms** |
| `git branch` | 22ms |
| `git worktree add` | 38ms |
| `rm -rf` | 7ms |

一句 `git commit` 占掉 2057ms，其余六步加起来约 100ms。真因是本机 `~/.gitconfig` 里一条
`core.hooksPath` 指向公司提交钩子，而 `runProcess` 用 `{...process.env}` 派生子进程环境，于是
**仓内每一个测试夹具都在跑那个钩子**。28 条真 git 用例 × 2 秒 ≈ 56 秒，正是这份文件慢的全部来源。

修的是隔离而不是文件结构（`vitest.setup.ts`，提交 3f40a183）：**65.4s → 5.8s，39 条全绿。**

拆文件本来能买到的那点并行度，在这个真因面前是舍本逐末：拆完两份文件各自仍然跑着那个钩子，
总 CPU 时间一秒不少，只是分摊到两个 worker 上。**先量再拆**，这条评审的真正产出是那次测量。

## 现在还该不该拆

去掉那 56 秒之后，原本的两条理由只剩一条（行数），而它单独不足以拆：

- **运行时间 5.8 秒**，在本仓测试文件里属于普通偏快，不再是关键路径。
- **只有一个被测对象。** 整份文件测的是 `WorktreeService` 一个类：创建、注册、删除、fan-out 取舍。
  按「快/慢」或「假 host / 真 git」切，切出来的是**按夹具类型分组**的两份文件，而不是两个独立的
  主题——读的人要回答「worktree 删除这块都覆盖了什么」时，得同时打开两份。这种切法把一个
  内聚的主题拆成实现细节的分类，是把行数摊薄，不是把结构讲清楚。
- **夹具共享。** `buildLocalWorktreeFixture` / `buildFanOutFixture` 被两类用例共用。拆文件就要
  把它们提到共享 helper 里，于是多出一个只为拆分而存在的模块，以及一处新的跨文件耦合。
- 文件内部**已经是分好段的**：解析器纯函数 → 假 host 用例 → 真 git 创建 → 真 git 删除 → fan-out。
  今天缺的不是文件边界，是这些段落没有各自的 `describe`（全文件只有一个顶层 `describe`
  套 37 个 `it`）。真要降认知负荷，加分组 `describe` 比拆文件便宜得多，也不引入共享 helper。

## 分组 describe：本轮没做，理由记下来

上面那条建议本轮尝试过，**没有落地**。用脚本按行号插入 7 个分组 `describe` 并配对闭合括号，
结果括号配错——脚本按行号插入，看不见嵌套深度，闭合位置落在了错的层级上。已撤回，文件与
a9aa6ffa 的版本逐字相同，39 条用例全绿。

留给下次的做法：这种改动要么手工逐段改（37 个 `it` 的边界是肉眼可判的），要么用能理解语法树的
工具，不要用按行号缝括号的脚本。它属于纯结构调整、不改任何断言，所以适合在这份文件安静时
单独做一次，而不是夹在别的改动里。

## 重开条件（任一成立即重新评审）

1. 行数越过 **1500**；
2. 单文件运行时间重新超过 **15 秒**（今天 5.8s；这条是防止又一个环境泄漏被当成「测试本来就慢」）；
3. 出现**第二个被测对象**——即这份文件开始测 `WorktreeService` 之外的东西，那时按对象拆，
   而不是按快慢拆。
