# Desktop and remote Core updates

This document describes the current source mechanisms that update the Desktop application and a remote Core: how a candidate's route is chosen, what each route keeps running, and which owner confirms each outcome. It is not an installation receipt. Route selection lives in [update-local.mjs](../../apps/desktop/scripts/update-local.mjs) and [update-policy.ts](../../apps/desktop/src/shared/update-policy.ts). Product constraints belong to the [interaction SSOT](../design/agentmux-desktop-interaction.md).

The commands, their order, signing setup steps, resource discipline and failure continuation belong to the [macOS packaging guide](../guides/macos-packaging.md); this page names scripts only as mechanism owners and does not add another installer or acceptance gate.

| Candidate change | Route | Running work |
| --- | --- | --- |
| Renderer only; host and ctxmux fingerprints match | Activate versioned frontend resources | Main and Runs stay alive; the renderer checkpoints drafts, dirty buffers and layout, then reattaches |
| Main, preload, IPC, Core or dependencies changed; ctxmux unchanged | Package, install and gracefully restart AgentMux | Existing ctxmux Runs remain available; Core owns attachment and semantic resume |
| ctxmux fingerprint changed or fingerprint identity is unknown; ordinary update | Require runtime compatibility/resume review before installation | Review rejection leaves the current application and Agents running |
| Explicit UI-only install intent | Install the application while retaining the existing compatible Runtime | UI and Native outcomes are reported separately; Native upgrade is deferred |

## Build and route selection

Renderer value imports use Core's portable public subpaths. Capsule settings and Toolkit results consume the unchanged object-link formatter through `@agentmux/core/sharing`; the Core root entry also exports Node Runtime owners and is not a browser entry. [The component bundle check](../../apps/desktop/scripts/verify-capsule-browser-imports.mjs) compiles both actual consumers for the browser and reintroduces each root import to verify that this dependency regression fails.

The frontend loader arrives only with a full application installation; until one has been installed, no Renderer-only route exists. The general route ([update-local.mjs](../../apps/desktop/scripts/update-local.mjs)) and the Renderer-only route ([update-renderer.mjs](../../apps/desktop/scripts/update-renderer.mjs)) both build before selecting or activating a release, and the Renderer-only route rejects a candidate whose host or runtime identity changed. [package-macos.mjs](../../apps/desktop/scripts/package-macos.mjs) refuses a dirty source tree before building and rejects the candidate if the commit, tree or status changed while it was packaging. LaunchServices smoke and the installed GUI relaunch remove the caller's `ELECTRON_RUN_AS_NODE` from a copied environment; intentional Node-mode CLI, SDK and semantic Host launches keep their own mode.

Release compatibility describes the actual candidate payload selected by the packaging owner. Main, Host, preload, mobile, runtime dependencies, resources, the prepared Electron artifact and branding belong to the application identity; Renderer resources have their own release identity. Copying and fingerprinting consume the same package facts. A normal successful build prepares the original Electron artifact and finishes mobile copying before publishing its release; missing or mismatched candidate artifacts reject that release without changing the installed application or its Runs. Source commit/tree fields report provenance and do not turn a Renderer-only change into an application update.

The private LaunchServices verification in `package-macos.mjs` gives launch, the ready receipt, Runtime ownership and normal application exit one shared 300-second absolute deadline. It is a hang guard, not a speed requirement: a freshly signed candidate's first launch on a loaded machine can take most of a minute before Main writes anything. Waiting for the relaunched installed GUI to prove its activation uses the same guard, because a large restored workbench can take longer than half a minute to answer. Main publishes ready only after connecting its configured local semantic Host, so the window includes that connection. Each stage consumes the remaining budget; it does not restart the clock. Exact product, version, packaged executable and Runtime ownership checks still apply. Exceeding the window rejects this candidate, without declaring a user Agent unhealthy. The original scoped cleanup remains authoritative: forced termination or unconfirmed cleanup cannot pass verification, and an unknown Runtime cleanup preserves its diagnostic profile.

The App and standalone runtime Core reuse the installed dependency graph owner in `scripts/package-dependencies.mjs`, including present optional packages and physical peer contexts. The assembled Core remains self-contained for portable extraction; Main roots share their own module scope. The planner resolves roots and sibling slots before copying, preserves shared peer objects, and rejects a candidate whose graph cannot be represented correctly. Host-native execution evidence does not qualify another target's native dependencies.

## Package artifact lifetimes

[The installer](../../apps/desktop/scripts/package-macos.mjs) creates an exclusive stage and records its object identity. On copy/signature/pre-cutover failure it reclaims that object only while the original signed source still matches its package, executable and signature seals. Cleanup observations do not qualify installation. Explicitly adopted stages and candidates retained after cutover or rollback remain available for continuation; diagnostics preserve the original operation result.

[The repository packaging publisher](../../scripts/package-artifact-publisher.mjs) owns completed archive generations consumed by the Mac DMG entry and Linux CLI entry; reusable Linux build calls keep their caller-supplied output boundary. It returns a structured publication/cleanup result; each entry owns its output format, including the Linux CLI's single JSON document. It publishes an immutable generation before retention and checks the original receipt and payload identity again after occupancy observation. Mounted DMG and open-file observations concern only deletion candidates; an observation hang ends as unknown, retaining the archive. These observations never terminate an App, Agent or Runtime. Artifact receipts do not authorize deletion of user data, worktrees or old application bundles. Retention and operational steps live only in the [packaging guide](../guides/macos-packaging.md#产物的自动收尾).

## Signing identity

[preflightMacosSigning](../../apps/desktop/scripts/macos-signing.mjs) qualifies signing at the start of [package-macos.mjs](../../apps/desktop/scripts/package-macos.mjs), before any build, candidate copy, signing or installation work. Environment certificate、本机 `identity.json` 建立／信任步骤与 `--ad-hoc` 边界以 [macOS 打包《签名身份》](../guides/macos-packaging.md#签名身份) 为准，本文不重复命令。

A missing or mismatched identity rejects the candidate cheaply and keeps the installed App and healthy Runs. The signing module owns exact configuration parsing and signed-output checks. Authorization continuity, the first identity transition and actual OS confirmation belong to the [screenshot capture contract](../design/behavior/capture-and-recording.md#资源权限与验收); signing Source alone is not an OS authorization receipt. Branding includes `NSScreenCaptureUsageDescription`, and packaged identity verification checks the actual plist.

## UI-only installation and rollback

UI-only intent is an explicit route that installs the application while keeping the existing compatible Runtime; on the packaging script it is valid only together with installation. It never declares Native upgraded and never replaces the daemon. [installApplication](../../apps/desktop/scripts/package-macos.mjs) compares the actual runtime trees and qualifies the existing listener. Without an outgoing workbench observation, an active candidate GUI still leaves complete workbench recovery `unknown`.

Frontend rollback, from the rollback mode of [update-renderer.mjs](../../apps/desktop/scripts/update-renderer.mjs) or **View > Revert frontend update** ([application-menu.ts](../../apps/desktop/src/main/application-menu.ts)), returns to the preceding compatible frontend. Rollback changes code, not user edits or Session facts; reapplying the current release preserves the rollback pointer.

## Owners and activation

Main owns `renderer-updates/` beneath Electron userData. Immutable release directories contain a manifest binding host/runtime identity and every resource hash. The release id includes compatibility identity, so equal UI bytes built for different hosts cannot collide. No symlinks, extra files or incomplete bundles are accepted.

The publisher atomically replaces `active.json`. Main serializes activation and rollback, validates the complete release, asks the current renderer to flush its checkpoint, and loads the candidate. A nonce-bound ready receipt follows renderer initialization. Only then does Main record success in `status.json`; the CLI waits for that receipt instead of treating staging as delivery. Failed checkpoints leave the current page loaded. Failed candidate startup restores the previous compatible page. Cold startup also validates and recovers staged candidates. Requests arriving during activation are not overwritten by the preceding request's completion.

The original Main loader owns two bounded document sources: the committed App document and its one in-flight load. Main navigation facts promote only a source named by that loader. An update keeps the serving document callable before the next navigation commits; the candidate preload may call before its ready receipt. Native load settlement releases only that attempt's pending source. A ready timeout alone does not revoke an in-flight navigation or the document already serving, including during rollback.

The App IPC registration owner admits the original live main frame against those sources before auditing or invoking any ordinary App handler. It never grants a new source from the frame's current URL. Capsule document IPC keeps its separate Browser/document admission and cleanup; Workbench child portals retain the original root preload path.

### Checkpoint scope

The frontend uses the existing workbench persistence owner for composer drafts, dirty buffers and layout. Clean file content is re-read from disk. Core Sessions, PTY bytes, attachments, timelines and process state are never copied into this checkpoint. Electron file-origin storage continuity is verified in an isolated native profile.

## Restart boundary

### Artifact identity

Source releases and the installer fingerprint the actual ctxmux artifact directory for the current `platform-arch`. Adding or changing another platform's artifact does not request a Native upgrade on this host. Changes to the current artifact, including its manifest, binaries or SDK archive, still change the Native fingerprint; an absent artifact remains an error rather than a guessed match. Main and Core changes still require full application installation and semantic Host reload even when this fingerprint is unchanged.

### Running application and Runtime continuity

The installer compares the actual installed and candidate host artifacts before requesting quit. For an existing workbench, an unchanged Native fingerprint does not replace the public SDK's positive confirmation of the serving Runtime and original Runs. A graceful-quit timeout stops installation; it never escalates to force-killing the user's application or Runs. The confirmed semantic Host and its bound Node descendants belong to that namespace, rather than the GUI quit barrier. The installer signals only the Host after normal GUI exit and waits for its original workers to close themselves; unknown modes, changed identities and other GUI workers remain protected. Activation, preserved workbench, Session/Run/PID continuity and Native upgrade are separate outcomes; an unavailable observation cannot stand in for confirmation.

The installation helper observes the original semantic Host through the shipped public owner identity and fenced bootstrap contract. Bootstrap allocates no semantic consumer or subscription; the helper closes only its RPC client. Real subscription owners still release their own consumers. Observation and connection-disposal failures remain explicit, while an unowned cleanup call must not obscure a successful observation.

[observeApplicationProcesses](../../apps/desktop/scripts/package-process-scope.mjs) returns current `serving` PIDs and an `admissions` history retained for the installer operation. An admission remains after that exact process exits; iterating all `admissions` as if they were live prevents a completed quit from settling. Current membership and UID/PID/birth bindings determine liveness; retained history preserves the original ownership evidence. A shared executable alone does not make a semantic Host or external Node client part of the GUI.

The installer retains auxiliary Desktop presentation and startup-check observations verbatim; their field evolution does not authorize or block installation. Loaded identity, storage, original topology, independent focus and healthy Run bindings keep their strict validation and continuity checks. Restart expectations follow the existing [private Browser contract](../design/behavior/browser-workface.md#匿名-browser): only the outgoing private URL is projected to an empty page. Incoming observations stay unmodified and strictly checked, so a retained private URL cannot pass as a valid restart.

Connection credentials stay with the executing Host's own store across an application update; their storage, permissions and the explicit conversion of older values are defined only in [Host credential storage](../../apps/host/credential-storage.md). An application update does not itself convert or certify stored credentials.

### Native handoff

Installer process-mode and code-identity observations run in the original Node/Electron runtime through `package-native-observation.mjs` and Core's shipped Koffi dependency. The original installer still owns process admission, inherited image descriptors, architecture and signature checks, child completion and resource cleanup; these reads require no development-tool interpreter on the target.

完整安装与 `--ui-only`／`--runtime-reviewed` 等入口选择、产物路径与安装位置以 [macOS 打包《入口、产物与安装位置》](../guides/macos-packaging.md#入口产物与安装位置) 为准。Changed runtime trees require a nonempty review artifact; the artifact does not prove continuity by itself—the installer also uses the public same-Runtime planned-exec path and confirms the handoff before starting the new GUI. UI-only intent defers that Native transaction and retains the compatible service. Neither route may treat missing startup provenance as proof that healthy Runs must be replaced.

Core and the installer use [ctxmuxOwnerReceiptPath](../../packages/core/src/runtime-paths.ts) to address product provenance by the exact public Runtime ID, daemon instance and artifact manifest digest. A late writer records only that tuple; same-process exec into another artifact has a distinct receipt. [The installer](../../apps/desktop/scripts/package-runtime-upgrade.mjs) reads the preflight tuple as a diagnostic and publishes the candidate tuple only after the original process, state and Runs confirm handoff. An absent or stale receipt does not override verified current kernel, manifest and public protocol facts. Existing legacy receipt files are retained without being read as a fallback.

A changed binary alone does not authorize killing the daemon. If neither Session retention nor semantic resume is possible, explain the loss and obtain the user's explicit confirmation before any destructive restart. The ordinary updater has no force flag that bypasses this boundary. Task acceptance and visual review follow [AGENTS](../../AGENTS.md); packaging reuses their evidence and does not add unrelated regression or review work as an installation prerequisite.

The [remote Core maintenance consumer](../../packages/core/src/remote-core-upgrade.ts) first binds the current Core and Native process images, source manifests, namespaces and held state leases through [OS inspection](../../packages/core/src/remote-core-upgrade-programs.ts). The original producer's public RPC and Native Hello then establish the current identities. A second inspection confirms the same physical objects and reads only the receipt address derived from those identities and that manifest. Missing or mismatched product provenance is reported in the maintenance check; verified current authority continues to protect the exact update and original Runs.

When the serving Native does not satisfy the candidate Core's Runtime contract and the candidate requires a newer protocol generation, the same maintenance operation can instead perform a reviewed Native cold replacement. It requires the serving Native to persist its runtime ID in its state directory. The check reads every Native Run through the serving Native's own SDK, the same reader the Core-only path uses, and the admission pins the running Run set with the Native instance and process birth identity. Execution stops the original Core, sends the original Native process its shutdown signal and waits for that exact process to exit, copies the complete Native state directory (database, WAL, shared memory and replay files, with owner and modes) into the operation's own location, and only then starts the candidate Core, which activates the candidate Native on the same state directory and socket. Reconciliation requires the same runtime ID, a new daemon instance, every original Session/Run binding, the previously running Runs reported interrupted or exited, and no retained history below its earlier durable position; only then is the release named current. A confirmed failure before the candidate Core starts restarts the original Core from its original release and arguments, which activates the original Native on the unchanged state directory; an uncertain result after that is inspected read-only and never replayed. The state copy is the only route back to the old Native, because the candidate may write store objects the old version refuses. Behavior and review rules are owned by the [remote maintenance contract](../design/behavior/session-recovery.md#联邦-runtime-与远端恢复边界).

A first install from the App reuses the same maintenance owner and programs. A read-only probe over SSH establishes Linux x64, a sufficient glibc, no installed Core under the target prefix and no owner on the target socket. Execution pushes the portable Core artifact and a pinned Linux Node, stages the release with the same staging program, names it current, writes the start script and, when the user chose it, a user-level systemd unit, then starts the Core and reads its public owner identity. That identity, the service command and the socket are written back to the saved Host; the ordinary connection flow then confirms it. An uncertain result is inspected read-only and never replayed; behavior and review rules are owned by the [Remote management contract](../design/behavior/remote-management.md#诊断维护与授权入口).
