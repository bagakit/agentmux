## 全局 Board 的三栏任务闭环

中间 Board 保留稳定的列标题、数量和加号入口；卡片第一眼读到 Task ID、标题、目标 Project 和 Task 状态，Attempt/Agent 活动压到次级行，超过可读数量折叠为“还有 n 个”。顶部筛选条保持一行低高度，搜索、Project、状态、优先级、标签和归档筛选不抢占任务卡空间。

右侧详情采用固定侧栏，不用弹窗遮住 Board；详情、文件、变更、Activity 和对话使用同一容器与 tab 语言。左侧“来源与依据”默认收起为按需抽屉，只有确有原始需求、路由理由、外部引用或待确认项时才占用空间，长文本进入右侧阅读面。窄窗优先保留中间任务标题/状态/Project 与右侧可回退的详情抽屉，不能让三栏同时压缩到不可读。

Task 卡的视觉质量高于参考实现的默认卡片：任务身份、目标 Project、状态和下一步动作形成清晰的第一阅读层；Attempt/Agent 活动用紧凑的执行 rail、头像和时间形成第二阅读层；进度、依赖和阻塞原因使用局部标记，不把卡片堆成信息表。选中卡片用完整轮廓和轻微层级抬升表达，状态颜色只做语义补充；动效用于真实执行变化，不能用装饰性发光掩盖状态。

编排 Agent 的浮窗与任务执行面板保持两种密度：浮窗优先对话连续性，执行面板优先任务事实、Attempt 和可操作的下一步。二者共享身份、状态和项目标识，但不复制同一段消息。

## Task 详情中的 Session Region 投影

右侧 Task 面板以 Region 为基本单位：一个 Session 占一个 Region，多个 Session 复用现有分屏/网格的几何语言。每个 Region 顶部保留轻量 Project/Workspace/Branch/Topic 标识和“进入项目”按钮，按钮与终端/对话区域分开，不覆盖内容。

投影默认使用观察密度：保留真实输出、状态、最近活动和进度，隐藏会改变 PTY 的输入工具与独立尺寸控制。详情面板中的多个 Region 共享同一身份、状态 glyph 和时间语言；当 Region 数量超过可读范围时，通过 arrangement/折叠入口表达，不把卡片压成细条。

行为约束见 desktop-interaction 的“全局 Board 的三栏任务闭环”。

## Board / Task 工作区的面性设计

Board、Task 工作区和 Topic Region 共享 AgentMux 原生 surface token：`surface-0` 作为工作面底，`surface-1` 作为卡片或 chrome 层，`surface-2` 只用于 hover、选中或临时控件。区域之间优先使用留白和 1px hairline；只有列间、Tab 边界、Region 头尾和真正的输入框保留线。

Task 卡默认是无边框的面，选中只增加一处统一焦点信号；Task 工作区是右半边连续的 surface，Session terminal 是其中的内容面，不再用“抽屉卡 → 执行卡 → terminal 卡”的套娃结构。任何新增边框、圆角、阴影或颜色都必须对应一个交互状态，否则不进入实现。

## Agents、Session 与 Board 的切换

主工作面切换使用低高度的 segmented switcher，当前项用单一选中 Surface 和焦点环表达；入口分组与位置归[《左下角导航与右下角工具组》](spaces-and-layout.md#左下角导航与右下角工具组)。顶部右侧保留搜索、筛选和当前工作面的动作，不重复主导航。 Session 顶栏也遵循此规则；删除重复导航后不保留空的右侧占位容器。

三种工作面有清晰的第一层信息：Agents 先读 Executor/Agent 状态，Session 先读 Session/Topic/Workspace，Board 先读 Demand/Project/状态。Board 的需求列不混入以 Session 为主身份的卡片；需要看执行 Session 时进入右侧 Region 工作区。

未分屏时主工作面保持连续的全宽 Surface，切换不做左右互换或把内容从右边“搬到左边”的过渡。只有真实存在多个 Region 时，才使用现有分屏 arrangement；没有详情时不保留空的右侧框、占位线或方向性动画。

## Agents 看板与 Board 需求流转

Agents 直接沿用原 Board 的工具栏、状态列、卡片和右半工作区设计。卡片以 Agent 显示名和 Executor 身份为主，观察与请求处理保留同屏上下文；选中 Needs you 卡片后，详情区的“在这里查看请求”保持一个明确的次级动作位，不能把回答动作藏回旧列表行。没有 typed request 时只显示定位 Session 的动作。Board 卡片先读需求标题、状态、负责人、Project 和优先级，Session 数量和运行状态是次级事实。零 Session 与多 Session 的需求具有相同地位。需求编辑与关联在固定详情区完成；行为约束见 interaction SSOT 同名小节。


## Board Demand 的全局层级

Board 是与 Project、Session 平级的最高级工作面。进入 Board 后 Project Rail 被 Board 连续 Surface 覆盖，不能在左侧继续显示 Project 树；Board 内的卡片、筛选、详情和右侧工作区以 Demand 为文案，Demand 才是需求身份，关联 Session 只作为执行事实。

## Demand 命名合同

Board 的可见文案、DOM 选择器和实现名称统一使用 Demand。`demand` 是需求身份，`Session` 是执行事实；同一 Board 语义不再混用 `task` 命名。控制操作、CLI 和持久化投影也使用 Demand 词根，避免在高密度卡片和详情工作区里产生两套身份语言。

- **Terminal 文件动作保持轻量且可扫读。** 右键中的系统文件动作放在路径动作分组，使用平台对应的短文案与统一 14px 图标；没有路径命中时整组缺席，不留空分隔线。菜单不能因长路径把动作裁掉，动作文本允许单行省略并保留完整 title/可访问名称。

## Demand 包与 Leader Topic 投影

Demand 由与 Core 平行的文件系统包提供，Board 和 Leader Topic 只消费同一份 Demand 投影。界面中的 Demand 卡第一层显示标题、状态和目标 Project，关联 Session / Attempt 作为第二层执行 rail；不在卡片内复制一套 Session 状态机或把 Agent 行伪装成 Demand。CLI/API 的失败沿用服务窗语言，保留已读到的 Demand，不用空列表覆盖工作面。

`pmo` 查询的过滤维度（`--status`/`--session`/`--since` 等）必须读投影里**真实存在**的字段：会话的进程活性来自 `observation.process`（`running`/`exited`/`interrupted`），与 CLI/渲染层共用的同一条观察轴。过滤不得把某个不属于该类型的字段（例如控制协议会话上的 `processState`）经类型洗白读进来——那会让整条过滤恒不匹配、`--status <任意值>` 永远返回空，正是"不用空列表覆盖工作面"这条在查询侧的反例。

## Demand 管理与业务流程表面

Demand 详情必须有可编辑的描述、优先级、状态、目标 Project、Executor 和关联 Session 列表；每个编辑动作沿用紧凑的行内控件与 receipt，不把详情做成空白表单或信息堆。关联 Session 使用稳定 ID 和 Agent/Project 摘要，提供添加、移除和进入原工作面的动作；删除 Demand 放在明确的危险动作菜单里，要求确认并保留审计信息。

Demand 卡片的执行 rail 使用统一的“Agent 工作拓扑摘要”组件：先显示 Topic/Branch，再按 Tab 展示其全部分栏，分栏内显示 Region 类型、Agent 名称、Provider/Executor 和运行状态。Tab/Region 信息采用紧凑树形层级，可折叠但不能默认只剩计数；组件在 Agents、Session、Demand 详情中复用同一间距、身份 glyph 和状态槽。

Leader Topic 浮窗承担“提出需求”和“分配上下文”的对话入口，Board 承担扫描、编辑和审计；两者共享同一 Demand 事实。一个流程从浮窗开始时，Board 不提前画空卡；确认写入后卡片立即显示描述、Project、状态和 Session 数量。CUI 查询与 UI 详情使用相同字段顺序和稳定 ID，Agent 可以完成与人相同的提出、分配、推进和删除流程。

## Demand 专属 PMO Tab 的表面

每个由 Board `New Demand` 创建的 Demand 都有一枚专属 PMO Tab。Demand 卡片和详情保留一个紧凑的专属 Mote 入口；Goals 当前下一步与 Grill/Grounding 表达见[《Goals 的目标正文与对齐密度》](#goals-的目标正文与对齐密度)，不在卡片上重复渲染整段对话。打开后浮窗直接切到对应 Tab，Tab 标题可用 Demand 标题辅助识别，内容区保持普通 PMO 对话密度。新 Demand 的 Tab 与其它 Demand 的 Tab 在 Tab 条上可并列扫读，但不得合并成一个共享的 Session。

绑定关系属于工作面恢复事实：Demand 的文件投影不增加编辑器字段，编辑器状态单独保存 Demand 到 PMO Tab 的映射。映射失效时，入口显示一次明确的恢复动作并创建新的专属 Tab；不能把用户送到另一个 Demand 的 PMO 对话，也不能因为映射暂时不可用把 Demand 详情清空。

从 New Demand 打开的 PMO 浮窗在目标 Agent 挂载前保持同一张目标 Tab 的等待状态；不短暂显示其他 PMO Tab 的内容，避免用户看到旧需求的对话闪回。

## Goals 的目标正文与对齐密度

用户要求「界面视觉风格也不够简约」，需求详情「一点都不现代化」。Goals 是安静、紧凑、可连续阅读的目标工作面；行为与事实边界统一见交互 SSOT[《Goals 的 Grill 与 Grounding》](../behavior/goals-and-demand.md#goals-的-grill-与-grounding)。参考 Multica 的正文/讨论优先与渐进属性，不复制其 Web chrome 或复杂字段面。

实际使用后的「goals 面板有点看不懂了」反馈，其行为约束见上述交互章节《普通语言说明当前事实与动作》。阅读层级先用目标、成功标准、待决定事项和结果；方法名、版本号与系统身份降为按需解释，不靠增加教程、步骤器或状态卡补救理解。

「不知道该从哪里开始、下一步点什么」的动作合同见交互 SSOT。每阶段唯一主入口必须能在当前正文或既有工具带直接找到；已确认且尚无结果时，强调原讨论入口，并以短说明指向原讨论/关联工作面继续推进，把发送结果核验请求留作次级。只换名称、同时保留多枚同等强调按钮或只说可以继续而不给入口，都不满足可理解性。

初始画面仍差、顶部是否放 CTA 的反馈及最新三句入口实施确认，统一归交互 SSOT[《Goals 的 Grill 与 Grounding》](../behavior/goals-and-demand.md#goals-的-grill-与-grounding)。现有低高度工具、连续列表和少噪音约束保持，不把教程或阶段卡当作起步入口。

用户已将起步 CTA 明确为点击即发出探索请求，行为唯一归交互 SSOT。紧凑起步区让零门槛探索先可发现，有可信项目时再呈现带项目名的条件入口；既有 New Goal 保留独立的次级创建语义。完整请求句子直接可读，长句在窄窗可换行且仍可操作，不把标签截短后藏另一份首发消息。等待、未知与原地恢复沿既有服务窗，不以大型教程、三张阶段卡、无依据计数或多个同等强调按钮替代起手。该方向替代此前仅突出 New Goal 的候选方案，三个入口的精确陈列由实施设计与实际图审收紧。

当前三句请求、项目条件、轻量对话与角色入口移出本轮的范围唯一见交互 SSOT[《Goals 的 Grill 与 Grounding》](../behavior/goals-and-demand.md#goals-的-grill-与-grounding)。首屏沿既有紧凑起步区与连续清单组织，不出现角色选择墙或角色资料表；项目名与所作用的条件入口相邻可读，不能让人猜本次建议针对哪个项目。上一批文案与两条角色候选只保留历史，不混入当前入口。

主 bot 待确认与未分配 Project 的行为边界见同一交互章节。主 Mote 的未知请求说明在其 launcher 内就地可读，原请求、未发送事实与明确选择动作保持清楚层级；不以另一 Agent 的绿色默认选中态代替原身份。正常未分配项目不铺大号恢复告示，已有关联的真实失败仍可读。

主 Mote 卡片与上述 launcher 说明保持同一事实，保留引用但状态未知的读法见交互章节；不能在同一个浮窗里同时宣称原 Agent 待确认和「No Agent yet」。

用户最新反馈「CTA 按钮在设计上太挫了，和设置页完全比不了」。起步区的视觉完成度以当前[《Settings 控制工作面》](settings-and-observation.md#settings-控制工作面)为本产品对照：完整请求是主要阅读对象，准确项目名是相邻次层，进入对话的动作明确可辨；用稳定阅读宽度、字重、留白、轻分隔和统一 Surface 边界形成层次。宽窗不能把短请求拉成横跨整页的空槽，窄窗不能靠缩字、截句或偶然挤排维持布局，也不能留下孤立的句尾或让项目说明挤压请求。起步区与目标清单的低高度管理带分工清楚，保留连续阅读空间。

起步请求形成一个克制的功能组，各动作的命中面、hover、按下与键盘焦点清楚；材质沿既有石墨、薄高光和中性边界，不为每个请求另叠玻璃、装饰渐变、阶段卡或重复图标。完整句子可用语义重点建立字重层次，不能另造短标签替代所见请求。准备中保持原句和作用项目可读，同时有真实文字反馈，不能只把全组变灰或把准备称为已送达；失败与未知的服务窗就地、持续且不遮挡原内容。两种主题以及已知减少动态、透明度或增强对比偏好下仍清楚可用，装饰不订阅无关 Session／Terminal 热路径。三句范围、点击、状态事实与恢复行为只引用 interaction[《Goals 的 Grill 与 Grounding》](../behavior/goals-and-demand.md#goals-的-grill-与-grounding)。实际宽窄初始页、真实项目、操作状态与清单同框的候选须独立逐图审美，修正后重拍；旧入口曾通过的图片不能代签此次品质改进。

用户进一步指出当前布局、设计和交互仍不及带图的 Settings，并要求包装成可自定义、可持续收敛的常用操作（；完整需求与正文唯一 owner 见 interaction[《Goals 的 Grill 与 Grounding》](../behavior/goals-and-demand.md#goals-的-grill-与-grounding)）。新的图文品质不能由上一轮三句控件审美代签，也不能只给原文字槽换边框或重复贴图标。常用操作应有一个有明确角色的、低高度图文起点：图形建立产品身份与探索区的视觉起点，正文仍是操作主层，可信项目和适用 Agent 是相邻次层，管理与收起不争主操作。参考当前 Settings 的真实品牌图、功能分组和图文节奏；阅读上限只约束正文，不固定整页扫描区为居中窄栏，不复制巨大 hero，不让装饰或随机大卡吞掉连续目标列表；图形失效不影响文字与动作可用。

新增与管理的控件必须处于图外清楚可读的区域，不遮住品牌主体；进入对话的箭头跟随正文首行，不在正文与项目元信息之间漂移。正常首批操作自然完整呈现；真实长正文或更多操作展开时才共享有界阅读预算，全文仍可键盘滚读且滚动不误发；窄管理使用库与编辑两种状态，返回同一稳定引用，而非把整库堆在编辑正文之前。常用区的正常执行、明确管理和正文编辑三种状态需可辨：新增以一句正文为主，修改同一指令及移出引用有不同语义；完整请求在宽窄窗口发前均可读取，不以截句、短名称或 tooltip 替代。更多操作采用有界渐进展开，展开、收起、管理关闭与排序移除的焦点可追踪；数量增加仍保留 Goals 连续阅读空间。两主题、窄窗长正文/长项目名和真实操作状态都须以本批 Source 的实际整页候选独立审美，旧图片、token 一致或仅采图成功不能替代判断；图形不增加无关 Session/Terminal 热路径工作。

常用操作的后续 Mote 建立项目、需求绑定与执行指派行为唯一归 interaction[《Goals 的 Grill 与 Grounding》](../behavior/goals-and-demand.md#goals-的-grill-与-grounding)；起步图文区不把这些职责画成必经阶段卡、角色入口或额外提交，原可见完整请求和连续目标阅读保持。

**整页成熟度一轮提升**。用户要求常用操作完成后对 Goals 页面打分并参考 Settings 提升一轮，目标与行为合同唯一归 interaction[《Goals 的 Grill 与 Grounding》](../behavior/goals-and-demand.md#goals-的-grill-与-grounding)。初始、清单和详情共享可辨的阅读边线、文字层次和控件语言；参考 Settings 的明确功能分组、真实当前值、紧凑行与可辨入口，让人沿完整页面读懂目标和结果。常用操作的品牌起点与正在阅读的目标形成明确主次；宽窗详情保留足够可扫描的目标导航，窄窗正文与返回沿同一节奏。目标对齐与结果核验各由其真实正文标题、当前事实和相邻动作辨认，成功标准、当前结果、证据及重要差距保持连续对照。清单结论的形态表达当前事实，打开目标的命中与方向可辨，讨论/请求/认可的操作反馈各有落点。属性与技术身份继续渐进展开，标题、正文、控件、服务窗及完整焦点在两主题宽窄下均可读。整页评分须依据可定位的当前候选观察；本轮改进在真实初始页、混合事实清单及关键目标/结果详情上独立实际看图复核，保留具体修正和原图身份。

**减少无意义占位与整页精炼**。用户反馈「有点难看，而且浪费空间」，并明确顶部常用操作区域最浪费；本轮首先改善该区，相邻列表与详情只消费有限对齐／边距。行为保留边界只归 interaction[《Goals 的 Grill 与 Grounding》](../behavior/goals-and-demand.md#goals-的-grill-与-grounding)。常用操作是低高度功能起点：既有品牌图作为标题附近的克制视觉身份，不再独立占据一整块宣传画面，重复的起步 slogan 与空态说明合并。宽窗利用可用宽度让完整请求并列，窄窗按自然阅读顺序换行；正常首批真实请求无需滚过装饰或嵌套滚区才能看全，也不靠默认收起功能冒充省高。更多／长内容才按真实阅读需要有界展开。管理、收起和未保存／未知反馈仍有清楚落点，不能靠缩字、截原句、隐藏真实项目或改正文 owner 换密度。

清单不再固定在居中的窄栏内，新增宽度应增加可扫描的目标。宽窗以标题和相邻 Project／执行事实为主格，真实当前结论为对齐的次格；较窄导航与窄窗自然回到两行，不强制每条目标永远堆成三层，也不把结论变成行内执行按钮。详情导航只占辨认与选择所需宽度，正文从分界附近与原工具带同边线起读，并保合理阅读上限；右侧可以保留阅读留白，不在分界与正文之间制造第二条宽空栏。标题、标准、结果、证据、重要差距和未知保留原字号与完整阅读，不用默认折叠关键信息或缩小全局文字冒充紧凑。空目标仅用一条就地事实指向上方可用起步入口，不重复品牌口号或铺大空卡；真实零匹配仍保完整原因与原地恢复动作。两主题宽窄的初始、混合清单、详情和原管理／草稿返回必须以本批真实 Renderer 完整图独立评审；几何测量只证明空间反例已关闭，不能替代品位判断。

- 首屏保持紧凑起步入口与连续列表；搜索、筛选和视图管理使用一条低高度工具带，不再让七状态、四个宽选择框、重复 Branch Board 导航与空列占满画面。唯一 New Goal 是独立创建入口，不与探索发起混称；筛选收为一个可展开入口，已生效条件才显示紧凑可清除标签。列表/看板切换使用一个克制的图标或 segmented 控件；全局工作面标题不在多个 chrome 重复。
- 默认列表以一条 Goal 为一个阅读单位：可读标题占主层，Project、真实执行摘要与更新事实占次层；待澄清、待决定、待确认、目标已确认、待查看结果或已接受以一条普通短文案表达，未知明确可读。工作状态不与这条结论并列冒充同一种进展；在看板、筛选与属性中保留明确入口。整行点击表示打开目标，当前结论不伪装成直接执行动作；不把 PMO、Grill、Grounding、Open Session 排成一串 CTA。选中使用整行中性 Surface、字重或可辨焦点，不能只靠单边色条。没有 Goal 时只留一句可操作空态；已完成/取消的历史按需展开。
- 可选看板采用单条横向轨道，列在同一水平阅读顺序中，窄窗水平滚动；不允许列换行成上下矩阵。列宽应保证真实标题可读，空列只保留列头、轻量空态和必要命中，不制造高大的 Nothing here 区域。默认不为完成/取消保留整列空白。
- 详情是一张连续正文面，而不是控件卡片集合。标题本身可编辑，用户原话与目标正文保持阅读宽度；目标、成功标准、待决定事项与逐标准结果使用直接的标题，不让 Grill/Grounding 与副标题竞争阅读。正常确认状态直接说明人的认可，版本号不占主要标题行。尚无提案时只呈现意图、简短说明和澄清动作；尚无结果时用低占用说明交代何时核验，不铺出空报告。已有旧版报告和未知/差距保持可见。当前阶段最多一个主动作，确认/接受贴近所作用的正文；打开已有讨论是次级入口，发送澄清或检查请求按其实际作用命名。避免大号步骤器、状态统计卡与套娃边框；其余区域可以按需展开，但重要差距与未知不能藏进菜单。
- 成功标准与结果采用对齐的短行/正文块：先读标准，再读结果结论和证据入口；met/gap/unknown 同时有文字或字形，颜色仅作补充。证据只显示可辨名称与定位入口，完整路径按需读取，长内容可展开；没有证据时显示缺少依据。服务窗紧邻相关失败步骤，以低占用、持续可见的说明和恢复动作表达，不覆盖正文与健康输入。
- 认可回执不明的行为归交互 SSOT《认可回执不明时先读当前事实》。该服务窗只突出一个读取当前提案的恢复动作；清单行的唯一下一步与详情恢复入口使用同一文案，不再添加一枚行内恢复按钮。正常确认/接受与重试不堆成竞争按钮，其他阶段入口收为次级而仍可达。读回失败的原因和保留内容就地可读，不制造遮罩、错误状态卡或让人选择三条相冲突的路径。
- 属性是一组紧凑行内项和命名明确的「更多属性」展开面，保留已有字段编辑能力；空值不画大输入槽，不为默认 Normal、Global 或 0 Sessions 重复制造徽章。执行上下文与活动按需读取，当前相关 Session 可直接进入原工作面，不默认把全部 Tab/Region 树摊满详情首屏。
- New Goal 不再出现事前意图表单，点击后真实 Goal 与同目标专属讨论可辨；创建与恢复行为唯一归交互 SSOT。细虚线表达该目标尚待定义，来自真实目标提案缺席事实，不能靠标题词或新增影子状态判断；已有意图、结果材料及恢复事实仍完整可读，目标提案出现后回到普通边界。必要的 Project 上下文轻量可见，不把草稿画成高大的空占位卡或默认填满标准。正文、控件使用现有 Surface、文字与焦点 token；hairline 只分割真实区域，hover/focus 才显编辑边界。宽窗列表与正文并置，窄窗详情保留返回入口并优先保证正文与动作可读，不把两栏同时压到不可用。新建后的完整宽窄工作面同样执行独立最高审美看图与修正直到满意的既有约束。

- New Goal 打开后的讨论表面须让人辨认「主 Mote 中的该 Goal 专属 Tab」：主 Mote 的既有名称/头像与 Goal 标题各有清楚角色，不把每个 Goal 的讨论 Tab 画成另一个 Mote 对象，不新增并列身份卡或重复人格说明。身份与恢复行为只归 interaction[《Goals 的 Grill 与 Grounding》](../behavior/goals-and-demand.md#goals-的-grill-与-grounding)的「Goal 在主 Mote 中有专属 Tab」，主 Mote 的外观规则沿[《Mote 头像与主 Mote》](../behavior/motes-and-coordination.md#mote-头像与主-mote)。 同一归属覆盖常用探索、New Goal 和已有讨论；主 bot 的真实可读名称/身份与本次 Goal 或探索正文相邻，不能只靠 Mote 图标掩盖换了执行者。已知适用范围冲突、准备/投递未知和真实保留请求用原低占用服务窗说明，仍保完整正文与健康输入；不新增流程卡、系统字段墙或重复确认入口。执行者选择和协调行为唯一归交互 SSOT。

## Demand 卡片与详情密度

Goals 当前列表、看板和详情密度统一归[《Goals 的目标正文与对齐密度》](#goals-的目标正文与对齐密度)。稳定 Demand ID、优先级、标签、日期、子 Demand 和执行摘要仍按需可达，字段超长省略并保留完整 tooltip/无障碍名称。

Board 顶部使用一条低高度工具带承载搜索、状态/Project/负责人/标签/日期筛选、视图切换和唯一的新建入口；路由队列作为可切换的同级筛选态，不额外制造一块高大的独立卡片。筛选结果、列计数和空状态在同一条视觉节奏中，批量动作只在确有选中项时出现。

Demand 详情是连续的右侧 surface：标题和状态在短 header 中，属性编辑使用行内 picker/紧凑输入，描述和评论保持阅读宽度；活动与决策收在可展开的时间线分组，进行中的 Demand 工作记录和 Session 固定在上方，历史记录可折叠。删除、取消、停止和重试使用统一危险/次级动作语言，不把运行状态画成第二套卡片。

右侧 Demand 首屏以需求标题、描述和路由属性建立阅读顺序，不重复显示一个静态大标题和一格同文案的 Title 输入框。标题编辑控件呈现为标题本身，描述默认是可直接编辑的正文面；输入框边界仅在 hover/focus 时出现。状态、优先级、Project、负责人排成可换行的紧凑属性组，不让四个宽选择框横跨整栏。标签、日期和批次放在明确命名的可展开“更多属性”区，空值不占据首屏。Session 区紧随需求正文；零 Session 使用短的就地说明，工作拓扑和排列按钮只在有可观察执行内容时出现。窄窗允许属性换行，控件仍保持可读标签和键盘焦点。

多 Session 投影继续复用现有 Region arrangement。卡片只显示可扫描的 Agent topology 摘要，完整 Topic/Branch/Tab/Region 层级在详情内可展开；unknown 或尚未恢复的事实占用同样的稳定槽位，不用空白或跳动布局掩盖缺口。
> 命名更新：历史 “Leader Topic” 与 “PMO Teams Topic” 现称 **Mote**；视觉与密度约束继续有效，当前产品身份由交互 SSOT[《Space、Folder 与 Topic》](../behavior/spaces-and-layout.md#spacefolder-与-topic)定义。
