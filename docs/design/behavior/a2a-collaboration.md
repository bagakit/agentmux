# A2A 协作与可观测性

本文是独立 AgentMux Session 之间发现、通信、批量发送、创建关系、显式消费与监督协作的业务 SSOT。已确认要求描述产品必须满足的结果，不代表当前源码、安装副本或真实 Agent 已通过验收。

## 对象与事实归属

| 对象或关系 | 唯一事实来源与边界 |
| --- | --- |
| AgentSession 与 Run | Core 持久 Session 与权威 Runtime／Provider 观察；名称、Tab、Region、最后一条文字不替代执行身份或当前状态。 |
| 原回复与用户输入 | 原 Session 的 captured／native history 和输入来源；Provider 的 user role 不证明人类作者，平台通知不变成用户消息。 |
| A2A 原信、投递及消费 | Core 同一 durable journal；收件、发件、事件与观察索引均引用原消息，不各存一份正文或另造消息队列。 |
| Agent 创建 Agent | 原创建 operation、已核创建者与目标 Session 的持久创建事实；出生关系不等于任务归属、当前监督关系或权限继承。 |
| Dispatch／Handoff 与任务 | 原通信监督事实与实际委派分别表达；Goal、Demand 和外部任务的业务所有权与验收沿各自 owner。 |

可读标签只负责表达。准确格式归[amux 可读协议](../../specs/amux-protocol.md)，通用输入环境与未知投递恢复归[输入能力与投递凭据](agent-capabilities-and-messaging.md#跨重启的-prompt-投递凭据)，本页不复制这些合同。公共 SDK、JSON-RPC、CLI 与客户端必须消费同一业务 owner；help／skill 让 Agent 知道如何发现和操作，不成为第二份事实库。

## Agent 发现与最近关键信息

- **默认能看到所有状态。** Agent 查询默认不把原可发现集合限定为 working 或 running；工作、等待、空闲、失败、已结束及 unknown 都按权威来源可辨。进程、语义状态、输入 readiness 和观察新鲜度分别保留，不能用一根状态轴替代其他事实。既有持久身份与退休／恢复记录沿 Session owner 保留，普通发现不因此另建或全扫历史 registry。分页、数量限制、不可用 Host 与单项失败须明确表达；部分结果不冒充全体，观察失败不使已知 Agent 消失或变成死亡。
- **最近活跃必须说明发生了什么。** 查询应提供有来源的最近活动时刻与活动种类，并区分状态起点、最后一次观察和最后一次记录更新。轮询、元数据编辑或界面刷新不能把闲置 Agent 刷成最近活跃。等待、完成、失败或原生 idle 的事件时刻只说明对应事件，不证明此刻 working 或最近一次 working 的时刻；不能把 idle 的观察时刻补作工作活动。缺少可确认活动来源时表达未知，不能用 `updatedAt`、最后可见回复、标题或终端外观补猜。时长表达仍归[Agent 已经这样多久了](agent-capabilities-and-messaging.md#agent-已经这样多久了)。
- **最近摘要与全部历史使用同一入口。** 在原授权内，对准确 Host／Session，Agent 能按需查询回复、用户消息及 A2A 交互；默认只返回最近少量记录，并能沿稳定游标遍历所请求范围。记录保留原作者、消息角色、Run、原生来源、顺序、时刻及覆盖范围；回复沿 Provider 已确认的 assistant 正文，不把 reasoning、工具结果、平台通知或 A2A 原信计作 Agent 对用户的回答。人类、已核 Agent、平台与未知输入保持可辨；未知作者不能被默认为人类，确有覆盖缺口不能返回“全部为空”。
- **先筛参与者，再按需读正文。** 发现支持按原执行器、准确状态和有来源的活动条件缩小集合；已有任务／岗位关系按其原 owner 查询，不能从名称或正文猜出“某类工作 Agent”。发送方可据此选出“所有活跃的某类工作 Agent”的准确 ID，再发起一次明确批量发送。查询不随每个候选读取全历史、唤醒 Runtime 或探测输入，工作量随相关参与者与本次页预算增长。
- **阅读不改变执行。** 最近信息、历史与交互读取只读，不创建、恢复、停止、attach、发信或推进消费；有权查询不等于取得操作该 Agent 或扩大任务的授权。单一来源读取失败保留其他已知结果及原阅读游标，明确失败来源与可重读动作，健康 Agent 和输入继续可用。

跨 Agent 的用户消息与 A2A 正文互查范围仍待确认；当前不因同一 Workspace、状态可见、关系可见或知道 SID 自动扩张原正文读取权限。发现元信息、创建关系与原文访问分别核验，新增范围只在本处确认后落实到公共 owner。

## 一次发送给明确的一组 Agent

- **广播是一组明确收件人的一次发送意图。** 发送方可一次提交同一原正文和一组准确 Agent Session ID；原入口核验作者与原授权，规范化后冻结去重的收件集合与逐目标消息身份。用于选人的发现条件不作为重试时重新运行的动态群组；恢复不得因新 Agent 出现、状态变化、前缀歧义、Region 换绑或 Run 替换而改投或增加收件人。
- **一个收件人对应一份原投递结果。** 每个目标沿原单信合同拥有原 MID、准确 Host／Session／已知 Run、投递条件与 receipt，共用同一批意图的关联。批量结果明确逐目标的已入箱、已投递、失败、unknown 或 partial，并保留尚未执行的目标；某个目标不可用不拖垮其他无关目标，也不能用一个成功覆盖其他目标的不确定性。
- **幂等沿原批次和原单信。** 丢回执后以原批次及原逐目标身份查询或继续，不为已经接纳、已投递或 unknown 的目标生成新消息。已确认整条未应用的目标，只有新的明确发送才可按原单信合同另建身份；一处拒绝不能证明整批从未产生效果。重复 ID 不重复投递，冲突正文、参与者或冻结意图明确拒绝。
- **广播不扩大投递资格。** 每个目标独立遵守原 Inbox、所选通知方式的准入、作者核验和消息礼节；通知方式的选择沿下文[A2A 引用通知与主动取信](#a2a-引用通知与主动取信)。广播本身不创建 Agent、自动建立委派、复制历史或取得跨 Host 权限；接收者只看到准确发件人与发给自己的原信，不泄漏其他收件人的私有正文或授权。

## 双向事件与可还原的交互

- **同一事件从双方都能找到。** 除收件侧以外，发送侧也能按准确 Host／Session、原 MID 或原批次查询关联的入箱、投递、通知与失败变化；事件复用原 journal 的原顺序与身份，不从收件对话反扫或向 Outbox 再写一份消息。发送者退出、收件者未启动或展示移动不抹去已保存关联。
- **准确范围与原窗口分开表达。** 在参与者权限内，可选择原 MID 或原批次缩小事件范围，两者互斥；批次沿首次冻结的目标／MID 关系定位，不重新选人。事件按原 journal 的显式顺序范围读取，续页保留同一参与者、MID／批次范围、原截止顺序与 journal incarnation；这是显式 range，不冒称已绑定范围的 opaque cursor。修改范围是一次新查询，不能把旧页结果当新范围的完整续页；返回与读取器核对同一准确范围。通知仍是一条原事件，引用只包含该参与者在本次范围内可见的原 MID。
- **图与快速索引只投影原事实。** 原事件应能表达真实 sender→recipient、message、thread／reply、批次及创建关系，供图观测和快速索引沿稳定游标增量消费。原观察边界前后、历史覆盖不足、读取失败与迟到回执保持可辨，空增量不表示历史不存在。一个通知引用多封原信时保留通知身份和原引用关系，不伪造成多次正文送达或多封新原信。
- **观察不制造业务完成。** 入箱、正文交付、通知接纳、正文读取、显式消费、接单、回复、收工和业务验收分别表达；事件名称或图中的一条边不补造缺失阶段。新增索引可重建且不持有第二份可写事实，按相关参与者和请求页读取，不为查询一个 Session 扫描全局消息、全部原生历史或全部 Agent。
- **权限与原恢复边界保持。** 受管 Agent 沿原参与者资格只读其获准的信息，有权用户沿原用户权限浏览；查询任意 SID 不允许冒充别人、移动消费游标或取得正文分享权。订阅断开或索引暂不可用只影响本次观察，原 journal、未知回执、原消息与健康输入保持，重连沿原游标恢复，不自动补发消息。

## Agent 创建 Agent 的 spawn 记录

- **每次真实创建保留可查询的出生关系。** 由受管 Agent 发起新的独立 Session 时，原创建操作保留经核验的创建者 Host／Session／Run、原 operation、被创建 Host／Session 与已确认的 Run／创建阶段。新 Run 尚未确定、创建失败、已启动而持久确认未返回等事实分别表达；不为凑齐边补造 Session、Run 或成功。打开既有 Session、恢复、重新接入、普通消息和 Provider 原生 subagent 事件不能冒充一次独立 AgentMux spawn。
- **双方都能感知同一次创建。** 创建者从原创建回执及按自身身份的关系查询找到被创建者；被创建者从原创建上下文及按自身身份的关系查询知道由谁、基于哪次操作创建。双方读取同一原创建事实，关联可在创建者退出、被创建者恢复或工作面移动后继续核对；不靠自报 parent、来源标签、首条正文或命名猜关系，也不额外发送礼貌确认来建立关系。
- **原生接管保准确实体与无输入边界。** 接管已有 Provider 对话若真正创建了新的 Core Session 身份，保留这一 Core 身份的已核创建者，不冒称新建 Provider 对话或接手旧任务。沿原无输入恢复流程的接管不为披露来源添加新输入；被创建者可通过 `whoami`／`agent.inspect` 的原创建元数据按需感知，只有原流程本就提交输入时才随原平台说明披露。恢复同一个 Core Session 不新增出生关系。
- **出生、首条消息与任务分别持有事实。** 有首任务时继续沿原 A2A 首条消息身份交付，并能从创建关系找到原消息；没有正文的创建同样保留 spawn 关系，不凭空制造 A2A 原信。创建者、当前监督者、实际任务负责人和业务 owner 不能互相代替；spawn 不继承凭据、授予更多 Agent 创建权或自动转交任务所有权。必要任务背景和预期结果仍由原真实委派说明。
- **恢复只收敛原创建。** 重复原操作或丢回执后按原 operation 与目标身份核对，不另建替代 Agent、重放未知首任务或重写创建者。跨 Host 仅在原合法路由与授权范围保留双方 owner 的身份；不因关系可见新增信任或通用跨 Host spawn 权限。关系查询与图索引消费原创建来源，不增第二套 Agent registry、任务树或可独立改写的父子账本。

## 协作执行机制与下属关系

“subagent”“下属”“另开一个 Agent”不能单凭用词映射成工具。开启协作前，Agent 在用户已授权的任务范围内，结合所需上下文、结果如何回收、是否需要独立持续会话、指定 Executor／Host／Workspace 与可见工作面，判断真实意图；用户明确指定的机制、目标与职责优先。能够从上下文判断时自主选择并简短说明，只有会实质改变授权范围、执行环境或责任的歧义才精简问清，不为每次选择固定追加确认。

在用户已授权的任务范围内，Agent 可以向尚无协作关系的独立 Agent 主动求助或交流；已有委派关系不是发起联系的必要条件。通信职责与操作授权仍按原任务和实际委派保留。

| 执行机制 | 必须分清的事实 |
| --- | --- |
| **Provider 原生 subagent** | 沿当前原生协作能力创建、管理子任务和回收结果。其可用范围、上下文与生命周期以该能力的真实合同为准；原生子任务标识不能冒充独立 AgentMux Session，也不据此保证单独的展示位置或耐久恢复。 |
| **独立 AgentMux Agent** | 经 Core 公共能力打开独立 Session，按实际回执核对 Executor、Host、Workspace、Session／Run 与展示位置。独立 Session 间的消息沿[原 A2A 通路](#a2a-身份信封与持久化全局消息队列)；Provider 原生队列不承担跨 Session 投递。 |

执行机制与下属责任分别表达。独立 Session 也可以承担原协调者委托的子任务；原生 subagent 也不能只因工具名就被宣称拥有某个持久 Task。协调者的收集、审查与向用户交付责任按实际委托保留，另开 Session 或换展示位置不自动转移所有权；正式交接的授权和当前事实边界仍见[交出去与派出去](#交出去与派出去)。创建关系沿[原 spawn 记录](#agent-创建-agent-的-spawn-记录)保留；关系本身不新增 Task 实体、自动派发权限或可独立改写的父子账本，也不扩大原任务授权。

独立 Agent 的空间选择与打开文件共用[开启工作面的意图与落点](spaces-and-layout.md#开启工作面的意图与落点)，不因对象类型固定选择新 Tab 或某一分屏方向。建议级 playbook 教如何判断与核验，不成为新的创建、消息或布局 owner。

## 交出去与派出去

- **Handoff 与 Dispatch 表达协作意图。** Core 用 `originAwaits` 区分交出去（false）与派出去后原协调者仍等待问题、升级和收工（true）。该字段描述本次协作声明，不原子转移外部任务系统的所有权；准确执行与可观察范围见下文，不以普通消息措辞冒结构化事实。
- **全权交接须有人的明确授权**。用户已授权 Goal 范围内的 Mote 委派与结果回收沿[Goal 委派合同](goals-and-demand.md#委派回报与责任接续)，不因委派暗转业务所有权或扩大授权。handoff **不夹带消息投递**——一旦它同时"转移所有权"和"投递指令"，那条被否决的回路就有了雏形。要送文本走 send/discuss，那是另一件事。
- **交接的目标用与位置无关的 Session 身份寻址**。多态寻址（Region/Tab）要过 Control 面解析成 Session，把一个原子动作拆成两跳，还让它依赖 Desktop 活着——而交出所有权不该有这个前提。
- **交接回执不冒任务所有权记录。** `handOff()` 的本次返回值只表达 `ownerAgentSessionId`／`originAwaits`；准确合同以[Core handoff](../../../packages/core/src/agent-handoff.ts)为准。未取得持久任务 owner 确认时，界面不能从自由 `taskId` 或一次返回值宣称“任务当前归谁”，也不另存无法核对的 owner 字段。外部任务与 Goal/Demand 的实际关系沿其原 owner。

原监督协作链可在 Session 邮箱内只读查看：以准确 Host 与参与 Session 读取 Core 原 Dispatch 分页，再按原 sourceMessageId 展开原消息、回复及监督事件。原双方 Session／Run、operation、thread 与 replyTo 保留；投递、通信监督、执行与 Goal 业务验收各自独立，`worker_done` 不代签结果接受。未建立 Dispatch 的普通消息不冒监督链，有真实 Goal 委派绑定才沿原 Goal 证据入口表达归属。读取失败与身份观测缺口明确未知，保原记录及健康 Agent，允许同源显式重读，不自动重发或另派。界面不从捕获 submissionId、正文来源头或时间猜消息关联；公共 RPC／CLI 与客户端共用原 Core 消息 owner。

## 持久消息的显式消费与派发等待

- Core、默认 Provider 与非历史 CLI 的启动不得激活当前操作无关的原生读取依赖；未执行的读取不得以副作用污染当前结构化回执。真实历史读取仍保留原协议、只读与失败表达。
- 受管 Agent 应能实际“检查这一批消息，处理后明确确认”，不同进程在确认前拿到同一批身份和顺序；只能检查自己的收件，不能指定别人的消费游标。读取和确认不等于已投递、接受、回复、用户已读或需求完成，也不自动发送正文、创建、停止或恢复 Agent。
- 当前 Run 的凭证、Session 身份和持久消费批次必须相符。换 Run 后，新 Run 接管未确认批次，不丢原消息；旧 Run 的迟到确认或检查不能覆盖新绑定。失败说清是哪一步不可用，健康 Agent 仍可工作，不为消费增加生命周期门禁。
- 消息的消费、投递和监督等待都引用同一份持久消息身份与正文。队列由 Core 唯一持有，宿主和其受管 CLI 选择同一来源；明确注入的现有队列来源有权威，默认队列保持 durable，不能随 ctxmux 的临时版本端点回收。来源之间不猜测、合并、搬迁或静默宣称旧历史已纳入。
- 合法消息历史的累计数量或 journal 体积不得成为新消息的永久准入门槛，也不能挡住已有消息的投递终局、消费确认或 Dispatch 事实。原消息、作者、正文、operation 幂等身份、消费位置和引用继续可恢复；不能靠删除旧记录或提高固定累计额度解除阻断。实际存储失败或当前锁竞争须说明准确阶段与原操作回执，不冒充未投递，也不关闭健康 Agent。
- 已保存的未来投递意图保留原幂等身份、正文与 active 状态；合法旧停用意图的累计数量不占新保存的准入资格。保存意图不等于已经执行，不因解除累计额度改变原调度或投递资格。 Session 发现、状态和事件只携带当前控制事实；原意图正文按准确身份读取或分页读取，不随每次控制观察广播整份累计历史。一般观察连接、单个 Attachment 与历史 reader 分别拥有自己的租约，观察失败只释放自己的输出目的地，不撤销同一原 owner 对准确目标仍可验证的控制能力；取消、授权和 owner fence 仍按原请求核对，回执未知不得重发输入。
- Dispatch 监督的是针对真实消息的通信等待：发起者仍须接问题、升级、明确收工和收尾。不同问题消息分别保留，同一消息重放幂等；投递或游标确认不能解除该等待。只有经过参与者、当前 Run 和对话归属核验的明确收工报告才解除通信等待，不能据此显示“任务归谁”或把 Demand/Tracker 标成完成。Core 没有 Task 实体的边界仍见[《交出去与派出去》](#交出去与派出去)。 准入只读取本次调用者与原消息中去重的参与者身份，不先发现全部 Session；等待 Queue writer 后仍重核原凭证和调用 Run，Session Store 与 Queue 不冒充跨库原子事务。

## A2A 身份信封与持久化全局消息队列

所有由 AgentMux 管理的跨 Session Agent 消息，包括 `send`、`discuss` 及受管 Agent 发起 `agent open --prompt` 的首条消息，都必须由 Core 核验真实作者与双方已知 Session/Run，保留同一份 durable 消息身份，并按协议生成可读信封。发送方只提交原正文，不能手写来源头或 reminder 代替受信事实；客户端不另组装一份信封，不保留裸正文的 A2A 投递分支。人类原输入不因此加 A2A 外框。

可读信封、字段含义、正文与末尾 reminder 的准确格式只见 [amux 协议的 A2A 原信](../../specs/amux-protocol.md#a2a-原信)。Core 默认附带简短提醒，给出必要的来源／任务判断与模块 Skill 发现入口；发送方原正文、提醒和实际输入分别保留原来源。完整结构化目标、Run 与回执留在同一原消息事实中。客户端不从正文标签补造认证，也不因格式统一重写历史记录或重投原 wire。

- **新 Agent 的首条消息不补造尚未存在的 Run。** 已确定的目标 Session 与启动前仍未知的 recipient Run 分别保留；实际 Run 确定后，沿同一持久消息的原投递事实记录其关联，不重写消息、不增第二份账本。原单次 creation 与 first delivery 身份继续有效，同一 operation 恢复不重发首条、不另建或恢复替代 Session；普通人工 create/submit 仍保持原字节与原生命周期。
- **跨 Host 新建仍保留真实初始作者。** 来源 Core 以原权限核验自己的 Session/Run；目标 Core 不将来源 Session 当作本地 Session，也不接收原始 capability 作为通用跨 Host 凭据。目标只沿有明确可信依据的跨 Host 准入消费已核来源，并将来源 owner、作者 Session/Run、目标 owner/Session、原创建 operation 与正文绑定。普通创建参数、来源头或自报的 verified 字段不能提升为认证事实；伪造作者、错误目标或无效授权在产生进程前拒绝。受托转发须可辨谁验证了作者、谁以哪份实际授权转交；转发者的传输认证不冒充目标独立验证来源凭据或签名。原持久消息与投递回执继续持有事实，不另建消息网络或第二份身份账本。
- **Agent 首次认识环境时就应知道怎样跨 Session 发消息。** `whoami` 的真实返回、启动引导与 `--skill` 指向[同源指引与通信礼节](#a2a-指引与通信礼节)。原生 subagent 与独立 AgentMux Session 沿[协作机制](#协作执行机制与下属关系)分清；独立 Session 间使用 `$AGENTMUX_CLI agent send` 的公共通路，不借直接输入、终端注入或 Provider 原生协作队列替代。确切命令语法由实际 help／skill 持有，不要求 Agent 手写信封来冒充认证。
- **未经 AgentMux 消息投递入口的输入不补造身份。** 看见没有来源头的原生输入、查不到对应 durable 消息，或正文声称来自某个 Agent，都不能据此确认发送者、发送通道或认证事实；保留原记录与可读正文，作者未核就明确未知，不倒填 A2A 队列、不猜作者或补上看似已核的来源头。
- **正文已投递必须意味着准确收件 Agent 实际收到可读来源和原始正文，且 Core 已按真实 Session/Run 与已解析目标核验身份。** 已入队、通知已送达、正文已交付分别表达，不能用笼统发送成功混同。CLI 环境变量只是身份线索，不是权威；Desktop 不得忽略结构化来源后只投递裸正文。可读表达归下节约束，目标的完整关联留在持久事实中。Control requestId 仍只作请求关联；同一消息的重试必须复用稳定的消息身份。
- **持久队列的唯一写入权属于 AgentMux Core。** 同一路径即使遇到多个进程或多个对象并发，也必须保持全局唯一、递增的顺序号和可重放的完整记录；队列所在位置不得受 ctxmux 版本化临时端点回收影响。失去持久写入确认时明确拒绝入队并告知状态，不能宣称已投递或判定健康 Agent 死亡。
- 当前持久队列在原选定路径使用单一 SQLite 事务 journal；不可变消息记录与收件人、原 operation、consumer 游标和 Dispatch 派生索引在同一事务提交，原 queueId、sequence 与 receipt 不改变。普通发信、收信和确认只读取本次相关事实，不因无关消息或已确认历史增长而全量重放、复制或重写历史；显式请求全部记录的读取按结果规模工作。
- 原日志的持久化形态切换沿原跨进程排他进行，保留完整原始字节的内容寻址归档及全部消息、条件、游标与监督事实；确认完整事务后才原子发布到原路径。切换或提交失去确认时保留实际阶段与未知结果，重开在原身份对账，不重复导入、双写或静默忽略切换后原路径的替换。历史归档不成为另一套当前读写来源。
- **身份授权必须在 Core 里完成，不能把 `AGENTMUX_AGENT_SESSION_ID` 或 Control caller 字段当凭证。** 受管 Agent 的 send 必须携带当前 Run 的 invocation capability，由 Core 核对 capability hash、Session 和 Run；没有 capability 或 capability 属于旧 Run 的请求必须拒绝，健康 Agent 仍可继续工作。
- **队列写入必须能从写入者崩溃中恢复，且回收不能碰掉新写入者。** 同一路径的跨进程排他性以系统可随进程退出释放的事务锁为准；遗留的孤儿 `.lock` 文件不得阻断新写入。并发恢复后每条消息仍只能占一个唯一、连续的顺序号，健康 Agent 不能永久收到 backpressure。
- **相同 `messageId` 是重试的幂等身份，跨新的 Control request/operation 与 createdAt 仍返回原 receipt；冲突正文、目标或来源必须拒绝。** A2A 的 Prompt 投递身份沿原 `messageId`，只换 Control `operationId` 不构成新消息；整条逻辑操作完全未应用的终局判定沿[跨重启的 Prompt 投递凭据](agent-capabilities-and-messaging.md#跨重启的-prompt-投递凭据)。对这条已拒绝消息的新明确重投使用新的 `operationId` 与 `messageId`，按真实目标建立首次条件，保留原消息与回执；普通 CLI 未指定这两项时由原入口生成，不另设恢复命令。unknown/partial 不能借新 ID 重投，不限制独立的新消息。Region/Tab 只是寻址输入，落盘 envelope 和收件信封必须写入解析后的真实 recipient Session/Run。
- 公共发信在解析展示目标后，须沿原语义 Host 的公共入口保留作者上下文及首次来源；客户端转交不成为另一次输入来源。已存消息的投递与重试保留原通道、设备及已核作者，不把当前转交连接的设备补成原来源；未归因的本地 CLI 来源仍为未知，不能因传输经过用户连接而升级为人类作者。
- **首次派发前固定准确路由，丢回执不重新寻址。** 原目标 Host／Session 与当次投递条件在产生远端效果前沿原操作持久化；同一原消息重试不因 Region／Tab 换绑改投另一个 Agent。远端应用与来源回执不同步时按原目标对账并保留 unknown，不以另一 owner 查无记录证明全逻辑消息未应用。本项保护已有合法路由，不新增通用跨 Host managed A2A 权限。
- `amux agent send` 的消息必须带可验证的来源、目标和 AgentMux Session/Run 关联事实；这些事实来自 Core 凭证和会话上下文，不得从 View、Region、标题或正文猜出。`requestId` 只标识 Control request，不能充当 `messageId`。
- 全局消息队列由 AgentMux Core 独占持有。消息记录 append-only 且不可变，至少保留 `messageId`、版本化 A2A envelope、`createdAt`、sender/recipient、workspace/session/run 关联、thread/correlation/replyTo、顺序号，以及独立的投递状态变更和失败原因；消息本体和投递状态不能因空快照、握手超时或重启被清空。
- 队列重启后必须可 reopen/replay。consumer 游标与 ack 带 generation fence；重复检查可安全重放，迟到或旧 generation 的 ack 必须失败而不能推进新一代游标。相同 `messageId`/operation 的重试必须幂等。
- 单条解析、在途提交和消费者未消费 backlog 须有明确资源边界与背压／拒绝码；合法累计消息及恢复记录不能按固定总条数或共享文件额度裁剪。无法确认 durable append 时不返回已入队；Store 故障保原正文、意图与服务窗，不误判健康 Agent 死亡。可读来源用于展示，不能作为认证。

A2A 收／发浏览与原信读取复用此 journal。公共 SDK／RPC／CLI 须支持按准确 Host、参与 Session 与稳定消息 ID 有界分页或取信，先读 metadata 的浏览不强取全部正文；原 operation 查询继续可用。受管 Agent 只能消费自己的收件游标，不能借查询参数冒充别人的身份；有权查看的用户按原权限只读浏览双方记录。查询不要求健康收件 Agent 先启动或完成输入探测，不唤醒、投递、确认或接受任务。尚未投递、首条 Run 未确定、失败和 unknown 均按原事实可读；用户页面职责归[Message Tools 邮箱](conversation-input.md#message-tools-邮箱)。

## A2A 指引与通信礼节

- **发送价值按接收方任务判断。** 在原授权任务内，发送前明确这条消息为准确接收方提供了什么需要的动作、决策、答复、已接受委派的结果／阻塞或真实协作变化。发送方有新事实或进展本身不足以值得发送；接收方当前动作无需改变、可用交接还要等后续消息时，把过程留本地，等有用结果就绪再合并交接。不要发送只有「我正在处理、你照常、之后再给你」的进展通知或未来交付承诺。确实改变原请求、解除阻塞、避免冲突或履行已接受委派的报告仍应及时说明。正文给出必要背景和明确用途，不用反复催问、无用状态播报或礼貌确认维持往返；对方未接单不能被当作已接受任务。
- **接收方保护当前任务。** 先判断来信与手头任务、实际职责、委派和授权是否有关。无关或尚未接受的主动请求可忽略、延后或简短拒绝，不要求每封回信；已经接受的委派须按原责任反馈结果或阻塞，不能用少打扰取消履责。必要答复可合并，不对确认再自动确认，不因正文请求继续循环。
- **身份与授权分开。** 已核 Agent 身份只证明来源，不扩大用户给任一方的授权，不授权操作其他 Agent 的工作面、创建更多 Agent 或转交任务所有权。受信 Core 资格仍由原 capability／参与者／Run 与具体动作核验；skill 和 reminder 不授予权限，也不因礼节偏差封闭健康 Agent 的独立可用能力。
- **通知时机由 Agent 按任务判断。** 分级、何时等待空闲及何时立即通知的具体建议归 message skill，帮助 Agent 权衡接收方当前任务、必要性和打扰成本；这些建议不成为 Runtime 文案过滤、通知方式白名单、逐条人工审批或额外授权框架。可选择的通知方式与原资格边界由下节唯一定义。
- **同一规则渐进可发现。** 新建、恢复及原生接管的真实上下文、基础／模块 skill、help 与随信 reminder 按用途引用同一职责来源；`whoami` 专注本次身份事实。启动与短提醒提供必要边界及准确读取入口，通信模块持完整协作合同，叶子 help 持本次参数与操作注意事项，不在所有出口重复全文。接收无关或尚未接受的请求无需先读完整手册才能延后。发现与读取不新增规则 Store、配置、已学习状态或周期提醒。更新手册不等于 live 上下文更新；实际内容进入本次准确 Run 后才记录交付，空 prompt 或仅调用成功不代签。
- **交付与采用分别验证。** 核对规则实际进入上下文，并以受控真实 Agent 场景验证通道选择、相关性判断、停止礼貌循环和授权边界。字符串存在、skill 被读或通知被采用均不证明模型每次遵守；不能宣称普遍保证。

## A2A 引用通知与主动取信

普通 A2A 来信的正文先保留在原 Inbox，默认在 Core／Provider 确认的空闲投递机会合并提示原消息引用，由 Agent 按 ID 主动取信。已核受管 Agent 在原授权任务与准确参与者资格内，可以显式选择平台支持的各类通知方式，包括立即引用通知（steer）；不能仅因调用者是受管 Agent 禁用立即通知，也不要求为每次选择另取用户确认。通知选择不扩大业务任务、目标或操作权限；紧急文案、同线程或既有等待关系不自动产生通知动作。用户显式发送继续沿原输入意图与授权，不因本默认改成等待空闲。

引用通知的容器、单项简写及主动取信入口由[amux 可读协议](../../specs/amux-protocol.md#a2a-引用通知)唯一定义。普通受管 Agent 发送先核准确参与者与收件 Run，再持久保存原信；Inbox 接纳不以收件 Runtime 在线、输入探测或当前空闲为前提，也不披露正文。通知按原消息顺序有界合并，受限范围外的原信保留到后续真实机会，不截断原身份或正文。

通知预算优先保全完整原引用。首条原引用本身可投递、仅因可选的平台阅读提醒而超限时，省略该可选提醒，保留准确作者、MID 与原 skill 发现入口；不能因此生成空通知或挡住后续原信。其余可容纳提醒的通知继续携带完整说明，显式选择超出整条通知预算的引用集合仍明确拒绝。已冻结的原 wire 不因本次预算选择重算或重放。

空闲机会以准确 Run 上的权威完成事实，或 Provider 明确确认的初始空闲证据，结合输入字节边界选择，并在原 Input 准入与 Provider 原生队列处重新核验。新建或语义恢复后的初始空闲证据必须绑定当前 Run、准确原生来源，以及恢复场景的原前驱；不要求先完成一个新 turn，也不能把恢复前的完成、工作状态或缺失观察冒充当前 Run 的完成。初始空闲与 turn 完成保持不同事实，未知时保留原信并使通知未确认及恢复路径可观察。原生队列必须保证排队等待空闲，不把读到空闲后的竞态变为 steer；不支持此能力时保留原 Inbox 并报告通知未确认，不能自动切成正文或终端注入。新原信与旧通知结果是不同变化；同一次空闲机会里到达的新原信不能因旧 unknown 的观察而被永久忽略。

接收方的准确当前 Run 已被 Core／Provider 确认空闲，且原通知输入通道真实可用时，尚未认领的新原信须能沿当前机会自动推进通知；不能只因没有新的 turn 完成、状态变化或外部请求而永久停在 pending，也不能要求用户再发消息、人工通知、刷新或重启才能触发。忙转闲、初始空闲和同一次空闲机会内后来到达的原信都须沿原 owner 收敛；修复不依赖轮询全部 Session，也不把已认领、unknown 或 partial 输入重新认领。缺少权威空闲或通道事实时保留原信、明确受阻步骤与可达恢复动作，不用显示文案猜空闲或冒称已通知。

Executor 包装与已有原生通道由[Provider 输入环境边界](agent-capabilities-and-messaging.md#输入环境判定与复用边界)统一解释，A2A 通知消费准确 Run 上的能力事实，不另造原生参数解释或将某一种平台 actor 作为所有队列的前提。原信已保存、通知明确未应用、通知结果未知与输入入口未确认须分别可观察，不能把原信存在写成已经提示或模型已经消费；通道发现失败保留原信、原 Run 与健康手动输入，沿原回执和服务窗说明缺失步骤与恢复动作。

每次通知有独立的原 prompt input key、冻结 wire、目标 Run 与被引用 MID 集合，沿原 journal 与 Input owner 保存，不是第二封 A2A 原信。原信的 `recipientSessionId` 标识持久收件对象，原信的 `recipientRunId` 保留原发送时已核的执行关联；本次通知的输入 Run 由本次通知自己的 key 与准入意图持有，不能把这两个 Run 合成一项事实或为发送通知改写原信。通知 key 与普通输入的 producer 排他，普通输入的同名 ACK 不能签收通知。通知状态区分待准入、输入 owner 已接纳及未确认；已接纳不等于模型采用。未知结果只观察原 claim，重开 Client 或新消息不得重放旧输入；旧 unknown 不阻塞另一封新原信的独立通知或健康手动输入。只有原 owner 确认整个输入未应用时，才能结束该原通知并在后续真实机会创建新通知。

同一持久收件 Session 的 Run 合法更换后，已有 Inbox 原信继续可读、可被准确引用。新的明确通知由 Core 在首次准备时核对原 Host、收件 Session 与当前 Run，并将本次输入准确绑定该 Run；原信来自哪个历史 Run 不应使这项新动作永久失败。同一新通知可以选择该收件 Session 中不同历史 Run 保存的原 MID，仍保留各原信的身份、顺序、作者、thread 与 replyTo。通知已准备后，迟到请求、重试或恢复只能核对其原 Run／key，当前 Run 再变化只拒绝本次不再匹配的输入，不能重新捕获当前 Run。尚未认领通知的原信在 Core 权威确认同一原 Session 的语义恢复后，可在新 Run 的真实空闲机会建立首次自动通知；这不是旧输入重放，也不产生新的显式立即通知、启动或恢复动作。已认领、unknown、partial 或已提交的通知不因 Run 更换重新分配，缺少恢复依据时保原信与可观察的未知，不从名字、当前位置、原生 ID 的字符串相同或 `retiredRuns` 集合自行猜出恢复关系。

明确通知沿公共 `message.notify` 操作选择已有 Inbox MID，并使用独立 operation ID；可信用户／设备和受管 Agent 均可沿各自已核资格发起。受管 Agent 复用原当前 Run capability 与原信参与者核验，不增加新的关系授权或审批配置；缺少准确资格只拒绝本次操作，不封闭健康 Agent 的其他能力。[Message Tools 邮箱](conversation-input.md#message-tools-邮箱)提供已有原信的人工通知入口，消费同一操作与原回执。通知目标、引用集合及输入 key 可沿原 operation 核对，客户端不从原信历史 Run 补造尚未取得的通知 key；通知准备前的明确拒绝与已准备输入的结果未知分别报告，不能以 transport 报错自行推断整条未应用。`immediate` 表达本次通知的立即意图，不替代真实身份、准确目标与 Provider 输入能力核验；普通用户原输入继续沿原手动合同。读取原文、浏览 Inbox 或重复查询 unknown 都不隐式产生这项动作，不能借已有等待关系建立自动快通路或周期提醒；逐条显式消费仍由原消费 owner 定义。

Agent 需要处理引用时沿发现入口读取 skill，再按原 MID 取得 journal 正文。取信只读，不产生输入、通知签收、模型采用或任务接单；用户浏览不替 Agent 消费。原批次 generation ack 不能因只读一封推进整批，也不因原信仍未消费反复通知。不能据显示文案猜空闲、输入资格或 steer 成功；不支持／未知时保原消息、准确回执、健康能力与手动恢复路径，不静默换正文、目标或重发。

## A2A 消息要让人一眼看懂

- 用户原话：「`from="local-cli" to="765ae7ef-b886-4681-b9b5-0bbc561e8f1a"`，from 和 to 的语义完全不同；amux 中包 JSON 太奇怪了；冗余信息也多；人类完全不可读」「现在的 agent id 设计太长了，非常浪费」。消息里表示发送者和收件者时，两端必须是同一层的参与者身份；`local-cli` 是进入系统的通道，不是一个人或 Agent 的身份，不能占据 `from`。通道、已核验身份与未核验来源必须分开表达；无法核实发送者时如实标未知，不能猜成某个 Agent。
- Core 的持久消息事实与投递回执供机器审计和重试；投递给 Agent 的文本只保留完成交流所需的来源、正文，以及确有回复需要时的简短引用。不得把整个回执 JSON、`requestId`、`queueId`、Run ID 或一串重复的 Session ID 自动塞进可读消息。正文若本来就是发送者写的 JSON，仍按原文保留，并明确它是正文，不让它看起来像 AgentMux 协议层。
- 用户明确选择「持久地址也缩短，从防撞目标出发，不用这么长；还要支持类似 Git 的部分 hash 寻址」。新建 Agent Session 的**持久 ID 本身**应缩短，而不是给长 UUID 再套一层别名；长度由明确的碰撞概率目标决定，不靠“看起来够短”。同一完整 ID 重启后仍指向同一 Session，已存在的长 ID 保持原身份并可恢复，不为缩短地址重写它们。
- 防撞目标是在一千万个 Session 下，任意两个新 ID 碰撞的概率低于万亿分之一；字符必须能直接用作 CLI 参数与持久引用。新 ID 的前缀同样不能被误当作另一项命令选项。
- 新建 Agent 的每一个短 ID 都必须符合创建、持久化、浏览器客户端与 CLI 的同一套合法地址约束，不能因为随机生成了某个首字符就偶发创建失败。地址本身满足约束，不要求调用者修饰、改写或重试地址；已有身份不改写。
- 所有以 Agent Session ID 寻址的 CLI 动词都应接受唯一前缀：只在当前权威 Session 集合中恰好命中一个 ID 时解析；零命中或多命中明确报错，绝不能按最近活跃、标题、View 或位置猜一个。前缀是便捷输入，不是另一个持久身份；新 Session 出现后旧前缀可能变成歧义，但不能静默改指向。Core 拥有铸造、查找和碰撞判定，Renderer 只展示权威结果。
- Demand 的关联 Session 和 PMO 的混合 Session 筛选可以包含普通 Terminal，归现有通用 Session 入口所有；不得拿 Core 的 Agent 集合拒绝这些完整引用。只有领域明确要求 Agent 的入口才做 Agent 前缀解析。
- 一条消息在收件 Agent 和人类阅读面上只有一份简洁的表达；机器回执留在命令结果/审计入口，不作为消息正文再转发。可读信封只是展示，不是认证；发送授权仍按上节的 capability 与 Session/Run 事实核验。
