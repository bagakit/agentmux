# Goals 与 Demand 闭环

本文定义 Work → Goals 中的目标讨论、人的确认、执行关联和结果接受。公开单项称 Goal，底层沿同一 Demand 领域身份与文件事实；Mote 是协调对象，AgentSession／Run 是执行身份，Tab／Region 是空间身份。以下要求不代签实现或安装验收。

Goal 同时是 Agent 的协作看板和人的信息看板。双方读同一个目标、成功标准、分工和交付记录。Agent 据此确定依赖、接手工作、交付证据并协调下一位负责人。人用这些事实看清整体进展与待决定事项，给出意图与关键取舍，确认目标、接受结果。在[多层注意力](../multi-layer-attention.md#各层替人吸收什么)中，Goal 以小时到天为尺度，替人跟住多条执行、委派和报告。

## Goals 的 Grill 与 Grounding

Goals 首先让人看懂要达到什么、还有什么关键取舍、接下来该对齐目标还是核验结果；持续 Goal 与执行 Session／Run 的身份保持分离。

用户不应先学习 Grill、Grounding、Mote 或版本协议，才能使用目标工作面；这些方法和身份继续支撑行为，主界面用普通语言回答目标是什么、怎样算成功、还有什么待决定、已有结果怎样以及接下来可以做什么。

每个阶段必须有可找到的真实入口，并让人预期点击后会打开原讨论、发送整理/核验请求，还是确认/接受所读内容；不能只替换方法名而仍让用户寻找入口。目标尚无结果时提供独立的一次执行入口，明确本次准确执行 Agent 和执行位置；它复用原有限开始，不创建持续 Loop，也不把目标确认变成已有有限授权的附加门槛。原讨论与关联工作面仍可达；结果检查是主动核验请求，不伪装成开始执行。多个负责人由用户明确选择，保存关系不自动执行；首次准备核对所见目标版本，原操作重读先返回原记录，不因目标后续变化重发。持续跟进是单独的次级选择，保留原 Loop 的事实与控制。

### 从探索开始

常用起步操作、目标清单与详情各有清楚主次。探索入口不要求先有 Goal、Project 或具体点子；起步不自动创建占位实体。

默认常用操作是三句完整请求：「我还不知道能做什么，可以了解我并给我建议吗？」「我有一些点子，我们开始尝试一个项目」「根据最近的项目情况，建议我下一步应该做什么」。前两条不要求已有 Goal、Project 或具体点子；第三条只在可靠 Project 上下文存在时可用，点击前可见准确项目名，所发送的上下文与之为同一对象；上下文来源只是当前项目时，句子改称「根据当前项目的情况」，不假称最近。学生、工程师等角色入口仍是候选、尚未成为要求，当前不建立这些入口、角色档案或角色配置；了解用户从轻量对话开始，不先要求填写兴趣、技能或身份字段，后续目标讨论由原对话 owner 承担。

可见的完整句子就是首发消息：点击一次就发送所见请求并进入真实对话，不在短标签后藏问卷、第二次提交或多阶段指令。准备、入队和实际送达分别表达；一次在途点击不重复创建或投递。失败与未知保留原请求、已建立的工作面、健康 Run、执行焦点和布局；探索不先造空 Goal／Project，与显式 New Goal 的草稿创建分别成立。

常用操作的完整请求、可靠项目条件、原对话、保存冲突与失败恢复沿本节；排版、宽窄密度和图形角色唯一见[《Goals 的目标正文与对齐密度》](../presentation/goals-and-demand.md#goals-的目标正文与对齐密度)。

常用操作的目录、顺序、显隐及新增入口归 Settings 的 Goals 分区；指令正文复用同一 Prompts 实体与配置 owner，引用与正文的保存保持原子及冲突边界。Goals 的保存只提交该目录及其当前有效引用的正文编辑；其他指令草稿和所有指令库删除仍由 Prompts 的显式保存处理，两页切换与保存回执保留各自未提交的原稿及冲突依据。Goals 起步区保持日常使用入口，配置导航不发起对话。保留上述默认完整请求与可靠项目条件，支持用户以一句指令新增、引用已有指令、修改正文、排序、移出常用及收起更多操作。自定义正文仍由原 Settings Prompts 指令实体唯一持有，常用操作只持引用与排列/显隐；修改同一正文会影响其他使用入口，应清楚说明，移出常用不等于删除指令库内容。新增只需正文，名称可辅助生成，高级属性按需；管理编辑与排序不能发起 Agent。已展开或准备执行的完整正文在发送前可读，名称不能代替真实请求；一次点击发送所见正文并进入原对话，不暗附问卷、第二次提交或多阶段流程。适用 Agent 与实际匹配执行者必须诚实可见，实际执行者先沿本节主 Mote 原 bot 的已确认归属，符合指令适用范围时复用其真实配置；没有已知原 bot 时才沿既有启动选择规则，并明确显示实际名称；不匹配不静默代换。没有可用匹配执行者时管理仍可用、请求保持而不猜选。更多操作与模块本身可收起，返回、取消、移除及重排保留明确焦点，增加数量不能吞掉连续目标清单；不自动恢复已移除项或复活被删正文。视觉与图形角色唯一见 surface-density[《Goals 的目标正文与对齐密度》](../presentation/goals-and-demand.md#goals-的目标正文与对齐密度)，原 Mote、保存冲突、服务窗及健康工作面继续由既有 owner 承担。

### Mote 协调与已有授权

Mote 默认承担协调职责：意图或授权未明确时继续轻量讨论，不早建空项目/需求、不强制每轮创建；当一个可检验尝试、实际位置与授权足够时，先检查并复用已有项目和 Agent，需要新项目时建立真实目录及最小初始指令，通过原公开 owner 注册项目、建立或绑定 Demand，并把包含原意、真实上下文、交付与证据标准的任务实际投递给可用执行 Agent、记录同一真实 Session 关联。细设计和实现默认由执行 Agent 承担，Mote 继续讨论、组织、跟进与取证；用户明确要求亲自执行时按该授权。通用协调职责只由应用署名的 Mote 启动指令这一个 owner 持有（见[《Wiki 与应用协调指令》](motes-and-coordination.md#wiki-与应用协调指令)），不能暗改可见 CTA 原句、只为某个按钮补隐藏流程、覆盖用户 SOUL/Wiki，或把普通 Topic/执行 Agent 改成协调者。项目注册不冒充目录/指令已创建，指派/记录/进程退出不冒充任务已送达或目标达成；用户仍决定目标与关键取舍，Grill/Grounding 的提案、人的确认及结果证据沿下述合同。能力、保存或投递未确认时保留讨论、实体及健康工作面，如实说明步骤，不能猜 API、身份或成功，也不能用直接配置写入代替未确认的公开能力。

协调职责在新讨论与复用已有 Goal 会话的实际请求中都可用，沿同一应用署名指令 owner，不只留在新会话启动时或要求用户重建 Mote。用户显式 New Goal 已保存的待定义实例应持续更新同一 Demand 的标题、原意与目标提案，不因「探索不早建空需求」拒绝该已存实例或另造一份。意图、实际位置和既有授权足够时，Mote 持续讨论并推进真实项目位置及初始指令、注册或复用、同一 Demand 绑定与其他执行 Agent 的实际任务；仅一轮 Grill 提案或自己包办细设计不算协调交付。公开帮助和实际请求应说明已支持的更新与发现、绑定、派发和回读入口，并按真实执行 owner 区分会启动／投递输入的 Goal 开始（`goal.start`）与只写领域元数据的命令（如独立的 `agentmux-demand`）；一次未确认结果先读原回执与实体，不重复 create、start 或发送。用户的明确新建/实施授权与目标确认、结果接受仍是分别可读的事实，不借后两者反复索取已给的有限授权，也不替人认可。

公开帮助必须完整说明现有 Project 身份、需求写入的风险与授权参数及回执含义，不能让 Agent 按帮助仍无法完成已授权的项目/需求绑定。写入策略（按风险确认、全部确认、默认直接创建）与决策记录只见[《需求写入授权与决策记录》](motes-and-coordination.md#需求写入授权与决策记录)；那里记录的写入确认只说明这次创建的授权来源，不是下文的目标确认或结果接受。项目注册返回的 workspace 身份不能冒充 Project 身份，所绑定的 Project 必须来自当前公开发现事实；未知风险、待确认授权与用户已经给出的授权要清楚区分。补齐帮助不得放宽原风险/授权判据、替用户确认目标或接受结果，也不得靠隐藏 CTA 指令、直接配置写入或临时绕路弥补公开能力说明缺口。

### 清单、详情与当前下一步

Goal 与其计划的阅读地址保留原 Goal owner 的稳定 Runtime 身份、准确 Goal 存储命名空间及 Goal ID；命名空间由原 owner 的真实存储资源限定，同一 Runtime 改用其他 Goal 存储不能接收旧链接。计划地址是同一目标的阅读位置，不是另一个业务对象或一次制定请求。公开导航复用 Goal 的原 focus 能力，能明确选择计划段；链接、命令和界面打开同一原 Goal 与原计划。不同来源即使有相同 Goal ID 也不能互相替代，来源不可达时保留原页面及链接并说明未确认，不借当前设备、负责人或工作目录猜测来源。复制链接不授予访问或执行权限。

打开计划位置显露[同一 Goal 的推进图](#详情工作台的原记录)。打开、请求制定、发起执行分别由明确动作触发，不能以导航自动补发请求、创建任务或恢复 Agent。导航回执区分 Goal 已选中与原图实际可见；重复打开和迟到的观察不覆盖用户后来选择或未保存编辑。

用户进入页面、打开一个目标及返回清单时，都能沿同一目标读懂当前事实、下一步和动作结果：清单结论在详情里有对应的正文与实际入口，打开目标、继续讨论、发出对齐/核验请求和人的认可各有清楚语义。当前工作状态、目标确认与结果接受仍沿下述同一 owner 和边界，既有未知、差距、旧报告与恢复动作继续可读。已有目标的阅读与探索入口保持主次，进入详情后的临时收纳与返回不改变用户常用目录、未保存正文、搜索/筛选、目标身份与原健康工作面；收纳后出现的新在途、未保存、失败或回执不明事实仍有可见摘要，并可回到保留原草稿的同一入口。确认前成功标准与真实未决问题保持展开可读，不能让人认可未读内容；关键决定尚未解决与可确认保持互斥的真实状态。产品语义、视觉和交互分别按实际观察范围核对；评分是设计判断，不代签安装、模型行为或未观察场景。视觉约束唯一归 surface-density[《Goals 的目标正文与对齐密度》](../presentation/goals-and-demand.md#goals-的目标正文与对齐密度)。

详情围绕同一当前局面组织原工作、证据与下一步。目标定义、工作状态、执行生命周期、关联身份与请求回执分别表达；已有原执行时，无结构化计划或尚未确认目标不把它重置成从未执行的起步流程。主动作对应同一当前结论，原工作/结果核对、原操作检查、讨论、有限新执行和持续推进各沿已有准确目标与资格，不能从显示文字反推控制。任务、责任和委派材料组织成一个工作区，保各原 operation 和结果来源，避免重复操作；未知/在途原记录仍可检查，不自动重放。历史或暂不可见 Agent 保原身份及已知元信息，按准确 Host/SID 复用公共持久来源读取，不以全 Host 搜索或展示名猜关系，不为呈现补造 control 或更换原会话。

清单按「轮到谁」分组并给出页头计数：等人确认目标或查看结果、回执不明的认可归「需要你」，停止、过期、未核验或待答复归「需要处理」，其余为待定义、由 Agent 推进、观察未知与已接受。分组、阶段字形、计数与清单下一步文案出自同一领域判定，详情首行复述同一阶段与下一步；它只是阅读投影，不授予确认、接受、输入或恢复资格，不改变工作状态，也不从展示文案反推。委派报告待回收归 Supervisor，不提前算作人的步骤。连续处理沿同一分组顺序：清单行可用 j/k 或上下方向键在所见顺序中移动焦点，输入框内的按键与组字不受影响；打开的目标显示其在本组中的位置，「下一个」打开同组中排在其后的目标。移动与位置只读当前所见分组，不新增状态或订阅；已显示的目标因事实变化换组时只给一次短提示，首次出现、新目标与减少动态偏好下不提示。

常用起步操作、目标扫描与正在阅读的正文各有明确主次，不因装饰、重复说明或固定空栏牺牲可见的目标与结果。保留三句原始一击即发请求及其可靠项目条件、同一常用操作指令与未保存草稿、搜索筛选和原目标选择；排列变化不增加提交、不自动发送、确认或接受，也不重建讨论、工作面或健康 Run。成功标准、重要未决问题、结果依据、差距、未知和认可回执不明仍沿本节真实人类确认边界可读可操作。具体密度、对齐与图形角色唯一见 surface-density[《Goals 的目标正文与对齐密度》](../presentation/goals-and-demand.md#goals-的目标正文与对齐密度)。

- **Project 关系沿同一真实身份**。Goals 的项目筛选、属性选择与明确创建/修改使用同一公开 Project 身份，不能把内部 Workspace 身份当成 Project。一个项目及其 worktree 只形成一个项目选项，跨 host 的同名路径保持不同身份。已绑定但当前无法找到的 Project 保留原 ID、已有名称及关系，并清楚说明暂不可用，不自动换绑、清空或显示成未分配；用户仍可明确改选或清除。结果的本地证据只沿报告捕获的原 Files 资源定位，规则见下述目标确认与结果接受；Project 关系不能代替文件来源，也不改动已有执行 Session、确认/接受及健康工作面。Project/Workspace 分层与分组真值继续归[《Project 与 Workspace》](spaces-and-layout.md#project-与-workspace)。

### 显式新建与专属讨论

- **显式新建直接开始目标讨论**。New Goal 一次明确点击就保存真实待定义的 Goal 草稿并进入它的专属 PMO，不再事前要求填写意图表单。草稿不虚构意图、完成标准或人的确认，以当前明确选择的真实 Project 作上下文，没有选择就保持未分配；普通常用探索 CTA 仍不先造 Goal/Project。讨论只整理和更新这同一个 Goal，不再创建第二个实例或项目，不启动目标的执行 Run。一次在途新建、短暂离开/返回及保存回执不明都保留原创建身份，不能重复造目标；只在 owner 已确认保存后进入 PMO，未知先读取同一目标。保存或 PMO 准备/投递失败就地说明实际失败步骤、已保留事实及恢复动作；已有 Goal、已建立的专属 Tab/launcher 和原请求保持，再试仍指向它们，不误称尚未建立的 Tab 已存在，也不停止健康 Run。优先级、日期、标签、批次、执行者与 Session 仍不是创建必填项。Agent 整理真实目标和标准，不虚构用户未表达的要求或查证不到的 Context，人工确认与结果接受继续沿原合同。

Goals 的 Work 导航归属、跨上下文打开和无唯一已知关联时不猜 Goal，只见[Work、Survey、Recall 与 Mote 的导航上下文](spaces-and-layout.md#worksurveyrecall-与-mote-的导航上下文)；下述专属讨论定义实体关系，不合并 Goals 与左下 Mote 面板的选择。

- **Goal 在主 Mote 中有专属 Tab**。主 Mote 的固定默认身份唯一见[《主 Mote》](motes-and-coordination.md#主-mote)；New Goal 在这同一个主 Mote 内建立该 Goal 的专属讨论 Tab，各 Goal 保持各自独立的 Agent 上下文，不能把新 Tab、Region 或 AgentSession 说成新 Mote。原主 Mote 名称、目录、SOUL、头像、Wiki 与资料保留，不按 Goal 或 Project 复制 Mote 实体或人格；Goal 所关联 Project 只提供该目标的真实上下文，不决定另一个主 Mote 身份。已有关联的 Goal 继续指向原专属 Tab，重入、重试与重启先保留并恢复同一 Goal/Tab/Region/Session 关系，恢复未知沿原服务窗说明，不借其他 Goal 的讨论冒充恢复。 同一个 Mote 目录不足以证明已经复用主 bot。常用探索、New Goal 与已有 Goal 的讨论都归原主 Mote：探索只在其中建立独立讨论 Tab，不新建 Mote，不提前造空 Goal/Project；New Goal 和已有 Goal 沿各自专属 Tab 与同一 Goal ID。新讨论沿原明确目标及已知 bot 的真实 Executor/Provider 配置，保原名称、SOUL、Wiki 和资料，不因配置顺序、产品名或活动项目静默换一个 bot；既有专属 Tab 映射的 Session 继续原上下文，不以复用 bot 为由暗中合并或更换这些会话。同一个真实提需或 PMO 对话可以创建、参与多个 Goal；默认 Supervisor 直接引用该准确来源 Session，不因此新建专属会话。专属讨论与默认指派是不同关系。明确指令的适用 Provider 限制仍成立，不匹配须可见，不另建每 Mote 偏好或身份名册。

已有 Goal 的首次讨论与原讨论恢复必须区分。用户明确打开该 Goal 的讨论，或对该 Goal 发出真实的澄清、结果核查请求时，若原 Goal owner 与 Core 的权威读取均确认没有既有讨论操作、冻结请求或讨论绑定，可以在同一 Goal 上显式建立首次专属讨论；不能因 Goal 早已存在或没有首次讨论记录而永久拒绝这个入口。首次登记由原 Goal owner 核对当前记录版本，保存同一首次操作与完整意图，再沿原主 Mote 和讨论 owner 建立工作面；不重建 Goal，不改写其创建来源、Supervisor、目标提案、执行关系或人的确认，不自动为旧 Goal 生成计划或派工。

任一已知原讨论操作、冻结请求、Tab／Region／Session 引用或绑定存在时，都先保留并核对同一原关联；缺少投影、读取失败、来源不可用或解析不明不能当成从未有过讨论。首次登记的并发或回执未知继续沿同一操作读回，不新建另一次讨论或覆盖已保存的关联。清单读取、详情浏览、启动恢复或后台观察不自行登记首次讨论。

已知主 bot 的事实尚未确认时，原主 Mote 的 launcher 内明确说明原 bot 未确认、请求未发送、完整草稿仍在同一 Region，以及手动选择 Agent 后启动的下一步。不能只把说明留在浮窗后，也不能把另一配置的默认选中态说成已复用原 bot；没有既有 bot 的首次选择和非主 Mote 的普通 launcher 沿各自原用途。已在运行的 Session 继续原上下文，不受新讨论的配置选择阻断。

同一浮窗内的主 Mote 卡片也沿已经保留的 Agent Region 表达事实：原 Agent 引用仍在、快照尚未确认时显示状态待确认，不能一边保原上下文、一边写「No Agent yet」。只有真正没有原 Agent 引用的冷启动才表示尚无 Agent；这条呈现不改变任何 Session、Run 或恢复动作。

PMO 请求必须使用所关联的真实 Project 与具体 Workspace 的身份、Host 和路径；Project 身份、Workspace 身份和 PMO 自身运行目录不能混称。所见项目与发出的上下文一致，未知、已删除或来源含糊时如实说明，不猜另一项目；用户原文保持。尚未分配 Project 是正常目标状态，不冒充关联失败或要求重试；项目相对文件引用保持原文，不借 Scratch 或活动项目代替其根。已经分配但被删除、失效或含糊的实际 Project 关联仍诚实说明。项目文件引用按原宿主、路径及项目根边界解析，`~/` 只有获得该 Host 的真实 home 才能展开，本机 home 不代替远程事实。没有既有变量 owner 时不许诺通用模板替换，也不对正文盲目替换 home 字符串；具体用户坏链接仍需按实际原句核验，不把尚未查证的原因写成已修复。

### 目标确认与结果接受

- **Grill 对齐目标**。一个目标的当前 Grill 结果是可阅读的目标摘要、稳定身份的成功标准与少量真正影响选择的未决问题；用户看过当前内容后明确确认，不能用完整 transcript、空模板或系统属性替代目标协议。Agent 可以从对话提出和更新方案；用户只提供意图、关键取舍和确认，不承担整理成表单的工作。来源对话仍可追溯，当前目标正文不重复堆历史聊天。没有标准或尚有关键未决问题时，如实说明尚未对齐，仍可继续讨论和使用原执行工作面。
- **Grounding 对齐结果**。每条当前成功标准都能对照真实结果、可打开或定位的证据与差距。Agent 自报完成、命令成功、Session/Run 退出、已有 done 状态与证据数量都不等于目标达成。缺项、未知、失效版本和没有依据各自如实呈现；未知不画成通过。普通「接受结果」只面向当前已确认且非空的标准、完整的当前检查和有依据的结果。已核实的差距可以由用户明确选择「接受结果，保留差距」；差距保留为差距，不改写成全部达成。缺项、unknown、空标准或无依据不能用这条动作绕过核验。旧目标已有 done 但没有对齐或证据时，保留旧实体与状态，同时明示缺失事实，不能伪装成已经接受。
- **确认绑定用户看过的内容**。目标内容或标准发生语义变化后，旧确认失效，旧 Grounding 标明针对旧目标；结果提案变化后旧接受失效。同内容重报不产生新版本或清除有效确认。确认与接受必须核对当前目标版本及结果身份；并发替换后不得认可用户没看过的新提案。只有显式用户动作记录确认/接受。Agent 身份不论经 RPC 还是 CLI 调用，都只能提交提案，不能自填认可时间或版本来冒充人已确认；`goal.confirm`／`goal.accept` 只接受经传输认证的人或设备，Agent 调用者被拒绝，提交时仍核对同一准确版本和结果。认可时间与版本身份由 Demand owner 生成。
- **接受与结束由人明确选择**。结果认可与业务状态分别成立；提供「接受并结束目标」与「只接受结果」两种明确选择，保留差距的接受仍须明说差距。接受并结束由同一 Demand owner 原子核对所见目标版本和结果身份、记录认可并设为 Done；已接受的当前报告可显式结束，重复读取或提交同一报告不造第二次认可。结束沿原 Done 语义结束该 Goal 的持续 Loop 和责任提醒，不停止或替换原 Agent／Run，也不抹去执行关系、证据和责任历史。当前有效接受事实优先于历史执行的下一步提示，原执行观察另行可读；不因后来增加的呈现校验撤销已有人的认可。
- **证据保留原资源**。证据可为作者原文引用或结构化文件来源。原文完整保留且可复制，明确外链可打开；未绑定来源的本地原文只说明未绑定，不能从 Project 默认 Workspace、当前焦点、执行 cwd 或文件名猜目标。结构化文件来源保存原 `file.read` 返回的 Host、Workspace、Zone、相对路径和 revision 快照，沿原 Goal update／report／collect 流转；Demand 保存领域引用，Files owner 持有读取与资源核对。打开时核对准确原资源，内容版本变化须明说当前文件与报告版本不同，不能把当前内容冒充原证据。Desktop 与 Mobile 消费同一来源；读取失败保原报告、引用及复制入口，不影响其他结果和健康工作面。
- **协调动作标明用途与实际接收者**。讨论目标、请求结果核查与请 Supervisor 跟进分别表达真实副作用；仅打开对话明确称导航。专属讨论接收者沿原绑定 Session 投影，Supervisor 沿原关系读取，两者不互相代替。尚未建立讨论时说明在主 Mote 中开始；已有原身份暂不可见时保留它并说明待确认，不从名字、当前焦点或首候选猜收件人。
- **认可回执不明时先读当前事实**。确认或接受的保存回执不明时，唯一主要恢复入口是读取持久 owner 的当前提案；不能同时让正常确认、接受、保留差距接受或重试认可成为可操作捷径。清单与详情的当前下一步都指向读取当前提案；点击清单整行仍只打开 Goal，不直接读取或认可。读回后仍由用户看过当前内容再明确选择，不自动认可或读后重试。其他阶段动作不与恢复争抢主强调，讨论、核查请求与原工作面继续可用；目标、草稿和失败说明保留。回执不明不能被说成保存已失败或 Agent 已坏，也不依据错误文案猜分类。
- **少噪音、可收敛**。默认扫描当前目标的连续列表；可切换同一数据与筛选的横向看板，看板不能把状态列折成两层巨大空格。完成与取消按需查看，筛选可清除，选择和详情身份不因投影变化丢失。列表或卡片优先呈现目标、当前对齐事实和下一步；Project、执行状态等只表达真实次级事实。不保留一份左侧 Branch Board 清单再复制中心目标列表。
- **正文优先、属性渐进**。详情首屏是目标标题、意图/目标正文和 Grill/Grounding 的当前结论与明确动作。优先级、Project、负责人、标签、日期、父子关系、批次和关联 Session 继续可查看/编辑，但低频属性按需展开，空字段不制造填写义务；执行拓扑、活动和决策在相应区域可达，不挤成首屏系统字段墙。详情的视觉层级与密度只定义在密度 SSOT[《Goals 的目标正文与对齐密度》](../presentation/goals-and-demand.md#goals-的目标正文与对齐密度)。
- **普通语言说明当前事实与动作**。目标、成功标准、待决定事项和结果使用直接可懂的名称；Grill/Grounding 是整理与核验的方法，不作为阅读或操作的前置知识。尚无目标提案时，用户原始意图与一个澄清入口即可说明下一步，不把尚无提案、尚无结果画成两块失败区域；已有报告即使目标提案缺失仍可阅读材料，并明确无法按当前目标接受。目标已确认但尚无结果报告时，说明目标已达成共识、仍可继续当前工作，有实际结果后再对照标准核验；不能从确认推断工作已经完成，也不能把结果未提交说成失败。工作状态已是 done 但没有报告时，无论目标是否已确认都明确结果尚未核验。已有结果的差距、未知、缺项和旧版事实保持直接可见。
- **工作状态、人的认可与执行事实各有名称**。Backlog/Todo/Done 等是可编辑的工作状态，不代表当前目标已确认或结果已接受；默认清单优先一个当前待办或结论，工作状态在看板、筛选与属性中明确可达。正常阅读不要求比对版本号；只有目标变化、并发拒绝或查看历史时才需要解释版本所影响的内容。版本和结果身份仍由原 owner 持有，确认与接受仍精确绑定用户看过的内容。打开已有讨论与发送澄清/核验请求必须明确区分；简化文案不能把未投递说成已执行，也不能把澄清动作包装成开始执行。
- **对话入口必须真实送达目标上下文**。Grill 与 Grounding 都复用该 Goal 专属 Mote/PMO 工作面，携带当前意图、目标版本、标准及相关结果。已有 Agent 时也必须通过既有公开输入/队列入口提交本次真实指令；只打开旧 Tab 或改按钮文案不算进入对齐流程。没有收到、正在等待或投递未知时明示事实，不虚构 Agent 已整理。跨面切换、Mote 打开/关闭和重启继续沿既有 durable Tab/Region/Session 恢复约束。

默认 Goals 扫描和详情的工作量随当前可见目标、实际关联 Session 和相关新事实增长；不为每张目标挂载完整终端/拓扑，不因无关 Run 输出重算全部目标或重挂载原工作面。相关消费者成本与连续阅读的 P0 边界继续归[《Terminal 连续向上阅读历史》](terminal-reading.md#terminal-连续向上阅读历史)；Goals 的验收只需证明自身新增表面不放大这些成本。

跨 Source 的 Agent 关系沿原 Goal 关系字段保留准确 Source Space／Region 与 creation 或 association 准入引用，以及原执行 Runtime／Session；旧裸 Session 值不推断升级。新增关系的当次访问只用于核对原 Source 的业务成员事实，不作为保存的权限。association 关系保存不要求另一个 Coordinator 的私有或活跃资格，creation 也不依赖 Native 健康；未修改的已存关系与普通字段编辑不增加联网门。实际 Start、输入或改名分别沿原 owner 的当前目标与权限核验，关系保存不授予这些能力。

桌面退出不改变 Goal 的领域 owner：原 Host 组合同一 Demand Store、Core 输入与空间能力，持有后台讨论、执行、持续跟进和安排的业务责任；客户端只保草稿、导航和呈现。Host 的局部观察或某次讨论缺少前提时只说明该操作未知，不能关闭健康 Agent、阻断无关 Goal 编辑或把调度责任转回某个窗口。

新 Goal 的专属讨论先在同一领域记录保存唯一创建操作引用，首次实际讨论冻结准确主 Mote、已确认 Executor、初始请求与平台 Goal 上下文。Tab／Region／Session 关联仍只有 Core 空间 owner 一份事实，Goal 不另存展示映射或创建日志；跨进程恢复沿原操作继续，Goal 后续修改不改写原首句。旧记录缺少创建来源时不补造创建或输入事实，原绑定的无损交接沿[专属 PMO Tab](#demand-的专属-pmo-tab)；原来源未知不能新建替代讨论。已知 bot 的选择继续遵循上文的准确来源与未确认服务窗。

Grill/Grounding 的领域事实属于独立 Demand 文件系统包，同一份公开 API/CLI、Main 与 Renderer 投影可读；UI 只持有草稿和展示状态。Provider 与 Core/ctxmux 的生命周期事实保持原 owner，Goals 不新增第二套 Runtime、流程引擎或转录库。目标内的依赖只沿[Goal 计划](#goal-计划节点评审与盯盘)表达；结果只由人接受（见上文），Goals 不提供自动结果验收；自动审批和自定义字段尚未确认为产品要求。

## Goals、Focus 与执行工作面

Goals 属于 Work；导航分组、入口和独立选择只见[空间导航合同](spaces-and-layout.md#左下角导航space-与-goals)。Goals 的清单／看板是同一 Goal 集合的投影；Board 只是历史名称或实现用语，不再定义 Branch／Topic × Agent 状态矩阵，也不是另一全局产品入口。Agent 注意力、请求和结果查看唯一归[Focus](focus-context.md#focus-执行上下文项目泳道与底部时间音轨)，具体 Session 的输入、回复和恢复沿原工作面完成。

选中 Goal 只更新该目标的同屏详情；没有详情时保持清单全宽，不留空右栏或用方向性重排冒充分屏。关联执行上下文、文件、Diff、Activity、决策、评论和对话在同一目标下可达，明确“进入原工作面”才导航。切换、键盘返回和重启保原选择及阅读位置；先恢复 durable Tab／Group／Region／布局和焦点，Session 恢复时机引用[冷启动合同](session-recovery.md#冷启动按需恢复p0-末位)。探测、握手或快照未知保原目标与关联，不以新实体代替恢复。

Activity 中的决策按原 DemandDecision 身份保留问题、决定、理由与记录作者，详情按需展开；普通活动不伪装决策，缺少理由或作者明确未知，不从正文、当前执行者或继续原会话的合理动机补造。相同 Goal 的新增活动和原记录更新保持已有展开、节点与选区，换 Goal 不继承另一目标的阅读状态；公开 Goal 读取与独立文件工具消费同一原对象，不为呈现复制决策 Store。

## Demand 文件事实与独立包

Goal 是长期产品目标，沿底层 Demand 身份持久化；它不属于 Core Runtime，也不是 Desktop Store 的临时 UI 状态。[Demand 包](../../../packages/demand/package.json)与 Core 平行，提供宿主无关 TypeScript API 和文件系统 CLI，唯一持有领域文件、索引、锁、原子写入与损坏恢复。Mote、GUI 与公共业务服务消费同一事实，不在 Mote 目录或 Renderer 另存任务账本。

Core 持有 Provider、AgentSession、语义恢复及持久空间身份／关系；ctxmux 持有 Run、PTY、ordered bytes 与 Runtime 生命周期。Demand 包只持领域关系，不启动或管理 Agent 进程。Demand 与 Project／Session／Attempt 的关联保存稳定 ID 与可验证引用；历史关联、当前执行和 unknown 分别表达，不存在的观察不能伪成 running。

同一 Demand root 的写入与持久回执确认由该包串行；写入锁与原子提交的当前机制见 [Demand 包 README](../../../packages/demand/README.md)。必须成立的边界是：写入资格在持有者结束或崩溃后能在原数据上重新取得；等待只影响本次 root 的写入，不阻塞 Core 事件循环、其他 root 或普通读取；同一 Goal 的正文、关联、revision 与 operation 保持，未知提交不重放，损坏或锁失败不变成一个空的替代 Store。旧格式、不完整或无法识别的锁记录保留原字节并表达 unknown，记录中的 PID、时间、本机进程查询或取得 advisory 锁都不授权转换或抢占；旧锁的通用写恢复不在保证范围内。

Goal 可以记录准确原内容资源的来源关联 `contentRefs`（Host、资源 Workspace、原 Zone 的完整身份），与执行 `sessionIds`、Project 及每次展示位置分别成立。已确认的来源不是唯一显示归属：Goal 仍可因明确关联的执行 Session 出现在包含该 Session 的工作面；这种发现不向其显示 Space 追加内容来源。来源由原 Goal owner 原子追加，关闭讨论 Tab、开始新讨论或改变显示绑定不删除已确认关联；Mote 沿其原内容 home Zone 找回同一 Goal 和结果，不从当前显示的外来 Zone、名称或执行 cwd 猜来源。已有记录只可用当前准确原资源与 Session 成员事实追加，证据缺失或多个可能来源时保原数据并说明未知。追加使用原 Goal update 的记录版本检查，冲突后先读取同一 Goal；不复制 Goal、结果或生命周期。

### 公开名称与接口来源

公开 GUI 单项为 Goal，Desktop RPC／CLI 使用现有 `goal.*`／`amux goal`；底层类型、文件和包保留 Demand 身份及领域名，独立文件工具是 `agentmux-demand`。这些是不同入口对同一领域事实的访问，不按改名重发身份，也不为旧 `task.*` 建同义兼容层。准确语法、参数、权限与回执只见[公共能力来源](../../specs/public-capabilities.md#cli-与服务的当前来源)、[公共 CLI parser](../../../packages/core/src/agentmux-cli-commands.ts)和[Demand CLI](../../../packages/demand/src/cli.ts)，本页不另手抄命令词典。

## Demand 的完整业务闭环

Goal活动的有界聚合明确其准确目标范围、截断与继续读取方式，不能在默认尾部窗口外静默省略后宣称完整历史。完整单Goal原活动与已知operation查询沿原Demand owner提供，复用原记录身份／顺序，不新建事件Store；聚合摘要、原记录和Runtime日志各自有边界。读取／分页不追加证据，不投递消息，不触发执行。 聚合的 Goal 条件选择与所选身份的活动同步确认是先后两次观察，不宣称原子筛选快照；批量活动确认在原 Store 一次写入锁、稳定快照与原文件及目录同步内完成，精确保全所选身份集合。稳定读取本身不是耐久性确认，失败保留原 Goal 与健康 Agent。

1. **提出目标**：显式 New Goal 保存一个待定义实例并进入其专属 Mote 讨论；探索从原对话开始，不先造 Goal／Project。目标确认与结果接受沿[前述合同](#goals-的-grill-与-grounding)。
2. **分配执行**：从真实 Project、Agent Session 与 Mote 发现事实选择准确对象。负责人是一个或多个实际 Agent Session，Executor 只用于新 Agent 创建配置；相关会话保留讨论与历史，不冒充负责人。可以未分配、只分配不启动、明确开始或重新分配；`backlog` 表示暂不启动，改变状态或负责人不隐式开始、停止既有 Session。具体关系与恢复见[负责人、相关会话与当前推进](#负责人相关会话与当前推进)。
3. **管理推进**：详情可编辑标题、描述、状态、优先级、Project、负责人、标签、计划起止日期、父目标／推进批次与 Session 关联。父子状态各自成立，批次解释一批子目标；活动、决策、评论、执行记录保来源及时间，不互相冒充。每次执行、失败、重试或取消沿原工作记录与 Session／Run 留事实；退出、报错、Needs you 或旧 done 都不推断目标完成。
4. **恢复审计**：跨进程读取后，同一目标、正文、关系、状态与 receipt 保持。文件或 Runtime 查询失败保已读内容、选择、草稿与服务窗；关联暂不可见保原 ID，区分尚未恢复与从未关联。取消保历史；删除是准确、显式、确认的危险动作，不连带删除 Project、Session 或健康 Run。

### 负责人、相关会话与当前推进

目标卡的 Agents 与超额人数入口可悬停或点击读取完整当前团队；准确 Agent 头像悬停预览、点击或键盘激活进入原 Agent 详情阅读，保留当前 Goal 选择。只有详情中的显式工作面动作才导航原 Session；查看不分配关系、不启动 Agent、不发送输入。未确认引用只读已知角色与来源，不用同名或同 ID 的本机会话代替。

提需参与事实独立记录实际创建、讨论与补充要求的 Agent/PMO/Mote：准确身份、参与时 Session、原来源和时间由真实调用/身份 owner 确认，元信息沿原身份读取，不复制聊天全文。参与不同于负责人、相关会话、Supervisor 或当前执行；Session 退出不删除参与历史，缺少来源不能从关联、名称、焦点或历史末项猜作者。选择器先推荐与该 Goal 相关且可选的 Agent，再排该 Project 的可用 Agent；其他 Mote/Agent 沿原选择规则。不可选的历史参与仍可读、可定位，不伪装成可立即执行。Supervisor 相邻提供有可辨头像/姓名的准确推荐和明确一键指派，推荐不是已经指派。

Goals 的原 Settings owner 保存「让提需 Agent 默认担任 Supervisor」偏好，有效默认开启，GUI 与公开 settings inspect/set 同源。仅新需求首次默认指派沿实际创建/提需链确认的原 PMO/Agent Session；开启时在同 Demand 一次纳入 Supervisor、负责人和相关会话，关闭仍保参与事实及推荐、等待明确指派。该默认不追改旧需求、后来的提需补充、已有人工选择或运行中的 loop；每个 Goal 仍可显式清空/更换。保存绑定不启动 Loop。缺少准确提需 Session 时保选择入口，不猜默认主会话或当前焦点；延后取得新 Goal 原始来源时仍核首次资格及未被人工覆盖。默认绑定直接用真实提需 Session，与手选 Mote 新建 Session 的意图分开。PMO/主对话可以复用服务多个 Goal，不能由当前一目标一新 Session 的实现习惯推断身份；每次操作保明确 Goal/来源及原回执。

负责人、相关会话和 Loop Supervisor 都引用准确的原 Agent Session。负责人可多选，承担该 Goal 的推进；相关会话承担讨论与历史关联，两种职责分别编辑，在同一区域共用 Agent 选择入口。旧 Session 关联及原 Executor 配置保留，不能从 Executor 或历史关联自动推断负责人。负责人同时属于保留的相关 Session 集合，增加负责人原子加入该集合；移出负责人不删除历史。Supervisor 非空时必须属于负责人，移出当前 Supervisor 时明确清空或指定替代，并以同 Goal 的 expectedUpdatedAt 一次保存，冲突先读原记录。旧公开 Executor 负责人写入及所有客户端消费一并撤换，不保留两套负责人权威。Supervisor 由负责人中明确选择一个；保存 Supervisor 不启动循环，更换负责人或 Supervisor 不静默重绑旧 loop、不停止原 Run 或重放未知输入。原 loop 的目标、Session、Run、版本与 operation 独立保留，可检查并控制原操作。Supervisor 资格只约束新 loop；检查或重读原开始先找到同 operation 的冻结 loop，再核原目标，不以新选择拒绝旧回执。旧 loop 未显式停止前不能为该 Goal 另起指向新 Supervisor 的 loop。

选择器可搜索名称、Project 和准确身份，呈现头像、名称、项目与权威可用状态。相关且可选 Agent 优先之后，未绑定 Project 时 Mote 优先；绑定后该项目的可用 Agent 优先，working 不是唯一可选状态。未知、尚未恢复及已保留引用诚实可见，不因列表缺席清空关系。选择 Mote 为该 Goal 建新的 Session，沿该 Mote 原身份与 launch owner；支持启动新的 Agent 作为负责人，Executor 是创建参数。未明确执行位置时选择真实 Project/目录，不从 PMO cwd、显示 Space 或名称猜测。创建、关联及任务投递分别报告；稳定 operation 与原 Session 的检查入口保留，回执未知先检查，不重复创建或发送。 新 Agent 的项目与执行设备复用原 Source 选择和公开 admission；Source 自有创建从原 C 与成员位置取得关系，独立 Coordinator 创建沿原 Main C owner、再以原 L 关联到项目，不能伪造 Launcher 位置。Goal 私有叶保完整原请求，检查只读，明确续办仍用同 C／L，不改为新身份；创建和关联不代发 Goal 正文。首次选择项目访问路径只显式读取该连接原 Core 的已保存前缀，不自动建路由或授信；完整访问选择仍由本次原 owner 核对。

原 Goal 显式开始 owner 在同 Demand 中保存结构化业务 dispatch 记录：准确 Session、稳定 operation、原时间、prepared/submitted/confirmed/unknown 投递阶段及原回执引用；只记录业务提交，不持 Runtime 生命周期。该记录只能由实际开始 owner 建立，普通活动类别不能冒充执行。confirmed 依据才称正在推进，unknown 保留最后事实与原检查入口；多个无法唯一确定的当前依据表达歧义，不猜最近条目。原 Goal 的显式开始、其实际任务提交及已核对来源的委派关联共同提供当前推进依据；负责人、历史关联、Run 活跃或 loop tick 本身不足以证明正在推进。Agent Region 可呈现具有准确执行关系依据的当前 Goal 并导航其详情，多个依据或尚未恢复时明确表达相应事实。导航保持 Agent/Goal 身份、输入草稿和健康 Run，不改 Session/Tab 名称、执行 cwd，不发送 Grill 或隐式消息。关系随原领域事实恢复，未知不冒充完成或终局。

Source-qualified 单次 Start 保留完整业务引用、原执行 Runtime／Session／Run、operation、正文与独立系统 note。creation 由原 Source 的准确 Region／C 成员事实定位；association 先核原 Source 的 L 与资源，再用独立当前通道核原 Coordinator 的 C 和输入资格。关系、标签、当前路径与已保存访问选择不授予输入权；没有该次准确权限时只拒这次动作，不借本机同 SID 或 Source transport 身份，原 Agent 与请求继续保留。旧裸 Session 的单次开始和持续安排仍沿原合同。

GUI 的单次开始复用原项目连接与已保存前缀选择；association 另选独立 Coordinator，关系保存不授输入权限。连接选择和未提交任务沿原工作面私有输入保全，首次实际提交前保存原 operation；原已保存请求的 Check 只读，明确 Continue 才续办同一原 operation。新的连接编辑、不可读的较新私有输入及旧回执分别保留，不能降为本机裸 SID、覆盖后来编辑或重建任务；不可读输入在原工作区给服务窗，隐藏工作面不自动检查。尚未提交的选择可明确放弃；若 Goal 内容已变，先明确采用当前版本，已经保存的输入正文、note 和 Run 仍只由原 owner 冻结。

Source-qualified 新请求在任何连接或 Core 准备前，由同一 Demand 事务保存原 OP、准确成员、Goal 版本与冻结正文；尚无 Run 时只记 requested，不补造 Run、系统 note 或输入回执。首次实际取得 Run 后才一次推进原记录并冻结 Run/note；请求保存不授输入权。原业务事务明确拒绝的版本或负责人请求记 rejected，不冻结未知旧正文，且该 OP 不再转输入；必须读到原明确拒绝后由用户显式准备新当前版本和新 OP。未知写入或 ACK 不开放换 OP。检查 requested/rejected 只读原领域记录，不为它连接 Agent、启动或输入。原四种 Run-bound 记录不迁移、不补造早期请求事实。

原 Goal 先保存同一次提交，再进入 Core 原 controlled intake。submitted 或 unknown 后的普通重入与检查不再提交；用户可明确续办同一原 operation，由 Core 以同一冻结 key、正文、note 与来源仲裁，再沿原 waiting reference 续接。另一个 producer 的同 key 不同内容必须冲突，空读不证明原请求从未进入，未知效果不自动重放；不换 Run、operation 或创建空 Session。只有原 Core canonical admitted／terminal-confirmed 回执才能确认输入，保留回执不表示当前 Run 健康、Goal 已完成或人已接受。Core 继续独占 waiting、gate、attempt 与权限事实，Goal 不保存它们的副本。 已保存输入的检查可明确只填写独立当前 Coordinator 的访问，不要求虚构 Source 通道，按原 Runtime／Session／Run 与 canonical 正文、note、来源读取，不以 Source 暂不可读挡住这条原观察；该通道被拒或身份不符不自动换路，检查不提交或续接，实际 Start 仍核完整原 Source 与当前输入资格。

关键过程记录沿原 Demand activities owner，公共 Core/RPC/对象式 CLI 可追加并检查准确 operation。原 Session 作者由调用认证取得，业务正文不能冒充另一作者；稳定操作重读不重复写，同操作不同内容明确冲突。需求变化、进展、评审/测试证据、main SHA、发布版本、缺口和接手入口分类可读，证据保存路径/SHA 引用，不复制聊天全文或工具逐行输出。GUI 与 CLI 消费同条原活动，工作实现、main 集成、发布安装与人的成果接受分别成立。

### 状态、筛选与路由队列

工作状态 Backlog、Todo、In progress、In review、Blocked、Done、Cancelled 由明确操作维护，与 Agent 状态、人的目标确认和结果接受各自成立。默认清单只将已接受当前结果的 Done 与 Cancelled 收入历史；标为 Done 但尚未接受、无报告或报告已过期的目标仍可见，并指向所缺核验。显式状态筛选与显示历史可查看全部原实体，结束后的当前详情仍保留可读回执。没有显式关联的 Session 不自动生成 `session:*` 目标卡；Focus 和原工作面继续负责这些 Session。

路由队列可恢复地发现无 Project、无负责人、未确认或需要人处理的目标，队列不改变生命周期状态。搜索与状态、Project、负责人、优先级、标签、日期、Session／Agent 及归档筛选作用于同一集合；清除、复制或公共接口重放保持语义。清单、看板、表格不各存数据。卡片只保足够扫描和路由的 ID、目标、状态及次级关系摘要，完整正文和危险动作在准确详情内可达；字段的默认展开与视觉密度引用[呈现 owner](../presentation/goals-and-demand.md#goals-的目标正文与对齐密度)。

Goal 清单的完整范围与有界读取分开表达。公共读取 `goal.ls` 默认只返回有界的一部分（当前实现为 100 条），明确传 `all: true`（CLI `--all`）才读取完整的筛选集合，`all` 与 `limit` 不能同时使用。Desktop 的完整目标清单读取完整范围，不能把截断范围外的原 Goal 当作不存在；单个 Goal 的准确变更沿对应的 `goal.inspect` 重读，观察失败时保留原投影。断线重连后的初始集合表达完整成员范围，不能遗漏断连期间的新增或删除。

`goal.inspect` 可带 `dispatchOperationId`（CLI `--dispatch-operation`）：它只核对同一 Goal 的一次准确原 Start 回执，复用原输入来源确认并更新该次开始已发生的阶段，不准备或提交输入，也不创建或激活持续安排；省略时仍是普通观察。

## 委派回报与责任接续

Goal 的委派沿 Core 原通信 dispatch 和实际独立 AgentSession，保存原 source message、operation、Host、owner／worker、Run、冻结任务正文及资料来源；Goal 持有业务关联和逐成功标准的报告，Core 持有通信、投递与回复事实。委派不更换 Supervisor，只有显式交接修改责任。Mote 的执行 cwd 与 Goal Project 分别成立，准确发现目标，不从名称、正文或显示位置推定执行身份。

未交付的执行 Agent 退出时，原 Goal、委派、负责人和工作面保留，明确需要原身份接续或处理阻塞。已有真实报告时显示报告待回收，并让 Supervisor 沿原回复核对证据、差距与未知，提交同一 Goal 的结果；回收后显示待人核验或接受。进程退出、idle、投递、ack、worker_done 和报告自称完成均不代签业务完成或人类接受。仅观测未知时说明失败步骤与恢复动作，保健康 Agent 可用，不盲重投。

委派意图、通信提交和报告回收分别沿原 owner 持久化与对账；回执丢失和重启后保持同一 operation／message、冻结正文和原责任。逐标准报告有准确作者、原 reply、证据位置与目标提案版本，重复或迟到回复不制造新工作、不覆盖已回收报告或人的接受。原 Mote 和 Goal 工作入口提供查看来源、回答提问／处理阻塞、回收报告及原 Session 接续的真实动作；不要求用户靠追问发现未收尾。

已有 Core 委派可由原任务 owner 显式关联到同一 Goal，先核对原消息主体、Host、Run、operation、thread 和冻结正文；关联不重发、不改原文，也不追认资料已被采用。旧的 Goal 显式有限开始仍沿原业务 dispatch 与 Core prompt 回执观察，不伪造 A2A 来源或 worker 报告。当前推进须同时核实该开始的准确输入与原 Run；Goal 级结果与该 worker 的关联缺席时保持未知。新开始由原业务 owner 捕获当时的标准和结果基线，旧记录缺失的基线不从当前目标或提示正文补造。原输入未知、退出待接续、已有 Goal 结果待核验分别可读，并可打开原 Agent 或原结果。

原执行 Run 的权威退出／中断或原报告待回收可触发一次给准确 Supervisor 的 AgentMux 提示，沿现有有源输入机制并保冻结操作与原目标；不新增周期 Loop。忙、草稿或观察未知保留准备与服务窗，提交回执未知后仅对账原输入，不自动重投。原 Core 已有明确结构化报告而 Goal 尚未记到时，责任 owner 可核对真实作者、原 source／reply、版本和逐标准证据后恢复报告再显式回收，不冒充 worker 再发消息。

## Goal 计划：节点、评审与盯盘

公开指南从同一 Goal 的计划、当次交付和评审进入，标明可分派与须返工的节点。命令帮助持有准确参数，评审回执不明时回读原节点与原委派。

一个 Goal 是一个完整目标；目标较大时，在 Goal 内拆成计划，而不是拆成多个零碎 Goal。计划是一组节点及其依赖构成的有向无环图。每个节点写明要达成的结果、依赖哪些节点、覆盖当前目标提案中的哪些成功标准，以及可由他人复核的检查。计划是同一 Goal owner 内的业务记录，不创建分支、不要求提交，也不依赖任何仓库状态；代码在各项目中如何合入仍按项目自己的方式。

Goal 详情中始终可读[推进图](#详情工作台的原记录)。「拆分计划」沿原制定入口经同一 Supervisor 请求机制向该 Goal 当前合法 Supervisor 发出明确的制定计划请求：围绕当前目标提出节点、依赖与检查，并将结构化计划保存到同一 Goal owner；仅打开讨论、返回一段拆分文字或准备了请求，都不算计划已建立。保存后的计划在原 Goal 详情可见，不要求用户另开隐藏视图或先学习 CLI。计划写入仍由当前合法 Supervisor 或人完成；专属讨论的存在不自动授予管理权，没有 Supervisor 时，客户端保留原请求并沿原关系入口明确选择；保存选择本身不发送，之后一次明确点击才发送同一请求。Agent 作为当前 Supervisor 应直接读取和修订计划，不能请求自己。不暗改负责人或冒用人的身份。阅读 Goal 不写入计划修订、节点、依赖、执行委派或持续推进。

制定计划与人的目标确认、节点派工、结果接受分别成立。已有真实目标提案时可以据其当前标准编制计划，不因尚未确认目标而隐藏计划入口；缺少目标定义或可引用标准时，在原讨论说明具体缺口并先整理同一 Goal 的提案，不虚构标准、人的确认或依赖关系。请求沿原 Host 的同一持久准备与输入机制冻结准确 Supervisor Host、Session、Run、请求者及当前提案与计划版本，和 PMO 巡查按用途隔离；忙、有草稿或观察未知时保留准备，可投递时只尝试一次，未知只对账。Supervisor 变更保留原请求为陈旧，新明确请求才指向新负责人；同一 Session 恢复后仅从未尝试且原 claim 确认不存在的请求可显式接续。计划请求不接受巡查回报、不进入巡查告警；保存新的计划版本才是完成事实。已冻结或已 claim 的旧专属讨论请求沿其原接收者只对账，不重发计划正文、不改投，也不妨碍向当前 Supervisor 发出独立新请求。请求准备、实际送达、计划保存与派工分别反馈；失败或回执未知保留原 Goal、计划请求与讨论身份，先核对原操作，不重复投递或新建替代目标。

计划由 Supervisor（通常是 Mote）在目标提案之后提出并维护，人可以随时修改。每次修订带计划版本并按版本比较写入，两个调用方同时修订时后到者被拒绝并先读取当前计划，不能静默覆盖。同一操作的重读须核对原作者、预期计划版本、提案版本与节点正文；该操作之后已有新修订时说明原操作生效的版本和当前版本，先读当前计划，不把新计划冒称原操作的重放。新节点或无执行记录节点本次改写的成功标准集合须非空且属于当前提案；未改动的既有集合保留，陈旧引用沿原节点明确对账。依赖必须指向同一计划内已有节点且不能成环；修订不能删除已经有执行、报告或评审的节点，只能把它标为取消并保留原记录。已有执行记录的节点保留原结果、检查与成功标准集合，换成另一项任务须取消原节点并新增节点；标题与执行者仍可明确修订。目标提案换版后，节点引用的成功标准按当前原文与原委派冻结的标准核对，缺失或正文改变的标准如实标出，旧评审仍可读但不代签当前完成、不解锁依赖；未变化的标准成果继续有效，不因无关提案换版作废。

节点只持有业务关联，执行仍沿[委派回报与责任接续](#委派回报与责任接续)：Supervisor 把一个依赖已全部完成的节点委派给一个准确的 AgentSession，沿 Core 原 thread 发送冻结任务；委派记录多出所属节点，其余身份、回执与报告事实不变。执行 Agent 可以在本机、在远端 Host，或通过远端执行绑定在远端项目中工作；节点以 Host 与 AgentSession 精确指向执行者，Project 与执行 cwd 分别成立，不从名称或显示位置推断位置。委派与回报沿 Core 原通信，跨 Host 的来源与反向回报沿[跨 Runtime 原消息与回报](a2a-collaboration.md#跨-runtime-原消息与回报)的独立目的信任与原签名成立；不转发受管 Agent 凭据。原 Goal 只在监督者的 owner 中保存，委派分别冻结 owner 与 worker Host、双方 Session/Run、标准版本和原消息。执行者从本机已核验的原 source 与严格结构化 Goal 载荷回报，不解析可见正文确定权限、不复制 Goal Store；回执明确区分远端报告已持久准备与原监督者已收集。原监督者沿现有连接取回已签原回报，再按原委派核对并收集评审。信任或观察不足时保留原计划、执行者和消息引用，明确未确认的阶段及恢复入口，不改派、不降为无来源的消息。节点可在计划中写明执行者（Host 与 AgentSession），委派必须指向该执行者；一个节点同一时刻只有一个当前执行委派。换人通过计划修订改写执行者完成，原委派、报告与 thread 保留。明确写入不同的非空执行者时，最新且尚无评审结论的尝试被取代，不再驱动节点状态；依赖已满足时可派给新执行者。清空执行者不取代原尝试，已通过的节点不因换人重开，要求修改的节点沿原返工规则明确改派。在新执行者尚未收到委派前改回原执行者，原尝试仍可恢复为当前尝试；新执行者已收到委派后，旧尝试只作历史。被取代尝试的迟到报告保留在原委派并标为前一次尝试，不能作为当前尝试接受节点评审。

人或当前 Supervisor 可直接指派执行者，也可把已有计划中依赖已满足、尚无执行者和当前委派的工作节点开放认领。既有计划默认维持原分工，缺少开放记录不产生认领资格。该 Goal 当前的负责人或 Supervisor 可通过公开 CLI／JSON-RPC 以经过认证的自身身份认领。仅被列为相关 Session 的 Agent 可读取计划。原 Goal owner 按准确节点、所见计划版本、当前资格与原操作原子保存一位执行者；竞争者可以读回最新分工，同一操作可对账。认领只建立责任关系，真实派工、交付、节点评审与人的结果接受分别沿原流程。对身份、版本或授权的拒绝只作用于本次写入。

执行 Agent 按节点的成功标准逐项回报，相当于一次待评审的交付。节点完成需要一次评审：评审方必须是执行者以外的 Agent 或人，实际运行节点声明的检查，并把检查命令、结果与证据位置记在评审结论里，结论只有「通过」或「要求修改」。要求修改时，Supervisor 在同一 thread 上向执行者发出返工委派，原委派、报告与评审保留。评审通过的节点才算完成，其依赖者才可开工。评审节点的结论不代签 Goal 的结果接受；所有节点完成后，Goal 的结果仍沿[目标确认与结果接受](#目标确认与结果接受)由人接受。

Goal 内的交付入口指向原计划节点和准确的当前委派。要求修改后的新交付与先前结论在同一节点可追溯。界面保存人的节点评审时沿原公开 `goal.plan.review` 与相同依赖推导；焦点、按钮操作、已保存的报告和独立复核各有明确回执。单次直接执行沿原结果接受入口。

节点状态不单独保存，由依赖是否完成、当前委派与报告事实、最新评审结论推出：等待依赖、可开工、执行中、待评审、要求修改、已完成、已取消，以及委派或观察事实未知时的未知。Agent 退出、idle、投递或 ack 都不推出完成。依赖未完成的节点不能委派；节点之间可以并行的就并行推进，不要求逐个排队。

盯盘复用已有的持续推进：Goal 的 Supervisor 以该 Goal 为任务来源开启持续推进时，每次检查同时读取计划。有可开工、执行中、待评审或要求修改的节点时继续推进，并把这些节点和各自的原 thread 交给 Supervisor 核对；全部节点完成时暂停，等待人接受结果；剩余节点都在等待已取消的依赖时暂停，说明需要修订计划；计划不可读时暂停并说明原因。节点处于未知时继续推进，并要求 Supervisor 先按原回执对账，不因观察缺口停掉盯盘。不为计划另起第二套调度或轮询。

公开能力：计划的读取、修订、节点委派与评审都经同一 Goal owner 的公开 JSON-RPC 与 `amux goal` 命令提供，帮助说明节点、依赖、评审与盯盘的关系，管理者与执行者的上岗指引引用本节。Desktop 与 CLI 读同一份计划和推导状态，不各自另算。推导由 Goal owner 随每份返回的计划一并给出，当前尝试只引用原委派的 `delegationOperationId` 与 `reported`；source、thread 和 worker 从同一响应的原委派唯一事实读取，不复制参与者身份。owner 未附推导、推导结构失效或与所附计划／委派对不上时，只隔离这份非控制推导，在该 Goal 显示节点状态不可用、具体原因及重读原 Goal／更新原 Host 的恢复入口；原计划、委派、列表其他 Goal、写入原 operation 与回执仍完整可读，不重复已保存的写入、不自行补算节点状态。控制写入仍由原 owner 核对权限、版本、依赖与原消息。公开方法和输入不变，只读投影附 `planStateIssue`；旧严格读者须与 Host 同时升级，不保留旧尝试镜像字段兼容层。

### 详情工作台的原记录

看板负责跨 Goal 的扫描与选择，详情围绕同一 Goal 阅读分工、依赖、当前交付和执行记录。分工、图、执行记录与协调入口定位同一原节点、当次委派及其检查；旧尝试保留原证据，不能用它评审新交付。Goal 默认就是图中的唯一工作节点，包含原目标、目标当前结论、成功标准与原执行。拆分后同一位置读取原 owner 保存的节点和依赖。图的 Start 和 Finish 只解释同一流程的首尾，不参与任务计数、委派或评审。完成标记同时依据 Goal 完成与当前结果接受事实，保留带差距接受、旧完成未验证和取消的区别。单次尝试失败继续归该尝试。默认节点直接读取 Goal 本身，既有 Goal 无需补写。

打开详情默认阅读推进计划，返回清单保留原筛选、视图和焦点。首个当前待评审交付可直接阅读，查看交付只定位原节点和当次委派，不提交评审。分工、图、执行记录和 Supervisor 的准确协调入口共用同一节点读取，显式选择保留在此次详情内。详情页头的当前结论可以定位到同一原委派或一次性任务。定位只改变阅读位置与焦点。提交、回收和确认仍在原记录操作。协调记录的作者按原身份及 Host 读取已确认的名字，来源不完整时保留原作者引用。

执行记录以原操作与确切时间事实为准。派发关联、结果回报及评审等只证明各自事件。可证实的执行时间区间才画成执行条；仅能确认当前语义活动时，区间止于原观测并标明尚未结束。Goal 的明确计划起止另画为排期，单侧日期仅标该日期。缺起止的历史保持为事件，输入未确认不推断开始，计划依赖不生成预计时长。

Supervisor 的待办和协调记录消费原负责人与已有派工、计划修订、评审、巡查及决定。作者按各自原记录展示，导航仅定位已确认的节点与尝试。阅读和联动不授予输入或验收权限，人的目标确认与结果接受仍沿原入口。

## 执行责任、停滞告警与 PMO 巡查

持久记录中的可缺省输入资格字段沿同一领域合同读取：缺省时保留原记录和未确认资格，字段存在时校验原值与来源；合法的旧责任记录不得因新增可选字段而使整份 Goal 快照不可读。

Goal 的责任回执沿 Core 原观测合同保留主会话与子会话各自的来源和状态；公共查询与 GUI 消费同一校验边界。合法的原观测字段不得造成整份责任读取失败，缺失或未知仍明确保留，不由客户端删字段、改状态或绕过来源校验。

Goal 的执行责任必须在 GUI 中可辨：明确任务对应的实际执行 Agent、管理者、当前业务阶段、最近业务进展与下一步负责人。执行绑定来自原 Goal 开始、原 Core 输入或核对过来源的委派关联；负责人、历史 Session、名称、当前焦点和进程 running 都不能单独证明正在执行。已关联但当前无确认执行、多个依据有歧义、尚未恢复或不可用分别表达，旧 Goal 不因缺少新字段补造绑定。Goal 列表、详情、Mote 当前工作及 Agent 工作面消费同一关系与状态来源，并可定位原 Goal 或准确执行工作面。

未结 Goal 的业务责任与原 Agent 的语义状态、readiness、Run 生命周期及观察新鲜度共同决定待处理事实。任务仍需执行而 Agent 已 idle、输入/运行异常、退出或被明确停止，且尚无报告、交接、已声明的等待或下一步处理时，必须暴露停滞及准确负责者；已有报告未回收、回收后未完成核查或状态回填时，明确由管理者继续处理。Supervisor 自身不可用或缺席也形成可见的监督缺口。正常短暂 idle、已明确等待用户验收或外部条件、完成责任后的空闲分别呈现，不仅凭非终态 Goal 加 idle 就判失败。关闭展示 Tab 与结束执行分别读取，后台健康执行仍可见；unknown、stale 或 unavailable 不冒称死亡，也不隐藏尚未交代的责任。

告警说明发生在何 Goal、原 Agent/Run、哪项责任未衔接、依据与时间范围及下一步入口。idle 持续时间只使用 Core 已确认的状态起点与业务事实；缺少起点如实未知。去抖、宽限和重复提醒根据实际状态与责任变化收敛，具体默认值属于实现选择，须说明依据，不固化成无来源的永久产品门槛。告警不依赖用户展开详情或保留某个 Region；客户端重启、重连和 late event 后，从同一原 Goal、Session、Run 与委派事实重建，不复制 Runtime/任务账本，不为每张卡轮询无关 Session。

告警提供一次点击的「PMO 巡查」：打开左下快捷交流浮窗，切到该 Goal 准确原 Supervisor Agent 的对应对话，并实际向该管理 Session 提交有源请求，携带原 Goal、执行关联、异常、待处理报告和可定位证据。浮窗先展示准确目标与准备状态，不等待慢观察或投递结束才出现。原 Supervisor 的对话与 Goal 专属讨论不是同一关系，不能仅打开专属讨论或泛称 PMO 就宣称已到达管理者。浮窗复用原 Agent、Tab／Region 与准确展示引用，不改变执行 cwd、Mote 成员或管理关系；既有输入与工作保留。原请求已经保存或在途时，仍可再次打开同一准确对话并读取原回执，不重复提交输入。

点击后的目标是让管理者实际开始巡查，但窗口已打开、请求保存、输入投递、Agent 工作和巡查回填各守原事实。工作状态只消费准确 Session／Run 的 Core／Provider 状态，不以导航、按钮或 spinner 代签。缺席、退出、输入忙碌、位置未确认或恢复未知时，仍打开保留原目标的浮窗，就近说明实际步骤、未知事实和准确接续／选择入口；不先显示旧 PMO 或其他 Goal 的对话，不猜当前焦点、不静默改派、恢复、重发或另建重复执行者。明确点击巡查时，已确认原 Run 结束、原身份与原生语义恢复条件成立且没有未知输入的，可沿 Core 可见地恢复同一 Session，再接续从未尝试的原巡查请求；不暗降为新会话或 Level A 重启。已有健康能力继续可用。导航到 PMO 与提交巡查分别留回执；只有导航、入队、delivered/ack 或提示已收到都不表示巡查完成。重复点击、回执丢失与重启沿同一次巡查 operation 和原输入身份对账；在途、已开始、失败或未知的反馈在原 Goal 和本次目标窗口可读。

PMO 巡查沿原授权核对原报告、执行健康与逐成功标准证据，收回实际结果或处理原阻塞，再通过同一 Goal owner 写回当前进度、证据/差距/未知、下一责任人和下一动作；需要更新业务状态时执行有来源的明确更新。告警根据这些新事实重新判定，单次点击或发出提醒不能消警；仍有缺口时保留可接续责任和原因。人的目标确认与结果接受仍由原人类 owner 完成，PMO 不代签。巡查请求本身不扩展原实现、安装或外部动作授权。

执行角色接单时读取该 Goal 与本模块指引，核对实际绑定；关键进展、提问、阻塞和交付及时回报到原任务，结束、交接或暂停时说明结果或未完责任。管理角色负责核查、回收、状态流转和后续安排，不能以派工或 Run 结束收尾。两类职责在注入 prompt、默认上岗手册和 Goal 模块 skill 中可发现，引用本节同一合同；分层和读取入口见[基础 skill、模块发现与渐进加载](public-control.md#基础-skill模块发现与渐进加载)。新会话、复用讨论和原生接续分别保准确资料来源及实际输入，不因更新文件假称现有 live Agent 已重新采用。

## 全局巡查

Goals 提供明确的「全局巡查」入口，一次点击在同一个主 PMO Mote 内新建这次巡查的独立 Tab 与 Agent 上下文，打开左下快捷交流浮窗并实际发送检查请求。主 Mote 身份、目录和原 bot 配置沿[主 Mote 与 Goals 协作](motes-and-coordination.md#主-mote-与-goals-协作)；不创建新 Mote、占位 Goal 或新的目标执行，不改派各 Goal 原 Supervisor，也不借用已有 Goal 的专属讨论承载全局工作。在途、保存或投递未知保持同一创建 operation、Tab／Region、Session 和原请求，不因重复点击、重入或恢复新增讨论、重复发送。

检查范围是本次可发现的全部持久 Demand，包括已结束的目标，不受当前列表的 Project、状态、负责人或搜索筛选限制。PMO 沿原 Goal owner 读取逐目标事实、执行／委派／巡查及可定位证据，核对现状后在这次新对话返回汇总与处理建议。结果保每个 Goal 的准确身份、观察来源及范围，区分已核对、读取失败、信息过期和未知；部分读取失败仍展示已取得的结果和具体缺口，不能静默漏掉目标或把未核对项冒充检查通过。检查、准备、投递和真实工作状态仍分别表达。

汇总应让用户知道哪些目标正常、哪些有未衔接责任或待处理结果、哪些缺少依据，以及建议下一步。可直接处理的建议列明准确目标、具体操作、影响及所需决定，由用户明确确认所选操作或一组操作后，沿原业务 owner 执行并回报实际回执；“一键”不等于默认同意。不能直接处理的事项结构化列出问题、依据、未知、需用户决定的内容和建议下一步，在同一对话继续讨论。对话是本次全局结果和讨论的入口，不复制另一份 Goal 状态或让全局巡查 Session 冒充各 Goal 原管理者的报告作者。

全局巡查本身授权检查、汇总和讨论，不自动执行任意修复、改变目标范围／管理关系、恢复或替换原 Session、安装或进行外部动作，也不代签人的目标确认或成果接受。确认后操作仍守准确原目标与版本、原权限和未知回执边界；范围或事实变化时说明差异，已确认操作的实际成功、失败和未确认结果分别保留。无法准备主 Mote、创建／投递未知或观察暂不可用时，保本次原 Tab、请求与已取得结果，在该对话入口给出具体恢复说明，不以失败关闭无关健康工作面。

## Goal 详情中的 Session 观察投影

从 Goal 团队激活准确 Agent 时，优先在当前 Goal 上就地打开既有原 Agent 对话工作面，保留目标选择、正文位置和草稿；明确进入持久工作面仍沿原空间导航。目标是已确认的 canonical Agent Session 与 Host，有准确 occurrence 时保留原 reference；未知引用只读其原来源，不借本机同 SID。打开只导航，不隐含发送、恢复、改派或目标执行。它复用原对话与输入 owner，和下述只读观察投影分别遵守各自合同。

执行拓扑按需表达准确 Project／资源 Workspace、Topic／Branch、已有 Tab、Region 与 AgentSession；多处合法绑定可辨，不以 Session 数量、当前焦点、最近顺序或终端标题猜位置。没有 Tab、Region 或当前 Agent 时诚实说明。共用原空间与 Session 投影组件，不为每张目标常驻完整终端或另建拓扑账本。

选中目标后，可用原 arrangement 为一个或多个准确 Session 建观察投影；它是详情的临时呈现，不修改原持久工作面的分割，不创建 Session 或第二个进程。Region 复用同一 Session／Run、ordered bytes、Replay、Gap 和 Attachment owner；新观察 lease 不成为 Runtime 真相或另一份缓冲。返回 Goals 保原目标、详情位置与筛选。

观察投影只读状态、输出、Activity 与待处理事实；禁止 PTY 输入、composer 发送、生命周期修改与主动尺寸控制，只禁 resize 不算观察模式。需要输入、编辑、停止 Agent 或调整终端尺寸时，明确进入准确原工作面；已授权的控制仍归原 owner。将来允许投影接管须显式转移唯一输入／尺寸 owner，不能由多 Region 争抢。跳转失败、位置歧义或恢复未知保目标事实、原引用与恢复入口，不清详情。

## Demand 的专属 PMO Tab

New Goal 与已有 Goal 的讨论关系只定义于[显式新建与专属讨论](#显式新建与专属讨论)：同一个主 Mote 内，每个 Goal 有独立讨论 Tab 与 Agent 上下文；不创建新 Mote，不共享别的目标讨论，也不启动目标执行 Run。Demand 文件保领域事实，准确 Tab／Region、拓扑及绑定持久化归 Core 空间 owner；Client 保呈现与真实输入焦点。

新旧专属讨论共用 Core 空间图中由原领域 owner 维护的唯一绑定，固定原 Goal、Tab、Region、AgentSession 与执行 Host；原 Launcher 明确尚无 Session。Host 解释讨论关系，Core 保护原 owner 的耐久写与整图提交边界，不解释 Goal 领域。陈旧布局或普通资源提交不能伪造、覆盖或丢弃该绑定；Region 后来被替换时保留原目标并说明未知，不随当前内容暗换收件人。创建 operation 只持有原创建幂等与来源，不能成为另一份讨论绑定。

已授权的旧绑定交接仅由原 Desktop 读取自己保存的准确关系，并核对原工作面、Session 与执行 Host 后贡献到同一空间图。Core 确认同一关系已耐久保存后，原保存 owner 才逐项删除重复字段；回执未知、冲突、来源缺失或删除失败均保原字段与工作面，重试核对同一关系，不清空数据或新建替代讨论。空来源不制造关系或多余写入，单个来源的零项观察不代表其他 profile 或尚未保存的状态。待交接原字段只供核对和继续交接，不作为另一套运行时绑定。交接不授予创建、首句输入、参与角色或 Supervisor 来源；后续发送继续核对原 Core 输入及真实调用者与 ACK。

未选 Agent 的原 Launcher 只导航原入口，不自动创建或宣称已发送。之后在同一原 Launcher 显式选择 Agent，须沿真实创建来源证明该次填充：Mobile 核对 Core 公开空间创建的原 operation、位置与真实 Session 回执；Desktop 由认证 Main 在原完整创建调用中捕获准确 Launcher，保留全部启动选项，再核对实际 Core operation、Session 与执行 Host 回执；位置意图的耐久与恢复沿[Durable Runtime 健康](session-recovery.md#durable-runtime-健康)。位置和同一讨论绑定原子耐久保存后才确认收敛，不为统一形式伪造另一条创建记录。当前 Region 的外观或内容变化不足以改绑；观察或绑定保存失败保留实际创建、输入与原工作面，明确局部未确认，不封闭健康 Agent。未知回执沿同一操作确认，不重复创建。

“打开 PMO／继续讨论”定位原 Goal 的准确讨论 Tab；读取、握手或恢复未知不证明 Tab 已关闭，更不授权替换 Session。保原 Goal／Tab／Region／Session 与服务窗，沿同一操作读取或恢复；只有权威确认原 Tab 已明确关闭后，本次显式打开／新建讨论意图才可为该 Goal 建立新专属上下文，保旧关联历史，不另加一次确认。浮窗有明确目标时等待并展示该目标，Agent 尚未挂上不先展示旧 PMO，也不回退另一个 Goal。

请求携带稳定 Goal／Demand ID、当前标题、原意／描述、真实 Project／Workspace／Host 及路由事实；Mote 只整理、组织与跟进，执行分工和既有授权沿[协调合同](motes-and-coordination.md#pmo-teams-topic-名称与职责)。原目标保存未知先读同一对象，准备或投递未知先核原操作，不重复 create／start／发送。

专属讨论创建时为准确 Agent Session 与 Tab 提供可读的主题／协调名，并沿原名称 owner 保存派生来源；不能只设置 Tab 名而使 Session 无名。尚未明确主题时保临时讨论名，明确后沿原协调消息中的命名责任细化。准备失败时保原 launcher、请求和已确认名称；复用已存在的讨论不强改名称或暗送请求。名称不改变持久 Mote、Goal、Session／Run、cwd 或执行授权。

### Goal 与原持续推进的连接

本节是 Goal 持续推进（loop）语义的唯一定义；Mote 中的入口与回访摘要只引用这里。

确认的 Goal 可以由明确指定的单一 Loop Supervisor 持续推进；该准确 Session 必须属于负责人。持续推进是有限开始之外的单独授权，默认不开启。未指定 Supervisor 时详情引导选择，Continue 的启动操作在准确 Supervisor 明确后可用；有多个候选时由用户明确选择，不借最后关联项、背景 Space、名称或当前目录猜测。原 loop 的检查和控制不被新的选择状态遮蔽。原 `goal.start` 通过可选 continuation 授权，绑定原 Goal ID、已确认 alignment revision、Supervisor 的准确 Host／Session／Provider／cwd 与同一业务 operationId；未提供 continuation 仍是原有限开始。一次开始的业务 operationId 与后续每次 tick 各自准确留存，丢失回执按原操作核对，未确认时不重复发送，也不创建替代 Session。原 `goal.inspect` 按该 Goal 投影原续跑 Manager 的准确目标、状态与原操作回执，读不创建调度或复制 Goal 账本。原 `goal.continuation-action` 以准确 Goal/loop、预期 revision 与业务 operationId 沿同一 Manager 执行暂停、恢复、停止或检查；普通日历 `schedule.*` 不承载 interval 续跑。Goal 续跑与日历消息共用同一个持久调度时钟和 Core 输入事务，各自保留业务语义；Goal 生命周期只由 Goal owner 解释，Core 的续跑来源与调度不新增 Mote、Demand 或 UI 依赖。RPC/CLI/GUI 与连接设备对同一操作、版本和结果使用一致语义。

持续执行以原 Host 在线、Supervisor Agent 可用和准确输入条件为前提；关闭当前面板或换设备不改变原执行身份。设备或连接不可达时显示最后已确认的事实与未知状态，不宣称云端全天候保证。应用或连接恢复后保原目标、同一 loop、待核操作与讨论，不追补一串过期 tick。

有限 Goal 开始把已确认的任务正常提交给明确的执行 Session；Provider 具备立即打断能力不等于这次目标开始获得抢占授权。提交方式与同一业务操作在首次入队时保存，重试沿原方式和原回执；已经选择立即打断或方式尚未确认的旧操作，不能被新的有限开始静默改成普通提交。忙碌、待权限、错误 Run 和投递未知仍由原 Core 判定并保留原任务、草稿与健康工作面，不在失败后换方式或换身份重发。用户的显式立即发送与原持续推进保留各自原合同。

Goal 完成/取消仅停止相应 loop，不停止健康 Run、不删除原工作面，也不冒充成果已接受；改名或无关目标变化不停止当前 loop。blocked、待决定、确认失效、原来源不可读或读取结果未知时暂停自动动作并说明原因，保留健康 Agent。继续执行须重新核对当前版本、目标和原输入条件；手动输入、权限请求、运行繁忙和未知投递仍由原 Core 保护，已有可用能力保留。原目标版本失效后，旧 loop 仍可检查或停止，但不能恢复旧授权；新确认的版本由用户先明确停止旧 loop，再以新的开始操作授权，不自动重绑或改写旧的未知事务。loop 与 Goal grounding 的人类接受各自成立，自动推进不替用户确认目标、接受成果或宣告成功。Mote 中的入口与回访摘要见[《目标、持续推进与成果回报》](motes-and-coordination.md#目标持续推进与成果回报)。

已有计划时，生成新的计划管理输入前须核对准确 Goal 当前的 Supervisor 关系。原 owner 已明确撤换或清空该角色时，旧 loop 暂停这类新输入，保留原目标、身份与可见原因，不自动改投或新建 Agent；经原 loop 入口显式处理。已有 pending／unknown 的冻结输入仍沿原 claim、正文与操作核对，不撤回已应用输入或重新构造任务。无计划时已授权的原执行者续跑不因这条管理用途检查而撤销；Goal 读取未知只跳过本次新管理输入并保留恢复，不能猜为角色已被撤销。
