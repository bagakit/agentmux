# 伙伴从哪里来：从 Topic 到 Mote

本文定义伙伴的两条诞生路径，以及把持续工作的 Topic 晋升为 Mote 的产品目标。组织与内部 Agent 的身份分层归[持久人格合同](motes-and-coordination.md#mote-预制与持久人格)，插图与设置 Banner 归[用户故事板](../presentation/motes-and-coordination.md#伙伴从哪里来用户故事板与教程-banner)。这是已确认的目标需求；教程与视觉预览不表示完整晋升能力已经实现。

## 从画像出发，也从事情出发

用户有时已经知道需要怎样的伙伴，可以按专家画像建立 Mote，例如具有明确协调职责的 PMO；也有时只知道有一件新事情值得做，希望先让 Agent 从具体任务开始。产品应同时支持这两条路径，让长期伙伴既可有明确的初始职责，也可随着共同工作逐渐形成。

新方向不要求用户先写出完整专家画像。用户可以在 Topic 中持续讨论、积累知识并让 Agent 执行具体工作；当同一方向变得重要、持续或高频，用户可以把这个 Topic 晋升为 Mote，为已有合作建立持久人格和团队责任。工作频率与重要性帮助用户判断，不替代用户作出晋升决定，也不要求每个知识库都成为 Mote。

## 用户故事

| 场景 | 用户想完成的事 | 应得到的结果 |
| --- | --- | --- |
| 已知专家画像 | 我需要一个 PMO，帮助组织目标与协作。 | 我能按明确画像建立 Mote，并认清团队身份、内部实际 Agent 和各自承担的工作。 |
| 从新方向开始 | 我还不知道这个方向最终需要什么专家，先让 Agent 帮我完成每天的一件具体事情。 | Topic 承接真实任务、讨论和知识；成员 Agent 的经验、特质与分工从实际工作中逐渐可辨。 |
| 为重要方向建立团队 | 越来越多相关事情都在这里完成，我希望以后仍然找这个伙伴负责。 | 我能将准确 Topic 晋升为 Mote，确认长期人格与职责，并接着原成员和积累继续工作。 |

以数据运维方向为例，用户最初只需要每天检查一个问题；后来研究、诊断和方法维护不断聚集，某些 Agent 更擅长领域判断，某些 Agent 开始组织分工。晋升使用户能够将这份已有合作确立为长期团队，未来可发展领域专家能力或拆解、委派、协调、验收等管理能力。具体产品名只属于使用背景，不成为机制、界面分支或验收前提。

## 晋升的结果与连续性

晋升是用户针对准确 Topic 发起的显式操作，把已有合作确立为长期伙伴。组织与内部 Agent 的概念用于保持准确关系，不要求每个概念对应一个用户操作；晋升不增加组建团队、确认成员、填写职责或选择默认交流对象的必经步骤。原名称和资料沿用，人格与职责可在后续合作及原资料编辑中完善；已保存内容可读、可改，不以默认画像覆盖原用户资料。

晋升后的 Mote 延续原 Topic 的知识、来源、讨论历史、成果、成员 Agent 与合法协作关系。用户能从新身份接回原事情，辨认实际执行者，继续已有工作；建立团队人格不意味着把全部成员合并成一个 Agent，也不声称任意成员已经读过全部历史。

原 Topic 的内容身份、Zone、Tabs、Regions、合法展示绑定、草稿、文件与恢复引用须连续保留。Mote 的 Space 关系沿[原空间模型](spaces-and-layout.md#空间模型)建立和核对，不能把 Topic Zone 改称 Space 或以新空白工作面代替原成员。Session／Run 与执行 cwd 继续由原 owner 持有，晋升不重启健康 Agent、不替换原 Session，也不隐含新建成员或授予执行与外部操作权限。资料和人格对已有或新 Session 的实际生效，沿[原文件加载合同](motes-and-coordination.md#会话入口与原文件记忆)表达。

持久人格、目录与空间绑定须有可核对的操作结果。界面显示晋升完成之前，相关 owner 必须确认同一原操作的实际结果；部分完成、回执丢失或观察未知时保原请求、成员、资料与可用工作面，并说明已确认部分、待恢复步骤及继续入口。再次查看或恢复核对原操作，不重复创建 Mote、不用删除原 Topic 掩盖未完成。物理目录如需调整，继续遵守[原目录与身份保护](motes-and-coordination.md#topic-与-mote-的物理目录)。

## 发现与公共消费

GUI、Agent 与 CLI 应能发现准确 Topic 及其成员与资料，发起同一晋升能力，并检查同一操作的原结果。空间身份和绑定由 Core 公共 API 持有，成员生命周期与输入继续经过 Core；持久人格与文件由原内容 owner 保存。实现计划须按[公共能力贡献约定](../../guides/public-capability-contributions.md)核对既有发现、Files、空间与 Mote 能力的复用及必要 JSON-RPC／CLI 扩展，不在客户端复制分类判定、成员名册或晋升事实。

教程只负责解释两条路径。查看插图或 Banner 不创建对象、不改变当前 Topic／Mote，不自动启动 Agent；尚未接通的晋升动作不得用可执行按钮或成功画面冒充可用能力。当前视觉评估先回答用户是否理解故事、能否区分组织与成员、是否愿意继续了解；完整晋升的交付仍需以真实消费者、操作回执及重启后原身份和工作面可恢复的证据成立。

## 功能方案提案

以下方案沿已确认的简化方向展开，具体入口与反馈样式仍是提案，尚未实施；它消费前文已确认的组织／成员分层与连续性要求，不改变原权限、空间、文件与会话合同。呈现提案见[晋升交互](../presentation/motes-and-coordination.md#topic-晋升交互提案)。

### 从原事情发起

建议在分类目录的 Topic 行尾菜单及 Topic 自身对象菜单提供同一「晋升为 Mote…」动作。用户不必先进入某个 Chat、启动 Agent 或达到使用次数门槛；高频与重要性是用户判断的理由。设置 Banner 继续承担介绍，实际晋升以准确 Topic 为起点。

入口以原 Topic 名称说明准确对象。同一对象已经晋升时显示「打开 Mote」；该对象有未完成的晋升操作时接回原结果。已有工作继续由原页面承载，无需为了晋升再浏览一遍成员和成果清单。读取不完整只标明受影响部分，不把未知成员数量写成零，不停止仍可工作的原 Agent。

已确认尚无 Agent 或讨论的 Topic 也可以建立长期身份；成员数量不决定晋升资格，晋升本身不自动补建成员。

### 一个晋升动作

建议点击「晋升为 Mote…」后只给一次轻量确认：展示原名字和一句「原来的 Agent、对话和资料都会保留」，用户选择晋升或取消。没有必填表单，也不在此时配置团队、成员、长期职责、合作方式或默认讨论。

晋升沿用原名字与已有外观；无自定义外观时使用 Mote 默认形象。已有资料保留，缺少的人格文件沿原新对象机制提供可编辑的基础内容；不以人格生成、完整历史分析或资料补全作为晋升前置条件。改名、头像、人格及合作偏好仍在原 Mote 资料入口编辑，不为晋升再造一份设置。

内部仍保留 Mote 的持久身份与实际 Agent 的区别，用户在原讨论中能辨认正在做事的成员。成员关系、默认交流和职责沿原 owner 持有；晋升不会自动指定 leader，也不替成员加载全部知识。后续共同工作中的职责与偏好积累沿原知识和人格文件合同表达，不宣称晋升本身已经完成学习或启动主动工作。

### 完成以后，接着原来的事

确认提交的作用是建立持久 Mote 身份、资料与原 Zone 的准确关系。源内容 ID 与 Zone 保留，Mote 增加自己的 Space，原 Tab／Region 和成员引用继续使用；不能复制一份 Topic 作为新团队，也不能把 Zone 的 ID 重新解释成 Space ID。物理目录转换继续由[原目录 owner](motes-and-coordination.md#topic-与-mote-的物理目录)保原 inode、旧地址与已有 cwd。

建议 Mote Club 出现该伙伴，原分类位置保留一个标明「已晋升为 Mote」的同对象入口，点击仍进入原内容及工作面；它是沿原关系的投影，不是另一个普通 Topic 或永久双份人格。原分类绑定与其他合法绑定保留，用户之后可明确整理。这样用户从原路径仍能找到伙伴，不因晋升让一个正在阅读的条目突然失踪。此项是导航提案，实施前需同时收敛原 Topics 列表的筛选及打开语义。

完成后在原处简短提示「已晋升为 Mote」，保留正在阅读的工作面、输入和位置，用户直接继续原讨论，无需再选择「继续」。提示可附「查看 Mote」入口；没有讨论时仍保原空工作面，由用户沿已有入口开始。异步完成不抢回后来切换的对象。Mote 的 Profile、Discussion、Ideas、Calendar、头像、行为和默认交流沿原能力承接，不另建一个晋升后的管理后台。

原知识的查找、读取、继续写入与来源引用应在首版同时接通。晋升结果不能只有文件仍在，却让原知识 API 拒绝同一内容。分类列举可以区分普通 Topic 和晋升后的 Mote 入口，准确内容与知识寻址必须能解析同一原对象并返回它的实际类型；GUI 与 CUI 共同消费这一事实。

人格保存、生效和执行分别表达。晋升不自动发消息或热替换正在运行的 Agent 上下文；继续旧讨论沿原上下文，新会话按[原文件加载合同](motes-and-coordination.md#会话入口与原文件记忆)读取保存内容。这些生效边界由原资料界面按需说明，不增加逐成员交接步骤。仅建立长期身份不自动开启巡查、日程、持续推进或外部机器人。

### 不完整结果仍可接续

取消轻量确认不改变对象。提交后保同一原操作，明确区分已确认完成、部分完成和结果待核实；关闭界面不冒充取消已经发生的写入。只有存在实际未完成步骤时才呈现局部恢复说明，用户可查看并明确继续同一操作；不再发一遍「创建 Mote」。已存在文件、后来的人格编辑和其他工作面变动按各自准确版本核对，不用全局停工换取一致性。

首版建议不提供一键「降回 Topic」：人格、默认交流和更多绑定可能已经发展，逆操作不能靠删除 `SOUL.md` 实现。已有资料编辑、归档及恢复能力继续可用，提交前可取消；完整反向转换如有需求再单独设计，不能把归档称作降级或回滚。

### 功能先后

| 范围 | 建议交付结果 |
| --- | --- |
| 首版：用户主动晋升 | 一个晋升动作、原资料与工作直接延续、必要人格资料及空间关系保存、目录及旧引用连续、知识访问接续、Mote 与原分类入口、同一操作恢复；GUI 与公共调用一起完成 |
| 后续：从工作里提炼人格 | 在原资料编辑或日常交流中提供带来源的起草帮助，保用户已写内容；不另建必走的成长向导 |
| 有实际需要再做 | 克制的晋升建议与更好的协作体验；成员能力发展不预设专门管理页、职级、积分、人事评分或自动晋升机制 |

首版的完成标准是用户晋升一个已有工作的 Topic 后，能从 Mote 和原入口接回同一批工作、知识与成员，并在中断或重启后继续；「设置了一个新头像」或「新建了一个空 Mote」不满足该结果。
