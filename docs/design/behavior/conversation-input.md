## Agent 输入行与视图切换

- Agent/Session 的单一身份位置归[《Agent Region 关闭与身份入口》](spaces-and-layout.md#agent-region-关闭与身份入口)：Region 顶部标明正在观察哪个 Agent，输入区不再复制名称与身份条。输入区继续表达输入模式与输入动作；Message Tools 保留现有 Agent 头像及其完整提示/可访问名称，让用户辨认消息接收者。
- Terminal 与 Activity 只保留一个紧凑的图标切换按钮。按钮的图标、tooltip 和可访问名称说明点击后将进入的视图；切换沿用同一个 Session 的 `viewMode`，不创建第二个 Terminal、Activity 或 Session。
- Scratch Topic 点击的成功条件是右侧存在可见的 Tab、Region 和内容面。若布局、会话或启动流程暂时不可用，原位置保留可操作的加载/失败表面与重试动作；不得以空白工作面表示正在加载或失败。

## System Reminder 的默认与单次选择

用户要求 System Reminder 有两层选择：Settings 设置「默认是否开启」，Launch 可以覆盖「本次会话是否开启」，参照现有 AgentMux guide 的默认初始指令设置。Settings 的选择提供新会话的默认值；Launch 未覆盖时沿用默认，显式选择只作用于本次会话，不回写 Settings 或改动其他已有会话。默认值与本次选择必须分别可理解，不能用一个含糊的开关同时表示两者。

本项已确认的是默认与单次覆盖的关系，尚未确认提醒正文、触发时机或频率、出厂初值、默认配置的具体作用域，以及已有会话恢复时是否继续原选择。不能据「System Reminder」名称自行推定周期调度、system-role 协议、额外提醒 Store，或把 Provider 原生历史里的 reminder 当作 AgentMux 通用提醒能力。提醒的实际语义与发送 owner 明确前，不交付只改配置却不能兑现效果的开关；保存、开启、启动或历史出现提醒文字，都不冒充提醒已按约定送达。提醒流程失败按原健康能力与服务窗合同如实说明，不取消已有可用输入或启动；既有 AgentMux guide 保持其原合同。

## 可收起的 Agent 快捷输入区

- 底部对话输入区应可收起并一键恢复，收起不丢草稿；主要提供文件引用、截屏、技能选择、快捷指令四类快捷入口。文件引用沿用当前 Agent 的文本提交通路，选择结果先进入草稿，用户决定何时发送。
- 展开/收起入口放在快捷工具行最左侧，与文件、截屏、技能、指令等按钮同排；展开态不额外占用一整行高度，收起后仍保留同一位置的一键恢复入口与草稿提示。**这一枚就是唯一入口**（三态语义见「Agents、队列与 Message Tools」一节）。
- 展开入口必须参与底部工具行的正常布局流，不能以浮动定位覆盖输入文字；收起态仍在该行同一位置提供恢复按钮。**绝对定位的第二入口已废止**：它此前靠给工具行留一段左内边距来避让，而工具行在窄宽度下会折行，避让与绝对定位一起错位——这正是本条约束要禁止的形态。
- 截屏使用系统选区，取消不改草稿；成功后生成可供当前 Agent 读取的图片引用。技能选择显示实际发现的技能及来源；快捷指令依据当前 Provider 提供，输入 `/` 可选择，选择只填写草稿，不暗中执行。
- 发送、中断当轮、收起输入区是三个清楚区分的动作；中断沿用 Core 的当轮 interrupt，不终止会话。输入法组字、失败保留草稿、运行中 steer 的既有约束继续成立。

## 当前 Agent 的上下文余量与输入焦点

- 用户要求「给你自己的对话框上加 context 剩余监控」：每个 Agent 输入区展示所属 Session 的原生上下文余量及观测时间；容量与当前占用来自 Provider，经 Core 的既有用量事件发布。累计计费 token 不是上下文占用，不可用它扣减容量。压缩后的新观测可降低占用，缺数时明确未知；最近一次观测不能伪装实时计量，监控缺失不能阻断输入。
- 用户要一眼看出哪个 Agent 快把上下文窗口用完了：Agent 名册和工作区 Agents 列表按同一原生占用率显示 70%／90% 的提醒，并说明可收尾或开新会话；这只是产品提醒，不宣称 Provider 的压缩阈值。低占用不添“安全”状态，未知不作 0% 或安全，提醒不改变 Agent 状态、输入权限或 needs-you。
- 聚焦 Region 时，Terminal/TUI 应收到其原生键；只对匹配且属于宿主作用域的动作消费事件。IME 组字不触发快捷键；没有消费的键原样交给聚焦内容。冲突解决复用既有快捷键注册与作用域，不在各组件复制拦截规则。
- 浏览器产生新页面时以来源 View/Region 归属决定打开位置：分屏来源在该工作视图中选择合理区域，独立 Tab 来源开新 Tab，不默认弹出独立窗口。网页链接右键提供既有分屏/Tab 打开位置菜单，用户显式选择优先。

## Composer 消息队列与紧凑状态
- Composer 的 Context、发送和中断控制采用紧凑工具栏布局；Context 以低噪声状态徽标呈现，完整剩余量通过 hover/展开查看，不占用正文行。
- 用户在 Agent 工作中发送的内容必须先进入该 Session 的有界消息队列；Provider 当前可接收时立即按序投递为 steer，否则保持 queued 状态并在下一次可投递时自动发送。队列条目可见、保序、可删除，失败保留原因，不得静默丢失。
- pending interaction 不得被普通消息绕过；消息继续排队，交互回答完成后再按序尝试投递。
- **队列里等着的是用户亲手写下的文字，它必须挺过一次重启。** 进程重启后草稿还在、排着的消息却没了，是把 AGENTS.md 第 12 条反过来做。恢复后这些条目仍按「它是对哪个 Run 写的」判定可投递性：对不上当前 Run 的照旧显示为不可投递、交给用户处置，但内容不得替用户丢掉。
- 发件列表还应允许调整尚未在途条目的顺序，保留同一消息身份、文字、目标 Run 和失败原因；调整只改变当前队列顺序，不授权执行、不触发恢复，也不解除重启后的待执行状态。已在途条目不能被移位、越过或伪装成可撤回；不存在或已确认投递的条目不参与重排。
- 条目有真实入队时间时可查看，首次接收入队记录的时间在恢复、重试和重排中保持不变；缺少这一事实时如实显示未知，不用 Session 创建时间、历史消息时间或当前时间补造。入队时间不是 Agent 闲置证据，冷启动仍只消费 Core 的语义状态事实。

## 内置任务持续推进（，AFTERTIME 使用需求）

- 用户开启一次「持续推进」后，不应因 Agent 阶段总结、关闭观察面板或正常结束一轮而丢失配置；默认每 30 分钟检查，可修改间隔与续行提示。目标必须显示并绑定精确 Host、Session、Provider 与 workspace，Run 是可替换的执行实例。
- 续行提示与其他输入表面遵守同一组字保护：中文候选未确认时，循环观察或其他界面更新不能覆盖输入法预览；结束后保留用户实际确认的文本。输入占用观察只读原草稿、队列与在途事实，不追加、替换或写回用户草稿；只读观察不能被当成另一个草稿写入者。
- 整理展开设置的编排不改变原目标、分钟值、续行提示、来源绑定或草稿/队列；开合不启动、停止或重绑循环。表单标签与原输入控件保持对应，键盘与组字沿原 owner；正常和窄分屏的控件语言只定义在密度 SSOT[《持续推进观察界面》](../presentation/conversation-input.md#持续推进观察界面)。
- 调度状态、Agent 执行状态、业务任务状态分别保留。调度不能批准权限、绕过问题、隐式 resume、改变权限策略或修改业务完成状态。检查失败只暂停自动续行并说明原因，不阻断健康 Agent 的人工使用。
- 到期遇忙跳过，不堆积消息，不在忙转闲时额外补发。只有正常一轮结束、输入就绪且仍有可推进工作时才能续行；立即检查遵循相同规则。working 活动证据过期显示未知并提示检查，不猜空闲或强杀重启。
- 权限或用户问题等待时不发送，并能定位原请求。用户中断/停止应暂停循环，恢复循环须明确操作；暂停循环与中断 Agent 是两个动作。无法分辨正常 Stop 与用户中断时，不宣称可以安全自动续行。
- 每次检查有 tickId；同一 Run 的同一就绪信号最多提交一次。提交边界必须复核身份、就绪信号、执行状态和用户输入占用，覆盖重复检查、直接 Terminal 输入和未提交的 Composer 草稿。自动续行不得挤掉用户输入；缺少证据时暂停自动投递并说明。
- 自动续行只消费精确目标的现有草稿/人工队列占用；观察缺席、取消或退出仅暂停循环并说明，不阻断人工使用。新自动认领须由同 Run 的真实 Native 输入栅栏确认，未知不能补零；旧未知操作仍按原完整请求调和。人工取消在认领前到达才撤销自动候选，已认领字节不能撤回；Renderer 观察与 Core 认领不宣称分布式原子。
- 决定发送、Host 接受、Provider 消费/新一轮开始分别记录，不能观察时标 unknown。结果未知不自动重发；检查与最小回执持久保存，界面重载不得造成双发。
- 应用退出或休眠期间不承诺调度；恢复后仅重新检查一次，不集中补发漏掉的周期。配置不依赖模型内部 Cron、调用者 shell 环境、临时终端或 UI 定时器。同一精确目标至多一个活动循环；接管内部 /loop 时提示用户停用旧循环，不声称可以自动检测和删除它。
- 可选绑定 Feature Tracker 等只读任务来源。无绑定时可设置截止时间/触发上限，只称定时续行，不能证明业务完成。Tracker 全部 Task done 但未 closeout 仍未完成；closeout 是待推进工作。archived 表示完成，discarded/transferred 表示终止或转交，不能都显示业务成功。依赖阻塞与任务来源不可读必须分别说明。
- 任务来源由用户显式绑定 root、Feature ID 和公开脚本；每次仅核一项公开 owner receipt，不重算 Task frontier。全部 Task done 待收口只暂停并说明，归档才可称业务完成；终止、转交、不可读不冒充成功。来源检查不改变旧未知输入操作，人工输入保持可用。
- 无可运行项时展示阻塞原因，不空发相同提示。空转提醒必须有任务适配器声明的进展证据；token、输出量、一次测试通过不能单独证明完成。
- 暂不包含自动批准权限、多 Agent DAG、模型切换、部署或成本优化。现有 Core 输入与生命周期 API 是唯一执行边界，续行策略由 Host 持有，不下沉到 ctxmux。
- 观察界面见 [Surface density](../presentation/conversation-input.md#持续推进观察界面)。评估与验收建议见 AFTERTIME intake（本机过程资料：`docs/reviews/continuous-progress.md`）。

## 持续推进与邮箱共享入口

用户要求：「现在看看 Continuous progress 是不是应该放到 mailbox 旁边或者里头去，这里好好设计，更新需求并优化」。持续推进收进当前 Session 邮箱浮层的独立 `Progress` 页，复用一个常驻入口，不在已经拥挤的输入操作组里再加按钮，也不保留 Composer 下方的独立持续推进行。Inbox、Outbox、System 仍分别表达来信、发件和系统告示；Progress 表达自动续行配置与控制，不是一类邮件。

- 邮箱入口的 Inbox 数字与 Notices 提示沿[《入口提示的清楚含义》](#入口提示的清楚含义)；持续推进的未启用、active、paused、unknown 用另一种可辨认状态标识与完整 tooltip/可访问名称表达；循环状态不计入未读、消息数量或投递成功，也不以 Agent 正在执行冒充循环正在启用。观察未确认时保持未知。用户不打开浮层也能辨认是否有自动续行及其当前状态。
- 打开仍沿既有未读与发件优先级选择邮件页；Progress 由用户明确选择。新消息、循环事件与观察结果不强制换页。选择 Progress 不把尚未看过的 Inbox/System 标为已读，也不改变队列投递状态。
- Progress 页有明确的持续推进标题、精确目标与原有配置和操作。浮层开合、邮件/Progress 切换与 Composer 三态切换都不丢未提交的分钟值、续行提示、来源字段或组字中的内容，不启动、停止、重绑循环，也不重复建立观察订阅；迟到结果仍只属于原精确目标。切换 Session 后不能把旧表单或循环状态带到新目标。
- 原启用、暂停、恢复、停止循环、立即检查与任务来源能力继续走已有 owner；停止循环不等于中断 Agent。未知或失败在入口保留可辨状态，详情可读原因与恢复动作，人工终端输入和 Composer 草稿仍可用。键盘可到达各页、操作和关闭入口，关闭后回到同一触发控件；打开浮层不改变原 Tab、Region、Run 或终端实例。

用户进一步要求：「Progress 里头的设计太难看了，重新设计吧，要现代化一点，至少有『设置』界面的水准吧」。该页先让用户配置自动续行或理解当前循环，再查看具体决定和目标；设置编辑、运行控制与最近决定各有明确对象，不以长标识、说明全文或无标签图标占据同一层。视觉与控件质量只定义在密度合同同名小节。

- 未启用时周期及分钟单位、续行提示、可选只读任务来源与明确启用动作完整可达；来源绑定后才展开原三个字段。启用后原周期、续行提示和来源仍可完整读取，属于已保存的只读配置，不增编辑接口或把再次启用冒充保存。精确 Host、Session、Provider、workspace 在同面可发现的目标详情中完整保留；概要不代替真实绑定。
- 当前循环状态与 Agent 执行状态分别有标签，next check 和最近检查／决定只消费已有时间与原事实。观察未确认或错误优先明确说明；仍保留的已知循环事实标为上次已知，不能同时暗示 active 已确认或承诺下次自动发送。paused／stopped／unconfirmed 不显示有效倒计时；缺少时间／决定不补造记录，不新增事件历史或业务成功结论。Host 接受而新一轮未确认仍沿原语言。
- Pause／Resume、立即检查、停止自动续行都有可辨文字及准确可访问名称，保持现有可用条件和一次原目标调用；停止自动续行不停止 Agent。完整失败原因与人工输入可用说明同面可读，不因改版新增输入禁用。目标、配置／来源详情和页切换不得卸载原表单或重建其观察，组字、未提交字段、迟到结果与原草稿／队列边界保持。

页面、标签与状态标识的密度只定义在 surface-density[《持续推进观察界面》](../presentation/conversation-input.md#持续推进观察界面)；邮件自身的已读、未读与投递约束仍见[《Message Tools 邮箱》](../presentation/conversation-input.md#message-tools-邮箱)。

## Message Tools 的事实来源与快捷语法

- 初始页与 Agent Session Composer 共用同一个 Message Tools 能力面。输入区支持常见的 `@` 文件/目录引用、`/` Provider command/subcommand、`$` skill 选择；工具选择和手写快捷语法最终都生成同一份可恢复 prompt 草稿。
- `commands` 与 `skills` 的能力范围优先来自当前 Provider 的 catalog/声明；AgentMux 自己提供的配置型能力复用工作区或用户目录下 `.agents` 事实协议，不复制一份 Provider 任务真值。来源、路径和不可用原因要可见。
- 未连接 Session 的初始页只能使用项目/工作区上下文与可发现的本地 `.agents` 内容；需要 Provider Session 才能解析的能力显示为待启动或 unknown，不能伪造可执行项。启动失败保留输入、引用、skill 和 command 选择。
- Provider command 与 AgentMux 自己的快捷命令命名冲突时，不静默改写；显示来源并按明确选择生成 prompt。未知 `@`、`/`、`$` 文本保留为普通输入。

### 对话里的贴图

- 粘进对话的图片要**看得见**：渲染成缩略图，而不是一颗只显示路径的文件链接按钮。点击放大到灯箱。
- 路径表示原样保留：Agent 要靠那个 `@path` 去读图，缩略图只是给人看的一层，不替换引用本身。
- 走 data URI 是 CSP 逼出来的（`img-src 'self' data:` 挡死 `file:`），不是选择。
- 读图有信任边界：落盘目录收成一处派生，读回时 realpath 双侧解析，防止 symlink 逃出贴图目录读到外部字节。
- 起头的 `@` 是记号不是路径字符，解析路径时要剥掉，否则 `@src/foo.ts` 永远打不开。
- 缩略图的读取失败或仍在加载时必须保留原始路径引用；不能留下破图框，也不能因为展示失败把 Agent 可读的引用删掉。读取成功但浏览器解码失败同样回到原引用文字，移除失效缩略图与放大入口；已打开的灯箱解码失败须收起。已读取贴图的显示事实绑定同一 path 与 reader；读取目标或 reader 变更后的首呈现不能把旧图字节配新引用，失败与灯箱状态只作用于该精确贴图。迟到读取或旧图事件不能使当前图失效；正常可解码图片仍沿原缩略图与共享灯箱查看。非本应用贴图目录的图片路径继续走普通文件引用规则。
- 灯箱是同一张图的放大查看，关闭后焦点回到触发缩略图；不建立第二份附件或图片字节事实。远程图片不因这条能力自动请求。

## Message Tools 失败反馈与 Browser Region 选中态

- 用户反馈「MessageTool 截图不了，已经授权还老弹出授权提醒」，并明确反复出现的是 **macOS 系统录屏／屏幕捕捉授权弹窗**。截图必须按实际截图通路的真实结果处理，已授权时可完成且不误反复请求系统授权；改善 AgentMux 内部文案不能冒充此故障修复，也不能让用户重复授权代替根因验证。当前 Electron 的授权读数不能单独证明系统截图命令被拒绝；已授权、unknown 或授权读取失败不得被误挡。真正未授权才在原工具旁准确说明当前副本、恢复动作和重试，不自动重复请求系统授权。不得重置权限或替用户授权。
- 用户进一步确认「重启后仍无法截图并弹系统授权窗」，且「打开系统设置」仍出现；重启或重复打开设置不能代替同一已授权实际运行副本可截图的验证。
- 「已授权」必须绑定实际运行副本与系统使用的签名身份；设置开关开启、安装包自身签名校验通过都不能单独证明当前副本拥有截图授权。交付更新须保持可延续的授权身份，不能靠每次重新打包后让用户重复授权维持截图能力。
- 截图选择器同一时刻只有一个；重复点击不启动第二个选择器，也不把第一张图交给另一份草稿。系统取消不算失败、不追加引用；截取、超时与保存失败必须分清并保留正文、已有附件和原 Session 目标。结果迟到或目标切换后不得写入新 Session、Workspace 或 Provider。真正完成且保存的图片仍沿既有粘贴目录、引用及缩略图能力进入草稿，不新增截图 owner 或隐藏替代通路。
- Message Tools 的文件、截图、Skill、command 和发送操作失败时，优先在组件自身显示短暂、可重试的原子错误层；全局通知只作为跨组件或无法定位来源的补充。错误层不得清空 prompt 或已选引用。重试与原入口的后续成功都应清除旧失败；切换 Workspace、Provider 或 Session 后，旧请求与旧重试不得污染新对象。多项工具结果同时返回仍须完整追加到当时的草稿。
- 组件内操作错误保留失败动作的重试入口；成功重试或主动关闭后收起，失败不覆盖当前草稿。初始页一次选择多个文件必须全部加入，并基于选择完成时的草稿追加。初始页共用工具能力，但没有三态输入宿主时不显示空转的形态切换键，工具保持直接可用。
- Browser Region 点击内容区必须更新 Workbench 的明确 active Region；选中边界、标题和键盘焦点与 Terminal/File/Agent Region 使用同一事实，不靠浏览器内部 URL 或 hover 猜测。

## Message Tools 触发与菜单

- 输入 `/`、`$`、`@` 分别打开 command、skill、文件引用候选；选择只写入草稿，不暗中发送。三者复用同一个可访问菜单，支持上下方向键、Enter、Escape，菜单展开不改变底部工具栏的布局高度。
- 候选菜单沿用 Message Tools 的浮层与控件语言，不另造一套高列表；当候选过多时在浮层内部滚动，输入框和底部操作保持可见。

## Gallery 到聊天页的生产替换

- 聊天页面的观察区直接消费 Gallery 已验收的 Workflow surface；Gallery 是隔离验收入口，不是另一套生产组件。
- 替换只改变观察区的展示与交互编排，消息、Session、Agent 状态和 Runtime 事实继续由原有 owner 提供；生产聊天不得读取 Gallery fixture。

## 观察界面最终统一

- Gallery 与聊天页面使用同一套生产组件；Gallery 不是样稿，而是聊天观察区的快速验收入口。
- 聊天页的 Activity、Workflow、服务窗、权限卡和 Composer 必须共享同一条观察主线：对象先于装饰，状态先于颜色，动作靠近事实。
- 统一后的界面必须同时表达“现在发生什么、为什么发生、用户下一步能做什么”；没有事实就不画空壳，不用示例数据冒充真实状态。
- 视觉效果可以有强烈的层次、光泽和动势，但不能牺牲密度、键盘可达性、reduced-motion 或状态可辨识性。

## 可复用对话与 Workflow 表面组件

用户确认的演进方向：技术方面向原有成熟组件靠拢，设计风格参考新的 Workflow；提高视觉设计感和产品成熟度，让工作流观察更清晰。组件事实归宿主，展示策略有唯一 owner，交互状态支持宿主控制；Gallery 展示必须能独立构建，不初始化桌面 Store 或 Runtime。现有聊天和观察表面的视觉改版保留输入、权限、滚动、身份轴与服务窗的既有行为，不把 Workflow 假数据接入真实聊天。前端技术栈按当前依赖、实际问题与迁移成本评审，不以换框架代替设计工作。视觉规范的层级和唯一来源见 Surface 密度合同。

- 参考页里的 Workflow 时间线不是一张只能复制的样稿，而是一组可以被不同 Client 消费的受控组件：普通 tool 行、Workflow 摘要头、阶段折叠、Agent 行、Agent 元信息、安静项折叠、旧 daemon 降级行、dock 压缩态和输入框上方提示条都必须有稳定的类型化输入与可访问状态。
- 用户进一步要求对话过程实际接入现有 Workflow 组件：聊天 Activity 的真实步骤与状态消费这套共同观察语言，不停在 Gallery 示例。数据适配归宿主，组件不读 Store、不猜 Provider／Run 状态；Gallery 不成为聊天数据源。记录组不等于有阶段、工作流或多 Agent 的执行事实，没有真实阶段与统计不画虚构阶段、Agent 数、tokens 或进度；已有普通步骤仍完整可读，未知观察保持未知，真实失败与在途状态不能因视觉适配丢失。 长过程默认突出最近记录与真实失败，全部原始步骤仍由一个清楚入口展开；隐藏数按实际成员计算，展开沿原顺序，整组记录起止与总 steps 不随局部展示窗口改变。披露只保存用户意图与已呈现记录身份，不复制步骤事实；切换披露保已读正文、原选区、展开和草稿。
- 用户反馈「streaming 旁边旋转的图标动画过于简陋」「这里的线框感太重了」，希望使用带动画的 SVG 和更现代的层次：过程状态仍由已有真实观察事实决定，动效不补造进度、状态或新步骤；减少动态效果时保留可辨的静态图形与状态文字。过程的轻层次不改变原起止、数量、未知／失败、完整步骤、键盘开合、已读正文、选区和草稿，也不增加数据读取。图形与层次只见视觉合同[《可复用对话与 Workflow 组件密度》](../presentation/conversation-input.md#可复用对话与-workflow-组件密度)。
- Workflow 组件只表达观察事实：`running`、`completed`、`failed`、`killed`、`paused`、`queued` 的视觉与中文文案一一对应；只有真实拥有阶段明细时才提供折叠箭头，旧 daemon 退化成普通 tool 行并持续说明“daemon 版本较旧，暂无阶段明细”，不留空壳。
- 折叠是统一的 disclosure 语义：按钮通过 `aria-expanded`/`aria-controls` 管理卡片、阶段和“还有 n 个”；Agent 行点击、Enter、Space 都能打开同一份元信息，失败行永不被安静折叠吞掉。运行中保持展开，终态默认摘要化；用户展开后状态更新不能把焦点或展开意图抹掉。
- 大规模列表超过 8 个 Agent 时自动分栏；分栏后尾部连续的 queued/completed 安静项可以收进可反复展开的“还有 n 个”，失败项不能进入该折叠。窄屏隐藏模型与最近工具，并把头部统计放到第二行；dock 使用同一组件的紧凑变体并限制内部滚动高度。

- 工作中的 Composer 同时保留“发送 steer”和“中断当轮”两个可见动作；发送只提交补充指令，不改变当前 Run 的生命周期。Enter 仍是发送快捷键，按钮文案必须让两者可区分。
- Activity 聚合行的状态只出现一次；等待、错误和阻塞等摘要不得再追加同义状态标签。路径与 Host 只作为次级元信息，不得把工作线行撑成多行卡片。
- 聊天页已有的 ConversationAxis、AgentMarkdown、AgentInteractionCard、ComposerTextarea、StatusDot 和 ServiceWindowNotice 是同一组件体系的既有成员；它们继续各自拥有身份轴、正文、请求回答、IME 输入、状态点和服务窗事实，不复制一份“聊天版”实现。Activity 内部的 Row/Run/Turn/Ruler 在后续接入时也沿用同一边界。
- 组件的可访问名称、键盘操作、焦点环、减少动画和非颜色状态提示是组件契约，不由 Gallery 或未来聊天宿主补丁式添加。颜色与侧边细条不得成为唯一选中/状态信号；状态必须同时有字形、文案或结构变化。

## 对话接入新组件与输入引用闭环

- 用户确认「继续推进，另外对话的样式也可以接入新组件」：真实对话与 Gallery 共用消息组件，沿用现有时间线、说话人身份、Markdown、文件打开、图片、继续会话和滚动行为；不把示例 Workflow 阶段或进度伪造为真实对话事实。
- 输入中的 skill/component 引用在正文原位显示短名、类型与下划线，可查看完整引用并打开；编辑、选择、粘贴、撤销、中文组字与发送保持可靠。引用目标随草稿一起恢复，重启后不能只剩无法解析的短名。
- Provider 原生命令保持原语义；本地预置 prompt 明确标识为提示词，点击后在原位展开为可编辑正文，保留其他草稿且不自动发送。两者复用已有工具候选入口，不建立第二套命令执行系统。

### Shortcuts（AgentMux 自己的快捷指令）与识别词

- **命名：Agent 的叫 commands，AgentMux 的叫 Shortcuts。** 用户原话：「如果现在的 commands 是指用到的 agent 自己的 commands, 那么我们再加一个 shortcuts 表示 Agentmux 提供的自定义能力」。`commands` 这个词归 Provider 原生命令（`/compact`、`/context` 这些由 Agent 自己执行的）；AgentMux 提供、用户可编辑的那一套叫 **Shortcut**。两者行为本就不同——一个交给 Agent 执行，一个只是把正文填进草稿——用同一个词称呼它们，用户没有办法表达「我要改的是我自己那套」。
- **Shortcut 只有一套，且由用户拥有。** 用户原话：「Review Changes 等快捷指令 和 commands 是不是重复了，应该只有一套，而且配置页面要支持用户自定义」。此前的形态是两套并存：一份写死在代码里的预置只能从两枚常驻按钮到达，而把它并入候选列表的那段代码从来匹配不上任何东西——即用户打 `/review` 一条候选都不会出。合并的判据是**候选入口只有一处**：Provider 原生命令与 Shortcut 在同一份候选里出现，不是两排按钮、也不是两个浮层。
- **同一个 `/` 列表，但按来源分组并带组标题。** 用户在被问到呈现方式时选定此项。候选浮层分成 Shortcuts 与 Agent commands 两段，各有小标题；用户因此只需记一个触发符，同时能看清每条是谁提供的。不采用第二个触发符（如 `>`）把两者彻底分开：那要求用户记两个符号，且这类前缀在终端语境里另有含义。命名冲突仍沿用本节上方「显示来源并按明确选择生成 prompt」那条。
- **代码不再持有 Shortcut 正文。** 内置的那两条作为**可改可删的默认项**落进用户配置，此后增删改全归用户；删掉即永久没有，不被补回。设置页是它唯一的编辑面。
- **缺席与空列表是两件事。** 配置里**没有这个键**＝这份配置写于本功能之前，读成默认那两条；**显式空列表**＝用户把默认那两条都删了，保持为空。两者只差一个键的有无，混为一谈会二择其一地坏：要么旧配置的用户永远看不到任何 Shortcut（功能像根本没做），要么用户删掉的东西被塞回来。
- **每条 Shortcut 可选绑定单个 Provider。** 留空即对所有 Agent 生效；绑定后只在该 Provider 的 Composer 出现——「这条只对某一家有意义」必须能表达，否则用户只能靠自觉不去用错。
- **识别词（keyword）是同一条 Shortcut 的另一个到达方式，不是第二份注册表。** 用户原话：「prompt 要支持 "识别词"，比如 eli5 或者 grill_me prompt，当用户在 messagetool 输入 eli5 或者 grill 时，要出现下划线 / 输入的时候就出现 tips 提醒，tab 一键替换 / 点击出现菜单，可以一键替换」。同一个 keyword 字段同时供 `/` 候选与**裸词**识别：命中即在正文原位加下划线（沿用既有语义 token 的下划线语汇，不新造一种视觉），打字过程中就给出提示，Tab 一键替换为正文，点击则复用同一份候选浮层。
- **Tab 只在光标处确实命中 keyword 时被接管**，否则原样放行给焦点遍历——沿用本仓既有纪律（方向键在没有候选时把按键还给光标移动）。未命中的 `eli5` 之外的普通词保持普通输入，不得因为像识别词就被改写。
### Skill 加载必须快到没有加载感

用户原话：「现在我加载 Skill 和 Command 的时候非常卡，既卡顿又很慢。Command 相对比较快，但 Skill
上来还要 loading 一会儿，而且在 loading 的时候就会卡住」「我理解 Skill 的 loading 应该有很多策略，
可以让它在 SSOT 的情况下加载得更好一些」。

这条差异本身就是判据：Command 与 Skill 同一时刻同一台机器，一个快一个慢，所以它是**代码路径**的
事实，不是环境的事实。

- **Provider 声明 skill 目录这件事已经是规范，不新建第二套。** 每个 Provider 在自己的 catalog 里
  声明 `composer.skillRoots`（用户原话「我们应该可以在 Provider 上定义规范」）。新增 Provider 只
  需要声明自己的目录，发现策略不得按 Provider 名分支。
- **发现必须剪枝。** 依赖目录、版本控制内部目录与构建产物里不存在 skill，遍历不得进入。仓内已有
  一处经过实测的同类策略（`project-appearance.ts` 的 SKIP_DIRS + 深度封顶 + 目录数预算 + 常规位置
  先试），Skill 发现沿用同一套，不各写一份。判据：遍历的目录数必须与**真实 skill 目录**同数量级，
  而不是与工作区的目录总数同数量级。
- **加载不得阻塞输入。** 菜单可以先出现再填充，但输入框在任何时刻都必须能继续打字。
- **同一份结果不得反复重算。** 打开菜单不是"目录变了"的证据；只有目录真的变了才重新发现。
- **两个入口一个策略。** Session 侧与 Workspace 侧的 skill 发现回答同一个问题，不允许一个入口比
  另一个多付代价（例如为查一个 session 先取整个运行时快照）。

### 已交付优化的保留与取证

用户反馈：「帮忙看下，我总觉得有些优化本来已经做了，但是由于并行推进又被搞丢了，看看有没有痕迹」。已交付的优化必须在并行集成与实际安装后继续可用；发现体验再次变化时，结论须区分实现被改回、实现仍在但当前产物未包含、当前运行副本未采用，以及尚未确认。历史修复提交或当前源码仍在，不能单独证明用户正在使用的界面已经保留该优化。本次点名的 Message Tool 一行态图标与输入间距只定义在密度 SSOT[《Composer 静息密度与主操作》](../presentation/conversation-input.md#composer-静息密度与主操作)。

### Composer 静息形态与主操作

- **静息即一行。** 用户原话「现在一上来就是两行的样式，是不是改成一上来是一行？」。空输入框的静息
  形态是一行；两行及大输入框是用户主动换的档位，不是默认。
- **切换键在一行态必须是弱的。** 用户原话「只有一行的时候存在感有点太强了（这个时候本来就应该是
  弱的），高度应该稍微再窄一些，最好不要有那么强的边框」。一行态是最安静的形态，它的控件也要最
  安静：控件同高（见密度 SSOT）、不要重边框。切换位置与图标统一遵循上文 Message Tools 三态约束。
- **Send 与 Interrupt 收成图标。** 用户原话「现在 send 和 interrupt 的样式也有点太强了，是不是直接
  用图标就好了？」。两者都降为图标控件；Interrupt 仍必须与 Send 在视觉上可区分——它是破坏性动作，
  收成图标不等于收掉这个区分。
- **Cmd+Enter 直接 steer。** 用户原话「如果发消息，现在好像默认不会 steer。有一些常见操作，比如说
  按住 command + 回车的话，应该就是直接 steer 发送出去这条消息」。约束：`Cmd+Enter` 表示"插到当前
  这一轮里去"，与裸 Enter 的"按常规发送"是两个不同的意图，不能互相退化；Agent 闲着时它也必须有
  确定含义，而不是只在忙的时候才存在。
  - 用户再次反馈「MessageTool 原始需求是发送直接 steer，结果现在都在排队」：Cmd/Ctrl+Enter、显式 Send 和发件条目的“立即发送”本身就是**这一条消息**的 steer 授权，不要求再点 Continue。它应立即尝试向当前 Run 投递；真实交互、部分投递或错误 Run 仍可拒绝，并保留原因和文字。缺少回合结束或屏幕确认属于流程观测，须如实说明，不能因此永久阻断本可输入的 Agent。
  - 同一原意适用于已通过目标、身份和当前 Run 校验的 Control `send` 与 CLI `agentmux send`：这一条明确命令就是当前消息的 steer 意图。缺少上一轮完成或输入框确认不能把它挡成未投递；沿 Core 既有单消息选择尝试，保留真实不确定性告示。交互、部分投递、操作幂等、Run 与能力边界仍由各自 owner 裁决；定时／持续推进、后台消费和普通队列不借用这一次命令的授权。
  - 裸 Enter 在 working／待答时仍表示排队，不借用另一条消息的显式授权。旧 queue-only 项不阻塞新明确 steer；多个明确 steer 保持自身队列顺序，共用唯一消费者，不双发。发送中再来的 steer 意图不能因 await 丢失；重启、自动消费、阅读、队列重排或其他消息不生成新的 steer 授权。

### Message Tools 的身份与右上角那行字

- **正在用的 Agent 要看得见。** 用户原话「我感觉 MessageTools 该品牌升级了，实际在用的 Agent 头像
  也应该显示出来，而不是只在右边有一个名字」。Composer 必须能直接看出此刻在跟哪个 Agent 说话。
- **右上角那行字要换成对用户有意义的名字。** 用户原话「右边的项目名字，也应该改成 tab 名 / region
  内的 session 名，要不然没啥意义」。它此前显示 Region 名（常常就是项目名，用户已明确说没意义）。
  连带约束：此前因为它是"无意义的装饰"而在一行态整个隐藏的处理，必须随内容一起重新判断——一个有
  意义的 session 名不能沿用"反正没意义所以藏掉"这个理由继续藏着。用户进一步明确「有了 Agent 图标，是不是就不用额外显示名字，而且最好是靠右边，不和功能区放一起」：常态只显示右侧头像，与左侧功能区分离；Session 名、Tab 上下文和状态保留在悬停提示及可访问名称，不再额外常驻名称文字。

- 交付证据必须覆盖真实宿主调用、关键实现变异变红、浏览器交互及草稿恢复；此前已归档任务的验收缺口在本次明确补证，不以归档状态代替验证。

- **Browser 内嵌 frame 发起的应用交接也必须走同一条应用链接交接。** 页面把自定义应用 scheme 放在跨域 iframe 或其他子 frame 中时，Browser 不能因为它不是顶层导航就静默放行或吞掉。约束：顶层页面和子 frame 的应用链接都先拦截、按 scheme 询问一次并交给系统，普通 http(s) 子 frame 继续由页面自行加载，页面本身仍留在当前 Browser。

## Message Tools 邮箱

邮箱的原生消息观察按本次工作面是否真正可见暂停或继续；打开的邮箱随工作面隐藏时保留原正文与阅读状态。具体隐藏、迟到读取与同身份正文保全沿[《Terminal 连续向上阅读历史》](terminal-reading.md#terminal-连续向上阅读历史)的原生对话阅读约束，其他仍可见的同 Session 消费者正常继续，readonly 不表示隐藏。

用户要求像游戏里的 Mailbox：“新消息有红点，看过了红点就消失”，排队消息也放到“发件列表”，“这两个组件就统一了”。Message Tools 只保留一个邮箱入口，与右侧 Agent 头像合成位置稳定的会话控件，内部区分收件通知与发件列表；不再同时摆放独立队列入口或在输入区铺设持久报错横幅。新通知的入口含义沿[《入口提示的清楚含义》](#入口提示的清楚含义)；打开并看到对应收件页即算已读，该页的未读提示消失，当前问题仍可回看。仅浏览发件列表不能把未看的通知标已读。数量与未读是不同事实，不能把正在排队误报成新通知。

用户曾要求「红点+数字」并避免与 Agent 状态叠压；数字可直接辨认、零时缺席、视觉上限不损害准确可访问数量与原工作面这些边界继续保持。原入口合计 Inbox／System 未读并旁置 pending 的含义，已由下节[《入口提示的清楚含义》](#入口提示的清楚含义)的新反馈替代；不新增计数或已读 owner。看过哪个收件页仍只按原规则读哪个页，hover经过、Outbox或Progress不代读；计数变化不改原 Session、草稿、发送或终端阅读工作面。

用户最新反馈：「现在 mailbox 上的红点感觉太大了」。未读提醒须更轻、更紧凑，同时保留直接可辨的数字与准确可访问数量；缩小视觉面积不能退回纯红点、隐藏正数或改变未读／已读与待发的事实。具体尺寸与可读性只见 surface-density 的[《Message Tools 邮箱》](../presentation/conversation-input.md#message-tools-邮箱)，原入口、阅读与工作面边界继续适用。

已读不表示运行时恢复。收件通知保留当前问题、影响和恢复动作；相同原因持续更新而非重复堆积，只有恢复后再发生、原因或严重程度变化、新 Run 的问题才重新提醒。切换 Tab、重挂载和应用重启不能把相同已读问题重新变成未读。已解决条目随权威事实消失，不维护第二份 Runtime 状态或无限错误历史。连接、投递核验、队列阻塞和局部操作失败都归入当前 Session 邮箱；局部重试仍然可用。发件列表的复制和手动重试失败也留在同一个邮箱中，不另开全局错误条；再次成功后相应局部错误消除。

发件列表保留实际待发送文字、次序、状态与原因，以及已有重试、复制和移除能力。看过通知不会取消或重投消息；发送中不能移除或并发重试；旧 Run 的消息不能误投到新 Run。空列表明确为空。邮箱在三种输入框形态都可访问，不因忙碌、输入禁用或窄分屏而不可用。视觉约束见密度 SSOT 的“Message Tools 邮箱”。

与持续推进共享入口后的 Progress 页及循环状态边界只定义在[《持续推进与邮箱共享入口》](#持续推进与邮箱共享入口)，邮件三分区继续保持上述语义。

### 入口提示的清楚含义
用户反馈邮箱入口“这个空白咋回事儿，小铃铛位置看起来也像 bug”：缺席的数字／提示不制造另一种状态或入口；只消费现有 Inbox、Notices 与 Progress 的真实可见事实。入口紧凑、数字缺席时无空槽、铃铛与进度对齐的呈现约束只见[呈现合同同名小节](../presentation/conversation-input.md#入口提示的清楚含义)，原未读确认、队列和观察行为不变。


用户进一步反馈：「现在 mailbox 的按钮，红点会把 inbox 也放里头，显得都是错误，右边的小数字挺好看的，但不明白啥意思；做些调整更清晰」。邮箱入口旁置数字只表示 Inbox 的既有未读来信数，不把普通来信表现为错误，不与 Notices、pending 或已加载 History 相加。原入口 pending 数字取消；待发事实仍在 Outbox 标签以实际 pending 数清楚呈现，队列／发送／已读 owner 和原打开优先不变。各数字零时缺席，1–99 直接显示，大于99显示99+，标题及可访问名称保准确数与对象语义。

Notices 的独立静态提示只表示当前既有未读告示，即原 system.unread；不表示告示全是错误、Agent 已坏、尚未恢复的总数或另一份 severity 判定。标题／可访问名称分别说明 Inbox unread、Outbox pending、Notices attention，并提供各自准确数量。零未读告示无该提示；已读告示仍按原问题 owner 保留可回看，已读不冒充恢复。原 occurrence／kind／cause 身份和按所见页确认规则不变，observedAt 不入已读身份；原降级、未知及真实 Agent 状态继续各自诚实呈现。absence／零不作为健康结论，Notices 来源未确认不补成已确认健康。

Progress 的原独立状态标识和右侧 Agent 头像状态不加入上述计数，也不被新提示挤占。新事实不强切页，hover 不代读；提醒和数量变化不增加行、不改原草稿、Session／Run、队列或 Terminal 阅读工作面。不新增全局错误条、状态机、计数缓存、读取观察或存储 owner。中性数字、独立告示提醒与入口几何只定义在[呈现合同同名小节](../presentation/conversation-input.md#入口提示的清楚含义)。

### 悬停访问与最近顺序

用户问「mailbox 有没有更好的设计方式, 比如 hover 时直接显示也支持鼠标移上去, 而不是特地点击。另外, 顺序是不是也都调整成最新的在上」。鼠标悬停邮箱入口即可查看同一内容面，允许从入口越过间隙移入面板、切页、滚动和操作；离开入口与内容面后，尚未显式打开的预览自然收起。悬停只显示，不执行发送、重试或循环动作，不夺走 Composer、终端或其他编辑字段的焦点、光标与组字状态。

点击、键盘和触摸仍能显式打开；点击入口或在内容中开始操作、编辑后，面板保持打开，不因鼠标离开打断。关闭、Escape 与点击外部沿原生浮层语言：仅悬停后按 Escape 保留原输入焦点；面板内的 Escape 或关闭按钮回到同一邮箱入口；外部点击已建立的新焦点不被拉回。经过入口不能吞掉未读；真正移入可见内容或显式打开后，才按当前所见 Inbox/System 页的既有规则记录已读，其他页不代读。

Inbox 来信和 Outbox 已发送／已记录的历史以各条原始展示时间统一最新在上，不能先按来源分组再拼接，也不能用刷新时间把旧正文抬成新消息。System 当前告示沿其实际 owner 提供的最近观察事实时间最新在上；缺少可比较时间的条目归在有时间条目之后，保持稳定次序并明确时间未记录，不解析身份、操作标识或正文猜时间，不另建随挂载与刷新变化的时间账本。展示时间更新不改变通知身份或已读，不因只有时间变化重新点红。相同时间保持稳定次序；加载更早历史后仍保持这一顺序。Progress 继续显示当前循环与最近决定，本需求不增加事件历史。

待发送队列单独保留真实投递顺序，排在发件历史之前；最新在上的历史不能重排待发消息、改变已有移动／重试／发送语义，队列时间仍只表达首次接收用户意图。新消息或循环事实到达不强切当前页。Progress 的常驻表单、状态 owner 与共享入口约束继续由[《持续推进与邮箱共享入口》](#持续推进与邮箱共享入口)定义。

### 内部信息流与完整阅读

用户进一步反馈「message 内部的信息流设计还是一塌糊涂啊」。邮箱内部须能先扫到具体记录及其真实来源、时间和状态，再读单条完整内容并处理对应动作；不能把全文、流程说明、历史边界和操作一股脑堆在同一阅读层。Inbox、Outbox、System 与独立 Progress 页继续各有既有含义，不把 Agent 来信、用户输入、当前服务问题或循环配置伪装成聊天 Thread、回复关联或同一种消息。

同一邮箱面内的列表与单条详情有明确来回路径；返回仍落在原分类与阅读位置，完整长正文、原始状态／原因及该对象动作可达。Outbox 明确区分先按真实投递顺序排列的 Pending 与按上述最近顺序排列的 History，分页边界和历史读取错误归在 History，不盖过 Pending 或让加载历史变成重发。当前能发送的消息及其目标可辨：仍只有原队列 first deliverable 目标可显式发送，任一消息 sending 时保原全局 Send 禁用，不因打开另一条详情允许越过队列。发送、移动、移除与复制仍沿原动作 owner 和已有 Run／sending 约束；看详情、切页或返回不派发消息，也不改变草稿。

来信身份、用户输入作者、记录来源、投递状态与时间分别消费公开事实，未知仍明确未知，不能把 native user 角色或无 Agent 字段猜成人类，把 Recorded 当作投递确认，或从正文／时间推断重复与回复关系。System 的当前问题、影响和恢复动作可快速辨认，完整三事实和原恢复动作仍在同面可读；详情展开和返回不消除问题或新增错误历史。Progress 继续呈现原循环当前状态／决定与原常驻配置，不把配置表单混入消息历史，不增观察、调度或存储 owner。

邮箱的打开优先、hover／pin／关闭／键盘和按所见分类记录已读继续按本节既有规则；不新增单条已读账本或在已被该规则确认的记录上保留假的 Unread 标签。来源变化不把另一个对象顶替当前详情；System 详情复用既有 serviceNoticeFingerprint 的 occurrence／cause／kind 身份，不把 observedAt 放进身份；单 id 复发或原因／kind 变化须返回本页，不能静默换成另一次问题。换 Session／Run 不带入旧详情或派发旧意图。固定导航、摘要层次与详情密度只定义在 surface-density 的同名小节。


### 统一对话阅读与简明操作

用户反馈「最新的包里没有看到有复用组件」「整个 mailbox 看起来，它的选项非常不清晰，到处都是字，不够现代化」，要求完整重新设计。邮箱须成为当前 Session 的清楚阅读与处理面：Inbox 来信、Outbox 待发与输入记录、Notices 当前服务告示的导航含义可直接辨认；Progress 是可发现的独立工具入口，仍沿《[持续推进与邮箱共享入口](#持续推进与邮箱共享入口)》的常驻表单和循环 owner，不增加二层模式导航或全局循环管理。

导航计数只表达要处理的事实：Inbox 与 Notices 为各自既有未读数，Outbox 为实际 pending 数；零时不显示 badge，可访问名称和标题说明对象与准确数量。已加载 History 的有界窗口不是全源总数，不能与 Pending 相加伪装成 Outbox 总数。邮箱入口提示只沿本节[《入口提示的清楚含义》](#入口提示的清楚含义)，打开优先、所见页已读、hover 不夺焦点、新事实不强切页均不变。

列表以真实作者／身份、原始时间和有界原文开头为主要信息，不逐条重复 Read full message、Captured input、Delivered 等说明。摘要的读取边界是原始字符串前240字符；预算内可按共享对话语法完整解释的来源声明，不得挤占正文摘要。有正文时摘要以同条正文开头为主；无法完整解释时保留有界原文，不伪装成已解析正文。完整详情、身份事实及原文 Copy 不受摘要投影影响。不得扩大预算、解析全文或扫描尾部来寻找正文，也不得维护另一份声明语法。来源及投递成功细节可渐进披露；影响当前处理的未知投递、Run 不可用或失败在对应记录附近保持简短可见，不能只为减字隐藏风险。缺失作者明确未知；缺失时间和完整来源在详情可读，不补造事实。Pending 与 History 仍分别按真实投递顺序及最近顺序呈现，分页／刷新／观察问题留在 History，不盖过队列。

Inbox 以及 Outbox 的 Pending／History 完整详情实际复用各 client 共用的 ConversationMessage 正文、头像／身份、Markdown 与原文 Copy；共享阅读层是这些呈现的唯一实现，Mailbox 不保留宿主专用副本或第二套正文、声明语法与复制反馈。共享阅读层只持呈现与单对象局部交互，不持 Session、Run、Queue、Read、Progress 或来源发现。Clipboard 结果与错误报告、浮层目标、焦点策略及身份／图标呈现由宿主明确提供；文件、HTTP、图片与当前来源上下文仍由宿主传入，共享层不借 Electron、宿主 Store 或隐含平台默认取得这些能力。仅邮箱记录阅读显式选择紧凑呈现与记录身份语义：未知作者仍为 Author unknown，不改变普通对话已确认的 unknown→You 展示默认，也不把 queued／restoring／deferred 或 native Recorded 映射成对话 complete／streaming／failed。尚未投递的队列不伪造 captured receipt；正文中的声明不升级成已认证作者。Copy 复制完整原记录字符串，包含原头部及末尾，不复制两行预览或解析后的正文；共享单条 Copy 只有原 Clipboard／feedback 明确返回 true 才显示 Copied；false／throw／void／undefined 不冒成功，失败保完整正文、原反馈与 Retry，Copy all 的原路径不换。

文件、HTTP 链接、图片和来源披露沿来源 Session 的既有 origin、workspaceRoot、homeDir 与实际打开／读取 owner；不能借当前 active Workspace 或收件 Agent 的资料补造发件人上下文，不新增逐行 Store 观察、正文缓存或持久 owner。列表只挂当前页轻量有界摘要，显式单对象详情才挂完整对话内容；不能把含 Copy／来源等互动的 ConversationMessage 嵌进整行按钮。返回保原分类、滚动位置与焦点优先级；旧 Session／Run、失效记录与 Notice occurrence／cause／kind 的详情隔离继续沿[《Message Tools 邮箱》](#message-tools-邮箱)合同。

Pending 只把当前原 first deliverable 的 Send 作为清楚主动作；任一条 sending 时全部 Send 仍禁用。移动／复制／移除可用低层级图标动作，但每个都有 tooltip、准确可访问名称和原次序／sending 禁用规则；Copy all 的原全文与顺序保持。风险说明归实际对象，不用每条重复长流程段来代替状态。查看、返回、切页、展开来源或重开邮箱均不派发、重投、重排、清草稿或改变 Run 绑定。

Notices 列表先给问题及轻量类型／时间，完整详情仍读原 problem／impact／restore 与原恢复动作；已读不冒充恢复，详情不替换另一 occurrence。空页有可辨的对象标题，最多一条必要提示。原 Mailbox 原生浮层、可见性租约、观察／刷新／分页、Read、Queue、Progress、Terminal 与输入 owner 均保留；本次只重设计呈现与真正共享阅读，不新增依赖、存储、调度或状态机。具体视觉及紧凑层次只定义在[呈现合同同名小节](../presentation/conversation-input.md#统一对话阅读与简明操作)。

### 邮箱记录一键定位对话

用户明确要求：「Inbox 和 Outbox 上的卡片不但要复用，而且还要有一键跳转到对话模式里对应位置的功能」。Inbox 与 Outbox 已有记录在列表和共享对话详情中均有可发现的“在对话中查看”动作；这是查看原记录，不是发送、重发、继续或切到声明作者的另一场对话。共享阅读层继续按[《统一对话阅读与简明操作》](#统一对话阅读与简明操作)呈现消息与宿主传入的动作，不持有导航、Session、Run 或读取状态的另一份 owner。

对应位置由记录所属 Host／AgentSession 与公开记录来源共同确认：captured 来源使用原 submissionId，native 来源使用原 providerId、nativeSessionId 与 recordId，消息投影的稳定 id 和记录命名空间不能丢失。声明作者、正文、预览、时间、相同裸 id 或队列 id 都不能代替对应关系；Inbox 的目标是这条输入实际被记录的对话，不是 authorAgentSessionId 声明的发件 Agent。尚未投递的 Pending 没有对话位置，明确呈现“尚未发送，暂无对话位置”，不能伪造 captured 记录或为了取得位置触发 Send。

明确点击或键盘激活后，在原 Session 的既有工作面切到真实对话模式，使确证的记录进入可读视口并短暂标明位置；成功只在该来源的准确记录已经呈现时成立。原已加载的有界阅读窗口不能仅因邮箱到对话的切换而丢失定位依据，不增加另一份全文缓存、全历史扫描、轮询、无关 Session 观察或 Runtime seek 机制。记录暂未加载时只沿原读取 owner 的有界读取与错误边界处理；未找到、来源变化、过期 Run、能力不可用或读取失败须如实区分，原记录仍可读、可复制，不能跳到近似对象或报告假成功。原生历史的来源身份可以跨 resume 保持，但须由当前公开 source 重新确认；不能把捕获于旧 Run 的意图投向当前 Run。迟到的定位结果不得更改另一 Session／Run、后续用户选择、滚动或焦点。

查看动作保留原草稿、Progress 常驻字段、队列顺序与 Run 绑定、原 Terminal 实例／rows／光标／输入、相邻 Region 和布局；不另建 Session、移动／拆分工作面或触发恢复、重投和终端输入。只有显式导航可移交阅读焦点；hover 不切模式、不定位、不夺焦点，Esc／返回和后续用户焦点继续沿原容器规则。动作与正文、Copy、来源、Send 保持独立命中，不形成 button 内 button。行为结果、暂不可定位说明与位置反馈的呈现只见[呈现合同同名小节](../presentation/conversation-input.md#邮箱记录一键定位对话)。本轮不改变 durable 布局或 Session 生命周期 owner；若实施实际需要改变，须先明确评审其范围与恢复回归。

### 当前查看位置与路径

用户补充要求：「看是不是把所在的 region 和项目等路径也给出」。邮箱记录详情须让用户辨认当前接收对话的查看目标，并能读全其项目、目录与空间地址；这些是当前上下文，不是消息发送时的位置或历史来源。

当前查看位置绑定本次点击所在的准确显示 occurrence，保留 displayWorkspace、Tab Group、Tab 与 Region 的完整身份。主面与同 Session 的其他投影分别消费各自确证的显示位置，不借当前 active Workspace、首个匹配 Region 或原工作面的名称替代点击位置；同一 Region／Tab 的多处显示不能合并成唯一位置。名字只是当前显示值，不替代稳定 ID。空间、资源与执行身份继续沿[《统一概念与空间寻址》](spaces-and-layout.md#统一概念与空间寻址)。

当前 Tab 所属资源的 Project、项目根目录、Workspace／worktree 目录与分支，仅在既有登记 Workspace 的 Host 与资源归属已确认时呈现；Space／Zone 不强称为 Project。Session 的执行 Host 与 cwd 单独消费其公开事实，不用项目根、资源目录或 displayWorkspace 路径替代；显示移到别处不改变执行目录。资源与执行的 Host 分别说明，显示容器标识不冒充机器 Host。项目未知、未登记或当前位置无法确认时明确说明，不从正文、声明作者、时间或路径外观推定归属。

接收 Session 的查看目标与发送者信息分别标注。现有 Current sender 及其项目仍只描述确证发送者的当前资料，不借来解释这条记录被接收的对话；消息来源仍是原 captured／native 记录身份。未记录的历史 Region、Tab、项目或 cwd 如实保留未记录，不新增历史字段、存储或原生读取来补造。Pending 只在 Info 读取已确认所属 Session 的当前执行事实，不显示消息定位目标，继续沿[《邮箱记录一键定位对话》](#邮箱记录一键定位对话)的原无位置说明与零派发边界。

位置与路径披露只在已打开的单条详情消费所需既有宿主元信息，关闭后不继续读取；列表不逐条建观察或扫描所有投影。披露不改变布局、焦点、模式、Run、草稿、Read、Queue 或 Progress。位置资料缺失不成为另一道导航门：已有记录仍按原来源确认与定位能力处理，原文、完整 Copy 和可用动作保持。完整路径与 ID 通过现有 Info 可发现、可选择和读全；概要与详情的密度只定义在[呈现合同同名小节](../presentation/conversation-input.md#当前查看位置与路径)。

## 输入框截图缩略图

## Message Tools 右侧操作整体

用户要求“右下角的所有图标，包括发送和打断也放一起”，现状“不够整体”。用量、主操作、邮箱与 Agent 头像共用固定右侧操作组，忙闲、三种输入框形态和窄分屏不改变组高度或右侧落点。邮箱与头像分别交互，打开邮箱不发送也不打断。头像名称留在 hover 和详情，不挤占功能区。

- 发送与打断共用一个主按钮：空闲时发送、执行中实心方块打断。打断仅中断当前回复并保留 Session，终止 Session 仍归生命周期入口；键盘发送／排队／steer 语义保持不变。
- Mailbox 分为 Inbox（其他 Agent 来信）、Outbox（用户发件及投递状态）、System（系统通知）。每次打开优先展示未读内容，没有未读且有发件时默认 Outbox，其余为空 Inbox；打开后不因新消息到达强制换栏。已读只表示用户看过，不代表 Agent 处理或投递成功。
- 邮件保留窗口与工具活动窗口分开，工具活动不能把尚未查看的来信挤掉；沿用 Core 持久记录，不另建交付账本。只把已确认投递的输入称为 Sent；初始／恢复输入的失败或未知结果如实呈现并保留内容。
- 已有持久送达事实的排队消息，即使发送调用随后因回包丢失而失败，也必须退出待发队列并继续处理下一条；不得重发已确认消息，也不得让后续消息无提示地停住。
- 已读回执不得复制正文或随消息长度增长，不得挤占布局与草稿存储。正文或送达状态改变重新提示，重启保持已读；仅明确终局移除 Session 时清理回执，未知或暂时空快照不得清理。
- 头像中央表示 Provider，颜色叠加与左上固定 Icon **按执行器配置**；右上表示状态，右下表示数量。菜单与头像共用状态语义，running（在线）与 working（正在处理）可区分。正常完成、主动打断与主动停止不得冒充真实错误；未知原因如实表达。
- 执行器 tint 采用珐琅标识语汇：Provider 与固定 Icon 先合并成一个闭合的相对实面，下面有不透明中性底片，底片外留 1px 间距后再用不透明 tint 画最外侧 1px 轮廓；Provider 本体颜色与镂空保持不变。不得用整幅 flood 覆盖图标本体，不得在镂空内侧画第二圈，也不得用模糊、半透明光晕代替珐琅轮廓。运行状态由右上共享状态角标表达。
- 图片保持内容比例并对齐正文行高。操作间距、hover、轮廓描边与颜色语言见密度 SSOT 同名小节。此确认取代此前举手与文字打断提议。

## Outbox 成功送达后的收尾

用户反馈「已发送成功的消息有时仍留在 Outbox 的待发送列表」。待发送列表只包含尚未证实送达的操作；Core 已确认并记录成功的消息必须退出待发送，不能继续像排队中一样显示或提供重复发送入口。Renderer 更新、重启或响应链路丢失后，待发送仍须与同一 Session 的权威送达记录收敛。按操作身份对账，不以相同文本、Agent 开始工作或模糊提示猜测成功。已发送历史属于历史展示，不重新进入待发送。

## Message Tools 单一主按钮与行内图片

按用户最新确认：发送与打断合成一个图标按钮，空闲显示发送箭头，执行中显示实心方形，打断保留会话。键盘的排队与 steer 意图保持独立且可用。粘贴截图按原比例适应内容，缩略图与正文行高对齐，仍可点开查看。头像与三分邮箱约束沿用本轮已确认设计，后续交付单独验收。
## Message Tool 粘贴保持光标与草稿

用户反馈「粘贴会覆盖内容，而非在光标位置 append」。普通文本、截图与文件引用必须插入光标处，只替换用户真实选中的范围，不能重置整段草稿。异步保存截图或选择文件期间继续输入的内容必须保留；插入位置随文档编辑移动，不能拿启动操作时的旧草稿覆盖最新输入。Agent 与 Launcher 共用此行为，粘贴可撤销。

## 对话消息、终端缺口与缩放重绘

- Codex 对话模式按 Session timeline 的每一条 `user_message` 渲染用户消息。首条消息不能成为唯一的用户气泡；后续发送、恢复和重连后的消息都必须单独可见，并保留它们原本的顺序与正文。时间轴同步遇到缺口时先重取权威快照，不能静默只留下第一条。
- 终端的有序字节缺口不能写成终端内容。保留历史不足时，在终端外显示可收起的服务窗，说明缺失范围和恢复动作；当前 Run 健康时继续显示最新字节，并请求一次当前屏幕重绘。缺口提示与当前画面正确性是两件事，成功重绘后提示收敛，但历史缺口事实仍可查。
- Region 缩放、分屏或字体变化后，顶部的 Redraw 提示只在当前可见网格尚未确认时出现；重绘已成功或尺寸已重新确认后自动消失。提示不能覆盖正确的缩放内容，也不能因为旧的历史缺口永久复活。
- Restoring 舞台与 Agent 启动舞台共享同一套全幅布局质量、身份锚点、状态语义和可读性。Restoring 明确表达“重放保留输出/接回当前画面”，通过 `FullPageLoadingSurface` 的 recovering 语义呈现；Agent 启动表达“等待进程首段输出”，仍可保留自己的局部启动提示，但不得再为 Restoring 另造一套终端专用全屏动画。
- Agent 的 Skill 必须能指导它为自己设置用户可读的显示名，并为当前工作区设置用户可读的名称。显示名是可持久化的展示事实，Session、Workspace、路径和其他内部 ID 保持稳定；设置失败要留在当前工作面说明，不得清空工作区。

## Agent 内部视图切换归 Message Tool

顶部 Chrome 只表达工作区、当前工作面和 Agent 生命周期汇总。Terminal 与对话/Activity 是单个 Agent 内部的交互模式，必须收进该 Agent 的 Message Tool 区域；切换不应占用工作区顶栏，也不能改变 Session、Tab 或 Region 的生命周期。切换控件要和消息工具同一套命中区、焦点、禁用和窄栏规则。

## 对话消息的阅读、复制与标注

对话模式不是左右两张客服卡。用户自己发出的消息靠右对齐，用独立但克制的身份样式表达；Agent 消息保持阅读流宽度，不使用左侧单像素竖线或大面积卡片阴影。每条消息都必须有可发现的复制动作，复制的是该消息的完整原文（含纯文本降级）。

用户要的是“划线＋出现跟随便签”：在对话或 History 已呈现的消息正文中选择原文，选中的实际范围保留划线，旁侧出现紧凑留言便签。两入口仅在当前 Session 确实有可编辑回复草稿且非只读时提供标注；无正文的遮蔽、signature 与非正文控件不进入引用，没有有效选区时不增加标注 chrome。添加动作保留真实引用文本、来源消息稳定 ID 与留言，将它们加到当前 Session 的回复草稿，由用户显式发送；来源 ID 必须由该引用消费者实际采用，不能只停在回调中，也不自动提交输入。

划线和便签只跟随当前真实 DOM 选区，跨行、相同引文的不同出现位置、滚动、展开与宽窄变化仍须贴合所选原范围，不覆盖原文或挤坏阅读面。没有产品消费者的数字坐标不作为标注契约，不按重复文本的首次命中或渲染后正文猜位置。折叠、隐藏或原 DOM 离开时，失效的定位层暂时隐藏并诚实说明位置不可用，留言保留；只有原范围再次有效才恢复跟随，不把旧便签绑定到别条消息或新 Session，不改变 History 阅读锚点。

新选区或消息切换不能悄悄改变已有留言的引用目标；更换或丢弃沿用户显式动作。键盘取消和回焦沿原控件/有效阅读位置，保留尚未添加的留言，IME 输入不触发提交；原地添加失败可见、可重试，引用与留言不丢，既有 Composer 草稿不被覆盖。临时便签不成为持久标注账本；添加后的引用与留言仍由现 Session 回复草稿持有。行为不影响健康 Agent 的普通输入。 用户进一步要求划词注解现代化：便签的引用预览、留言与“加到回复草稿”层级清楚，长引用按需展开全文；关闭和 Escape 只暂收便签并保留言，可以从所属阅读面恢复，丢弃明确只丢此便签草稿。便签保原真实 Range 跟随与窄面不遮正文的行为，不把视觉精修变成新的标注或浮层系统。便签与共同聊天的紧凑外观、引用披露和阅读字号唯一遵守呈现文档[《对话消息的视觉语言》](../presentation/conversation-input.md#对话消息的视觉语言)及[《用户消息气泡的内文密度》](../presentation/conversation-input.md#用户消息气泡的内文密度)；视觉缩放不改变原 Range、引用目标、关闭／丢弃、恢复、失败保值或回复草稿行为。

## Agent Input 的可用宽度

Agent Input 的编辑区是这一行的主要内容，单行姿态下应优先获得剩余宽度。左右工具和发送、邮箱、身份控件保留稳定命中区，但不能用固定宽度把中间文字压成窄列；长文本在编辑区自然换行。Agent 名称、Executor 和 Session 信息留在上方身份 rail，不能为了给编辑区让路而重复塞进正文行。

## Message Tools 的底部回看入口

当 Message Tools 的编辑区或消息内容已经离开底部时，在 composer 内提供一个紧凑的“滑动到底部”入口。入口只负责把同一个编辑区滚动容器带回最新内容，不创建第二个滚动面，也不改变草稿或工具状态。编辑区已经在底部时入口必须消失；用户继续向下滚动时它可以重新出现。入口要有键盘焦点和无障碍名称，并且不能挤压 Agent 身份、工具、邮箱或发送控件的稳定命中区。

## Result ready 在小 Region 中的可用性

Agent 完成后的 Result ready 只占一行紧凑摘要，默认不展开文件和链接。用户可以明确展开、收起或关闭它；终端、Message Tool 和 Region 的主要操作保持可用，关闭提醒不应是继续工作的前置条件。展开的结果按文件和预览目标分组为可扫描列表，内容有独立滚动上限，不能靠把每个目标平铺成按钮而把小 Region 撑成十行左右。窄 Region 里所有可见控件必须可点、可键盘到达；面板不能盖住或挤走输入区。

**自动出现不能挡住 Terminal 输入**。用户原话：「"result ready" 是个好的 hitl 设计, 但是出现的时候就挡住了 terminal 的输入, 太霸道了」。保留结果已就绪的提醒与主动查看、处理结果的入口；自动出现只是告知，不能盖住或挤走正在使用的 Terminal 输入位置、抢走原焦点、打断正在编辑的文本，也不能要求先 Review 或 dismiss 才能继续输入。正常与窄分屏都必须保持原输入可见且可继续键入；用户主动 Review、收起或关闭后，仍能回到原 Session 继续工作。结果提醒的呈现不能改写 Session、Run 或工作面归属，不得停止健康 Agent。

关闭只针对当前这轮结果。同一完成状态的重复观测不能强制重新展开；Agent 开始下一轮并再次完成时，新结果仍有可发现的入口，不能被上一次关闭永久吞掉。

## 对话中用户消息的阅读方向

用户消息气泡整体靠右，用来表达对话轴上的发言归属；气泡内部正文、Markdown、列表和代码块统一居左对齐，长内容从左侧开始阅读。用户头像、时间和操作元数据可以继续沿右侧排列，但不能让正文跟着气泡方向右对齐。

用户进一步要求「用户发的消息，是否可以用稍微不一样一些的样式」，且「只有用户消息」的宽高用优雅的方式自适应：仅用户显示的气泡随实际内容收敛，短消息不被撑成固定宽高，长正文与按需详情仍完整可读；当前会话 Agent 与其他已核 Agent 的气泡布局保持。既有作者事实、用户显示默认、来源详情、复制原文与原 DOM 选区边界保持，不凭气泡样式认证来源；视觉约束只见[《用户消息气泡的内文密度》](../presentation/conversation-input.md#用户消息气泡的内文密度)。

## Fork / Resume 的工作面归属与 Message Tools 编辑器

- Fork 出来的 Agent 仍属于它自己的 Session/Tab/Region 映射。之后从旧 Session resume、打开 Browser 或创建新 Tab 时，目标必须由被操作的 Session 上下文解析出所属 Workspace、Tab、Region 和插入位置；不能使用当前鼠标焦点、最近全局焦点或“旧 Agent 右侧”作为隐式落点。
- 如果目标 Session 已不可定位，界面必须显示明确的恢复/选择目标动作；不能悄悄把内容挂到另一个 Agent 的 Region，也不能因为焦点切换而改变目标归属。创建后的新 Tab 必须能从 UI 直接确认它属于哪个 Session。
- Message Tools 的编辑区在单行状态下输入增长时自动扩展为多行，保留左右工具、Agent 身份和发送动作的稳定命中区；中间编辑区占据剩余宽度并从左侧开始阅读，不得把长文本压成居中的窄列或只露一条细线。达到上限后才滚动，回删后可以恢复单行。

## 按状态配置 Prompt 按钮

用户原话：「每种状态, 都支持用户去设置里头自定义一些 prompt, 变成按钮, 方便一件点 (比如用户可以自定义 "大白话说说做了什么" "继续优化")」。Settings 的 Prompts 是这些正文、名称与状态选择的唯一编辑面；同一条用户 Prompt 可以关联多个 Agent 状态，一个状态可以关联多条 Prompt，也可以保持没有按钮。通用与单个 Provider 的既有范围继续生效，不维护第二份状态提示词库。新增、改名、改正文、改状态选择与删除均须持久保存；退出设置、重新挂载及进程重启后仍以用户已保存的内容为准，删掉的按钮不重新出现。

状态按钮是这条 Prompt 的明确发送入口；点击只提交该按钮的正文给原 Session，保留原 Composer 草稿和用户正在阅读的工作面，不把草稿替换后偷偷一起发送。明确点选后的首次发送或入队同样适用《明确手动消息作者》，作者定义与边界只见该节。原有 `/` 候选与识别词继续只展开草稿，沿[《Shortcuts（AgentMux 自己的快捷指令）与识别词》](#shortcutsagentmux-自己的快捷指令与识别词)的合同工作。按钮可见状态与发送能力是两个事实：只依据现有 Agent 状态决定出现，只依据现有 Composer 的输入与提交模式决定动作，不在 Renderer 再造 readiness、握手或超时门禁。恢复中的发送继续交给既有 Session 恢复与 Core 公共 API；不启动另一 Session、不替换健康 Run。

真实 Permission / Question 待答请求仍由原卡片回答；状态 Prompt 不能替用户授权、回答或绕过请求。待答期间，状态按钮明确标注 Queue，单击将正文存入现有持久队列，保留目标并如实显示待发；不能把“已排队”冒充“已发送”。拒绝、失败或投递未知沿现有消息与服务窗反馈说明，保留可重试的文字和具体原因。自动出现与状态变化不抢终端焦点、不遮住输入、不改变当前草稿，不要求用户先关闭通知才能继续工作。状态动作的出现与消失仍须保留原生终端输入、阅读位置和 Terminal rows，不能靠没有内容的永久占位实现稳定性。

用户再次反馈：「为 prompt 设置了 running 的按钮，对话组件会凭空多一行，但是按钮又没显示」「这个状态按钮好像永远的占了个位置，不管有没有要展示的状态」，并询问「状态定义不够清晰，有明确的定义和边界吗」。状态动作只在当前 Provider 范围和当前 Agent 显示态有匹配 Prompt 时出现；没有匹配动作不制造空组、空行或保留槽，配置其他状态的 Prompt 不能成为占位理由。本次约束替换此前“为任一状态配置后永久保留一行”的稳定方式，视觉密度只见 surface-density 同名小节。

状态定义必须说清进程、Agent 语义与输入能力的边界，沿 Core 现有 `AgentDisplayState`、`agentDisplayState` 和 `observeAgent`，不另造状态机。`running` 是进程仍在运行／语义未确认时的中性显示，不代表正在处理任务，也不保证已空闲或可发送；`working` 是 Agent 的活动声明；`done` 是回合结论，不是进程退出，也不证明用户目标完成或全部成功。`waiting`／`blocked` 的语义提醒与精确 Permission／Question 请求分别持有，不能由状态名猜回答方式。状态动作按当前显示态精确匹配；动作的 Send、Queue、恢复或禁用仍由已有输入与提交合同决定。观察缺失、过期或 Provider 不支持语义活动时如实表达边界，不把未知冒充空闲、工作中或输入就绪。

用户进一步明确：「一方面优化；另外这个 message tool 状态组件，感觉需要彻底重新设计」。Message Tools 以现有右侧接收者头像作为唯一的状态与关联动作入口，沿同一个身份与语义角标，不增加第二枚状态灯、独立状态条或 Prompt 轨道。显式点击、Enter 或 Space 可固定打开；hover／focus 预览的是同一份内容，不能另造 hover 状态或另一套动作。入口与工具带的宽高不随状态、Prompt 数量或名称变化；长草稿、三态 Composer 与正常／窄 Region 均不因动作显隐重排或改变 Terminal rows。这里替换此前所有状态 Prompt 常态平铺的呈现要求；选择一条 Prompt 仍只授权一次原正文投递。

展开面先说明当前真实状态和用户下一步，完整进程／语义／输入能力事实按需可读；只消费该 Session 既有观察，不轮询或扫描无关 Session。Desktop 尚未取得的 Core 正式 Prompt readiness 如实标为未报告，交付降级记录、语义状态或当前可点击的 Send 都不能冒充已证实 ready；当前输入动作只说明沿原合同是发送、排队、恢复还是不可提交。当前匹配的用户 Prompt 独立成段，明确是用户指令以及 Send 或 Queue 的实际结果；无匹配则整段缺席，不显示空白区域或催配置的占位。回合结束时的 Review 与原结果详情保持同一个 owner，在这同一内容面可达，不开嵌套结果浮层或保留第二枚 Review 入口；hover／focus 预览和普通固定打开不挂 Git，只有用户明确进入 Review 且内容可见时才消费 Git 等既有事实，返回／关闭／隐藏后释放。没有 Composer 的既有 Header 仍可进入原 Review；非就绪、关闭或无真实 Review 内容时不制造空槽。Permission／Question 仍由原请求卡回答，流程失败仍由原服务窗／邮箱持有完整说明与恢复动作；状态内容不复制请求、故障历史或代答控件。

极矮窗口的展开面仍须让状态、正文与全部动作可读可达，不能因固定摘要占满可用高度而让内容区归零。身份、关闭与返回始终可达；空间不足时可让状态摘要随正文滚动，并借用窗口内位于该 Region 上方的空间，正常高度仍保留固定摘要。展开面必须与完整 Composer 及原生终端末 32px 输入保护带分别不交叠；可以选择保护带上方，或其下方至 Composer 之间更可用的区域，不能强制上方狭缝而舍弃实际可用空间。正文区至少能完整显示一行可读文字，并能滚动读到全部内容和动作。临时展开面可覆盖原 Permission／Question 卡片的正文；退出后原卡内容、已有输入与操作仍完整可用，Prompt 仍只按原合同 Queue，不代答或取消请求。适配不改变 Terminal 尺寸或新增提交门禁；长状态说明不靠缩字、截短或隐藏解决。紧凑首屏的当前动作可发现性、分类标题优先级及具体密度只见 surface-density 同名小节。

Escape、显式关闭和点击外部可以收起，不丢草稿或改变运行事实。主动键盘关闭时返回原触发入口；用户已点击、聚焦或打开另一个工作面时，以较晚的用户焦点为准，不被旧浮层收尾拉回。进入 Diff、Activity、Browser 或 Session 的动作以目标工作面焦点为准。状态内容或 Session 改变后旧动作不能误投给新 Session；状态自动变化不抢焦点。Settings 仍使用同一状态绑定值和保存 owner，以可理解的名称与简短说明区分进程显示、Agent 声明和输入能力，不静默扩大 running 绑定为 working，不以说明文字建立另一份状态判定。

### 回复卡片的 reaction 快捷回复（提案）

用户希望在本会话执行 Agent 的回复卡片上，用有明确意义的表情发送特定回复；含义能在 Settings 和 CLI 中设置，Agent 能通过 CLI 查询 code。当前仍是提案，见 Feature `f-2jy8f6nn9`，尚未提供发送能力。推荐复用 Prompt 配置，让「认可」与「继续执行」有不同含义；用户补充图标不用 emoji，要有质量的 SVG，最好带动画；每次发送保留原回复引用和接受时的含义，不因以后修改配置改变历史意义。快捷回复是新的人工消息，不是点赞，也不隐含批准权限请求。system reminder 必须来自应用拥有的发送事实，用户正文中的 XML 声明不能成为认证事实。
