## 输入、草稿与提交意图

### Agent 输入行与视图切换

- Agent/Session 的单一身份位置归[《Agent Region 关闭与身份入口》](spaces-and-layout.md#agent-region-关闭与身份入口)：Region 顶部标明正在观察哪个 Agent，输入区不再复制名称与身份条。输入区继续表达输入模式与输入动作；Message Tools 保留现有 Agent 头像及其完整提示/可访问名称，让用户辨认消息接收者。
- Terminal 与 Activity 只保留一个紧凑的图标切换按钮。按钮的图标、tooltip 和可访问名称说明点击后将进入的视图；切换沿用同一个 Session 的 `viewMode`，不创建第二个 Terminal、Activity 或 Session。

### 可收起的 Agent 快捷输入区

- 底部对话输入区应可收起并一键恢复，收起不丢草稿；主要提供文件引用、截屏、技能选择、快捷指令四类快捷入口。文件引用沿用当前 Agent 的文本提交通路，选择结果先进入草稿，用户决定何时发送。
- 展开/收起入口放在快捷工具行最左侧，与文件、截屏、技能、指令等按钮同排；展开态不额外占用一整行高度，收起后仍保留同一位置的一键恢复入口与草稿提示。**这一枚就是唯一入口**，三态语义见本节。
- 展开入口必须参与底部工具行的正常布局流，不能以浮动定位覆盖输入文字；收起态仍在该行同一位置提供恢复按钮。**绝对定位的第二入口已废止**：它此前靠给工具行留一段左内边距来避让，而工具行在窄宽度下会折行，避让与绝对定位一起错位——这正是本条约束要禁止的形态。
- 截屏使用系统选区，取消不改草稿；成功后生成可供当前 Agent 读取的图片引用。技能选择显示实际发现的技能及来源；快捷指令依据当前 Provider 提供，输入 `/` 可选择，选择只填写草稿，不暗中执行。
- 发送、中断当轮、收起输入区是三个清楚区分的动作；中断沿用 Core 的当轮 interrupt，不终止会话。输入法组字、失败保留草稿、运行中 steer 的既有约束继续成立。

- Message Tools 使用独立于队列的图标和三态点击，三态改变的是**输入区自身的形态**：收起成一行（只留输入行与主动作，工具整排隐藏）、两行常态（输入行 + 一排工具）、大输入框（输入区放高供长文编辑，工具排仍在）。用户原话：「最左下角的 message tool 按钮才需要支持三态点击（收起成一行，支持展开两行可输入格式和大输入框）」。
- **三态的触发入口只有一个**，即工具行最左侧那枚键。用户原话：「而不是右边那个 collapse」——曾经并存的第二个入口（绝对定位在左下角、与这枚键共用同一枚图标的 disclosure）已废止：同一枚图标出现在两处，用户无法从图标区分两者管的是不同的事，而它们管的本就是同一件事。此后新增任何收起/展开手势都必须并入这一枚键，不得再长出第二个入口。
- **三档必须有真实可见的形态差异，切换入口始终留在左边。** 用户补充：「第三次切换好像没有变化」「换个更一看就懂的图标，且保持在左边」。空草稿和短文字切到大输入框也必须立即变高，不能只增加生长上限；回到一行时草稿、引用和编辑能力保留。唯一切换键用展开工具行、放大输入框、收回一行的动作图形与可访问名称说明下一步，不再用设置滑杆暗示它是参数设置。该键在三档里都在输入组件左侧，不随工具数目或分屏宽度漂到右边。
- **一行态里任何东西都不许叠在另一样东西上。** 用户原话：「现在 messagetools 收成一行的时候会叠在一起」。两行态下有两处不参与文档流、靠绝对定位待在输入框上方空白里的元素（Region 名水印）以及一排允许折行的工具按钮；收成一行之后，那片空白不存在了，绝对定位的元素正好落在工具条与主操作的位置上，而允许折行的按钮排在窄宽度下会叠成两层。约束是：**可读宽度足够时，一行态保持真正的一行**——没有安放位置的装饰性元素在该形态下不显示（其信息在别处仍可得，例如 Region 名在标签页上），控件排不折行。窄工作面不能为保持物理一行把草稿挤成两三个字一行；保留同一紧凑模式、编辑器、草稿与全部原动作，由密度 SSOT[《PMO Teams 浮窗的参考驱动简约规则》](../presentation/motes-and-coordination.md#pmo-teams-浮窗的参考驱动简约规则)定义输入与控件的让位。判据不是 z-index 谁在上面：叠在可点击控件上的装饰即使不吃点击，读起来也是糊成一团。
- 输入中的 skill/component/subcommand 以带下划线的语义 token 呈现，显示短名，hover 显示完整引用，点击打开对应交互或预置 prompt。
- **启动页的 message tool 与页面其余块同一条列居中，不许偏左。** 用户原话：「初始页面上 message tool 偏左」。启动页（Launcher / NewTabSurface）里标题、Agent 目录、命名输入与页脚都在同一条 640px 列内居中；message tool 是同一列的一员，必须与紧邻其上的 Agent 目录、其下的命名输入左右对齐。它复用会话 Composer 的表面样式，但会话 Composer 那份贴着 Region 边缘的侧向 inset 只属于 Region 内，不得让启动页这一块被钉到左缘。
- **启动页的 message tool 整个可见框都必须能打字。** 用户原话：「而且无法输入」。用户看到的输入框有多高，可编辑区就有多高——不许出现「上面一行能输入、下面一片是死区」：点击可见框的任何位置都落在可编辑元素上并放置光标，而不是点空、把已聚焦的编辑器 blur 掉。约束落在**可编辑元素自身**的高度上，不靠撑高它外层那个不可编辑的包裹容器（那正是死区的来源）。

### Message Tool 按 Agent 的输入历史

Message Tool 支持上下键回溯和可查询的历史列表。范围绑定准确 Host 与 AgentSession；各 Agent 的历史独立，同一 Agent 的 Terminal／对话切换不改变归属。列表包含 Message Tool 的既有输入记录及该 Agent 原生对话中实际提交的用户消息，不把终端按键、草稿或回显拼成已发送消息。

每项显示原记录能够证明的来源，区分输入渠道与原生记录来源；缺少渠道时明确未记录，不因原生 user role、正文或时刻推断是 Terminal、人工或某个设备。读取沿已有 Core 历史与 Provider 语义 owner，已保存意图、字节确认、原生记录和任务完成仍分别表达；同一真实记录按原身份收敛，不能按相同正文删除重复发送的真实记录。

查询与回溯保留当前 Agent 的未发送草稿；选择历史只用于阅读或填入草稿，发送仍由用户明确操作。上下键不能吞掉输入法组字、正文中的正常光标移动或已打开候选菜单的操作。未读取范围、来源不可用与没有匹配结果分别说明，失败不关闭健康 Agent 的既有输入能力。

首次进入历史浏览保留原未发送草稿，向下越过最新记录时恢复；浏览多行记录可连续切换，不要求每次移回首行。人工编辑或另一入口替换同一草稿后退出旧浏览，旧备份不得覆盖新稿。临时方向键浏览不逐项加入撤销历史；列表明确的“填入草稿”是一笔可撤销编辑，撤销恢复回填前的稿件且不激活旧浏览。

可查询列表演化现有 Message Tool 历史入口，待发意图与已记录消息仍分别表达。刚保存或入队、尚无原生记录的正文保持可回忆，不因统一读取而丢失；旧缓存缺时间和来源不补造。查询按原历史分页继续，已读取但零命中与所有可用范围已读完仍无命中分别表达；来源未保留或不可用如实说明，不声称可找回已不存在的历史。

本节定义已确认目标与方案，不代签当前源码、历史来源覆盖、键盘行为或安装交付。

### 当前 Agent 的上下文余量与输入焦点

- 用户要求「给你自己的对话框上加 context 剩余监控」：每个 Agent 输入区展示所属 Session 的原生上下文余量及观测时间；容量与当前占用来自 Provider，经 Core 的既有用量事件发布。累计计费 token 不是上下文占用，不可用它扣减容量。压缩后的新观测可降低占用，缺数时明确未知；最近一次观测不能伪装实时计量，监控缺失不能阻断输入。
- Message Tools 的上下文短标签支持悬停读取同一原生观测详情；点击、键盘与触屏有等价显式入口。悬停不抢原输入焦点，移入详情保持阅读，主动固定后不因指针离开关闭；旧来源或卸载后的动作不打开新来源详情。只展示 Provider 实际提供的有效已用量、容量和原观测时间；原 turn 输入／输出／合计可单独说明，不能冒充上下文组成、缓存、剩余额度或压缩阈值。缺少来源数据明确未报告，详情披露不增加轮询或阻断输入。
- 用户要一眼看出哪个 Agent 快把上下文窗口用完了：Agent 名册和工作区 Agents 列表按同一原生占用率显示 70%／90% 的提醒，并说明可收尾或开新会话；这只是产品提醒，不宣称 Provider 的压缩阈值。低占用不添“安全”状态，未知不作 0% 或安全，提醒不改变 Agent 状态、输入权限或 needs-you。
- 聚焦 Region 时，Terminal/TUI 应收到其原生键；只对匹配且属于宿主作用域的动作消费事件。IME 组字不触发快捷键；没有消费的键原样交给聚焦内容。冲突解决复用既有快捷键注册与作用域，不在各组件复制拦截规则。
- 浏览器产生新页面时以来源 View/Region 归属决定打开位置：分屏来源在该工作视图中选择合理区域，独立 Tab 来源开新 Tab，不默认弹出独立窗口。网页链接右键提供既有分屏/Tab 打开位置菜单，用户显式选择优先。

### Composer 消息队列与紧凑状态
- Composer 的 Context、发送和中断控制采用紧凑工具栏布局；Context 以低噪声状态徽标呈现，完整剩余量通过 hover/展开查看，不占用正文行。
- 用户在 Agent 工作中提交的内容由该 Session 的有界消息队列保序；普通排队与显式 steer 的投递时机、授权及快捷键沿下文[《Composer 静息形态与主操作》](#composer-静息形态与主操作)的输入意图边界，不把所有入队内容概括为立即 steer。暂不可投递的条目保留，并按原意图等待相应可投递时机。队列条目可见、保序、可删除，失败保留原因，不得静默丢失。
- pending interaction 不得被普通消息绕过；消息继续排队，交互回答完成后再按序尝试投递。
- **队列里等着的是用户亲手写下的文字，它必须挺过一次重启。** 进程重启后草稿还在、排着的消息却没了，是把 AGENTS.md 第 12 条反过来做。Run 是 Session 可替换的执行实例，入队时记录的 Run 不构成尚未准入消息的永久发送限制。对于确定尚未准入的条目，用户新的一次明确 Send 可在同一执行 Host、同一持久 Session 下，按当前 Run 建立首次投递条件，保留同一 operationId、原正文与执行选择；Run 变化、恢复完成或后台唤醒本身不授权迁移或发送。已建立原投递条件、投递结果未知或缺少原投递事实的条目保留原目标、条件与输入回执，先核对原结果并沿原操作续接，不因当前 Run 可用而重建；当次未输入不能证明该操作此前从未输入。
- 发件列表还应允许调整尚未在途条目的顺序，保留同一消息身份、文字、目标 Run 和失败原因；调整只改变当前队列顺序，不授权执行、不触发恢复，也不解除重启后的待执行状态。已在途条目不能被移位、越过或伪装成可撤回；不存在或已确认投递的条目不参与重排。
- 条目有真实入队时间时可查看，首次接收入队记录的时间在恢复、重试和重排中保持不变；缺少这一事实时如实显示未知，不用 Session 创建时间、历史消息时间或当前时间补造。入队时间不是 Agent 闲置证据，冷启动仍只消费 Core 的语义状态事实。
- 尚未发送的消息支持编辑。保存只更新原条目正文，保留消息身份、目标 Session／Run、入队时间与队列位置，不提交、不重排、不授予新的执行许可，也不覆盖当前 Composer 草稿。编辑与完整队列共用原 owner；保存前复核该条仍未准入、正文未被其他修改替换且未进入准备／发送。已经在途、已准入但结果未知或缺少原投递事实的消息保留原正文与输入回执，不能用改过的文字冒充原操作重试；编辑不可用的原因及原复制／查看动作仍可发现。
- 显式发送可选择任一当前可投递且未在途的条目，只授权所选消息的原正文和准确目标；其他条目保留原相对顺序，不被一并发送。自动投递仍按队列顺序推进；有任何条目准备／发送中或存在待答交互时不另行发送，不能以查看另一张卡片取得额外许可。

#### 输入框外的待发提示

待发消息及其操作浮于所属 Message Tool 上方，与工具本体分离，让用户无需先打开邮箱也能辨认当前 Session 的待发内容、是否正在发送，并可明确触发对应消息的直接发送。提示不进入正常布局占高，不因队列出现、数量变化或悬停聚焦挤高输入区、缩小终端或改变原阅读锚点。完整队列、原文、顺序和失败原因继续复用同一 Outbox；卡片叠层表达真实排队关系，不创建第二份消息集合。每条待发消息的卡片都必须可发现，长队列不能只有总数而无法逐条抵达。悬停逐条卡片可查看对应原文，并发现该条发送、复制、编辑及原 Outbox 更多操作；键盘提供等价查看与操作路径。查看与聚焦本身不发送、重排或抢走输入焦点；显式动作始终绑定所查看卡片的准确消息身份，不把一条卡片的动作投到另一条。没有待发内容时不保留常驻空位或另一组队列工具栏。

同一条卡片的悬停／聚焦只披露一份全文；紧凑摘要与全文阅读分工，不同时打开重复的全文面或再用原生 tooltip 弹出同段正文。复制仍沿[《统一对话阅读与简明操作》](#统一对话阅读与简明操作)的原文、Clipboard 结果与反馈合同。单行卡片、贴近工具的间隙与动作密度只见下方呈现合同。

入队、准备或恢复、实际提交中与投递已确认是不同事实；排队或 Agent 忙碌不能显示为发送中，开始提交不能显示为已送达。等待、阻塞和投递未确认有可读解释，消息与原允许动作保留。直接发送继续沿同一 Session 的准确 operationId、原正文、执行选择和去重 owner；尚未准入条目的 Run 与首次投递条件沿上文[队列合同](#composer-消息队列与紧凑状态)由新的明确 Send 绑定，其余条目守原冻结条件。原生权限／问题回答和 Goal 续行仍绑定原请求／投递条件，不借普通待发消息重绑；引用原对话记录的人工快捷回复保留原引用与含义，不冒充原生交互回答。不能绕过 pending interaction，不静默后台迁移，也不改变原 Enter／Cmd+Enter、草稿、IME、终端阅读与已存在记录的准确定位。外部提示的密度见[呈现合同同名小节](../presentation/conversation-input.md#输入框外的待发提示)。

记录可定位只证明准确记录与展示目标存在。投递提交回执、CLI 原生接纳记录和 Agent 的回复分别表达；不得把提交确认、消息出现在对话或可跳转当作 CLI 已显示或已开始执行的证明。

### Message Tools 右侧操作整体

用户要求“右下角的所有图标，包括发送和打断也放一起”，现状“不够整体”。用量、主操作、邮箱与 Agent 头像共用固定右侧操作组，忙闲、三种输入框形态和窄分屏不改变组高度或右侧落点。邮箱与头像分别交互，打开邮箱不发送也不打断。头像名称留在 hover 和详情，不挤占功能区。

- 发送与打断共用一个主按钮：空闲时发送、执行中实心方块打断。打断仅中断当前回复并保留 Session，终止 Session 仍归生命周期入口；键盘发送／排队／steer 语义保持不变。
- Mailbox 分为 Inbox（其他 Agent 来信）、Outbox（用户发件及投递状态）、System（系统通知）。每次打开优先展示未读内容，没有未读且有发件时默认 Outbox，其余为空 Inbox；打开后不因新消息到达强制换栏。已读只表示用户看过，不代表 Agent 处理或投递成功。
- 邮件保留窗口与工具活动窗口分开，工具活动不能把尚未查看的来信挤掉；沿用 Core 持久记录，不另建交付账本。只把已确认投递的输入称为 Sent；初始／恢复输入的失败或未知结果如实呈现并保留内容。
- 已有持久送达事实的排队消息，即使发送调用随后因回包丢失而失败，也必须退出待发队列并继续处理下一条；不得重发已确认消息，也不得让后续消息无提示地停住。
- 已读回执不得复制正文或随消息长度增长，不得挤占布局与草稿存储。正文或送达状态改变重新提示，重启保持已读；仅明确终局移除 Session 时清理回执，未知或暂时空快照不得清理。
- 头像中央表示 Provider，颜色叠加与左上固定 Icon **按执行器配置**；右上表示状态，右下表示数量。菜单与头像共用状态语义，running（在线）与 working（正在处理）可区分。正常完成、主动打断与主动停止不得冒充真实错误；未知原因如实表达。
- 执行器 tint 采用珐琅标识语汇：Provider 与固定 Icon 先合并成一个闭合的相对实面，下面有不透明中性底片，底片外留 1px 间距后再用不透明 tint 画最外侧 1px 轮廓；Provider 本体颜色与镂空保持不变。不得用整幅 flood 覆盖图标本体，不得在镂空内侧画第二圈，也不得用模糊、半透明光晕代替珐琅轮廓。运行状态由右上共享状态角标表达。
- 图片保持内容比例并对齐正文行高。操作间距、hover、轮廓描边与颜色语言见密度 SSOT 同名小节。此确认取代此前举手与文字打断提议。

### Message Tools 单一主按钮与行内图片

按用户最新确认：发送与打断合成一个图标按钮，空闲显示发送箭头，执行中显示实心方形，打断保留会话。键盘的排队与 steer 意图保持独立且可用。粘贴截图按原比例适应内容，缩略图与正文行高对齐，仍可点开查看。头像与三分邮箱约束沿用本轮已确认设计，后续交付单独验收。

### Composer 展开与 Run 终局反馈

- Composer 的展开/收起入口与底部快捷工具行保持同一布局行，不得覆盖或压住输入文字。

- 权威 Run 已 stopped／exited／done 时，pending Composer readiness 须失效或清理，界面给出准确 resume／restart 出口，不继续声称仍运行。尚未观察到 readiness 不等于整个 Session 不能输入：错误 Run、pending typed 回答、冲突在途或不能确认安全目标时，只拒绝本次操作并说明缺失事实；已有健康人工输入、普通排队与 raw Terminal 沿[Steer 与投递合同](agent-capabilities-and-messaging.md#steer-与-provider-输入能力)，不盲发、不重放未知输入，也不以旧 readiness 失效永久禁用后续操作。

### Agent Input 的可用宽度

Agent Input 的编辑区是这一行的主要内容，单行姿态下应优先获得剩余宽度。左右工具和发送、邮箱、身份控件保留稳定命中区，但不能用固定宽度把中间文字压成窄列；长文本在编辑区自然换行。Agent 名称、Executor 和 Session 信息留在上方身份 rail，不能为了给编辑区让路而重复塞进正文行。

### Message Tool 粘贴保持光标与草稿

用户反馈「粘贴会覆盖内容，而非在光标位置 append」。普通文本、截图与文件引用必须插入光标处，只替换用户真实选中的范围，不能重置整段草稿。异步保存截图或选择文件期间继续输入的内容必须保留；插入位置随文档编辑移动，不能拿启动操作时的旧草稿覆盖最新输入。Agent 与 Launcher 共用此行为，粘贴可撤销。

### Outbox 成功送达后的收尾

用户反馈「已发送成功的消息有时仍留在 Outbox 的待发送列表」。待发送列表只包含尚未证实送达的操作；Core 已确认并记录成功的消息必须退出待发送，不能继续像排队中一样显示或提供重复发送入口。Renderer 更新、重启或响应链路丢失后，待发送仍须与同一 Session 的权威送达记录收敛。按操作身份对账，不以相同文本、Agent 开始工作或模糊提示猜测成功。已发送历史属于历史展示，不重新进入待发送。

### 按状态配置 Prompt 按钮

用户原话：「每种状态, 都支持用户去设置里头自定义一些 prompt, 变成按钮, 方便一件点 (比如用户可以自定义 "大白话说说做了什么" "继续优化")」。Settings 的 Prompts 是这些正文、名称与状态选择的唯一编辑面；同一条用户 Prompt 可以关联多个 Agent 状态，一个状态可以关联多条 Prompt，也可以保持没有按钮。通用与单个 Provider 的既有范围继续生效，不维护第二份状态提示词库。新增、改名、改正文、改状态选择与删除均须持久保存；退出设置、重新挂载及进程重启后仍以用户已保存的内容为准，删掉的按钮不重新出现。

状态按钮是这条 Prompt 的明确发送入口；点击只提交该按钮的正文给原 Session，保留原 Composer 草稿和用户正在阅读的工作面，不把草稿替换后偷偷一起发送。明确点选后的首次发送或入队同样适用《明确手动消息作者》，作者定义与边界只见该节。原有 `/` 候选与识别词继续只展开草稿，沿[《Shortcuts（AgentMux 自己的快捷指令）与识别词》](#shortcutsagentmux-自己的快捷指令与识别词)的合同工作。按钮可见状态与发送能力是两个事实：只依据现有 Agent 状态决定出现，只依据现有 Composer 的输入与提交模式决定动作，不在 Renderer 再造 readiness、握手或超时门禁。恢复中的发送继续交给既有 Session 恢复与 Core 公共 API；不启动另一 Session、不替换健康 Run。

真实 Permission / Question 待答请求仍由原卡片回答；状态 Prompt 不能替用户授权、回答或绕过请求。待答期间，状态按钮明确标注 Queue，单击将正文存入现有持久队列，保留目标并如实显示待发；不能把“已排队”冒充“已发送”。拒绝、失败或投递未知沿现有消息与服务窗反馈说明，保留可重试的文字和具体原因。自动出现与状态变化不抢终端焦点、不遮住输入、不改变当前草稿，不要求用户先关闭通知才能继续工作。状态动作的出现与消失仍须保留原生终端输入、阅读位置和 Terminal rows，不能靠没有内容的永久占位实现稳定性。

用户再次反馈：「为 prompt 设置了 running 的按钮，对话组件会凭空多一行，但是按钮又没显示」「这个状态按钮好像永远的占了个位置，不管有没有要展示的状态」，并询问「状态定义不够清晰，有明确的定义和边界吗」。状态动作只在当前 Provider 范围和当前 Agent 显示态有匹配 Prompt 时出现；没有匹配动作不制造空组、空行或保留槽，配置其他状态的 Prompt 不能成为占位理由。本次约束替换此前“为任一状态配置后永久保留一行”的稳定方式，视觉密度只见 surface-density 同名小节。

状态定义必须说清进程、Agent 语义与输入能力的边界，沿 Core 现有 `AgentDisplayState`、`agentDisplayState` 和 `observeAgent`，不另造状态机。`running` 是进程仍在运行／语义未确认时的中性显示，不代表正在处理任务，也不保证已空闲或可发送；`working` 是 Agent 的活动声明；`done` 是回合结论，不是进程退出，也不证明用户目标完成或全部成功。`waiting`／`blocked` 的语义提醒与精确 Permission／Question 请求分别持有，不能由状态名猜回答方式。状态动作按当前显示态精确匹配；动作的 Send、Queue、恢复或禁用仍由已有输入与提交合同决定。观察缺失、过期或 Provider 不支持语义活动时如实表达边界，不把未知冒充空闲、工作中或输入就绪。

用户进一步明确：「一方面优化；另外这个 message tool 状态组件，感觉需要彻底重新设计」。Message Tools 以现有右侧接收者头像作为唯一的状态与关联动作入口，沿同一个身份与语义角标，不增加第二枚状态灯、独立状态条或 Prompt 轨道。显式点击、Enter 或 Space 可固定打开；hover／focus 预览的是同一份内容，不能另造 hover 状态或另一套动作。入口与工具带的宽高不随状态、Prompt 数量或名称变化；长草稿、三态 Composer 与正常／窄 Region 均不因动作显隐重排或改变 Terminal rows。这里替换此前所有状态 Prompt 常态平铺的呈现要求；选择一条 Prompt 仍只授权一次原正文投递。

展开面先说明当前真实状态和用户下一步，完整进程／语义／输入能力事实按需可读；只消费该 Session 既有观察，不轮询或扫描无关 Session。Desktop 尚未取得的 Core 正式 Prompt readiness 如实标为未报告，交付降级记录、语义状态或当前可点击的 Send 都不能冒充已证实 ready；当前输入动作只说明沿原合同是发送、排队、恢复还是不可提交。当前匹配的用户 Prompt 独立成段，明确是用户指令以及 Send 或 Queue 的实际结果；无匹配则整段缺席，不显示空白区域或催配置的占位。回合结束时的 Review 与原结果详情保持同一个 owner，在这同一内容面可达，不开嵌套结果浮层或保留第二枚 Review 入口；hover／focus 预览和普通固定打开不挂 Git，只有用户明确进入 Review 且内容可见时才消费 Git 等既有事实，返回／关闭／隐藏后释放。没有 Composer 的既有 Header 仍可进入原 Review；非就绪、关闭或无真实 Review 内容时不制造空槽。Permission／Question 仍由原请求卡回答，流程失败仍由原服务窗／邮箱持有完整说明与恢复动作；状态内容不复制请求、故障历史或代答控件。

极矮窗口的展开面仍须让状态、正文与全部动作可读可达，不能因固定摘要占满可用高度而让内容区归零。身份、关闭与返回始终可达；空间不足时可让状态摘要随正文滚动，并借用窗口内位于该 Region 上方的空间，正常高度仍保留固定摘要。展开面必须与完整 Composer 及原生终端末 32px 输入保护带分别不交叠；可以选择保护带上方，或其下方至 Composer 之间更可用的区域，不能强制上方狭缝而舍弃实际可用空间。正文区至少能完整显示一行可读文字，并能滚动读到全部内容和动作。临时展开面可覆盖原 Permission／Question 卡片的正文；退出后原卡内容、已有输入与操作仍完整可用，Prompt 仍只按原合同 Queue，不代答或取消请求。适配不改变 Terminal 尺寸或新增提交门禁；长状态说明不靠缩字、截短或隐藏解决。紧凑首屏的当前动作可发现性、分类标题优先级及具体密度只见 surface-density 同名小节。

Escape、显式关闭和点击外部可以收起，不丢草稿或改变运行事实。主动键盘关闭时返回原触发入口；用户已点击、聚焦或打开另一个工作面时，以较晚的用户焦点为准，不被旧浮层收尾拉回。进入 Diff、Activity、Browser 或 Session 的动作以目标工作面焦点为准。状态内容或 Session 改变后旧动作不能误投给新 Session；状态自动变化不抢焦点。Settings 仍使用同一状态绑定值和保存 owner，以可理解的名称与简短说明区分进程显示、Agent 声明和输入能力，不静默扩大 running 绑定为 working，不以说明文字建立另一份状态判定。

#### 回复卡片的 reaction 快捷回复（提案）

用户希望在本会话执行 Agent 的回复卡片上，用有明确意义的表情发送特定回复；含义能在 Settings 和 CLI 中设置，Agent 能通过 CLI 查询 code。当前仍是提案，见 Feature `f-2jy8f6nn9`，尚未提供发送能力。推荐复用 Prompt 配置，让「认可」与「继续执行」有不同含义；用户补充图标不用 emoji，要有质量的 SVG，最好带动画；每次发送保留原回复引用和接受时的含义，不因以后修改配置改变历史意义。快捷回复是新的人工消息，不是点赞，也不隐含批准权限请求。system reminder 必须来自应用拥有的发送事实，用户正文中的 XML 声明不能成为认证事实。

## 引用、资源与工具

### System Reminder 的默认与单次选择

用户要求 System Reminder 有两层选择：Settings 设置「默认是否开启」，Launch 可以覆盖「本次会话是否开启」，参照现有 AgentMux guide 的默认初始指令设置。Settings 的选择提供新会话的默认值；Launch 未覆盖时沿用默认，显式选择只作用于本次会话，不回写 Settings 或改动其他已有会话。默认值与本次选择必须分别可理解，不能用一个含糊的开关同时表示两者。

本项已确认的是默认与单次覆盖的关系，尚未确认提醒正文、触发时机或频率、出厂初值、默认配置的具体作用域，以及已有会话恢复时是否继续原选择。不能据「System Reminder」名称自行推定周期调度、system-role 协议、额外提醒 Store，或把 Provider 原生历史里的 reminder 当作 AgentMux 通用提醒能力。提醒的实际语义与发送 owner 明确前，不交付只改配置却不能兑现效果的开关；保存、开启、启动或历史出现提醒文字，都不冒充提醒已按约定送达。提醒流程失败按原健康能力与服务窗合同如实说明，不取消已有可用输入或启动；既有 AgentMux guide 保持其原合同。

### Message Tools 的事实来源与快捷语法

- 前缀、命令目录与 skill 根由 Provider 贡献；Renderer 合并已声明命令和实际磁盘发现，不假定各 CLI 都有相同机器可读目录。远端或来源不可读时明确不可用及 Retry，不以空集合冒“没有 skill”。
- 派发按未 trim 的行首 token 判断；以空格开头的普通正文仍是正文。名称或来源有歧义时展示真实候选，不替 Agent 裁决。参数保自由文本，选择只插入 token 与一个空格，参数语义归 CLI。
- 派发记录必须基于实际派发，入队不冒送达。消息分类与身份事实由 Core 公共合同提供；具体 kind／toolName 以实际类型和 Provider 解释为准，不在 Renderer 造字段或把历史调查问题当当前缺口。
- 初始页与 Agent Session Composer 共用同一个 Message Tools 能力面。输入区支持常见的 `@` 文件/目录引用、`/` Provider command/subcommand、`$` skill 选择；工具选择和手写快捷语法最终都生成同一份可恢复 prompt 草稿。
- `commands` 与 `skills` 的能力范围优先来自当前 Provider 的 catalog/声明；AgentMux 自己提供的配置型能力复用工作区或用户目录下 `.agents` 事实协议，不复制一份 Provider 任务真值。来源、路径和不可用原因要可见。
- 未连接 Session 的初始页只能使用项目/工作区上下文与可发现的本地 `.agents` 内容；需要 Provider Session 才能解析的能力显示为待启动或 unknown，不能伪造可执行项。启动失败保留输入、引用、skill 和 command 选择。
- Provider command 与 AgentMux 自己的快捷命令命名冲突时，不静默改写；显示来源并按明确选择生成 prompt。未知 `@`、`/`、`$` 文本保留为普通输入。

#### 对话里的贴图

- 对话中的本地图片以缩略图显示，可复用路径引用到草稿。远程图片不自动请求，读取失败保留引用；沿用已有受控文件读取入口，不新增任意 URL 读取通道。
- 粘进对话的图片要**看得见**：渲染成缩略图，而不是一颗只显示路径的文件链接按钮。点击放大到灯箱。
- 路径表示原样保留：Agent 要靠那个 `@path` 去读图，缩略图只是给人看的一层，不替换引用本身。
- 图片加载复用受控文件读取与原安全策略；具体 URI／CSP 形式属于当前实现，不成为永久产品约束。
- 读图只访问同一可信贴图目录，路径与 symlink 解析不能逃出该目录读取外部字节；安全读取沿既有文件 owner。
- 起头的 `@` 是记号不是路径字符，解析路径时要剥掉，否则 `@src/foo.ts` 永远打不开。
- 缩略图的读取失败或仍在加载时必须保留原始路径引用；不能留下破图框，也不能因为展示失败把 Agent 可读的引用删掉。读取成功但浏览器解码失败同样回到原引用文字，移除失效缩略图与放大入口；已打开的灯箱解码失败须收起。已读取贴图的显示事实绑定同一 path 与 reader；读取目标或 reader 变更后的首呈现不能把旧图字节配新引用，失败与灯箱状态只作用于该精确贴图。迟到读取或旧图事件不能使当前图失效；正常可解码图片仍沿原缩略图与共享灯箱查看。非本应用贴图目录的图片路径继续走普通文件引用规则。
- 灯箱查看当前明确选择的原图，提供围绕光标的缩放、放大后的平移和适配视口；关闭后焦点回到触发缩略图。平移边界以原图和当前视口的真实几何确定，缩放与拖动只改变局部呈现，不改变原引用、草稿、消息或资源权限。
- 同一正文或草稿中实际呈现的贴图引用可在原灯箱中连续浏览。集合由原内容显式派生并沿用原 reader，不从 DOM、当前焦点、文件系统或其他 Session 发现图片。灯箱只额外读取当前选择的资源，不预读未选图，原缩略图的必要读取保持；切图复位缩放，读取失败保留该图原引用和重试，并允许继续浏览其他图。集合或 reader 改变后不将旧字节配到新目标；原生记录资源继续沿精确记录 reader 查看，不因图库绕过来源校验。
- 灯箱和图库不建立第二份附件、持久图片集合或图片字节事实。远程图片不因这条能力自动请求；复制、草稿持久化、撤销、删除和提交继续使用原引用。图片浏览只是已授权资源的本地呈现，不新增权限或 Runtime 状态。

### 显式选择的文件引用

从原文件选择或当前文件入口插入的普通文件，可用已有语义引用草稿格式显示可读文件名，并按需阅读完整准确引用；手打正文不自动改写为附件。实际发送仍由原草稿展开为同一引用，工作区相对路径与外部准确路径保持，不读全文或猜大小、上传状态。引用的移除经原编辑器事务只删当前节点，保同名／同路径其他项、相邻文字、撤销、源文件与历史；不可编辑或节点离开后旧动作不改写新草稿。Session 与 Launcher 共用呈现／事务，图片仍沿原贴图 reader 和节点。此为本地编辑与阅读，复用原提交、文件选择和可用的打开引用动作，不新增 Core、RPC 或 CLI。

### 输入框截图缩略图

草稿图片提供显式移除动作，经原编辑器事务仅移除被操作的准确节点，保相邻文字、选区、草稿回写和撤销／重做；同路径重复引用不被一并删除，源图片文件和历史消息保持。读取失败的图片引用也可移除；不可编辑或节点已离开／替换后，旧动作不改写新草稿。移除后焦点回原编辑器的删除位置，预览和同草稿图库继续消费原引用与 reader。该本地草稿编辑复用原提交与持久化路径，不新增 Core、JSON-RPC 或 CLI。

用户反馈“现在截图在输入框里头还是没有变成缩略图展示”。截图与粘贴图片进入草稿后，必须在输入框内显示可辨认的缩略图并可放大检查；发送前即可确认是哪张图。缩略图只是同一图片引用的展示，不改变实际发送路径、草稿持久化、复制、撤销或删除语义。加载中和不可读取时原始引用仍可见，不能把图片引用悄悄丢掉。重挂载后仍能从同一持久引用恢复缩略图；Session 输入框和新建 Agent 的输入框共用这项能力。尺寸语言见密度 SSOT。

### Message Tools 失败反馈与 Browser Region 选中态

- 用户反馈「MessageTool 截图不了，已经授权还老弹出授权提醒」，并明确反复出现的是 **macOS 系统录屏／屏幕捕捉授权弹窗**。截图必须按实际截图通路的真实结果处理，已授权时可完成且不误反复请求系统授权；改善 AgentMux 内部文案不能冒充此故障修复，也不能让用户重复授权代替根因验证。当前 Electron 的授权读数不能单独证明系统截图命令被拒绝；已授权、unknown 或授权读取失败不得被误挡。真正未授权才在原工具旁准确说明当前副本、恢复动作和重试，不自动重复请求系统授权。不得重置权限或替用户授权。
- 用户进一步确认「重启后仍无法截图并弹系统授权窗」，且「打开系统设置」仍出现；重启或重复打开设置不能代替同一已授权实际运行副本可截图的验证。
- 「已授权」必须绑定实际运行副本与系统使用的签名身份；设置开关开启、安装包自身签名校验通过都不能单独证明当前副本拥有截图授权。交付更新须保持可延续的授权身份，不能靠每次重新打包后让用户重复授权维持截图能力。 首次从 ad-hoc 换到合法签名代码身份时，旧授权是否适用于新身份须按系统实际结果说明，可能需要本人明确授权一次；此身份过渡不冒充后续更新的授权连续性。后续同一合法 signer 与 designated requirement 的更新须由实际系统授权匹配证明；不得弱化或伪造 requirement、重置权限库或替用户授权来伪装连续。
- 截图选择器同一时刻只有一个；重复点击不启动第二个选择器，也不把第一张图交给另一份草稿。系统取消不算失败、不追加引用；截取、超时与保存失败必须分清并保留正文、已有附件和原 Session 目标。结果迟到或目标切换后不得写入新 Session、Workspace 或 Provider。真正完成且保存的图片仍沿既有粘贴目录、引用及缩略图能力进入草稿，不新增截图 owner 或隐藏替代通路。
- Message Tools 的文件、截图、Skill、command 和发送操作失败时，优先在组件自身显示短暂、可重试的原子错误层；全局通知只作为跨组件或无法定位来源的补充。错误层不得清空 prompt 或已选引用。重试与原入口的后续成功都应清除旧失败；切换 Workspace、Provider 或 Session 后，旧请求与旧重试不得污染新对象。多项工具结果同时返回仍须完整追加到当时的草稿。
- 组件内操作错误保留失败动作的重试入口；成功重试或主动关闭后收起，失败不覆盖当前草稿。初始页一次选择多个文件必须全部加入，并基于选择完成时的草稿追加。初始页共用工具能力，但没有三态输入宿主时不显示空转的形态切换键，工具保持直接可用。
- Browser Region 点击内容区更新其所在导航上下文的准确选择；选中边界、标题和键盘焦点消费同一原位置事实。Work 与 Survey 不因此共享选择，也不从 URL 或 hover 猜位置；新页和子 frame 交接沿[Browser owner](browser-workface.md)。

### Message Tools 触发与菜单

- 输入 `/`、`$`、`@` 分别打开 command、skill、文件引用候选；选择只写入草稿，不暗中发送。三者复用同一个可访问菜单，支持上下方向键、Enter、Escape，菜单展开不改变底部工具栏的布局高度。
- 候选菜单沿用 Message Tools 的浮层与控件语言，不另造一套高列表；当候选过多时在浮层内部滚动，输入框和底部操作保持可见。

### 对话正文中的 Agent 对象引用

对话正文中的合法 `amux://agent|region|tab|space|zone/<ID>` 裸引用与 Markdown 链接共用紧凑的行内对象呈现，原消息、链接地址及原始复制保持原文。引用严格解析为原 Core 类型与 ID；Agent 名称、Provider 图标与当前状态消费原 Session 事实，详情按悬停或键盘焦点读取。它表达被提及对象，不改变记录作者、来源、权限或消息时刻的事实；当前资料须与记录事实区分。未知或不可用时保留可辨的原引用与说明，不用同名对象、当前会话或替代 Session 补位。

共享阅读组件只负责识别与受控呈现，宿主持有对象事实、详情和打开动作；复用既有消息、头像、状态及导航能力，不为行内引用建立另一份 Session／位置事实。打开准确对象、位置歧义、输入保留与失败恢复沿[寻址与复制](public-control.md#对象地址分享与方向)，显示或展开详情不自动发送、启动或恢复 Agent。代码保持字面语义，只读预览保留无导航／资源读取边界，空间对象用类型图标、显式 Markdown 标签或原 ID 呈现，完整地址可查看和复制，不从 ID 内文字推断标题或用途。所有对象的打开沿原地址，非法 URI 保留可读原文。

同一原 SID 已由现有身份解析确认属于 Mote 时，沿原 Mote 名称、头像与表情呈现；普通 Agent 沿原显示名与 Provider 呈现。Mote 仍使用 Agent URI 与同一导航，不按前缀另立协议、持久身份或位置匹配。

状态更新只消费相关原 SID 的现有观察，不为每条历史引用独立轮询、订阅全量资料或预读详情。重复引用共享原事实；隐藏／离屏面停不必要动态。更新不替换正文阅读锚点、选区、展开意图或草稿。视觉与可访问呈现只见[真实对话与行内引用](../presentation/conversation-input.md#真实对话与行内引用)。

### 对话接入新组件与输入引用闭环

- 用户确认「继续推进，另外对话的样式也可以接入新组件」：真实对话与 Gallery 共用消息组件，沿用现有时间线、说话人身份、Markdown、文件打开、图片、继续会话和滚动行为；不把示例 Workflow 阶段或进度伪造为真实对话事实。
- 输入中的 skill/component 引用在正文原位显示短名、类型与下划线，可查看完整引用并打开；编辑、选择、粘贴、撤销、中文组字与发送保持可靠。引用目标随草稿一起恢复，重启后不能只剩无法解析的短名。
- Provider 原生命令保持原语义；本地预置 prompt 明确标识为提示词，点击后在原位展开为可编辑正文，保留其他草稿且不自动发送。两者复用已有工具候选入口，不建立第二套命令执行系统。

#### Shortcuts（AgentMux 自己的快捷指令）与识别词

- **命名：Agent 的叫 commands，AgentMux 的叫 Shortcuts。** 用户原话：「如果现在的 commands 是指用到的 agent 自己的 commands, 那么我们再加一个 shortcuts 表示 Agentmux 提供的自定义能力」。`commands` 这个词归 Provider 原生命令（`/compact`、`/context` 这些由 Agent 自己执行的）；AgentMux 提供、用户可编辑的那一套叫 **Shortcut**。两者行为本就不同——一个交给 Agent 执行，一个只是把正文填进草稿——用同一个词称呼它们，用户没有办法表达「我要改的是我自己那套」。
- **Shortcut 只有一套，且由用户拥有。** 用户原话：「Review Changes 等快捷指令 和 commands 是不是重复了，应该只有一套，而且配置页面要支持用户自定义」。此前的形态是两套并存：一份写死在代码里的预置只能从两枚常驻按钮到达，而把它并入候选列表的那段代码从来匹配不上任何东西——即用户打 `/review` 一条候选都不会出。合并的判据是**候选入口只有一处**：Provider 原生命令与 Shortcut 在同一份候选里出现，不是两排按钮、也不是两个浮层。
- **同一个 `/` 列表，但按来源分组并带组标题。** 用户在被问到呈现方式时选定此项。候选浮层分成 Shortcuts 与 Agent commands 两段，各有小标题；用户因此只需记一个触发符，同时能看清每条是谁提供的。不采用第二个触发符（如 `>`）把两者彻底分开：那要求用户记两个符号，且这类前缀在终端语境里另有含义。命名冲突仍沿用本节上方「显示来源并按明确选择生成 prompt」那条。
- **代码不再持有 Shortcut 正文。** 内置的那两条作为**可改可删的默认项**落进用户配置，此后增删改全归用户；删掉即永久没有，不被补回。设置页是它唯一的编辑面。
- **缺席与空列表是两件事。** 配置里**没有这个键**＝这份配置写于本功能之前，读成默认那两条；**显式空列表**＝用户把默认那两条都删了，保持为空。两者只差一个键的有无，混为一谈会二择其一地坏：要么旧配置的用户永远看不到任何 Shortcut（功能像根本没做），要么用户删掉的东西被塞回来。
- **每条 Shortcut 可选绑定单个 Provider。** 留空即对所有 Agent 生效；绑定后只在该 Provider 的 Composer 出现——「这条只对某一家有意义」必须能表达，否则用户只能靠自觉不去用错。
- **识别词（keyword）是同一条 Shortcut 的另一个到达方式，不是第二份注册表。** 用户原话：「prompt 要支持 "识别词"，比如 eli5 或者 grill_me prompt，当用户在 messagetool 输入 eli5 或者 grill 时，要出现下划线 / 输入的时候就出现 tips 提醒，tab 一键替换 / 点击出现菜单，可以一键替换」。同一个 keyword 字段同时供 `/` 候选与**裸词**识别：命中即在正文原位加下划线（沿用既有语义 token 的下划线语汇，不新造一种视觉），打字过程中就给出提示，Tab 一键替换为正文，点击则复用同一份候选浮层。
- **Tab 只在光标处确实命中 keyword 时被接管**，否则原样放行给焦点遍历——沿用本仓既有纪律（方向键在没有候选时把按键还给光标移动）。未命中的 `eli5` 之外的普通词保持普通输入，不得因为像识别词就被改写。
#### Skill 加载必须快到没有加载感

用户原话：「现在我加载 Skill 和 Command 的时候非常卡，既卡顿又很慢。Command 相对比较快，但 Skill
上来还要 loading 一会儿，而且在 loading 的时候就会卡住」「我理解 Skill 的 loading 应该有很多策略，
可以让它在 SSOT 的情况下加载得更好一些」。

Command 与 Skill 的体验差异要求分别核对实际发现路径、目录规模、资源来源和执行成本；同机对比不能单独排除存储或目录环境因素。

- **Provider 声明 skill 目录这件事已经是规范，不新建第二套。** 每个 Provider 在自己的 catalog 里
  声明 `composer.skillRoots`（用户原话「我们应该可以在 Provider 上定义规范」）。新增 Provider 只
  需要声明自己的目录，发现策略不得按 Provider 名分支。
- **发现必须剪枝。** 只发现 Provider 声明的真实 skill 来源，排除无关依赖、版本控制内部目录与构建产物。共享发现 owner 统一处理剪枝与资源边界，不按 Provider 或入口复制算法。判据：遍历成本随实际相关目录增长，
  而不是与工作区的目录总数同数量级。
- **加载不得阻塞输入。** 菜单可以先出现再填充，但输入框在任何时刻都必须能继续打字。
- **同一份结果不得反复重算。** 打开菜单不是"目录变了"的证据；只有目录真的变了才重新发现。
- **两个入口一个策略。** Session 侧与 Workspace 侧的 skill 发现回答同一个问题，不允许一个入口比
  另一个多付代价（例如为查一个 session 先取整个运行时快照）。

#### 已交付优化的保留与取证

用户反馈：「帮忙看下，我总觉得有些优化本来已经做了，但是由于并行推进又被搞丢了，看看有没有痕迹」。已交付的优化必须在并行集成与实际安装后继续可用；发现体验再次变化时，结论须区分实现被改回、实现仍在但当前产物未包含、当前运行副本未采用，以及尚未确认。历史修复提交或当前源码仍在，不能单独证明用户正在使用的界面已经保留该优化。本次点名的 Message Tool 一行态图标与输入间距只定义在密度 SSOT[《Composer 静息密度与主操作》](../presentation/conversation-input.md#composer-静息密度与主操作)。

#### Composer 静息形态与主操作

- **初始形态可选一行或两行，默认一行。** Settings 中的 Message Tool 初始形态偏好只作用于新挂载、支持三态的输入区；“两行”是输入行加工具行，不是正文行数限制。保存偏好不改变已挂载输入区的手动档位、草稿或编辑状态；一行、两行、大输入框的原手动三态继续可用。没有三态切换的入口保持原工具行常态，不受此偏好影响。
- **切换键在一行态必须是弱的。** 用户原话「只有一行的时候存在感有点太强了（这个时候本来就应该是
  弱的），高度应该稍微再窄一些，最好不要有那么强的边框」。一行态是最安静的形态，它的控件也要最
  安静：控件同高（见密度 SSOT）、不要重边框。切换位置与图标统一遵循上文 Message Tools 三态约束。
- **Send 与 Interrupt 收成图标。** 用户原话「现在 send 和 interrupt 的样式也有点太强了，是不是直接
  用图标就好了？」。两者都降为图标控件；Interrupt 仍必须与 Send 在视觉上可区分——它是破坏性动作，
  收成图标不等于收掉这个区分。
- **Cmd+Enter 直接 steer。** 用户原话「如果发消息，现在好像默认不会 steer。有一些常见操作，比如说
  按住 command + 回车的话，应该就是直接 steer 发送出去这条消息」。约束：`Cmd+Enter` 表示"插到当前
  这一轮里去"，与裸 Enter 的"按常规发送"是两个不同的意图，不能互相退化；Agent 闲着时它也必须有
  确定含义，而不是只在忙的时候才存在。
  - 用户再次反馈「MessageTool 原始需求是发送直接 steer，结果现在都在排队」：Cmd/Ctrl+Enter、显式 Send 和发件条目的“立即发送”本身就是**这一条消息**的 steer 授权，不要求再点 Continue。它应立即尝试向当前 Run 投递；实际输入语义由[《Steer 与 Provider 输入能力》](agent-capabilities-and-messaging.md#steer-与-provider-输入能力)唯一约束。真实交互、部分投递或错误 Run 仍可拒绝，并保留原因和文字。缺少回合结束或屏幕确认属于流程观测，须如实说明，不能因此永久阻断本可输入的 Agent。
  - 同一原意适用于已通过目标、身份和当前 Run 校验的 Control `send` 与 CLI `amux agent send`：这一条明确命令就是当前消息的 steer 意图。缺少上一轮完成或输入框确认不能把它挡成未投递；沿 Core 既有单消息选择尝试，保留真实不确定性告示。交互、部分投递、操作幂等、Run 与能力边界仍由各自 owner 裁决；定时／持续推进、后台消费和普通队列不借用这一次命令的授权。
  - 裸 Enter 在 working／待答时仍表示排队，不借用另一条消息的显式授权。旧 queue-only 项不阻塞新明确 steer；多个明确 steer 保持自身队列顺序，共用唯一消费者，不双发。发送中再来的 steer 意图不能因 await 丢失；重启、自动消费、阅读、队列重排或其他消息不生成新的 steer 授权。
  - 对未恢复 Session 的显式发送仍是这条原消息的发送意图，不能因用户在 Conversation mode 输入、等待恢复、保存或回答既有交互而降为普通排队；同次发送的原身份、正文、目标与执行意图跨这些等待保留。恢复沿[Session 恢复合同](session-recovery.md#sessionrun-与-view)交给 Core，不暗中重建另一个会话或将 Level B 降为重启；原来已绑定旧 Run 的意图不能自动改投恢复后的新 Run。普通队列与后台事件不借此取得新的 steer 授权，应用重启后旧待执行条目仍沿原显式 Send 边界。恢复完成、字节被 Runtime 接受和 Provider 按原输入意图接纳继续按[《Steer 与 Provider 输入能力》](agent-capabilities-and-messaging.md#steer-与-provider-输入能力)分别表达，不把正文留在原生输入框或普通 Enter 的字节回执写成立即执行已兑现；这个回执边界同样适用于已经运行的 Session，未确认不能统一归因为尚未恢复。

#### Message Tools 的身份与右上角那行字

- **正在用的 Agent 要看得见。** 用户原话「我感觉 MessageTools 该品牌升级了，实际在用的 Agent 头像
  也应该显示出来，而不是只在右边有一个名字」。Composer 必须能直接看出此刻在跟哪个 Agent 说话。
- **右上角那行字要换成对用户有意义的名字。** 用户原话「右边的项目名字，也应该改成 tab 名 / region
  内的 session 名，要不然没啥意义」。它此前显示 Region 名（常常就是项目名，用户已明确说没意义）。
  连带约束：此前因为它是"无意义的装饰"而在一行态整个隐藏的处理，必须随内容一起重新判断——一个有
  意义的 session 名不能沿用"反正没意义所以藏掉"这个理由继续藏着。用户进一步明确「有了 Agent 图标，是不是就不用额外显示名字，而且最好是靠右边，不和功能区放一起」：常态只显示右侧头像，与左侧功能区分离；Session 名、Tab 上下文和状态保留在悬停提示及可访问名称，不再额外常驻名称文字。

- 交付证据必须覆盖真实宿主调用、关键实现变异变红、浏览器交互及草稿恢复；已有归档状态不代替当前候选的实际验证。

- Browser 内嵌 frame 的应用链接与新页面交接统一沿[Browser 通用交接合同](browser-workface.md#browser-通用交接闭环)，不由输入工具另建协议。

## 共同对话与阅读

### 共同对话协议与外部交流入口

交互模式与外部聊天连接器消费同一 Core 对话与交互语义：准确的原 Session、带原来源的消息和内容更新、问题与权限请求、有限类型的动作及可查询原回执。原历史、输入与交互 owner 保持唯一；Core 不依赖客户端框架、不输出平台卡片布局，也不新增独立 Conversation Runtime 或第二份完整历史。客户端分别持有呈现、草稿与阅读状态，连接器持有外部认证、绑定及收发事实。

当前状态读取、来源变化观察和实际副作用分别表达。界面可以刷新到最新状态；连接器必须凭原持久来源与自身耐久投递记录补读、核对，不能把临时通知、页面已更新或平台 ACK 当作原生采用、回答结算或任务完成。变化缺口与不可补读范围如实可查，未知不当作未执行，重试保同一原操作身份；此要求不把整个 Core 改成事件溯源，也不授权从终端展示文案猜控制事实。

同一 Core Client 对同一原 Session、相同调用选项的原生历史观察共享底层 Provider watch，每个消费者独立取消与释放；最后一个消费者离开才释放共享观察。共享层只持活跃观察资源，不缓存页面、来源事实或控制资格。确证来源变化或观察终止后，新消费者重新取得原来源观察；资源终止只消费原 owner 的实际关闭事实，不从 unavailable 的错误码猜测。没有资源终止事实的观察未知保留已有 watch、已读内容与健康 Run，不扩散成其他消费者的取消。

一个 Agent Region 可作为一个明确外部群聊的配置与导航入口，实际输入与对话绑定准确 Host／AgentSession。Zone 组织多个入口，原 Tab 层级与空间关系保持；群内线程默认组织同一原对话，不自动另建 Session。移动、分屏或重启保原身份、群关系与 cwd；Region 换成另一 Agent 不自动继承旧群，待投和未知操作继续守原目标及绑定修订。关闭展示不终止健康 Agent 或删除外部群，群名与位置不作为路由或授权依据。

在明确的受众和共享范围内，系统负责把原结构化对外消息及更新可靠地交付群，Agent 负责生成内容，不要求模型记得调用外部发送工具。绑定不默认导出旧历史或内部 reasoning／工具过程；既有私有上下文接入群须明确分享授权，外发过滤不等同模型上下文隔离。桌面与外部入口操作同一原问题，原 owner 核准确请求和当前权限，不能按卡片状态或普通文本猜答案、权限决定或完成。机器人聊天授权与账户工具、远程权限批准分别成立。

以上定义已确认的产品方向与边界，不代表任一 Provider 已支持全部结构化语义、连接器已接入或相关回执已完成验收。现有阅读与呈现沿本节后续合同，原人机交互资格见[分层收敛](agent-capabilities-and-messaging.md#provider-与人机交互的分层收敛)。

### Provider 系统记录

Provider 原生协议明确标记的运行时上下文、环境更新及系统指令，在公共历史中与用户消息、Agent 回复和过程活动区分，并以专门的只读系统卡片呈现。Provider 解释原生结构化来源，Core 传递通用分类；客户端不按正文标签、标题或 Provider 名字猜系统身份。未知或混合来源保持原文和已确认分类，不将用户粘贴的系统形状文本提升为系统事实。

卡片标明原 Provider 来源，保留准确记录身份、顺序、原文和资源引用，可展开、收起及复制完整原文；不冒称由 AgentMux 发送，不进入用户输入历史或提供用户消息的发送动作。历史系统分类只用于阅读，不授予指令优先级、权限或控制资格，也不改变原 Session、Run 和健康能力。

### 可复用对话与 Workflow 表面组件

共同组件由 Gallery 与生产聊天直接消费。组件说明现在发生什么、原因与可执行动作；缺少事实不画空壳或示例状态。对象先于装饰，动作靠近事实；层次和动效保密度、键盘可达性、reduced-motion 与非颜色状态辨识。Gallery 可独立构建，不初始化 Desktop Store 或 Runtime，数据与适配由真实宿主持有。

开发 Gallery 的组件边界及可用宽度检查只持有当前示例视角，覆盖同一套原组件并保原交互状态；不写生产配置、读取 Runtime 或把示例值变成事实，也不另造生产组件副本。检查关闭或宽度恢复不替换原示例节点。

用户确认的演进方向：技术方面向原有成熟组件靠拢，设计风格参考新的 Workflow；提高视觉设计感和产品成熟度，让工作流观察更清晰。组件事实归宿主，展示策略有唯一 owner，交互状态支持宿主控制；Gallery 展示必须能独立构建，不初始化桌面 Store 或 Runtime。现有聊天和观察表面的视觉改版保留输入、权限、滚动、身份轴与服务窗的既有行为，不把 Workflow 假数据接入真实聊天。前端技术栈按当前依赖、实际问题与迁移成本评审，不以换框架代替设计工作。视觉规范的层级和唯一来源见 Surface 密度合同。

- 参考页里的 Workflow 时间线不是一张只能复制的样稿，而是一组可以被不同 Client 消费的受控组件：普通 tool 行、Workflow 摘要头、阶段折叠、Agent 行、Agent 元信息、安静项折叠、旧 daemon 降级行、dock 压缩态和输入框上方提示条都必须有稳定的类型化输入与可访问状态。
- 用户进一步要求对话过程实际接入现有 Workflow 组件：聊天 Activity 的真实步骤与状态消费这套共同观察语言，不停在 Gallery 示例。数据适配归宿主，组件不读 Store、不猜 Provider／Run 状态；Gallery 不成为聊天数据源。记录组不等于有阶段、工作流或多 Agent 的执行事实，没有真实阶段与统计不画虚构阶段、Agent 数、tokens 或进度；已有普通步骤仍完整可读，未知观察保持未知，真实失败与在途状态不能因视觉适配丢失。 长过程默认突出最近记录与真实失败，全部原始步骤仍由一个清楚入口展开；隐藏数按实际成员计算，展开沿原顺序，整组记录起止与总 steps 不随局部展示窗口改变。披露只保存用户意图与已呈现记录身份，不复制步骤事实；切换披露保已读正文、原选区、展开和草稿。
- 原生公开进度说明采用轻量、非正式的共同消息表面，按原 Source 顺序出现在对话中；正式回答、未记录阶段的消息与真实 reasoning 继续各有原含义，进度不能被当思考或归入尾部摘要。真实协作步骤进入同一 Workflow 观察呈现，原 sender／receivers、操作与目标最后记录状态按需可读；一条原生记录仍只是一条步骤，不把目标数量变成 steps、阶段或完整任务进度。无记录时间／状态不造时间或 Streaming；切换披露保原正文、Range、展开与草稿。原生事实归属仅见[《Provider 能力对齐与移植边界》](agent-capabilities-and-messaging.md#provider-能力对齐与移植边界)。
- 旧原生过程沿既有 History 公共读取与 opaque 游标继续可达，与当前对话复用相同阶段及过程呈现；现有有界附近页、原身份锚点、trace 披露和选区保护保持。较早记录不靠扩大 live Hook 窗口、重建旧 Hook 或拼接 captured 投递消息获取；局部窗口和未观察缺口仍诚实，不宣称完整会话或补造执行因果。
- 用户反馈「streaming 旁边旋转的图标动画过于简陋」「这里的线框感太重了」，希望使用带动画的 SVG 和更现代的层次：过程状态仍由已有真实观察事实决定，动效不补造进度、状态或新步骤；减少动态效果时保留可辨的静态图形与状态文字。过程的轻层次不改变原起止、数量、未知／失败、完整步骤、键盘开合、已读正文、选区和草稿，也不增加数据读取。图形与层次只见视觉合同[《可复用对话与 Workflow 组件密度》](../presentation/conversation-input.md#可复用对话与-workflow-组件密度)。
- Workflow 组件只表达观察事实：`running`、`completed`、`failed`、`killed`、`paused`、`queued` 的视觉与中文文案一一对应；只有真实拥有阶段明细时才提供折叠箭头，旧 daemon 退化成普通 tool 行并持续说明“daemon 版本较旧，暂无阶段明细”，不留空壳。
- 折叠是统一的 disclosure 语义：按钮通过 `aria-expanded`/`aria-controls` 管理卡片、阶段和“还有 n 个”；Agent 行点击、Enter、Space 都能打开同一份元信息，失败行永不被安静折叠吞掉。运行中保持展开，终态默认摘要化；用户展开后状态更新不能把焦点或展开意图抹掉。
- 大规模列表超过 8 个 Agent 时自动分栏；分栏后尾部连续的 queued/completed 安静项可以收进可反复展开的“还有 n 个”，失败项不能进入该折叠。窄屏隐藏模型与最近工具，并把头部统计放到第二行；dock 使用同一组件的紧凑变体并限制内部滚动高度。

- 工作中的 Composer 使用[单一主操作](#composer-静息形态与主操作)表达当前发送或中断；键盘发送、Queue 与明确 steer 的意图仍分别可用。steer 只补充输入，不改变 Run 生命周期；中断当前回复与 Stop Session 沿不同操作 owner。
- Activity 聚合行的状态只出现一次；等待、错误和阻塞等摘要不得再追加同义状态标签。路径与 Host 只作为次级元信息，不得把工作线行撑成多行卡片。
- 聊天页已有的 ConversationAxis、AgentMarkdown、AgentInteractionCard、ComposerTextarea、StatusDot 和 ServiceWindowNotice 是同一组件体系的既有成员；它们继续各自拥有身份轴、正文、请求回答、IME 输入、状态点和服务窗事实，不复制一份“聊天版”实现。Activity 内部的 Row/Run/Turn/Ruler 在后续接入时也沿用同一边界。
- 组件的可访问名称、键盘操作、焦点环、减少动画和非颜色状态提示是组件契约，不由 Gallery 或未来聊天宿主补丁式添加。颜色与侧边细条不得成为唯一选中/状态信号；状态必须同时有字形、文案或结构变化。

### Gallery 到聊天页的生产替换

Gallery 是[共同生产组件](#可复用对话与-workflow-表面组件)的隔离验收入口，生产聊天不读取 Gallery fixture。观察区替换只改变展示与交互编排，消息、Session、Agent 状态和 Runtime 事实继续由原 owner 提供。

### 观察界面最终统一

Activity、Workflow、服务窗、权限卡与 Composer 沿[共同组件合同](#可复用对话与-workflow-表面组件)表达实际事实；此入口不另定义一套观察表面。

### 共同对话与原生记录

持久会话历史在原 Session 的工作面内阅读，来源与终端回放明确区分；进入与退出阅读不能重建终端、发送应用按键或改变 Run。向上读取更早页保留正在阅读的项目及其位置，每次读取有界且只有一项在途；失败保留已读内容和输入，并提供重试。消息正文、交错的图片／音频／资源引用按来源保留，无法预览的引用如实显示；没有记录的时间和状态不得补造。Core 提供与 Provider 无关的分页接口，Provider 持有原生读取协议；Desktop 不解析厂商文件、不维护第二份历史账本。

当前原生来源核对、已保存历史来源与同观察资源内临时可读来源的边界仅见[《Provider 能力对齐与移植边界》](agent-capabilities-and-messaging.md#provider-能力对齐与移植边界)。共同阅读面消费 Core 确认的来源；核对或保存失败保留已读正文、选区、草稿与可用输入并显示原服务窗，不自行猜当前源或混用旧游标。

用户进一步要求「复用每个 provider 提供的 session 解析能力，以及我们的对话模式组件」「即使那个对话模式组件实现得不好，要优化的话，应该也是先去优化这个组件」。原生会话协议与记录解释只有对应 Provider 一个 owner；已经存在的读取／解析能力应被复用，缺少完整对话读取能力时明确说明，不能把用量统计或实时事件解析当作完整历史。历史与实时对话中的同类消息使用同一消息组件；说话人、正文、资源、链接、复制与未知元数据的呈现只定义一次。组件的不足在这个共同 owner 上改进，历史入口只持有读取窗口与阅读位置，不能另造一套消息渲染、身份或时间事实。改进仍保持上述原工作面、终端行为与健康 Run 约束。

用户进一步指出「对话模式组件和 history 组件还没有合成一个复用的」「对话组件显然设计得好很多，但它现在很多地方都有 bug」，并要求说明本轮 Provider 完善是否能修复这些问题。同类消息展示与共同阅读行为只有一个 owner；已有组件复用须沿真实产品调用核验，不能以两个入口导入同名组件就宣称体验一致。Provider 负责身份、内容和事件的真实解释，面板负责呈现、选择、复制、展开、滚动与交互状态；原生数据修复不能替代面板缺陷的独立复现、修复和实际操作验收。实时输入／权限交互与原生历史分页各自持有数据和生命周期，不为复用引入第二份事实或把历史读取变成控制活跃 Run。健康输入、原阅读位置、同 Session／Run 与重启后的原工作面仍须保留。 用户进一步要求共同 Conversation／History 现代化、产品化，质量不能弱于本地 Orca。回答是主要阅读面，reasoning 和工具按需展开，姓名、真实时间、状态与动作清楚但不抢正文；仅 trace／资源记录保持紧凑与身份可辨。输入的用户默认外观与跨 Agent 来源统一遵守下文《共同对话的用户默认外观与协作来源》；本会话 Agent 回答在左侧，不把缺 speaker 的机器事件右移。reasoning 默认收起且不挂载重正文，展开沿共同 Markdown 和原链接规则，保原 parts 顺序、记录身份、空／遮蔽与复制边界，不造思考内容、完成或时长。 用户进一步反馈“当前看不到 CoT”；已经记录的原生 reasoning、工具与回答 parts 必须可从对话阅读入口按需读到，复用共同专用 trace 呈现，不把 Hook 摘要或仅 user 投影称为完整原生对话。原生内容与 captured 观察来源明确分区，记录身份与 parts 顺序保持，不能按正文或时间猜两者对应并去重；若只展示原生 trace 子集，须明确范围且完整原生记录仍可达，不能隐去回答后冒充完整会话。原生阅读复用同身份已经读取并提交的有界页，不能为显示思考记录再建立第二份正文缓存、Reader、计时器或读取事实；遮蔽或未记录内容如实说明，不生成思考文本。隐藏后停止新增页并废弃迟到，保同身份已呈现正文、Range、展开、滚动和草稿；换身份不带入旧内容，无关 Session 输出不扩大读取工作。两入口的键盘、选区、复制、链接及原展开选择均须实际操作验证；同内容、宽窄与关键阅读操作须和本地 Orca 做有限匹配独立评审，不足则返修，缺比较不算完成。

共同对话时间尺必须保其已声明可见交互面积；身份轴与时间尺共用坐标盒时，纵向布局不能把时间尺压为零高度。宽窄均能按实际事件键盘读取，看得到但不可focus不算可用。

**共同过程与消息的记录顺序**。用户指出过程不能全聚成一大段，中途用户或其他 Agent 的输入应清楚可见。Provider 同一原生页沿其真实记录顺序连续阅读，user 输入在该来源内分隔 assistant／思考／工具过程；缺时间、逆序时间和同正文不同 ID 不破坏记录顺序，不把所有原生思考另堆在会话末尾。同一原生 rawID 在当前阅读窗口只挂一次，正文、reasoning、工具和资源保持原 parts 顺序、展开与完整记录可达；窗口有界和较早 History 仍明确。captured 提交回执与 Hook 观察是另一来源，保持完整独立可达的记录层和真实失败／未确认状态，不按正文或时间猜原生对应、去重或执行因果。若按跨来源的 recorded time 展示，仅称记录时间排序，不称真实执行或接受顺序；已知同来源原顺序优先，缺跨源位置不能补 now／0。现 captured 已明确记录时间的输入仍分隔该观察层的连续步骤组，不能为统一界面吞掉它。共同阅读不另设 Reader、正文账本或消息缓存；hidden／History 覆盖与返回保持原记录节点、Range、展开、滚动和草稿，无关输出不扩大读取。

用户明确要求参考成熟项目的既有实现覆盖所有已接入 Provider 的原生会话阅读。记录来源、身份、内容及资源顺序由对应 Provider 解释，client 通过同一公开接口阅读；参考实现已经支持的能力不能因未接线而被报告为不存在。确实缺少读取途径或格式依据的 Provider 必须单列缺口，不用未核验的解析结果或静默降级补齐能力清单。

Provider 专有的完整外层输入包装由对应 Provider 解释为阅读范围；公开记录只保留一份完整原文，并附原文中的有界正文范围，共同投影与阅读组件复用同一纯解释能力。默认阅读不暴露已识别包装，完整 Copy 仍取原始文本；未识别、引用／代码内、残缺包装保原文，不据包装升级作者、渠道或设备事实，不增加第二解析器、Reader 或账本。原生记录缺发送渠道／设备时显示“原生 - 未知来源”；既有提交记录中的渠道与设备须完整穿过共同投影。没有明确记录关联时，不按正文或时间把提交来源补给原生记录。

Provider 已识别的结构化问题回复，共同消息投影与卡片直接消费其答案，默认正文不裸露回复协议的 XML／JSON。 原生问题卡的回答确认只消费同一 Session、Provider 与原生来源已读到的结构化回答及准确 questionId；正文窗口之外的同源已读回答也须使原问题显示已有回答，原页已经呈现的记录回答保持优先。确认不替换正文窗、重挂节点或清除选区，不新增读取、轮询或重发，不以提交成功、声明正文、Hook 状态或另一来源记录代替回答；已读事实缺席时保留未确认及原阅读入口，不改变 Core 输入／交互结算和投递回执。该回复记录携带的问题文字可按需展开，属于记录内的上下文，不认证原问题或当前待答状态；opaque 问题引用、作者、渠道、设备与记录身份不变。答案只替换首个原始文本的阅读位置，同条记录的其他文本、资源和过程保原顺序；没有原始文本或问题文字也必须显示已记录的答案。完整 Copy 仍取原 contentParts；没有结构化回复事实的普通、引用、残缺或未识别标签保原文。不新增客户端协议解析器、跨页问题缓存或正文／时间关联，原页字节预算与发送合同保持。

原生异步问题的明确答复由宿主持有原完整输入意图：准确 Session／来源／问题记录、答案、operationId、执行 Host／Run 及首次提交条件。第一次提交前保全，卡片重挂载、界面重载或设备工作面重新读取不重建该意图，也不自动重放。回执未知时保原答案与原条件，明确重试只续接同一原操作；首次或后来一次调用的单阶段未输入回执，均不能证明原逻辑操作整次未输入。结果未知期间不以新正文另起操作；Core 确认同原逻辑操作、同 Run 的整次输入完全未应用后，可由用户明确建立新的答复意图；整次未应用的权威判据与终局性仅见[《跨重启的 Prompt 投递凭据》](agent-capabilities-and-messaging.md#跨重启的-prompt-投递凭据)，不从后次调用失败推断；已读原生确认不因负向回执降级。同源准确 questionId 的已读原生回答仍按上文独立确认。新编辑的答案草稿与原在途／未知答复分存并可恢复，编辑不替换原正文或授予发送许可；未确认仅约束这次答复的重试，不封闭草稿编辑、原会话阅读、终端或正常消息输入。

**共同对话的用户默认外观与协作来源**。用户希望“聊天界面更像 Discord 之类的，如果能识别是其他 Agent 的消息，也用一种特殊消息气泡样式”，并进一步确认“作者未记录，就认为是用户发的”。共同 Conversation／History 中，明确输入但未记录作者的消息按用户外观显示：右侧 You、用户头像与用户色，不再显示 Input／作者未记录；这是本次用户指定的展示默认，替换此前该输入使用 Unknown 中性块的呈现约束。Core 的 unknown 作者事实、记录身份、来源和受信提交凭据保持原样，不据默认外观伪造人类来源或写回数据。无 speaker 的机器事件不套用用户默认。

共同聊天识别对象还包括 AgentMux 系统自己发的消息，尤其首次启动的运行时引导和 Topic 上下文。系统内容在真实组装／发送来源处明确归属，沿现持久消息记录保留，显示为 AgentMux 系统消息，不能套右侧 You 或某 Agent 的身份；混有系统说明与用户／其他 Agent 请求时，各确定来源段分别表达，原请求、身份和投递事实保持。用户未记录作者的显示默认不覆盖已核系统来源。正文信封、第一条位置、时间或入口不升级来源；没有原生记录与系统提交的精确关联，不把旧混合首条拆成新的来源事实、不按正文去重，不宣称 captured 系统记录即原生已接受。无 speaker 机器事件仍用其机器呈现。

AgentMux 自身通过 User message 提供内容的范围、包装与组合约束只见[《AgentMux 注入上下文》](agent-capabilities-and-messaging.md#agentmux-注入上下文)；本节只定义原记录的阅读表达。

**完整前导声明上下文的同记录阅读**。Goals 的阅读反馈希望把输入开头完整的 `<amux from="amux">…</amux>` 声明上下文收拢，让随后原请求可连续读。完整且边界明确的前导声明可以折叠、随时展开并选择原文；连续的完整前导声明保持其原次序，同一记录的真实尾文完整可读。没有普通尾文时保留声明和记录，不补写用户请求或捏造一段用户话。第一段普通正文以后不再寻找并隐藏声明；引用、blockquote、fenced／inline／缩进代码、非前导样例、不完整或结构含糊的前导序列保持全文可读。

完整、位于输入起始的连续 `<amux from="amux">…</amux>` 上下文之后，紧接的既有来源头／完整消息包沿同一阅读语法组合呈现。各上下文保留原始 source span，来源仍明确为声明，原始 unknown／已知 Agent 作者不变且可信作者优先；正文的开头换行、尾部与完整 Copy 保原始内容。未完成、未知、引用或代码中的声明保原文可读，不按启动用途、发起工具或特定 Provider 分支。

这只是原记录内的阅读分层，不创建新的消息或来源事实；声明即使来自用户原文也只叫声明，不认证 System、Agent 或人类，不改变原 unknown 作者、source、record ID、time、parts 或 native／captured 关联。已明确的 producer systemContext 仍以其原事实表达，不从这层声明投影反推系统记录。整条 Copy 保持完整原 wire，缩进、空格、引用及各 parts 不因折叠或展开而改写；原正文节点、Range、阅读位置、展开和草稿保持，查看不发送、导航、切 focus 或控制 Run。隐藏和无关 Session 输出不增加读取，不新增消息／身份账本、第二 Reader 或独立 parser。 声明收起后的尾文分隔与普通段落排版只见密度文档[《用户消息气泡的内文密度》](../presentation/conversation-input.md#用户消息气泡的内文密度)中的“声明尾文的连续排版”。

已核 Agent 身份与当前对话 Session 均存在且身份不同，才是本对话中的其他 Agent。用户进一步明确“发消息过来的其他 Agent 必须与用户同在右侧，本会话执行 Agent 回答左侧”：其他 Agent 在右侧使用独立轻气泡与可读 Agent 来源标记，姓名和头像仍绑定真实发送者；本会话执行 Agent 的回复也采用气泡，仍在左侧，与右侧用户／其他 Agent 输入沿真实身份和方向区分。气泡不改变正文、parts 或作者事实，不能只靠颜色区分，也不能把本会话回答当作协作输入。当前会话缺席、作者未核或资料缺席时不按正文、名称、时间或本地入口猜出其他 Agent。事实判定与展示默认各有一个共同 owner，两入口同类消息复用，不另造消息或作者缓存。正文、Markdown、trace 与资源顺序、记录 id、复制、划线便签、展开与阅读位置保持；新增来源标记不发送、不控制 Run。

完整消息头中的准确 Agent ID 可作为声明引用，复用共同解析和唯一现有身份资料查询来显示它所引用对象的当前名字及头像；卡片清楚保留声明性质，不能因查到对象就将 unknown 作者升级为已认证 Agent，更不能画成人类用户。没有资料时保留可用声明名与准确 ID；没有 ID 时不补造。可信作者与声明冲突时以原可信作者为准，原文和完整 Copy 保持。只处理当前有界已读记录中的准确引用并去重；不新增查询、登记册、正文缓存、逐卡观察或轮询，不为卡头预读完整资料或 Goals。复制 ID 沿原平台 Clipboard 结果显示成功或就地失败；它不改变整条消息复制内容，也不发送、导航、切焦点或控制 Run。

用户进一步要求「对话气泡可以更加精致紧凑吗？」「过程也是」。共同消息气泡与已接入的 Workflow 过程须一起形成更精致紧凑的连续阅读面；收紧后仍能分辨用户、其他 Agent、本会话回答与真实过程状态，完整正文、失败与进行中、全部原步骤、按需展开及原选区均保持。仅调整共同呈现，不改变记录、来源、读取与原交互 owner；密度方式只见[《用户消息气泡的内文密度》](../presentation/conversation-input.md#用户消息气泡的内文密度)。

用户还明确“message detail 文字换成图标，内部信息紧凑、现代、设计精良”。消息详情使用有可读名称的图标按钮，鼠标与键盘均可进入和关闭；来源、记录／提交身份、作者事实、声明与当前 Sender／Project／显式 Goals 各自清楚，缺资料如实说明。收起详情不读取完整发送者资料或 Goals；打开只读该精确发送者的当前已有资料，关闭与查看不导航、不切 focus、不控制 Session／Run、不改原 Copy 内容。项目图形、头像与姓名不会新增消息或身份账本，隐藏阅读面和无关 Session 输出不扩大资料、历史读取或更新。紧凑度与控件视觉只见密度文档[《用户消息气泡的内文密度》](../presentation/conversation-input.md#用户消息气泡的内文密度)。

共同输入卡支持将明确的 [Message From …] 等消息前缀呈现为紧凑来源标签，解析只解释声明文字，不升级 Core 作者或投递事实；未知输入仍按用户指定外观。同样的前缀不因来自 Message Tool 或 Provider 原生 user 内容而漏读，未识别、缺正文或不完整声明保原文可读，完整复制保持原始字节。严格匹配 Agent 加精确 Session ID 的声明可以查询现有公开 Session 资料，匹配成功时明确称“按消息头查询的当前资料”；不规范、未匹配或不存在的声明保留文字，不获得导航权。无可信作者的 Agent 声明也可成为“Message from …”卡片抬头，仍是右侧输入，原始 unknown 作者在来源详情可读，不能把抬头或资料匹配升级为认证作者。可信作者事实优先，声明冲突不能覆盖它；卡片不得把标题、名称或正文关联冒充可信身份。 用户截图进一步指出消息卡裸露的 <bagakit-msg type/name/time> 包装抢过正文。完整、位于消息起始且边界明确的既有包装可成为轻量声明信息，正文按原语义阅读；未识别、不完整、嵌套未知结构或代码／引用中的相同标记保原文，不扫描正文猜包装。包内 name/type/time 只作声明，不认证作者、不升级权限，不替换原 recorded time 或表示送达；可信作者仍优先。原引用归因和内容保持，完整 Copy 仍为原始 wire 字节；包装处理复用唯一纯消息解析能力，Native user 与 captured 两入口同等采用，不引 UI／Node 依赖或第二 parser／身份账本。

输入卡区分“Provider 原生输入”及其 Provider 与“AgentMux 提交记录”，但来源不证明物理发送渠道，渠道未记录时如实说明，不能把所有原生输入叫作 Terminal。来源资料按用户显式查看才读取，关闭不新增读取；复用现项目图标、名称、Session 与目标事实，不增加第二注册表。可信引用或已匹配精确 ID 可以查看当前项目、标题与明确关联的主要目标，过去标题、历史项目或当时目标缺记录就未知，不把当前资料冒充当时。主要目标只来自已有显式 Session 关联；Session 创建时刻只叫生命周期开始，终止只用明确退休时刻，不用最近更新时间冒充结束。资料与来源动作保原选区、阅读位置和草稿，不触发消息投递或 Run 控制。

**Activity 记录时间的直接阅读**。用户要求“+48h24m00s 这类数字应该具体［开始时间－结束时间］ x steps，hover 再显示到开始时间的偏移”，并确认行内读起止、悬停读偏移。Activity 单条机器事件直接显示已记录的具体时刻；折叠步骤组直接显示本组首条创建时刻至本组最大更新时间的记录范围和 steps 数。该范围只描述这些记录，不能称为 Session／进程的运行起止或完成事实；原步骤仍在进行的状态保持，不把最近更新冒充完成。相对已有原点的偏移进入悬停与键盘可读的时间说明；同日简短，跨日显示日期，不让相同钟表时间掩盖相隔日期。无时间事实如实未知，不补 now／0；原 ruler 时间／序数退化、原分组和折叠行为不变，不新增计时器、读取或时间事实。

**用户消息从 Provider 原生会话取得**。用户明确指出「我们的 user 消息都是从 provider 去取，现在项目里用的是只有 Message Tool 发送的消息，这是不对的」，要求「不管用户是在 terminal 里面发消息，还是在 Message Tool 里面发消息」，Outbox、Focus 时间轴和对话模式「都应该要包含，不管用户是以任何方式把消息发给 agent」。原生会话中的用户输入不因发送入口或目标 Agent 不同而遗漏；内容与记录身份由对应 Provider 解释，三个表面消费同一公开 Core 事实，各自归属正确的 Session／Context，不把一条消息复制到不相关 Agent。Message Tool 的待发送、投递中与未确认记录继续如实可达，投递回执不冒充 Provider 已接收的会话消息。

同一原生记录重复读取只出现一次；同正文的不同输入仍是不同消息。同一次提交后来成为原生记录时，只有可核实的关联事实才合并其会话呈现与投递说明，不能靠相同正文、接近时间或终端回显猜对应关系。无法确认关联时明确区分已存在的原生消息和仍待核实的投递，不重发、不吞记录，也不把两份观察都宣称为已接受消息。原生 user 角色、内容来源、发送入口与作者身份分别表达；已知 Agent 作者仍按 Agent 归属，缺作者时原始作者事实仍保留 unknown；共同聊天的用户默认外观见《共同对话的用户默认外观与协作来源》，不将显示默认写回作者事实。缺少原生发生时间的消息仍可读，但不捏造 Focus 上的时间位置。缺原生身份、读取能力或服务暂不可达时保留已读消息、草稿、原工作面和健康输入，用既有服务窗说明缺口，不把“只有 Message Tool 记录”宣称为完整消息历史。

消息来源的更新与阅读有界，工作量只随真正相关的 Session、消费者与新事实增长；无关 Session 输出不能触发其他 Agent 的原生历史重读。 用户进一步明确 Terminal 直接发给 Agent 的用户输入也必须沿唯一公开原生阅读与共同消息事实进入对话、History 和 Focus，不能让已读窗口一直停在首次读取而将新的原生输入静默漏掉。来源更新只基于已核相关原生事实或用户显式阅读，缺更新事实就说明当前窗口与刷新入口，不由任意输出、正文或时间猜新输入。Provider 已明确的 user 记录不因作者 unknown 或来自 Terminal 而丢弃；没有物理渠道事实仍只叫原生输入。已有明确提交凭据与原生记录只有精确关联才整合说明，重复正文不能当关联；读取范围之外或缺时间的输入仍明确可达，不捏造时间轴位置。收起、隐藏、切换 Context 与重启后的重新阅读保持同一记录身份、已知关联、原阅读位置及 Tab／Region／Session 恢复约束，不建第二份厂商解析、持久消息账本或 Runtime。终端连续阅读与输入性能仍按[《Terminal 连续向上阅读历史》](terminal-reading.md#terminal-连续向上阅读历史)验收。 对话原生输入是已读的有界窗口；正在读取、失败与仍有较早原生记录须就地可辨，不能把最近窗口没有输入画成整个会话没有输入。较早记录沿同一 Session、同一 Region 的已有 History 显式可达，按原游标继续阅读；游标不保证较早页有用户消息，失败可就地重试原读取。打开和返回保原正文、选区、阅读位置、草稿与健康输入，回到仍有效的原触发控件；读取说明与重试不重发消息、不控制 Run，不新增第二份历史或无界读取。

用户再次反馈「直接发 terminal 的消息，对话组件里仍然没出现」。首次打开或显式刷新对话时，不能只因最近一页均为工具／活动就遗漏仍在既有有界阅读范围内的真实用户输入；已核原生来源发生相关变化后，新输入继续沿同一公开来源与共同消息组件可读。达到阅读边界仍未取得输入时，如实说明当前范围与较早记录入口，不能声称整个会话没有用户消息，也不能为寻找输入无界扫描、另建解析／缓存或干扰健康 Agent。原记录身份、parts 顺序、unknown 作者／时间、已有窗口与草稿保持。

用户进一步反馈「很多，比如你自己，这条消息我回复后，就不会在对话模式显示」「这条也不会」。健康原生 writer 保持记录文件打开时，已经落盘的相关新增记录也必须沿同一公开来源发出变化通知，不能依赖 writer 关闭文件才更新，也不能把观察注册成功当成后续变化已可观察。来源绑定失效或观察明确不可用时沿既有服务窗如实说明，保留旧窗与健康输入；更新后的阅读仍服从本节已有预算、原记录身份、选区保持、冻结与显式继续读取约束。

**明确手动消息作者**。Focus 同事转述用户进一步要求时间轴明确区分人类与其他 Agent。作者只消费明确事实：第一方 Message Tool 在手动提交或手动排队、首次创建消息意图时记录人类来源，沿原有队列、投递与 Core 回执保留，公共消息作者统一表达为人类、已核 Agent 或未知；已存在的 Agent 作者事实继续保留。共享发送函数、队列消费、控制命令、自动继续以及未归因本地 CLI 入口都不能凭缺少 Agent 字段变成人类；受信 Renderer 本身也不证明某条消息由人类发起。重试或重启后执行旧意图不改变原作者，未知记录保持未知，冲突声明不得升级成人类。原生 user 角色不等于人类，未核原生作者与未核投递关联仍按上述未知和分层规则表达，不从正文、时间或终端回显猜归属。Focus、Outbox 与共同对话呈现采用同一公开作者事实，Agent 标记、发送者导航、投递状态与已有阅读状态保持；作者事实暂缺不重发消息、不阻断健康输入，不增第二份账本。

Focus 时间轴标记、输入列表与消息来源说明表达原作者事实；固定阅读复用的共同正文外观沿《共同对话的用户默认外观与协作来源》。未知作者的正文默认外观不升级原记录、不改标记和来源说明，也不产生发送者导航或执行关联。

Focus 的固定消息正文也遵守《共同对话的紧凑消息、复合头像与按需详情》：原记录的来源、精确收件 Session 和共同说话人资料在正文中保持一致，已核其他 Agent 的方向、当前项目头像与按需详情不能因入口不同而丢失。来源详情仍可核未知作者的原生记录；只在明确打开详情时读取该精确发送者的当前资料及显式关联 Goals，轻量 hover 和收起状态不作完整资料读取。当前资料不冒充消息发生时的项目或发送 Run，未知项目不从收件人、活动项目或声明补出；既有 Sender Context、返回与未知 Run 说明保留。

**共享消息投影的客户端边界**。Outbox、Focus 时间轴、历史与对话模式在浏览器运行的客户端须消费 Core 公开、无 Node 运行时依赖的同一纯消息投影，正式生产构建可加载并呈现非空消息；消息的读取、进程与存储职责仍归原 owner。消费纯消息事实不能将文件、进程或 Runtime 依赖带入 Renderer，不能靠宿主 shim、别名、fallback 或复制投影修补接入；记录身份、作者、时间、来源与投递边界继续服从上述全来源消息合同。

Focus 查询旧时间窗口时，不能把尚未读取的原生记录写成「没有消息」。时间轴保持一个按需阅读 Context；当前 Context 的最新输入沿共享事实取得，用户也可明确选择别的 Context 查看输入而不改变执行焦点。原生记录没有时间时仍能从 Focus 的输入入口查看原正文与来源，不补造横向时间位置。旧窗每批最多读取三页、每页最多三十条原生 record，正文窗口至多保留九十条原生 record；继续读取沿真实不透明游标推进并有界轮换，当前预览正文与其选区保持可读。未到读取快照边界明确说明覆盖不完整，不能凭某条消息时间较早推定已读完；来源发生变化时保留旧内容，由用户明确刷新。隐藏、收起或换阅读范围后停止新增页、废弃迟到结果并释放无消费者正文；已经发出的单页读取按公开能力处理，不能为取消界面读取而停止健康 Run。

用户进一步要求「注意代码品位」「发挥全部水平，成熟产品级别，高级、优雅、简约，所有功能自己测试满意」。Provider 的会话分析、对话模式与 trace 必须沿原生协议闭合到真实产品调用；内容顺序、主会话身份、恢复、长对话阅读和资源边界分别有真实验证。原生事件的同名不等于同义：依赖负载才能区分的收尾、取消、普通通知与子主体必须由 Provider 声明真实语义，不能把所有通知画成工作中，也不能让子主体覆盖主 Session。未知原生元数据如实缺席；不能靠猜测别名、默认成功、最近文件或额外运行时补齐。成熟度与竞品优越性是验收目标，只有绑定实际版本、同等任务与数据的比较证据才能报告为结论。

### 同步原请求与耐久答复回执

桌面对话、公共客户端与连接器回答同一个 Core 待答请求。作答意图保留原 typed 请求的内容与 evidence、准确 Session／Run 和稳定 operationId；显示文案与焦点不授予响应资格。同一 operationId 不能换答案或目标，多个入口竞争由原请求 owner 只接受一个有效意图。问题完成、新题到达或 Run 更换后，原操作回执仍可按原身份读取，不把当前 pending 列表当作操作历史。

保存、派发未知、PTY 字节接受、Hook 原连接写入、ACP adapter 确认、原生采用和准确原请求完成分别报告；没有原生采用协议事实时保持未知。丢回执先查原操作，查询不发送输入，也不因返回空值证明其他操作未发生。用户明确重试同一操作与同一答案时，沿原 recoverable Input join；可能首次施效时仍由原 Provider 目标资格核对原请求与当前 Run，已经施效时消费原去重回执。不能自动重放未知动作、换 ID 绕过原意图或把旧卡答复应用于新题；Hook 回调未知不改投另一连接。

桌面请求卡保留已选答案与操作身份，传输回执丢失时查询原 owner；未知结果可就地再次检查。迟到答复与查询不得覆盖另一请求的卡片状态。原生终端、草稿、阅读位置和健康输入保持可用；同步待答请求与历史异步问题的读取和回答仍由各自原 owner 解释。公开接口及第一方接线见[公共能力来源](../../specs/public-capabilities.md)。

### 对话消息的阅读、复制与标注

展开的思考／工具详情提供各自局部复制，复制完整原 reasoning、参数或结果，不混入标题、Call ID、Markdown展示标记，不拼配 call／result 或推断完成。redacted、空内容与缺少宿主复制能力时不提供伪内容操作；原折叠、顺序和按需 mount 保持。详情与普通代码块复用同一客户端 clipboard 回执机制；成功只来自真实确认，失败可重试，处理保焦并避免同次重复投递；反馈绑定原记录、原内容、宿主和本次动作，换源、折叠卸载及迟到回执不污染新内容。此呈现不新增 Core、JSON-RPC 或 CLI。

对话模式不是左右两张客服卡。用户自己发出的消息靠右对齐，用独立但克制的身份样式表达；Agent 消息保持阅读流宽度，不使用左侧单像素竖线或大面积卡片阴影。每条消息都必须有可发现的复制动作，复制的是该消息的完整原文（含纯文本降级）。

普通 Markdown 代码围栏提供独立的代码复制动作，复用宿主 clipboard 出口；复制当前代码的完整原内容，保留首尾空白、缩进和换行，不混入语言栏、按钮、行号或高亮标记。处理中、确认成功和失败可重试清楚可辨；没有 clipboard 成功回执不能显示成功。复制反馈绑定原代码、语言和宿主来源，换内容、往返切换或卸载后，迟到回执不能污染当前代码。图表分支、原高亮与可见性调度保持；只读预览和无宿主 adapter 的独立 Markdown 保留原无操作边界。该呈现复用现有客户端复制能力，不新增 Core、JSON-RPC 或 CLI。

对话选区留言统一称「批注」，避免与全局 Note 混淆。划词首先是阅读动作：在可编辑且非只读的当前对话阅读面选择正文，仅出现贴近真实选区的「批注／复制」工具条，不自动建立批注草稿或抢焦点。复制保留选区的完整文字；点击批注才打开留言浮窗并划线。跨控件、跨消息及非正文内容不拼成引用；没有有效选区不增加 chrome。

批注保留来源消息稳定 ID、真实引用文本及原 Range。浮窗跟随原范围，跨行、滚动、展开及宽窄变化保持所选位置；不能按重复文本首次命中重新定位、重排正文或改变阅读锚点。折叠、隐藏或原 DOM 离开时停止几何读取，失效定位暂隐，书写内容与原身份保留，返回后仅在原 Range 仍有效时恢复。新选区可以复制，但不能悄悄替换已有书写批注的引用目标。关闭／Escape 仅暂收，丢弃明确只丢此草稿；IME 不触发发送，回焦不夺走用户后来主动选择的控件。

批注可显式加入当前 Session 的回复草稿，沿原追加 owner 保留既有草稿；也可直接发送给所选 Agent。默认当前 Agent，推荐按本项目（包含新建）、Mote、其他排列；项目归属沿原执行 Workspace／Project，Mote 沿既有 owner，显示名称、头像与精确 Session 身份，不能按当前显示位置或名称猜关联。新建明确选择本项目执行 Workspace 与已有 Executor，通过原 agent.open 单次 initialPrompt 创建并交付批注，不再补发第二条输入。

直接发送沿原发送队列与公共输入合同；「已入队」不冒充 Agent 已收到或执行完成。入队前拒绝保留批注并可显式重试，入队后由原队列持有输入及失败／待确认状态。新建结果不确定时保原 requestId 核对该操作，不自动再建或重发。引用、留言及发送来源只定义一次，不新增标注账本、Reader、轮询或 Runtime。所有失败只影响本次动作，保留健康 Agent 的普通输入；选择、复制和模式切换保持响应。真实 Renderer 故障的恢复与退出见[《工作中界面崩溃的隔离、恢复与退出》](session-recovery.md#工作中界面崩溃的隔离恢复与退出)。视觉与密度唯一见[《对话消息的视觉语言》](../presentation/conversation-input.md#对话消息的视觉语言)。

### 对话中用户消息的阅读方向

用户消息气泡整体靠右，用来表达对话轴上的发言归属；气泡内部正文、Markdown、列表和代码块统一居左对齐，长内容从左侧开始阅读。用户头像、时间和操作元数据可以继续沿右侧排列，但不能让正文跟着气泡方向右对齐。

用户进一步要求「用户发的消息，是否可以用稍微不一样一些的样式」，且「只有用户消息」的宽高用优雅的方式自适应：仅用户显示的气泡随实际内容收敛，短消息不被撑成固定宽高，长正文与按需详情仍完整可读；当前会话 Agent 与其他已核 Agent 的气泡布局保持。既有作者事实、用户显示默认、来源详情、复制原文与原 DOM 选区边界保持，不凭气泡样式认证来源；视觉约束只见[《用户消息气泡的内文密度》](../presentation/conversation-input.md#用户消息气泡的内文密度)。

### 对话消息、终端缺口与缩放重绘

- Codex 对话模式按 Session timeline 的每一条 `user_message` 渲染用户消息。首条消息不能成为唯一的用户气泡；后续发送、恢复和重连后的消息都必须单独可见，并保留它们原本的顺序与正文。时间轴同步遇到缺口时先重取权威快照，不能静默只留下第一条。
- 终端的有序字节缺口不能写成终端内容。保留历史不足时，在终端外显示可收起的服务窗，说明缺失范围和恢复动作；当前 Run 健康时继续显示最新字节，并请求一次当前屏幕重绘。缺口提示与当前画面正确性是两件事，成功重绘后提示收敛，但历史缺口事实仍可查。
- Region 缩放、分屏或字体变化后，顶部的 Redraw 提示只在当前可见网格尚未确认时出现；重绘已成功或尺寸已重新确认后自动消失。提示不能覆盖正确的缩放内容，也不能因为旧的历史缺口永久复活。
- Restoring 舞台与 Agent 启动舞台共享同一套全幅布局质量、身份锚点、状态语义和可读性。Restoring 明确表达“重放保留输出/接回当前画面”，通过 `FullPageLoadingSurface` 的 recovering 语义呈现；Agent 启动表达“等待进程首段输出”，仍可保留自己的局部启动提示，但不得再为 Restoring 另造一套终端专用全屏动画。
- Agent 的 Skill 必须能指导它为自己设置用户可读的显示名，并为当前工作区设置用户可读的名称。显示名是可持久化的展示事实，Session、Workspace、路径和其他内部 ID 保持稳定；设置失败要留在当前工作面说明，不得清空工作区。

### 对话完整性

对话视图必须按时间顺序显示用户消息与 Agent 回复，不能只呈现 Agent 一侧。

## 邮箱、位置与工作面入口

### Message Tools 邮箱

邮箱的原生消息观察按本次工作面是否真正可见暂停或继续；打开的邮箱随工作面隐藏时保留原正文与阅读状态。具体隐藏、迟到读取与同身份正文保全沿[《Terminal 连续向上阅读历史》](terminal-reading.md#terminal-连续向上阅读历史)的原生对话阅读约束，其他仍可见的同 Session 消费者正常继续，readonly 不表示隐藏。

用户要求像游戏里的 Mailbox：“新消息有红点，看过了红点就消失”，排队消息也放到“发件列表”，“这两个组件就统一了”。Message Tools 只保留一个邮箱入口，与右侧 Agent 头像合成位置稳定的会话控件，内部区分收件通知与发件列表；不再同时摆放另一套常驻队列工具栏或在输入区铺设持久报错横幅；仅有待发内容时的外部摘要和对应显式动作沿[《输入框外的待发提示》](#输入框外的待发提示)，完整队列仍复用同一 Outbox。新通知的入口含义沿[《入口提示的清楚含义》](#入口提示的清楚含义)；打开并看到对应收件页即算已读，该页的未读提示消失，当前问题仍可回看。仅浏览发件列表不能把未看的通知标已读。数量与未读是不同事实，不能把正在排队误报成新通知。

用户曾要求「红点+数字」并避免与 Agent 状态叠压；数字可直接辨认、零时缺席、视觉上限不损害准确可访问数量与原工作面这些边界继续保持。原入口合计 Inbox／System 未读并旁置 pending 的含义，已由下节[《入口提示的清楚含义》](#入口提示的清楚含义)的新反馈替代；不新增计数或已读 owner。看过哪个收件页仍只按原规则读哪个页，hover经过、Outbox或Progress不代读；计数变化不改原 Session、草稿、发送或终端阅读工作面。

用户最新反馈：「现在 mailbox 上的红点感觉太大了」。未读提醒须更轻、更紧凑，同时保留直接可辨的数字与准确可访问数量；缩小视觉面积不能退回纯红点、隐藏正数或改变未读／已读与待发的事实。具体尺寸与可读性只见 surface-density 的[《Message Tools 邮箱》](../presentation/conversation-input.md#message-tools-邮箱)，原入口、阅读与工作面边界继续适用。

已读不表示运行时恢复。收件通知保留当前问题、影响和恢复动作；相同原因持续更新而非重复堆积，只有恢复后再发生、原因或严重程度变化、新 Run 的问题才重新提醒。切换 Tab、重挂载和应用重启不能把相同已读问题重新变成未读。已解决条目随权威事实消失，不维护第二份 Runtime 状态或无限错误历史。连接、投递核验、队列阻塞和局部操作失败都归入当前 Session 邮箱；局部重试仍然可用。发件列表的复制和手动重试失败也留在同一个邮箱中，不另开全局错误条；再次成功后相应局部错误消除。

发件列表保留实际待发送文字、次序、状态与原因，以及已有重试、复制和移除能力。看过通知不会取消或重投消息；发送中不能移除或并发重试；旧 Run 的消息不能误投到新 Run。空列表明确为空。邮箱在三种输入框形态都可访问，不因忙碌、输入禁用或窄分屏而不可用。视觉约束见密度 SSOT 的“Message Tools 邮箱”。

与持续推进共享入口后的 Progress 页及循环状态边界只定义在[《持续推进与邮箱共享入口》](#持续推进与邮箱共享入口)，邮件三分区继续保持上述语义。

#### 入口提示的清楚含义
用户反馈邮箱入口“这个空白咋回事儿，小铃铛位置看起来也像 bug”：缺席的数字／提示不制造另一种状态或入口；只消费现有 Inbox、Notices 与 Progress 的真实可见事实。入口紧凑、数字缺席时无空槽、铃铛与进度对齐的呈现约束只见[呈现合同同名小节](../presentation/conversation-input.md#入口提示的清楚含义)，原未读确认、队列和观察行为不变。


用户进一步反馈：「现在 mailbox 的按钮，红点会把 inbox 也放里头，显得都是错误，右边的小数字挺好看的，但不明白啥意思；做些调整更清晰」。邮箱入口旁置数字只表示 Inbox 的既有未读来信数，不把普通来信表现为错误，不与 Notices、pending 或已加载 History 相加。原入口 pending 数字取消；待发事实仍在 Outbox 标签以实际 pending 数清楚呈现，队列／发送／已读 owner 和原打开优先不变。各数字零时缺席，1–99 直接显示，大于99显示99+，标题及可访问名称保准确数与对象语义。

Notices 的独立静态提示只表示当前既有未读告示，即原 system.unread；不表示告示全是错误、Agent 已坏、尚未恢复的总数或另一份 severity 判定。标题／可访问名称分别说明 Inbox unread、Outbox pending、Notices attention，并提供各自准确数量。零未读告示无该提示；已读告示仍按原问题 owner 保留可回看，已读不冒充恢复。原 occurrence／kind／cause 身份和按所见页确认规则不变，observedAt 不入已读身份；原降级、未知及真实 Agent 状态继续各自诚实呈现。absence／零不作为健康结论，Notices 来源未确认不补成已确认健康。

Progress 的原独立状态标识和右侧 Agent 头像状态不加入上述计数，也不被新提示挤占。新事实不强切页，hover 不代读；提醒和数量变化不增加行、不改原草稿、Session／Run、队列或 Terminal 阅读工作面。不新增全局错误条、状态机、计数缓存、读取观察或存储 owner。中性数字、独立告示提醒与入口几何只定义在[呈现合同同名小节](../presentation/conversation-input.md#入口提示的清楚含义)。

#### 悬停访问与最近顺序

用户问「mailbox 有没有更好的设计方式, 比如 hover 时直接显示也支持鼠标移上去, 而不是特地点击。另外, 顺序是不是也都调整成最新的在上」。鼠标悬停邮箱入口即可查看同一内容面，允许从入口越过间隙移入面板、切页、滚动和操作；离开入口与内容面后，尚未显式打开的预览自然收起。悬停只显示，不执行发送、重试或循环动作，不夺走 Composer、终端或其他编辑字段的焦点、光标与组字状态。

点击、键盘和触摸仍能显式打开；点击入口或在内容中开始操作、编辑后，面板保持打开，不因鼠标离开打断。关闭、Escape 与点击外部沿原生浮层语言：仅悬停后按 Escape 保留原输入焦点；面板内的 Escape 或关闭按钮回到同一邮箱入口；外部点击已建立的新焦点不被拉回。经过入口不能吞掉未读；真正移入可见内容或显式打开后，才按当前所见 Inbox/System 页的既有规则记录已读，其他页不代读。

Inbox 来信和 Outbox 已发送／已记录的历史以各条原始展示时间统一最新在上，不能先按来源分组再拼接，也不能用刷新时间把旧正文抬成新消息。System 当前告示沿其实际 owner 提供的最近观察事实时间最新在上；缺少可比较时间的条目归在有时间条目之后，保持稳定次序并明确时间未记录，不解析身份、操作标识或正文猜时间，不另建随挂载与刷新变化的时间账本。展示时间更新不改变通知身份或已读，不因只有时间变化重新点红。相同时间保持稳定次序；加载更早历史后仍保持这一顺序。Progress 继续显示当前循环与最近决定，本需求不增加事件历史。

待发送队列单独保留真实投递顺序，排在发件历史之前；最新在上的历史不能重排待发消息、改变已有移动／重试／发送语义，队列时间仍只表达首次接收用户意图。新消息或循环事实到达不强切当前页。Progress 的常驻表单、状态 owner 与共享入口约束继续由[《持续推进与邮箱共享入口》](#持续推进与邮箱共享入口)定义。

#### 内部信息流与完整阅读

用户进一步反馈「message 内部的信息流设计还是一塌糊涂啊」。邮箱内部须能先扫到具体记录及其真实来源、时间和状态，再读单条完整内容并处理对应动作；不能把全文、流程说明、历史边界和操作一股脑堆在同一阅读层。Inbox、Outbox、System 与独立 Progress 页继续各有既有含义，不把 Agent 来信、用户输入、当前服务问题或循环配置伪装成聊天 Thread、回复关联或同一种消息。

同一邮箱面内的列表与单条详情有明确来回路径；返回仍落在原分类与阅读位置，完整长正文、原始状态／原因及该对象动作可达。Outbox 明确区分先按真实投递顺序排列的 Pending 与按上述最近顺序排列的 History，分页边界和历史读取错误归在 History，不盖过 Pending 或让加载历史变成重发。当前能发送的消息及其目标可辨；逐条显式发送与自动投递的边界统一遵守[《Composer 消息队列与紧凑状态》](#composer-消息队列与紧凑状态)，详情不授予额外许可。发送、移动、移除与复制仍沿原动作 owner 和已有 Run／sending 约束；看详情、切页或返回不派发消息，也不改变草稿。

来信身份、用户输入作者、记录来源、投递状态与时间分别消费公开事实，未知仍明确未知，不能把 native user 角色或无 Agent 字段猜成人类，把 Recorded 当作投递确认，或从正文／时间推断重复与回复关系。System 的当前问题、影响和恢复动作可快速辨认，完整三事实和原恢复动作仍在同面可读；详情展开和返回不消除问题或新增错误历史。Progress 继续呈现原循环当前状态／决定与原常驻配置，不把配置表单混入消息历史，不增观察、调度或存储 owner。

邮箱的打开优先、hover／pin／关闭／键盘和按所见分类记录已读继续按本节既有规则；不新增单条已读账本或在已被该规则确认的记录上保留假的 Unread 标签。来源变化不把另一个对象顶替当前详情；System 详情复用既有 serviceNoticeFingerprint 的 occurrence／cause／kind 身份，不把 observedAt 放进身份；单 id 复发或原因／kind 变化须返回本页，不能静默换成另一次问题。换 Session／Run 不带入旧详情或派发旧意图。固定导航、摘要层次与详情密度只定义在 surface-density 的同名小节。


#### 统一对话阅读与简明操作

邮箱的 Collaboration 页只在打开且可见时按当前准确 Host／Session 读取原监督协作链，分页、显式刷新与详情沿[协作合同](agent-capabilities-and-messaging.md#交出去与派出去)。原 sourceMessageId 固定选择，背景读取保已读节点、文本选区与展开；失败保已知记录并就地重读，换来源或隐藏后拒绝迟到结果，不扫描无关 Session，也不改变草稿、消息投递或 Agent 生命周期。

协作查找只投影当前已加载记录的原双方身份、原消息 ID 与通信等待／报告已记录事实，明确标出已加载范围和匹配数量；空匹配不代表全历史为空。当前已知名称可辅助查找和阅读，不能代替原身份、历史作者或执行资格。查找、清除、加载更多与显式刷新保原选中详情、展开、阅读位置和草稿；不为过滤额外预读正文或轮询其它 Session。

所选原协作记录可显式复制一份证据，包含原请求／回复、消息／operation／thread／Session／Run、投递和监督、已记录的身份观测缺口与本次读取问题。复制范围限定当前准确来源已读取的记录，不另读全历史或工作区文件，不自动保存或发送；缺失事实保持未知，不推断 Goal 关联、执行成功或费用。复制沿原 Clipboard 回执与来源／尝试隔离，失败可原地重试；换来源、选中或隐藏后旧动作／回执不污染当前对象。

用户反馈「最新的包里没有看到有复用组件」「整个 mailbox 看起来，它的选项非常不清晰，到处都是字，不够现代化」，要求完整重新设计。邮箱须成为当前 Session 的清楚阅读与处理面：Inbox 来信、Outbox 待发与输入记录、Notices 当前服务告示的导航含义可直接辨认；Progress 是可发现的独立工具入口，仍沿《[持续推进与邮箱共享入口](#持续推进与邮箱共享入口)》的常驻表单和循环 owner，不增加二层模式导航或全局循环管理。

导航计数只表达要处理的事实：Inbox 与 Notices 为各自既有未读数，Outbox 为实际 pending 数；零时不显示 badge，可访问名称和标题说明对象与准确数量。已加载 History 的有界窗口不是全源总数，不能与 Pending 相加伪装成 Outbox 总数。邮箱入口提示只沿本节[《入口提示的清楚含义》](#入口提示的清楚含义)，打开优先、所见页已读、hover 不夺焦点、新事实不强切页均不变。

列表以真实作者／身份、原始时间和有界原文开头为主要信息，不逐条重复 Read full message、Captured input、Delivered 等说明。摘要的读取边界是原始字符串前240字符；预算内可按共享对话语法完整解释的来源声明，不得挤占正文摘要。有正文时摘要以同条正文开头为主；无法完整解释时保留有界原文，不伪装成已解析正文。完整详情、身份事实及原文 Copy 不受摘要投影影响。不得扩大预算、解析全文或扫描尾部来寻找正文，也不得维护另一份声明语法。来源及投递成功细节可渐进披露；影响当前处理的未知投递、Run 不可用或失败在对应记录附近保持简短可见，不能只为减字隐藏风险。缺失作者明确未知；缺失时间和完整来源在详情可读，不补造事实。Pending 与 History 仍分别按真实投递顺序及最近顺序呈现，分页／刷新／观察问题留在 History，不盖过队列。

Inbox 以及 Outbox 的 Pending／History 完整详情实际复用各 client 共用的 ConversationMessage 正文、头像／身份、Markdown 与原文 Copy；共享阅读层是这些呈现的唯一实现，Mailbox 不保留宿主专用副本或第二套正文、声明语法与复制反馈。共享阅读层只持呈现与单对象局部交互，不持 Session、Run、Queue、Read、Progress 或来源发现。Clipboard 结果与错误报告、浮层目标、焦点策略及身份／图标呈现由宿主明确提供；文件、HTTP、图片与当前来源上下文仍由宿主传入，共享层不借 Electron、宿主 Store 或隐含平台默认取得这些能力。仅邮箱记录阅读显式选择紧凑呈现与记录身份语义：未知作者仍为 Author unknown，不改变普通对话已确认的 unknown→You 展示默认，也不把 queued／restoring／deferred 或 native Recorded 映射成对话 complete／streaming／failed。尚未投递的队列不伪造 captured receipt；正文中的声明不升级成已认证作者。Copy 复制完整原记录字符串，包含原头部及末尾，不复制两行预览或解析后的正文；共享单条 Copy 只有原 Clipboard／feedback 明确返回 true 才显示 Copied；false／throw／void／undefined 不冒成功，失败保完整正文、原反馈与 Retry，Copy all 的原路径不换。

文件、HTTP 链接、图片和来源披露沿来源 Session 的既有 origin、workspaceRoot、homeDir 与实际打开／读取 owner；不能借当前 active Workspace 或收件 Agent 的资料补造发件人上下文，不新增逐行 Store 观察、正文缓存或持久 owner。列表只挂当前页轻量有界摘要，显式单对象详情才挂完整对话内容；不能把含 Copy／来源等互动的 ConversationMessage 嵌进整行按钮。返回保原分类、滚动位置与焦点优先级；旧 Session／Run、失效记录与 Notice occurrence／cause／kind 的详情隔离继续沿[《Message Tools 邮箱》](#message-tools-邮箱)合同。

Pending 的可投递条目以 Send 为清楚主动作；可用边界统一遵守[《Composer 消息队列与紧凑状态》](#composer-消息队列与紧凑状态)。移动／复制／移除可用低层级图标动作，但每个都有 tooltip、准确可访问名称和原次序／sending 禁用规则；Copy all 的原全文与顺序保持。风险说明归实际对象，不用每条重复长流程段来代替状态。查看、返回、切页、展开来源或重开邮箱均不派发、重投、重排、清草稿或改变 Run 绑定。

Notices 列表先给问题及轻量类型／时间，完整详情仍读原 problem／impact／restore 与原恢复动作；已读不冒充恢复，详情不替换另一 occurrence。空页有可辨的对象标题，最多一条必要提示。原 Mailbox 原生浮层、可见性租约、观察／刷新／分页、Read、Queue、Progress、Terminal 与输入 owner 均保留；本次只重设计呈现与真正共享阅读，不新增依赖、存储、调度或状态机。具体视觉及紧凑层次只定义在[呈现合同同名小节](../presentation/conversation-input.md#统一对话阅读与简明操作)。

#### 邮箱记录一键定位对话

用户明确要求：「Inbox 和 Outbox 上的卡片不但要复用，而且还要有一键跳转到对话模式里对应位置的功能」。Inbox 与 Outbox 已有记录在列表和共享对话详情中均有可发现的“在对话中查看”动作；这是查看原记录，不是发送、重发、继续或切到声明作者的另一场对话。共享阅读层继续按[《统一对话阅读与简明操作》](#统一对话阅读与简明操作)呈现消息与宿主传入的动作，不持有导航、Session、Run 或读取状态的另一份 owner。

对应位置由记录所属 Host／AgentSession 与公开记录来源共同确认：captured 来源使用原 submissionId，native 来源使用原 providerId、nativeSessionId 与 recordId，消息投影的稳定 id 和记录命名空间不能丢失。声明作者、正文、预览、时间、相同裸 id 或队列 id 都不能代替对应关系；Inbox 的目标是这条输入实际被记录的对话，不是 authorAgentSessionId 声明的发件 Agent。只有原投递 owner 已确认尚未提交且没有对应记录时，才能呈现“尚未发送，暂无对话位置”。投递未确认或未知不能称为未发送，提交已确认但位置未确认也不能改写为未发送；投递状态与记录是否可定位分别说明。已有准确记录仍沿原定位能力查看，不因消息仍列在 Pending 或提交回包缺失而隐藏真实记录；没有确证记录时如实说明位置未确认，不能伪造 captured 记录、借文字猜位置或为了取得位置触发 Send。

明确点击或键盘激活后，在原 Session 的既有工作面切到真实对话模式，使确证的记录进入可读视口并短暂标明位置；成功只在该来源的准确记录已经呈现时成立。原已加载的有界阅读窗口不能仅因邮箱到对话的切换而丢失定位依据，不增加另一份全文缓存、全历史扫描、轮询、无关 Session 观察或 Runtime seek 机制。记录暂未加载时只沿原读取 owner 的有界读取与错误边界处理；未找到、来源变化、过期 Run、能力不可用或读取失败须如实区分，原记录仍可读、可复制，不能跳到近似对象或报告假成功。原生历史的来源身份可以跨 resume 保持，但须由当前公开 source 重新确认；不能把捕获于旧 Run 的意图投向当前 Run。迟到的定位结果不得更改另一 Session／Run、后续用户选择、滚动或焦点。

查看动作保留原草稿、Progress 常驻字段、队列顺序与 Run 绑定、原 Terminal 实例／rows／光标／输入、相邻 Region 和布局；不另建 Session、移动／拆分工作面或触发恢复、重投和终端输入。只有显式导航可移交阅读焦点；hover 不切模式、不定位、不夺焦点，Esc／返回和后续用户焦点继续沿原容器规则。动作与正文、Copy、来源、Send 保持独立命中，不形成 button 内 button。行为结果、暂不可定位说明与位置反馈的呈现只见[呈现合同同名小节](../presentation/conversation-input.md#邮箱记录一键定位对话)。本轮不改变 durable 布局或 Session 生命周期 owner；若实施实际需要改变，须先明确评审其范围与恢复回归。

#### 当前查看位置与路径

用户补充要求：「看是不是把所在的 region 和项目等路径也给出」。邮箱记录详情须让用户辨认当前接收对话的查看目标，并能读全其项目、目录与空间地址；这些是当前上下文，不是消息发送时的位置或历史来源。

当前查看位置绑定本次点击所在的准确显示 occurrence，保留 displayWorkspace、Tab Group、Tab 与 Region 的完整身份。主面与同 Session 的其他投影分别消费各自确证的显示位置，不借当前 active Workspace、首个匹配 Region 或原工作面的名称替代点击位置；同一 Region／Tab 的多处显示不能合并成唯一位置。名字只是当前显示值，不替代稳定 ID。空间、资源与执行身份继续沿[《统一概念与空间寻址》](spaces-and-layout.md#统一概念与空间寻址)。

当前 Tab 所属资源的 Project、项目根目录、Workspace／worktree 目录与分支，仅在既有登记 Workspace 的 Host 与资源归属已确认时呈现；Space／Zone 不强称为 Project。Session 的执行 Host 与 cwd 单独消费其公开事实，不用项目根、资源目录或 displayWorkspace 路径替代；显示移到别处不改变执行目录。资源与执行的 Host 分别说明，显示容器标识不冒充机器 Host。项目未知、未登记或当前位置无法确认时明确说明，不从正文、声明作者、时间或路径外观推定归属。

接收 Session 的查看目标与发送者信息分别标注。现有 Current sender 及其项目仍只描述确证发送者的当前资料，不借来解释这条记录被接收的对话；消息来源仍是原 captured／native 记录身份。未记录的历史 Region、Tab、项目或 cwd 如实保留未记录，不新增历史字段、存储或原生读取来补造。队列所属 Session 的当前执行事实仍在 Info 读取；消息是否可定位只沿[《邮箱记录一键定位对话》](#邮箱记录一键定位对话)，不从排队状态或当前路径补造消息目标，查看保持零派发。

位置与路径披露只在已打开的单条详情消费所需既有宿主元信息，关闭后不继续读取；列表不逐条建观察或扫描所有投影。披露不改变布局、焦点、模式、Run、草稿、Read、Queue 或 Progress。位置资料缺失不成为另一道导航门：已有记录仍按原来源确认与定位能力处理，原文、完整 Copy 和可用动作保持。完整路径与 ID 通过现有 Info 可发现、可选择和读全；概要与详情的密度只定义在[呈现合同同名小节](../presentation/conversation-input.md#当前查看位置与路径)。

### Message Tools 的底部回看入口

当 Message Tools 的编辑区或消息内容已经离开底部时，在 composer 内提供一个紧凑的“滑动到底部”入口。入口只负责把同一个编辑区滚动容器带回最新内容，不创建第二个滚动面，也不改变草稿或工具状态。编辑区已经在底部时入口必须消失；用户继续向下滚动时它可以重新出现。入口要有键盘焦点和无障碍名称，并且不能挤压 Agent 身份、工具、邮箱或发送控件的稳定命中区。

### Result ready 在小 Region 中的可用性

Agent 完成后的 Result ready 只占一行紧凑摘要，默认不展开文件和链接。用户可以明确展开、收起或关闭它；终端、Message Tool 和 Region 的主要操作保持可用，关闭提醒不应是继续工作的前置条件。展开的结果按文件和预览目标分组为可扫描列表，内容有独立滚动上限，不能靠把每个目标平铺成按钮而把小 Region 撑成十行左右。窄 Region 里所有可见控件必须可点、可键盘到达；面板不能盖住或挤走输入区。

**自动出现不能挡住 Terminal 输入**。用户原话：「"result ready" 是个好的 hitl 设计, 但是出现的时候就挡住了 terminal 的输入, 太霸道了」。保留结果已就绪的提醒与主动查看、处理结果的入口；自动出现只是告知，不能盖住或挤走正在使用的 Terminal 输入位置、抢走原焦点、打断正在编辑的文本，也不能要求先 Review 或 dismiss 才能继续输入。正常与窄分屏都必须保持原输入可见且可继续键入；用户主动 Review、收起或关闭后，仍能回到原 Session 继续工作。结果提醒的呈现不能改写 Session、Run 或工作面归属，不得停止健康 Agent。

关闭只针对当前这轮结果。同一完成状态的重复观测不能强制重新展开；Agent 开始下一轮并再次完成时，新结果仍有可发现的入口，不能被上一次关闭永久吞掉。

### Agent 内部视图切换归 Message Tool

顶部 Chrome 只表达工作区、当前工作面和 Agent 生命周期汇总。Terminal 与对话/Activity 是单个 Agent 内部的交互模式，必须收进该 Agent 的 Message Tool 区域；切换不应占用工作区顶栏，也不能改变 Session、Tab 或 Region 的生命周期。切换控件要和消息工具同一套命中区、焦点、禁用和窄栏规则。

### Fork / Resume 的工作面归属与 Message Tools 编辑器

- Fork 出来的 Agent 仍属于它自己的 Session/Tab/Region 映射。之后从旧 Session resume、打开 Browser 或创建新 Tab 时，目标必须由被操作的 Session 上下文解析出所属 Workspace、Tab、Region 和插入位置；不能使用当前鼠标焦点、最近全局焦点或“旧 Agent 右侧”作为隐式落点。
- 如果目标 Session 已不可定位，界面必须显示明确的恢复/选择目标动作；不能悄悄把内容挂到另一个 Agent 的 Region，也不能因为焦点切换而改变目标归属。创建后的新 Tab 必须能从 UI 直接确认它属于哪个 Session。
- Message Tools 的编辑区在单行状态下输入增长时自动扩展为多行，保留左右工具、Agent 身份和发送动作的稳定命中区；中间编辑区占据剩余宽度并从左侧开始阅读，不得把长文本压成居中的窄列或只露一条细线。达到上限后才滚动，回删后可以恢复单行。

## 持续推进

### 内置任务持续推进（AFTERTIME 使用需求）

- 用户开启一次「持续推进」后，不应因 Agent 阶段总结、关闭观察面板或正常结束一轮而丢失配置；默认每 30 分钟检查，可修改间隔与续行提示。目标必须显示并绑定精确 Host、Session、Provider 与 workspace，Run 是可替换的执行实例。
- 续行提示与其他输入表面遵守同一组字保护：中文候选未确认时，循环观察或其他界面更新不能覆盖输入法预览；结束后保留用户实际确认的文本。输入占用观察只读原草稿、队列与在途事实，不追加、替换或写回用户草稿；只读观察不能被当成另一个草稿写入者。
- 整理展开设置的编排不改变原目标、分钟值、续行提示、来源绑定或草稿/队列；开合不启动、停止或重绑循环。表单标签与原输入控件保持对应，键盘与组字沿原 owner；正常和窄分屏的控件语言只定义在密度 SSOT[《持续推进观察界面》](../presentation/conversation-input.md#持续推进观察界面)。
- 调度状态、Agent 执行状态、业务任务状态分别保留。调度不能批准权限、绕过问题、隐式 resume、改变权限策略或修改业务完成状态。检查失败只暂停自动续行并说明原因，不阻断健康 Agent 的人工使用。
- 到期遇忙跳过，不堆积消息，不在忙转闲时额外补发。只有正常一轮结束、输入就绪且仍有可推进工作时才能续行；立即检查遵循相同规则。working 活动证据过期显示未知并提示检查，不猜空闲或强杀重启。
- 权限或用户问题等待时不发送，并能定位原请求。用户中断/停止应暂停循环，恢复循环须明确操作；暂停循环与中断 Agent 是两个动作。无法分辨正常 Stop 与用户中断时，不宣称可以安全自动续行。
- 每次检查有 tickId；同一 Run 的同一就绪信号最多提交一次。提交边界必须复核身份、就绪信号、执行状态和用户输入占用，覆盖重复检查、直接 Terminal 输入和未提交的 Composer 草稿。自动续行不得挤掉用户输入；缺少证据时暂停自动投递并说明。
- 自动续行只消费精确目标的现有草稿/人工队列占用；观察缺席、取消或退出仅暂停循环并说明，不阻断人工使用。新自动认领须由同 Run 的真实 Native 输入栅栏确认，未知不能补零；旧未知操作仍按原完整请求调和。人工取消在认领前到达才撤销自动候选，已认领字节不能撤回；Renderer 观察与 Core 认领不宣称分布式原子。
- 决定发送、Host 接受、Provider 消费/新一轮开始分别记录，不能观察时标 unknown。结果未知不自动重发；检查与最小回执持久保存，界面重载不得造成双发。
- 应用退出或休眠期间不承诺调度；恢复后仅重新检查一次，不集中补发漏掉的周期。配置不依赖模型内部 Cron、调用者 shell 环境、临时终端或 UI 定时器。同一精确目标至多一个活动循环；接管内部 /loop 时提示用户停用旧循环，不声称可以自动检测和删除它。
- 可选绑定 Feature Tracker 等只读任务来源。无绑定时可设置截止时间/触发上限，只称定时续行，不能证明业务完成。Tracker 全部 Task done 但未 closeout 仍未完成；closeout 是待推进工作。archived 表示完成，discarded/transferred 表示终止或转交，不能都显示业务成功。依赖阻塞与任务来源不可读必须分别说明。
- 任务来源由用户显式绑定 root、Feature ID 和公开脚本；每次仅核一项公开 owner receipt，不重算 Task frontier。全部 Task done 待收口只暂停并说明，归档才可称业务完成；终止、转交、不可读不冒充成功。来源检查不改变旧未知输入操作，人工输入保持可用。
- 无可运行项时展示阻塞原因，不空发相同提示。空转提醒必须有任务适配器声明的进展证据；token、输出量、一次测试通过不能单独证明完成。
- 暂不包含自动批准权限、多 Agent DAG、模型切换、部署或成本优化。现有 Core 输入与生命周期 API 是唯一执行边界，续行策略由 Host 持有，不下沉到 ctxmux。
- 观察界面见 [Surface density](../presentation/conversation-input.md#持续推进观察界面)。评估与验收建议沿[测试策略](../../testing/strategy.md#任务验收与假绿防护)，实际候选与未覆盖范围留本机证据。

### 持续推进与邮箱共享入口

用户要求：「现在看看 Continuous progress 是不是应该放到 mailbox 旁边或者里头去，这里好好设计，更新需求并优化」。持续推进收进当前 Session 邮箱浮层的独立 `Progress` 页，复用一个常驻入口，不在已经拥挤的输入操作组里再加按钮，也不保留 Composer 下方的独立持续推进行。Inbox、Outbox、System 仍分别表达来信、发件和系统告示；Progress 表达自动续行配置与控制，不是一类邮件。

- 邮箱入口的 Inbox 数字与 Notices 提示沿[《入口提示的清楚含义》](#入口提示的清楚含义)；持续推进的未启用、active、paused、unknown 用另一种可辨认状态标识与完整 tooltip/可访问名称表达；循环状态不计入未读、消息数量或投递成功，也不以 Agent 正在执行冒充循环正在启用。观察未确认时保持未知。用户不打开浮层也能辨认是否有自动续行及其当前状态。
- 打开仍沿既有未读与发件优先级选择邮件页；Progress 由用户明确选择。新消息、循环事件与观察结果不强制换页。选择 Progress 不把尚未看过的 Inbox/System 标为已读，也不改变队列投递状态。
- Progress 页有明确的持续推进标题、精确目标与原有配置和操作。浮层开合、邮件/Progress 切换与 Composer 三态切换都不丢未提交的分钟值、续行提示、来源字段或组字中的内容，不启动、停止、重绑循环，也不重复建立观察订阅；迟到结果仍只属于原精确目标。切换 Session 后不能把旧表单或循环状态带到新目标。
- 原启用、暂停、恢复、停止循环、立即检查与任务来源能力继续走已有 owner；停止循环不等于中断 Agent。未知或失败在入口保留可辨状态，详情可读原因与恢复动作，人工终端输入和 Composer 草稿仍可用。键盘可到达各页、操作和关闭入口，关闭后回到同一触发控件；打开浮层不改变原 Tab、Region、Run 或终端实例。

用户进一步要求：「Progress 里头的设计太难看了，重新设计吧，要现代化一点，至少有『设置』界面的水准吧」。该页先让用户配置自动续行或理解当前循环，再查看具体决定和目标；设置编辑、运行控制与最近决定各有明确对象，不以长标识、说明全文或无标签图标占据同一层。视觉与控件质量只定义在密度合同同名小节。

- 未启用时周期及分钟单位、续行提示、可选只读任务来源与明确启用动作完整可达；来源绑定后才展开原三个字段。启用后原周期、续行提示和来源仍可完整读取，属于已保存的只读配置，不增编辑接口或把再次启用冒充保存。精确 Host、Session、Provider、workspace 在同面可发现的目标详情中完整保留；概要不代替真实绑定。
- 当前循环状态与 Agent 执行状态分别有标签，next check 和最近检查／决定只消费已有时间与原事实。观察未确认或错误优先明确说明；仍保留的已知循环事实标为上次已知，不能同时暗示 active 已确认或承诺下次自动发送。paused／stopped／unconfirmed 不显示有效倒计时；缺少时间／决定不补造记录，不新增事件历史或业务成功结论。Host 接受而新一轮未确认仍沿原语言。
- Pause／Resume、立即检查、停止自动续行都有可辨文字及准确可访问名称，保持现有可用条件和一次原目标调用；停止自动续行不停止 Agent。完整失败原因与人工输入可用说明同面可读，不因改版新增输入禁用。目标、配置／来源详情和页切换不得卸载原表单或重建其观察，组字、未提交字段、迟到结果与原草稿／队列边界保持。

页面、标签与状态标识的密度只定义在 surface-density[《持续推进观察界面》](../presentation/conversation-input.md#持续推进观察界面)；邮件自身的已读、未读与投递约束仍见[《Message Tools 邮箱》](../presentation/conversation-input.md#message-tools-邮箱)。
