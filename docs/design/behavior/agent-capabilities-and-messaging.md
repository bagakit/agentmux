## AgentMux 消息与分享格式

可读信封、业务标记、内容分享外框与对象链接的唯一格式合同见 [amux 可读协议](../../specs/amux-protocol.md)。本页持有注入上下文、Agent 语义身份与通用输入能力；A2A 的参与者、投递、协作与授权语义归[A2A 行为合同](a2a-collaboration.md)；空间导航、恢复和快捷回复仍由各自原行为 owner 定义，格式表不再在行为文档重复维护。

实际生成与共同阅读见[对话架构](../../architecture/conversation.md#可读信封与原输入)。可读声明不改变 Provider 消息角色，不认证来源，也不触发运行操作。

## AgentMux 注入上下文

原《AgentMux 对 Agent 说的话》中平台自身生成的内容在此统一为注入上下文规范；跨 Session 通信继续由原 A2A owner 定义。

**AgentMux 注入上下文（AgentMux Injected Context）**指 AgentMux 自身生成、通过 User message 送给 Agent 的内容，用来明确平台说明与原请求的边界。这是内容归属，不改变 Provider 的消息角色，不另造运行时协议。外部 Skill 或作者声明包、Provider 原生注入、A2A 结构化记录及 RPC 回执不属于此规范；它们沿各自 owner，不能因正文看起来相似而合并。

- **用途与投递形式分别表达。** 启动引导、运行上下文和提醒是用途；独立发送、附加在原请求前是投递形式。同一用途不只限首条或独立发送，同一形式也不代表用途、触发频率或优先级。提醒列为用途不证明已有周期调度；默认与本次选择、未确认语义仍见[《System Reminder 的默认与单次选择》](conversation-input.md#system-reminder-的默认与单次选择)。本规范不新增独立持续提醒、开关或调度功能；已有自动推进只按下文在原发送时刻附带共享消息规则。
- **共享行为规则按职责单处定义。** 启动引导、运行时提醒与随请求附带的上下文按需复用同一职责 owner 的规则，不在各入口复制维护多份正文，避免语义漂移。这里只确定内容归属与复用边界，不新增规则注册表、配置层或调度设计。
- **平台说明与原请求由 producer 分开提交。** 包装与编码只见 [amux 平台说明格式](../../specs/amux-protocol.md#平台说明)。原始用户或发起 Agent 的正文保持独立且逐字节不被包装改写；普通用户 prompt 无需因此包裹。A2A、continue、reaction 沿协议导航中各自的业务 owner，不与平台通用说明混同；跨 Session 作者核验继续归原 A2A owner。
- **平台内容与原请求通过同一 Core 通路分开提交。** 启动和既有会话都由实际 producer 显式交出平台内容与原请求，Core 统一生成实际输入并沿既有记录分别保留平台内容与原正文；客户端不先拼混合信封再要求 Core 从标签恢复归属。原内容与格式化后的输入各有明确边界，普通正文、用户复制或编辑后的内容不能自称为受信平台记录。公开通路沿既有 Host、权限及 A2A 作者边界，不新增信任模型、规则 Store 或消息账本。
- **组合与读取必须解释同一边界。** 独立发送可以只有完整平台上下文；附加发送时上下文在原请求前，多个完整前导上下文按实际组装顺序保留。生成、实际输入、阅读展开与完整 Copy 必须一致，真实尾文不能被吞掉或补造；平台内容中的尖括号、实体或标记不能破坏包装边界或改变内容。本项定义一致性结果，不把尚未修复的生成与读取失配写成已满足。原记录内的阅读、引用与代码边界以及完整复制只见[《完整前导声明上下文的同记录阅读》](terminal-reading.md#terminal-连续向上阅读历史)。
- **文本声明不是已核来源。** `<amux>` 或 A2A 的 `from` 均可被用户、Agent 或其他输入伪造，不是认证、权限或信任凭据。平台归属来自实际 producer 与受信提交记录，不能从标签、首条位置、时间或旧混合正文反推 System。平台注入、Topic/Wiki 等历史内容也不能覆盖当前用户指令、权限或权威 Runtime、Session、Run、Project、Task 事实。声明阅读不创建消息或身份台账，不改变原作者、parts、顺序或 recorded time；未识别、不完整或含糊的声明保持全文可读，不扫描正文猜来源。
- **业务上下文与用户审批正文分开。** Goal/PMO 和 Goals 探索生成的职责、项目及执行上下文通过同一平台通路附带，用户选择或填写的请求保留原正文；平台说明引用的 Goal 描述、项目文字或外部内容不因此获得权限或当前事实资格。Browser 元素／批注分享仍沿[《寻址与复制》](public-control.md#对象地址分享与方向)的共用分享外框进入可编辑草稿，由用户审批后作为其正文提交；不解析分享外框或编辑后的 amux 文本来补造平台来源，也不因此自动发送。
- **Progress 保留用户 prompt，平台提醒复用共享消息规则。** 自动推进仍按原条件与原发送时刻提交用户配置的 continuation prompt，逐字节保留为用户正文；同次附带的消息使用要求来自上述共享职责 owner，作为平台内容走同一通路，不在自动推进入口复制规则。没有新周期、开关或独立 Reminder 任务；用户输入、草稿、暂停、停止及原 completion／input fence 继续决定是否发送，不因附带说明放宽资格。
- **组合内容跟随原投递身份恢复。** 同一 operation 的平台内容、原正文、来源分界和实际输入沿首次准入后的原冻结意图续做，重试或冷恢复不根据变化后的 Goal、规则正文或当前 Run 重组输入，也不重新发送未知正文。即使实际输入字节相同，后一次调用也不能将原用户正文重新声明成平台内容；无法确认原来源分界时保留未知，不从 wire 反推。新的内容冲突不能冒充原操作继续；保存、Native Input 接受、Provider 消费和阅读记录各自按原 receipt 表达，平台记录缺失或保存失败不能反推未投递或另建第二份消息。
- **注入失败不阻断健康 Agent。** 保存或投递未确认沿原 receipt 与服务窗如实说明，不假报送达、不自动重发，不取消已有可用输入、启动或健康 Run。阅读识别失败不等于未投递；本规范不增加恢复前置门，不改原 Session、布局、阅读位置或草稿。字节层的 bracketed paste 继续负责终端输入定界，不替代这层内容归属。

当前 producer、提交与发现接线见[注入上下文机制](../../architecture/conversation.md#注入上下文与发现入口)，本页不另存实现状态表。独立 System Reminder 的正文、触发和兑现范围仍未定，沿[原 Reminder owner](conversation-input.md#system-reminder-的默认与单次选择)阅读，不由 Progress 的既有随信规则代签。

## 启动握手与自命名

- **Agent 启动时应当先认识自己所处的环境**。先通过原 `whoami` 取得本次准确 Host、Session、Run、资源 Workspace 与可用能力，并区分执行目录和展示位置；沿[自身位置与邻居发现](spaces-and-layout.md#agent-的自身位置与邻居发现)认识准确 Space／Zone／Tab／Region 及其绑定，知道怎样按需查询同 Tab 邻居。启动引导给出必要的空间意识与发现入口，完整布局和邻居内容在相关任务需要时读取，不把全局布局塞入每次启动。已知任务域直接加载对应模块，不知道能力归属时才从基础 skill 查目录。身份或空间观察缺失保持未知；身份握手与模块读取不启动其他 Agent 或提交任务，也不是健康 Agent 的输入许可闸。
- **握手要一次问答就够，且不与 skill 争夺唯一真相**。返回坐标与能力清单，而不把完整 CLI 语法抄进提示（与上文同源：抄进去会在语法演进时立刻过期）。验收沿用同一条行为断言口径——证明启动路径确实携带并执行了握手，而不是断言提示文本里含某个字符串。
- **身份事实与操作手册分开。** `whoami` 保留原 Session、状态、View 与不可用事实，不携带静态通信规则或文件域提示；通信规则由对应模块及当次消息提醒披露，Topic 发现归原文件／Topic 模块。收窄说明文字不能压扁 unknown、缺 View 与观测失败的区别，也不改变准确原身份、权限或恢复事实。
- **启动只披露最早需要的共同边界。** 简短引导给出身份读取、按任务查模块、原生协作与独立 Session 的区别、授权边界及未知操作不自动重放；开启工作面和 Browser 的细节在动作前按对应模块读取。启动、恢复和提醒按用途引用同一职责来源，不要求先读全部基础目录、通信、布局或恢复手册。
- **先说明本次阶段，再披露后续细则。** 平台生成的引导先让 Agent 辨认本次职责、当前业务请求或等待状态、准确 source 与第一步；业务等待不延后原只读身份初始化，恢复仍可依赖原历史，不为自包含而重发旧任务。协作选择只在任务确需协作时展开，不让通用能力路线遮住当前动作；后续阶段的详细规则按[渐进加载](public-control.md#基础-skill模块发现与渐进加载)读取，不删除本次正在适用的身份、授权、恢复和回报义务。
- 启动引导应提前指出协作和开启工作面有多种用法，指向[协作执行机制与下属关系](a2a-collaboration.md#协作执行机制与下属关系)和[开启工作面的意图与落点](spaces-and-layout.md#开启工作面的意图与落点)。具体选择偏好放在现有 skill 的建议级 playbook 中，不另造强制默认或运行时策略，确切语法仍由原能力发现入口持有。
- **理解任务后尽早为自己提出任务名。** 启动引导用一句话指向 `name --skill`；Agent 在前几轮理解目标与自身职责后，为自己的准确 Session 提出简短的派生显示名。第一条请求已明确时即可命名；尚不明确时先澄清，不用固定轮数倒计时，不单独注入催促。名称描述实际任务与阶段，不把计划写成完成状态。
- **自命名沿原名称 owner 与用户意图。** 通过既有 `agent.inspect` 读取准确对象的名称来源和 revision，再用 `agent.rename --derived` 提交；优先级和持久事实沿[《显示名与身份》](spaces-and-layout.md#显示名与身份)，不覆盖用户手改、手动清除、启动指定或来源未知的保留名称。只修改自己的 Session，Tab 沿原派生策略展示，不因命名操作其他工作面或改变执行身份、cwd、Run 与授权。
- **命名不制造额外工作循环。** 默认只在理解任务时命名一次，任务实质转换后才考虑细化；名称受保护、能力不可用或操作失败时继续主任务，不反复改名、催问或发送无进展消息。未知写入沿原 operation 与 revision 核对，不换身份重放；读取说明、提交名称、持久确认与模型实际采用分别表达，不承诺每个 Agent 都会采用。

- **岗位与 Goal 职责可发现**。有准确 Goal/委派或管理岗位的实际请求须携带原身份、必要责任及 Goal 模块必读入口；执行者知道绑定、进展/阻塞/交付回报，管理者知道核查回收、状态流转与停滞巡查。规则唯一见[执行责任、停滞告警与 PMO 巡查](goals-and-demand.md#执行责任停滞告警与-pmo-巡查)，默认上岗手册和注入 prompt 引用同源模块，不复制完整合同或改变原授权。
- **渐进加载保实际来源**。基本 skill 的模块目录和只读模块读取沿[基础 skill、模块发现与渐进加载](public-control.md#基础-skill模块发现与渐进加载)。新启动、明确复用的 Goal 讨论和原生接续分别保本次实际输入/已读资料来源；更新手册不假称热更新 live 上下文，不覆盖用户 SOUL/Wiki，不把读取回执当作模型采用证明。

## Agent 已经这样多久了

- 用户需要知道“这个 Agent 已经这样多久了”：干了多久、等我多久、完成后闲置多久。Activity 明细采用 Core 已确认的当前语义状态起点；最后一次观察不等于状态起点，重复同状态的观察不得重置时长。
- 已确认的工作状态显示持续时长，并保留真实上下文压力；等待、完成和语义错误也各显示对应状态的持续时长。起点缺失、已失效、无法确认、来源不符或当前状态已衰减时，明确显示起点未知；进程活着、退出或断开本身不能证明空闲从何时开始。
- 完整 Session 更新必须忠实表达已有语义事实的新增和清除，包括观察时刻未变而旧起点已被清除的情况。时长不改变状态新鲜度、断开状态或输入可用性，不为显示时长生成第二份起点。
- 单 Agent 工作线在现有摘要行直接展示状态时长和上下文，不要求用户展开一张不能展开的列表。只有完成态 Agent 的项目仍保留 Activity 的紧凑入口，用户可以查看完成后的闲置时长；完成数量不升级为待处理告警。
- 静默等待的时长在打开且可见的 Activity 菜单中继续前进，关闭或窗口不可见后停止显示刷新；菜单内所有 Agent 使用同一时刻，不为每个 Agent 启动常驻计时或 Runtime 轮询。
- 注意力跳转保留现有“最早观察到待办”的顺序；该顺序不冒称等待最久。状态持续时长与最后活动时刻分开表达。
- 新状态观察到达时，时长必须使用该次实际渲染的当前时间；不能因菜单的秒钟还停在上一拍，把有效起点闪成未知。未来或不可信的来源时刻仍如实拒绝。

## Agent 当前阶段与动作的可见表达

Agent 的状态和动作应可具象辨认：原身份旁显示当前有依据的阶段或动作，具体工作面提供就近反馈，已经发生的过程仍归原 trace。动作提示不创建新的执行、身份、权限或完成事实；本节定义行为要求，不声明所有 Provider 已具备实时细分阶段能力。

- **当前必须有当前来源。** 阶段绑定准确 Host、AgentSession、当前 Run 及协议实际给出的 turn／operation／tool 身份，由原 Core／Provider 或工作面 owner 提供。新鲜度、边界与失效沿其原合同；旧 Run、旧轮、历史 reasoning／tool part、最后一条文字或终端外观不能证明现在仍在做这件事。Provider 的当前阶段缺失或未知时明确缺失，不由客户端命名补齐，也不因此关闭健康 Agent。
- **处理不等于思考。** 只有 Provider 原生协议明确给出当前 reasoning 阶段及其准确主体和起止时，才表达“思考中”。只确认 working 时使用“正在处理”等原有通用语义；进程 running 不冒 working，工作状态未确认不冒任一种细分阶段。气泡只表达短状态，不生成、推测或概述隐藏推理。已记录 reasoning 的阅读、空／遮蔽与完整复制仍归[原生过程阅读](conversation-mode.md#共同阅读组件与完整原生内容)，不从历史内容反推实时思考。
- **动作沿真实派发与回执。** 读取、脚本执行、协议／工具调用、点击、输入、滚动、导航、等待和需要本人分别消费各自 owner 的准确事件与结果。通用层不能用展示名称或工具名正则猜业务动作；Provider 在自己的原生协议边界解释工具语义，语义不足保持通用工具调用。Browser 的 raw CDP 是协议／工具调用，不一律叫脚本；生成脚本、snapshot、read 与 wait 不冒执行脚本，输入反馈不披露值、秘密或代码参数。
- **并发与结果各守原对象。** 同时动作保留真实并发身份，不把到达顺序画成唯一串行进度；当前工作面的准确目标不因其他动作更新而换对象、抢焦点或覆盖输入。某步完成、工具返回、整轮结束和业务任务完成分别表达，不能用一个成功图形互相代签。没有确证结束或观察来源失效时保持未知／上次已知，不能因为气泡收起而把操作判完成。
- **只投影原能力。** 客户端、RPC／CLI 与工具消费同一公共状态和动作事实，不在各处新增检测器、事实 Store、轮询或全历史读取来维持拟人反馈。来源缺失只降低相应细节，保原身份、草稿、可用输入及恢复路径；有限动态和就地布局由[同主题呈现](../presentation/agent-capabilities-and-messaging.md#头像旁的阶段与动作提示)持有。

## Provider Launch Option

- Provider 以数据形式声明自己可供选择的启动项（例如 model、权限或沙箱模式）。每个 choice 把 UI 展示的标签与兑现它的 argv 写在同一处，两者不可能漂移。
- 契约分成两半：describe 半边是纯数据，跨 IPC 供 Renderer 渲染；argv 半边只留在 Core。**Renderer 永远看不到命令行**，Launcher 也永远不知道 Provider 的名字——任何调用点都不得按 `providerId` 分支决定启动项。
- 未声明即不渲染。Provider 落地速度不同是常态，没有声明的启动项在界面上完全不出现，而不是显示一个禁用控件。给某个 Provider 后补一项能力，不需要改动 Renderer 任何一行。
- 作用域是**启动时**，这不是过渡方案而是运行时的全部事实：Agent 是经 PTY 驱动的真实 CLI 进程，当前没有 Provider 走 ACP，不存在能让运行中进程改换 model 的通道。把选择编码进 spawn 时的 argv 是运行时唯一能兑现的形式，类型系统据实表达这一点，不得用暗示"运行中可切换"的控件掩盖它。将来某个 Provider 具备 ACP 后，实时能力作为**并列**的另一项能力加入，启动时这一条不被拆除。
- 只声明对着真实二进制核实过的 flag。核实不了的一律不声明——这正是部分 Provider 目前不提供任何启动项的原因。核实的对象是 Provider 真正的可执行文件（如 cursor 是 `cursor-agent` 而非 `cursor`），拿错二进制核实等于没核实。
- **不声明自由字符串 model**。gemini / grok / traex / hermes / antigravity 以及 codex / cursor 的 `--model` 都收任意字符串、无枚举，手写一张模型名清单会在厂商改动阵容时立刻过期，故一律不声明、依"未声明即不渲染"保持无按钮，绝不为对称而编造一张会过期的清单；只有当 CLI 自身 `--help` 给出可声明的取值才声明，且据实区分它给取值的两种方式——claude 的 `--model` 是**例举式**（`--help` 以 e.g. 举出 fable / opus / sonnet，并非严格 possible-values），我们只把这组指向"最新模型"的**稳定别名**据实声明（它同时也接受模型全名，但**全名不声明**，出自同一条会过期的理由），措辞按"稳定别名"表述、绝不写成一份穷举清单；claude 的 `--effort` 则是**严格 possible-values 枚举** low / medium / high / xhigh / max。核实到的是**枚举**才落一个选项：gemini `--approval-mode`、grok/claude/traex `--permission-mode`、codex/traex `--sandbox` 都是显式 possible-values；hermes `--yolo`、antigravity `--sandbox` 是布尔开关，落成两档 choice（保守档贡献空 argv，激进档贡献 flag）。每档 tier 据实标注：绕过审批或沙箱为 `danger`，收窄一类为 `caution`，保守默认为 `safe`（agy 的 `--sandbox` 是**加**限制，故开启档才是 `safe`，无沙箱的默认档为 `caution`）。
- **model 与 effort 不带 tier**。claude 的 model 与 effort 是仅有的两处按**能力**（而非权限）据实声明的启动项。RiskTier 分级的是审批/沙箱姿态的危险程度，而选模型或选推理深度既不放宽也不收紧任何权限——给它标一档 tier，会在名册行上打出一个无人记录过的假风险标记。claude 的启动项里只有 permission-mode 真正移动权限姿态，故只有它带 tier。
- Permission option 是并列的一套按 Provider 声明（见 `packages/core/src/agent-interaction.ts` 的 `TerminalPermissionOption`）：与 launch option 同构地拆成 describe/contribute 两半——DESCRIBE 半边（id/label/kind/description/tier）跨 IPC，CONTRIBUTE 半边（回答提示的 PTY 按键 `input`）只留在 Core，于 reply 时解析。两者的区别在于作用时机：launch option 作用在 spawn 的 argv，permission option 作用在运行中 Provider 自己的编号提示上；同样只声明位置稳定、对真实 CLI 核实过的行。
- Posture control 是第三套并列声明（见 `packages/core/src/agent-interaction.ts` 的 `PostureControlDeclaration` 与 `createPostureControl`），是 Composer 上"这些权限设置也要能在聊天框上设"这一诉求唯一诚实的兑现方式。它专治运行时的 live 权限姿态：与 permission option 同处 Provider 的 interaction protocol 声明，同样拆成 DESCRIBE 半边（`AgentPostureControl`：control 的 id/label + 每个 mode 的 id/label/description/tier）跨 IPC，CONTRIBUTE 半边（每个 mode 的 in-band 按键 `input`）只留在 Core，由 `planPostureSet(modeId)` 在 set 时解析、经既有 PTY-input 通道（`setAgentPosture` → `writeAgentInput`）写入。诚实性由结构强制：一个 posture control **必须**声明 ≥2 个 mode，每个 mode 的按键**非空且互异**——因此一个只有盲态 Shift+Tab cycle（一枚按键在读不到的状态间轮转）的 Provider 结构上无法被表达成 set-mode 控件，绝不会伪装成"切到 mode X"。**盲发按键是真实风险，故只声明效果确定、可寻址的控件**：仅当存在能指名目标态的 slash 命令时才声明。据此对着真实二进制复核后，只有 grok 合格——它的 `/always-approve [on|off]`（clap ValueEnum 核实）给出 Ask / Auto-approve 两个各由独立 slash 命令 SET 的具名 mode；claude、gemini、codex 只有盲态 cycle（codex 另有无法盲导航的 `/approvals` 弹窗），一律不声明，Composer 对它们不画任何控件（未声明即不渲染）。控件是 fire-and-forget 的 SET，不是有状态开关：Composer 从不标记"当前 mode"，因为 live 姿态活在读不到的 CLI TUI 里，标一个 active mode 就是谎称掌握了它——菜单只提供可寻址的目标态，当前落点归 CLI 自己。

## Provider 能力对齐与移植边界

- 用户要求「很多 Provider 的实现不完整」，全面分析后对照最新参考实现逐家完善，尤其是 Agent 的 Session 分析、对话模式与 trace 观察。每个 Provider 的能力闭环必须分别可验证：原生 Session 身份与记录解析、完整对话与资源顺序、工具与推理等观察事实、恢复与交互能力不能只凭启动成功或 Hook 存在宣称完成。已有参考实现的能力应核验并复用；缺少协议依据时如实保留未知或不支持，不能把观察缺口变成健康 Agent 的阻断。完善任务按 Provider 分开验收，共享协议与展示只有一个 owner。
- 用户进一步要求「实现达到成熟产品级别，且交互体验和性能远超竞品，所有功能你自己也要测试后满意」。Provider 完善必须经实际使用链与独立复核验收，覆盖真实身份接入、重启后原 Session 与工作面、对话阅读、trace 展开与完整复制；测试通过不替代交互验收。阅读与刷新只处理目标 Session 的有界记录，不因其他健康会话增加扫描或轮询工作。竞品比较须在相同输入、数据规模与观测条件下有实测证据，不能将结构更简单或合成测试更快直接称为领先。终端连续阅读及成本底线仍以[《Terminal 连续向上阅读历史》](terminal-reading.md#terminal-连续向上阅读历史)为唯一合同。
- 外部对照只提供对照证据，不是 AgentMux 的第二份 Provider 注册表。每个 AgentMux Provider 必须以真实可执行文件与真实运行回执为准，分别声明 launch、ready、Hook、permission、status、resume 与 reply-correlation 能力；未核实的能力保持未声明，不用 UI 对称性或终端字节推断补齐。
- Executor 的启动包装不改变 Provider 的语义归属。对应 Provider 解释真实执行链、原生配置与可用协议通道，Host、Desktop 和通用输入层不按包装名称或另抄一份参数名单判断原生能力；已确认同一原生协议与等价启动时，不能只因包装形式不同丢失能力。适配优先复用原生主体已解析的配置与真实通道，不能近似重建参数而改变权限、信任、认证、网络、工作目录或恢复语义；真实差异和未确认范围分别说明，`providerId` 相同本身不证明通道存在或本次操作已获授权。
- 可执行文件检查使用这次 Provider 最终启动计划的 command、执行环境和 Workspace；发现列表没有 Workspace 时不猜相对路径。文件确证缺失与检查失败分别呈现：准确命令的文件观察失败不能单独封闭已授权的 Native 启动或原身份恢复，由原 Runtime 执行给出结果，并保留失败步骤、当前 Run 与重查动作的非阻塞服务窗。`installed` 不因允许执行尝试而改为 true；Provider 未贡献准确文件观察、真实不支持、身份或授权不足仍守本次操作合同。GUI、Doctor 与公开 API／RPC／CLI 复用同一探测事实；公开发现输入不泄露环境正文，未知启动回执不重放。
- 现有 Provider 的 parity 工作按能力闭环推进：Grok 与 Gemini 若二进制支持 native resume，就必须同时接通可信 native handle、resume argv、managed Hook 与事件字段归一化；Pi 的 resume 与扩展部署是两件事，不能只做 locator；Claude、Hermes、Cursor 的事件/信任细节分别按各自 CLI 合同接入。Cursor 没有 native resume 时必须明确保持 unsupported，不伪造恢复入口。
- Hook 入口同时接受厂商的 camelCase 与 snake_case 字段，但在 Core 内收敛到同一 canonical event；`sessionId` 等 provider-native handle 只能由对应 Provider 解释，不能由 ctxmux 或 Desktop 猜测。流程探测或 Hook 安装失败属于非阻断降级，必须在服务窗说明当前状态与恢复动作。
- 尚未纳入的 Agent 分成三类：具备完整 Hook/session/resume 证据的优先纳入；只有 status/Hook 的按实际需要纳入；只有 launch 配置或宿主专属 wrapper 的明确记录为暂不纳入。**同名不等于同身份**：TraeX (`traex`) 与 Trae CLI (`traecli`) 是两个不同 Provider，二进制与合同都不同，不得合并身份。
- 所有 Provider、Agent Session、Hook 与 semantic resume 逻辑归 `packages/core`；ctxmux 只持有 Run、PTY、ordered bytes、Replay、Gap、Attachment 与进程事实。Provider parity 不得在 ctxmux 复制第二套实现。
- 原生会话切换后，旧会话晚到的 Hook 只能保留为原始观察，不能覆盖当前会话身份、状态、用量、交互或工具记录。当前已知 native handle 与真实协议中的转换引用共同决定归属；缺少引用时不能按到达顺序、时间或正文猜。真实 native ID 已知而新记录文件尚未落盘时，身份与可恢复性分别表达，不能沿用旧会话的路径或阻断同一健康 Run 的普通输入。已核子任务对主轮的聚合结束语义保留；没有真实 turn 身份时，同会话旧轮与 ABA 仍明确未知，不伪造完成。
- 原生 reasoning 的空文本、缺失文本与被遮蔽文本要分清：合法空记录仍可查看，未知结构原样保留，不能借别家字段补正文。协议确有的 opaque signature 与 redacted 事实沿公共内容记录保全，不当可读正文或混入普通消息复制；只有可读复制内容时才提供 Copy，空或仅遮蔽的记录仍能展开，不能通过复制空字符串清空用户剪贴板。对话与历史仍复用原有 trace 折叠，工具结果只有图像时也保留真实调用关联与失败事实。

原生对话内容和身份确认不得以 Hook 送达为前提；公开说明、正式回答、工具及思考沿 Provider 原生记录读取，Hook 只可提供刷新线索。健康 active Agent 缺少已记录的原生身份时，可由对应 Provider 基于同 Host、同一当前 Run 的可信只读进程及开放记录事实确认唯一主会话；不得按 cwd、正文、时间、目录位置或子会话猜身份。确认结果保存在现有原生身份中，旧 Run 的迟到结果、并发不同身份与含糊事实不覆盖当前绑定。已有权威原生身份的读取仍不依赖 Runtime；身份确认、保存或读取失败保留原工作面、已读内容和健康输入，明确失败步骤及恢复动作，不新增另一份 Runtime、来源台账、历史 reader 或轮询。

当前健康运行会话的原生来源与已保存的历史来源分别核验；已有原生句柄不证明它仍是当前 CLI 的主会话。获取当前观察或明确刷新当前来源时，Core 可基于同 Host、同一当前 Run 的可信 Provider 事实有界核对并在原身份中原子确认唯一当前源；普通同源读页和历史分页不因此反复探测进程。观察资源存活期间，已确认但尚未保存成功的当前来源与其见证沿这份既有资源供同身份读页复用，不能让观察与正文退回不同来源，资源释放后不称耐久事实。统一窗口的来源范围、页、切点和观察共同消费该资源的准确来源；已有固定来源的窗口不得将另一来源的观察宣称为原窗口的健康观察，差异须明确说明并保留原文与准确重读路径。缺少当前事实、含糊来源或预算失败保留可读原记录、工作面与健康输入，明确核对步骤和重试动作，不把旧记录空页当成没有回复；确切 Host、Run、进程、原记录或并发绑定发生冲突时拒绝该次错误重绑定。离线、退役与 Runtime 暂不可用时，已保存来源仍沿原只读历史能力读取。真实来源改变不混用旧游标、身份或正文，不增加另一份来源台账、历史 Reader 或轮询。

原生对话读取必须持续采用 Provider 已记录的新输入，不能在过程窗口达到保留上限后永久停更；终端、Message Tool 或其他来源的原生输入都沿同一读取 owner，捕获投递记录仍保其独立来源。有分支的原生记录沿 Provider 的准确选中链与原切点解释，物理追加本身不证明分支连续；分支改变保留已接受原窗与旧分页，说明准确边界及取得当前记录的动作，不将废弃分支拼入同一连续对话。过程记录与对话发言分开控制保留，密集工具调用不能把仍在当前对话保留范围内的输入挤掉。保留原记录 ID、来源与实际顺序，重复正文的独立输入不能合并；被淘汰的旧窗口仍从原生 History 的 opaque 分页可达，不把有界窗口冒充完整会话或重建旧 Hook。当前同身份已有正文、选区与草稿在重读失败、覆盖或暂停时保留；隐藏消费者停止新增读取，迟到旧身份结果不得覆盖当前会话。

单条合法原生记录超过一次读取预算时，沿现有 Provider 与原生 History 的同一 owner 提供有界分段或精确资源续读；后续小记录不能因此永久不可达。游标和内容继续绑定原 Host、Session、来源与记录身份，保留原字节、顺序与完整性说明；不静默跳过大记录，不将片段冒充完整正文，也不通过无限扩大整页读取或序列化额度解决。原生角色、侧链与资源含义仍由 Provider 解释，公共 SDK、RPC 与 CLI 消费同一续读合同，不能让客户端自行猜测厂商协议。

原生公开说明的阶段与协作结构只由 Provider 的正式记录解释，并沿同一公共 History item 保全；阶段缺失或未知不从正文、位置或时间猜。公开进度说明与正式回答可区分，但不等同隐藏推理、任务完成或作者认证。原生协作保原步骤 ID、sender／receiver native 引用、操作状态与目标最后已知状态，彼此不替代；native Agent 引用不能冒 AgentMux Session／Run 或当前 Runtime 状态。未知结构和附带内容仍完整可读、可复制，不增加另一套来源、身份 registry、记录缓存或轮询。阶段与协作的共同呈现只见[《可复用对话与 Workflow 表面组件》](conversation-mode.md#可复用对话与-workflow-表面组件)。

## 模型请求失败与工作结果

Provider 必须将原生协议实际暴露的请求与轮结果归一为准确来源的类型化事实（typed outcome），供 Core 状态、公共对话、历史和外部连接器共同消费。同一原生终局只能有一种结果解释；带真实失败的轮结束不能在状态链是失败、在历史或发布链又成为成功。失败不能只留在终端或日志，也不以额外模型请求探测服务容量。

| 事实 | 唯一含义与 owner |
| --- | --- |
| 当前活动 | Core 依据准确 Provider／Runtime 事实形成当前 working、idle 或 unknown 等投影；新活动可更新它。 |
| 原生请求或轮结果 | Provider 解释原记录的主体、范围、结果与失败原因，Core 保留准确关联；这是可引用的历史事实，不随当前活动更新而删除。 |
| 观察或操作诊断 | 原读取、保存、Hook、RPC 或操作 owner 解释失败步骤与原副作用回执；观察失败不证明模型失败，结果未知不证明未执行。 |
| 外部投递结果 | Connector 原 Outbox 持有内容表示、投递操作及平台回执；错误卡发送失败不改写原生结果。 |

原生结果、观察诊断和投递失败可复用呈现原语，但不合并为一个万能错误状态。具体记录身份、公共类型及变化流合同只见[原生请求与轮结果协议](../../specs/conversation-protocol.md#native-request-and-turn-outcomes)。

- 对应 Provider 只解释其声明的原生机器协议，提供同源解码供当前状态、历史页与增量读取复用。Hook 原始名字和负载字段的语义也由准确 Provider 声明，不能从其他 Provider 的同名事件继承生命周期。普通聊天、引用、工具正文、终端文案、颜色或布局不授予失败、完成或重试资格；Core、Runtime、Main、客户端与连接器不复制厂商分类器。
- 公共失败保留稳定的本地分类、可读原因及准确原记录引用；原生错误码、类型、HTTP 状态、请求／attempt、重试提示及模型只保留实际暴露的值。本地分类不冒充原生码，不能依据说明补造字段；未识别原码仍保留，不以白名单静默丢弃。恢复说明只表达适用于原事实的建议，不是执行授权。
- 归属按准确 Host、Session、原生来源与可证明的主体、请求／轮确定；只有原证据确认时才绑定发生时的 Run 或输入。恢复后负责观察的当前 Run 不自动成为旧错误发生的 Run。子 Agent 失败保其主体，不无依据改写主轮；缺少归属的错误仍可读并明确未知，不按正文、时间、相邻记录或最新输入补配。
- 原记录和结果先按其自身身份保留，再独立判断能否更新当前活动。旧来源、旧 Run、旧轮、同批后续新轮及迟到观察不能覆盖当前事实，也不能因失去当前显示资格而丢掉原错误。既有原记录、身份和字节保持可读；缺少类型化结果的旧记录不被删除、改写或猜补。不同来源只有准确同一发生关系才归并，重连与分页不重复制造结果。
- 原生重试中的请求失败、最终请求失败、轮完成、轮中断与进程退出分别表达。重试通知不伪造成最终失败或成功；同请求后续成功按真实关系收敛当前提示，原失败观察仍可读。完成事实不代签用户任务验收，metrics、最终回复样式、普通 Stop、终端字节或观察静默均不独立证明完成。可被否决或追加上下文继续的收尾 Hook 不授予最终 turn-end 或下一次自动操作。
- 原主轮／子轮结果与现有子任务聚合使用唯一原生身份；名称和类型只作描述，缺身份不猜人数，不伪造成功或永久 working。准确原主结果或 Runtime 终局可收敛原聚合，普通终端输入与原身份保持可用。
- 工作面与公共检查入口保留原因、已知码／未知边界和恢复指引；当前恢复正常后服务提示收口，原历史结果仍由[同一对话阅读面](conversation-mode.md#原生请求与轮结果)可达。请求失败、分类失败、读取失败或保存失败均不关闭健康 Run，不删除 Session、Tab、Region、历史或草稿；失败步骤沿原非阻塞服务窗说明。不自动重试输入、换模型、重启或创建替代 Session，尤其不重放结果未知的操作。
- Provider 的能力发现分别说明结果观察与历史读取的实际覆盖；支持、当前不可用与未知不能混用，`complete-events` 不代签全部结果语义。声明必须与注册贡献一致，缺实现不能等到真实用户操作时才被发现为不支持。SDK、JSON-RPC／CLI、对话与连接器消费同一 Core 事实；官方资料覆盖不表示 CLI 暴露全部 API／SDK 字段或产品已通过验收。Focus 的当前结果资格只见[《项目归属、任务状态与恢复》](focus-context.md#项目归属任务状态与恢复)。

## 同一 Run 内的原生会话切换

AgentMux Session 持有一个已确认的原生语义目标；原生前台正在显示或接受键入的对话是另一项事实，只有 Provider 的准确协议依据才能证明两者相同。同 Run 的这份 conversation binding 可以变化；Provider 解释当前、已改变、未知或含糊的原生依据，Core 持有绑定转换、旧语义资格的来源隔离与历史保全，Region 不因此替换 Run。fork 的来源和 ancestry 可作为已有事实的可选元信息，不成为 Client 操作当前会话的前提，也不将公共 Provider 模型提升为原生 Session 树。已存在的单一主来源及当下有效性见证沿原 Provider 接缝复用，子任务观察不另造当前主会话或 Runtime。

在同一 Region 的健康原生 CLI 内新建、fork 或恢复另一原生会话时，AgentMux 必须可靠区分 Provider 原生来源是否改变，不能因 AgentMux Session／Run 未变继续把旧来源的状态、用量、交互或历史当成当前事实。转换依据由 Provider 解释真实当前主主体与原生协议，Core 在原 Session 绑定中持有确认、候选与未知；Client 不按 slash 命令、终端正文、cwd 或到达次序猜身份。无法确认时保留原来源、可读历史、工作面和健康输入，并持续说明未确认步骤及恢复动作。

已确认来源变化或待确认的可信候选须在该 Region 的右上 Agent 信息入口可见，展开能辨原绑定、候选、确认范围及可执行动作。可靠自动确认暂不可成立时，允许以就地提醒和用户明确点击采用准确候选完成切换；人工确认必须绑定当前 Host、AgentMux Session、Run、原来源与本次候选，过期、冲突或未知的那一次操作如实拒绝，不能顺带关闭健康 Agent。读取历史、Refresh、普通 Hook 或恢复握手不隐式替换用户明确选择的 Level B 原生目标；明确选择新源也不能伪称原目标已经恢复。

当 Provider 能核实同一 Run 持有多个主对话，却不能证明前台当前选择时，公开准确候选并允许用户明确采用其中一个语义目标。候选成员和原文件身份在采用时重新核对，顺序、最近活动、读取或附着成功均不代替前台选择。用户采用的依据与自动确认依据分别保留；定向原生输入、目标自身的活动观察和后续语义恢复沿同一个持久目标，前台选择仍保持未知。用户也可继续采用原目标，仅更新确认依据，不丢失原目标的待答请求；这仍是一次新的明确选择，先前在途的另一选择不能覆盖它。后续恢复到同一目标时保留用户选择依据，新 Run 的成员、actor 和输入资格重新核验。默认语义输入始终定向该目标，原生通道无法确认时只拒绝该次投递，不能改为终端键入。自动输入仍要求 Provider 原子执行“仅空闲入队”，不能以较早的完成观察授权打断新一轮。此选择不切换前台，不替代 PTY、菜单、权限答复、readiness 或自动队尾的准确请求、轮次和输入边界，也不改写同 Run 原前台重连的启动目标。

确认新来源不启动、停止或重建原 Run，不改变执行 cwd、空间身份、布局或未发送稿。旧来源的 pending interaction、回答、readiness 和输入资格不能借同一 Run 留到新来源；旧 Hook、观察回调、分页游标与迟到保存不能覆盖新事实。在途及 unknown Input 继续沿原 operation 和真实受据核对，不自动重放或把未知当作未发生；旧记录仍按原来源可读，新源采用自己的窗口和游标。原生 ID 确认与记录可读／持久确认分别表达，候选尚无记录时不能借旧路径拼造可恢复身份。公共确认、发现和回执复用同一 Core owner，GUI 与 Agent 使用同一目标、权限和结果合同。

来源冲突使语义目标尚未确认时，迟到的 transcript 活动不能重新授予当前 working、idle 或自动动作资格；准确旧轮次的结束记录仍按原来源保留，可核对其原权限请求。仅前台选择未知不撤销一个已准确采用且仍有效的语义目标；目标自身的活动与前台位置分别表达。

连续确认保留同一 Session 的原操作回执与来源定位，当前绑定仍只有一个。重复历史 operation 只核对那次已持久确认的结果，并明确它是否仍是当前确认；不会重新切换来源。旧来源的 unknown 权限回答和输入事实仍可检查，不因后续确认被覆盖。默认旧历史入口读取最近一次确认的前来源，更早定位留在原回执中。

## 注意力处理与结果审查闭环

- 用户能以更少操作完成「发现需要我 → 做决定 → 检查结果 → 继续运行」，并保持原来的工作区和 Session 上下文。
- Needs you 的集中入口应能直接显示具体 Session、请求内容和可执行回答；处理后可以继续进入下一项，并能回到原工作面。它复用 Core 的 typed interaction 和已有通知/Session 定位，不建立第二套 Inbox 或 Session Registry。
- Agent 完成后，结果附近应能直接进入工作区变更、已确认的开发预览或同一 Session 的后续对话。完成、变更存在、预览可用和任务成功必须分别表达，不能把停机或进程退出当成成功。
- 预览只能使用已确认的通用开发服务事实；没有端口、发现失败或服务状态未知时保留工作面并说明当前事实，不猜测 URL。
- 终端、对话、审批和审查切换时保留同一 Agent Session、草稿、附件和待回答交互；重连失败不能清空工作面或删除健康 Session。
- 移动端、语音、Watch、Push 和 Remote/SSH 不属于本轮闭环，后续必须基于 Core/ctxmux 的公开能力另立需求。

- Needs you 不保证一定有可回答的结构化请求；没有 typed request 时只提供定位原 Session 和真实状态，不能猜允许/拒绝按钮。聚合入口中的回答属于显式交互入口，不改变 Board 观察 Region 禁止发送和生命周期修改的约束。
- 请求以 Core 当前 Session、Run 与 request 身份为准。提交中禁止重复点击；失败保留问题与用户选择，不自动重发或跳过；旧请求已被替换时刷新投影，不把旧回答送给新请求。成功按 Core 确认收敛后才进入下一项；到末项返回空状态和稳定焦点，不自动批准下一项。 在 Focus 中关闭请求面板时，原请求入口仍可见就归还焦点；最后一项确认后入口已收起，则回到当前可见的检索控件。用户随后已转到其他控件时，关闭回调不得抢回焦点。
- 查看变更展示所属工作区的 Git 事实，明确它可能包含其他人或其他 Agent 的改动；无仓库、无变更、读取失败是不同状态。继续追问只聚焦同一 Session 的既有 Composer，不自动发送、创建新 Session 或暗中 resume。
- 明确的 HTTP/HTTPS 地址可以由用户输入或从当前 Session 的链接中明确选择，再使用既有 Browser 打开能力；地址合法不等于服务在线。多个地址由用户选择，不能挑最近端口或从其他 Session 借用地址。没有服务观测时显示尚未验证可用；自动扫描端口、自动启动服务不属于本闭环。
- 显示投影的失败不停止健康 Run；旧请求、无效地址等动作仍须拒绝错误目标，拒绝该次动作不等于阻断整个 Agent。切换可恢复原焦点和草稿；只有 Core 确认终局事实才允许移除对应 Session 投影。

## Agents 入口与 Activity 详情归一

- Activity 工作线展开的每个 Agent 必须显示所属 Project/Workspace、Provider、执行状态、最近活动与等待/停止时长；统计至少区分总数、running、needs you、error，缺失事实显示 unknown。
- Agents 列表只有一个主入口。左侧 Projects/Agents 工具作为统一入口，右侧重复的 Agents roster 不再单独占位；原有定位、筛选和状态统计能力并入统一入口。

## Agents、队列与 Message Tools

- Agents 二级菜单优先呈现对象、当前动作和下一步，不堆叠 provider、配置名、路径和重复状态；详细信息在展开或 hover 中补充。
- 进程 running、语义 working、输入可用与业务完成分别消费[状态事实 owner](#provider-与人机交互的分层收敛)。最近动作已确认时优先显示动作，未知如实说明；不从正在输出推断 working，也不以进程运行证明输入可用。
- Agent 的用户显示名、Provider 名和配置名必须分别标注，不能把 Provider/配置名伪装成用户给 Agent 起的名字。
- 消息队列项必须可展开后删除或立即发送，保留原消息和失败原因，发件列表逐条表达受阻与失败，未读提醒通过统一邮箱红点表达。**「自动发送失败后停止重试」只对真的失败成立，不对「我们没看清」成立。** 这条原先写成无条件停止重试，那是把 AGENTS.md 第 11 条的第 2 类写成了第 1 类：readiness 还没观察到（`epoch-missing`）时 Agent 进程活着、PTY 照收字节，停止重试等于我们自己的观测没走通就把用户的消息判了死刑。用户原话：「即使当时发不出去，它也应该还是在队列里面一直等着，对吗？」——对。因此：Agent 仍可工作时，条目**留在队列里并继续等下一次可投递时机**，同时如实说明当前没投出去和原因。这里「如实说明」是硬约束而不是补充：投递受阻必须是一个**与正常排队并列的独立状态**，不能复用「排队中」那一档。只有两档（排队中／失败）时，受阻只能借「排队中」的文案，数量标识会**肯定地**说「N messages queued for delivery」，而真相是此刻投不出去——那是第 11 条的另一侧边界：不许静默降级。反过来也不许借「失败」那一档：Agent 好着，画成报错样子是往第 1 类说谎。所以三档各说各的话，且各自要求另外两档的说法**不在场**；受阻这一档说明哪一步没走通、当前状态与可达动作；能否继续等待或需要明确重试沿本节准备等待合同，不能无依据承诺自动恢复。同一条受阻**只在第一次发现时上报一次**：用户刚敲完回车那次必须说（邮箱红点与收件通知让真正原因可发现），之后的自动重试保持安静——已读后的驻留状态由邮箱中的当前问题表达，不靠反复弹窗。只有权威 Runtime 确认原 Run 终局，或 Core 确认原操作已被终局拒绝时，才停止该次自动尝试；未接纳、准备超时与观察未知不证明终局，原消息及可达恢复动作继续保留。
- **一个未投出的条目不得堵住它后面能投的条目。** 保序是「按作者顺序投递」，不是「卡在第一个上」。一个条目进了终局，队列不能因此整条停摆——那会让一次失败升级成整个 Session 再也发不出消息。
Message Tools 的形态、工具入口与启动页编辑行为只由[快捷输入区](conversation-input.md#可收起的-agent-快捷输入区)定义；消息准备、排队与投递资格仍由本节及后文持有。

## Provider 与人机交互的分层收敛

交互模式与外部连接器共同消费对话、更新与原动作的目标边界见[《共同对话协议与外部交流入口》](conversation-mode.md#共同对话协议与外部交流入口)；本节继续持有 Provider 资格、原请求与回执的准确合同。

### Agent 全局状态：唯一事实与投影

AgentMux 不接管 harness 的模型循环、工具执行、上下文压缩或内部任务真值。Provider 解释原生协议差异，Core 组合跨 Provider 的 Session、状态、投递、交互与恢复语义，client 负责呈现和用户手势，ctxmux 独占 Run／PTY／Replay 等 Runtime 事实。Agent 状态以准确 Host／Session／Run 及原生主体为范围，全局入口共享同一事实，不能因所在页面不同改变状态，也不另建全局状态 Store。缺失、过期或矛盾证据保来源与时间；Provider 特有工具、Goal 或 Workflow 事件只按已声明能力呈现。

| 事实 | 唯一 owner 与来源 | 展示与未知边界 |
| --- | --- | --- |
| Run 与进程 | ctxmux 持有 Runtime lifecycle，Core 投影进程状态 | running 只证明进程运行；连接不可达、Run 未观察、中断和退出分别表达，不推断工作或成功 |
| 当前活动 | Provider 解释原生协议，Core 的公共观察合同组合当前活动与语义状态 | active、等待、idle、unknown、unsupported 保原义；输出、CPU、标题或图标不能证明活动 |
| 输入资格 | Core 组合 Provider 就绪、原请求和准确输入目标 | ready、pending、unknown 独立于活动；健康普通终端输入不因观察缺口被撤销，具体合同见[输入环境边界](#输入环境判定与复用边界) |
| 待答请求 | Core 持有原 Session／Run／request 生命周期及受据 | 需要用户、具体问题、可回答性与投递确认分别表达；没有 typed request 不猜选项 |
| 结果与目标 | 原生轮次、消息／工具结果和业务 Goal 各由原 owner 确认 | turn 结束、可读回复、工具返回、Run 结束和 Goal 完成互不代签；Focus Results 资格归[原 Focus 合同](focus-context.md#项目归属任务状态与恢复) |
| 观察与服务问题 | Core／Provider 保来源、最后确认事实、失败步骤与恢复动作 | 活动过期、尚未确认、不支持和 Agent 故障不混同；未知不补成正常、死亡或任务超时 |
| Client 呈现 | client 消费同一公共 Session／观察投影；共享语义图标只负责画形状 | Focus 分组、Board 列和头像提醒各保原作用域，不成为新的控制真值；标作 Working／Idle 的活动指标必须依据同一当前观察，不能用粗分组冒充 |

跨入口统一的是事实、含义和同义字形；不是把这些轴压成一个 busy 布尔值。客户端不新增检测器、轮询或全历史读取。具体阶段与动作仍沿[当前阶段合同](#agent-当前阶段与动作的可见表达)，状态时长仍沿[状态起点](#agent-已经这样多久了)；图形、动态与密度归[同主题呈现](../presentation/agent-capabilities-and-messaging.md#状态标记与-executor-叠加密度)。

- Agent 的进程已经停止、正常退出或退出原因未知时，不能因为流程告警或投递检查失败而显示成红色错误。只有 Core 给出真实崩溃、非零退出或明确故障事实时才进入 error；连接丢失单独显示为 disconnected。左侧 Project 树保留原 Session 及准确状态数量，头像和 Executor 角标不因此常驻亮起。
- **当前活动与历史完成分开。** 完成记录与 completion identity 属于已经观察到的轮次；新输入或 prompt admission 已消费其空闲或下属活动证据后，不能继续宣称旧的当前状态；Core 的当前事实顺序同时约束冷快照和实时投影，不篡改原生事件时刻来使投影前进。输入 ACK 只证明字节接收，不能据此宣称 working，也不能仅因收到输入字节就认定原任务状态已失效；已确认不改变任务语义的查看、滚动或草稿编辑保留原状态事实。对已支持原生状态的 Provider，unknown 应是少见的观测缺口，不能成为正常交互后的长期状态；状态确需重新确认时，沿原 Provider 协议和准确 Session／Run 观察当前事实。已确认的 Agent／进程／模型请求异常明确呈现具体异常；状态观察失败则说明失败步骤、原因、最后确认状态与时刻及恢复动作，不冒充 Agent 本身故障。 当前活动未知须区分已有活动证据过期与尚未确认到当前活动；最后确认的状态和原观察时刻独立保留，不冒充当前状态。只有确认操作确实超时才称状态确认超时，静默或活动证据过期不称任务超时；原生身份／历史来源未确认与当前活动分别表达，不覆盖仍可信的活动或等待事实。真正缺少当前语义事实时仍明确 unknown，不能为降低未知数量而猜 idle、working 或 error；保留原 completion、readiness、Run 和已有输入能力。
- **当前主轮空闲不代签成功。** Provider 可贡献原生决策收口后的准确主轮活动，沿同一 Core Session 的临时当前投影表达 active／idle／unknown，与历史任务结果分开。来源须绑定准确 Run、原生主体和真实轮次，并保留原来源顺序；旧轮迟到、身份变化、断流或 Core 重启后的旧快照不能冒充当前。主轮 idle 不结束在途子任务、不结算权限请求、不授予自动输入或任务完成；真实新活动或语义提交消费其当前性，查看、滚动和原始输入 ACK 不凭空改任务语义。观察缺口保留原工作面与可用输入，给出具体原因和重新确认路径。

- **真实活动续报与状态起点分开。** 准确 Session／Run／原生主体和当前轮次的新协议活动，按原来源顺序刷新其真实活动观察时刻；同状态续报不重置状态起点、不新增重复状态转换历史。重读同一快照、重复或倒序记录、旧轮及已确认终局后的工具回执不能刷新当前活动；原生时刻缺失或过期时保留观察缺口，不以读取时刻制造新鲜度。原 Hook／当前活动仲裁、待答请求与已确认轮次终局保持，不为显示 Working 清除其他已确认事实。

### 原请求与输入回执

- 人机交互由 AgentMux 统一承接：Provider 描述原生权限/问题及可回答选项，Core 绑定精确 Session、Run 与 request 身份并维护其生命周期，Client 复用对应交互面。普通消息、排队、steer、回答权限/问题、interrupt 当前轮、stop 执行、pause loop 的意图必须区分；共享身份、投递与回执规则不等于共用一种写入语义。
- 用户消息从草稿到已入队、Host 已接收、Provider 已消费的证据必须区分；未知回执不冒充成功，也不自动重复发送。尚未成功生效的内容应保持可取回；草稿编辑状态由 Client 持有，提交后的投递事实由 Core 持有，不能把草稿硬搬成 Runtime 真值。
- 原生 typed 回答首次可能输入前，Provider 必须确认准确请求对应的原生输入目标可接纳该回答。受信观察 Hook 证明请求的归属，不单独证明终端输入目标已经就绪；仍开放、可回传决定的原生请求 callback 本身则是准确的回复目标，不额外要求当前 pane、终端按键或该协议未提供的 tool call ID。资格由原生协议或其实现事实确认，并由 Provider 绑定当前 Session／Run／request，Core 消费这一事实，client 不猜厂商文案、数字选项或输入目标，完整画面只作诊断。准备只观察相关请求，不能借等待占住健康 Agent 的普通输入；目标、请求或来源改变时拒绝该次回答，保留原请求、所选回答、工作面和准确原因。
- 回答沿现 pending owner 保留原 response、operation、内容和准确 transport 的受据；Runtime 字节 ACK、决定已保存、已交给原 Hook 连接、Hook stdout 已写出与原生采用分别表达，不能互相代签。只有 Provider 对准确原生调用及同一 Run 的 completion 才允许认定原请求完成。ACK 先到或 completion 先到均沿同一 owner 收敛，已有输入不重发，新请求不被旧 ACK 或迟到 completion 覆盖。丢回执、部分输入或消费未确认保留原 tuple 与待核实事实，不猜未发生、不新认领原回答；旧终端回答已尝试或结果未知时，不改用 Hook 重放。
- 权限决定复用统一的 `respondAgentInteraction` 及现有 Desktop／Mobile 消费，派发前重核准确原请求与当前回答者授权。Provider 只沿原协议支持的选项答复，不扩大授权范围；无决定、断连或放弃本地等待按该 Provider 原协议保留原生处理路径；原协议回到 reviewer 时，不冒充拒绝或批准。原 callback 等人答复不占用 Hook 事件处理队列，Core／binding 退出及时释放未决定的等待；普通 Hosted 答复调用结束不撤销独立的原生请求。回调已关闭时保原请求与终端出口，不能重建回调、猜按键或停用健康 Run。
- 原 Provider 状态协议已确证的准确轮次结束沿原 Session 持久事实保留，绑定原 Run、Provider、完整原生主体及来源、turn 与原 record；原 Hook 先到或后到均消费同一事实，效果前再次核对。当前状态投影对旧轮的抑制、其他轮后续活动及未知观察不擦除该结束事实；不同主体、来源、Run 或 turn 不借用。原生时间缺失仍缺失，Core 接受时间仅为记账，不能按时间推断结束或过期。重启后保原身份及准确事实，不增加第二份 Store、固定截断或时间淘汰。只拒绝准确已结束对象的 typed 回答，原请求、操作受据、健康 Run 与原终端继续保留。
- 原终端或其他客户端已确证处理的准确请求应自动收口：同一 Session／Run／原生来源／request 的完成事实到达后，Session 和注意力面中的当前请求卡片同步消退，不要求用户关闭、刷新或再次回答；未结清的旧回答受据仍保留原记录，不冒充已结算。只有输入 ACK、后来状态、超时或不完整观察时不能认定完成；保留原请求事实、待核实原因与原终端入口，以非阻塞方式呈现并保持健康的原终端输入。旧 Run/request 的迟到回复不得作用于新请求；不自动选择选项，不用普通 prompt 绕过权限问题。
- 新启动或恢复 Run 的原首条输入，在任何可能输入前可有界、只读等待 Provider 确认该准确 Run／原生来源的 transport 资格，并在准入前重核身份、来源与输入边界。一次暂不可确认不等于 Run 已坏或永不支持；真实不支持、身份变化、终局和等待后仍未知各按准确事实处理，保留原请求、执行意图和非阻塞原因。准备不能占住健康 Agent 的普通输入，不能以新输入、重启、自动重放旧 unknown 请求或降低资格来制造就绪；transport 资格不代替后续完整输入目标、草稿、pending 与字节护栏。
- Agent 活着但我们的握手、探测或观察失败时，保留其已有可用操作并呈现服务窗；不通过盲发、猜选项或伪装 ready 来“恢复”。完全损坏才诚实阻断，未知如实标未知。
- 人机交互反馈分为：当前输入组件内的操作结果、Session 的待答请求/持续服务窗、跨工作区的注意力摘要。每一层消费同一个请求或结果身份；已关闭 transient 提示不因重放复活，尚未解决的持久问题仍可找到并定位原对象。
- 同一请求在 Session 与注意力面板中必须显示相同的可回答性和终端确认原因；其他视图处理后，不再保留“Needs you”的旧文案。回答失败保留当前选择和请求，原因留在回答处，允许明确重试；旧 Session、Run 或 request 的迟到结果不得写到替换后的卡片。Session 的持续问题可从全局告示定位，阅读或收起告示不能抹掉未解决事实。

 用户要求：Agent 需要用户确认一些选项时，聊天视图当中应出现对应选项，并用清楚的样式表示需要用户交互。当前待答请求在同一 Session 的对话阅读面内可见：显示真实问题、Core 已验证的原选项及“需要你回答”，选择仍只走上述 typed response；没有请求就不占位。Terminal 与聊天复用同一请求 owner，不制造第二份可回答请求或把当前请求写成历史消息。只读聊天可观察问题和待处理事实，但不能回答；历史记录中的旧同步 pending 请求只作阅读，不重新获得当前请求的响应资格。Provider 已明确的原生异步问题沿[原生异步问题与答复](conversation-mode.md#原生异步问题与答复)使用原问题引用和明确答复入口，不将其冒充当前同步 pending 请求。unsupported 或无法确认投递/结束时，保原问题事实及准确原终端出口，不从正文、时间、toolInput 或状态猜选项、答案或完成。提交中不重复投递，失败保原问题与选择，只经用户明确重试；切换 Activity/History/Terminal、当前请求/Run 替换与迟到结果保持原阅读正文、选区、展开、滚动与草稿，不把旧回答或本地错误绑定给新请求。

- 重启／重装／暂缺快照时先恢复原 durable 空间，再按[冷启动恢复合同](session-recovery.md#冷启动按需恢复p0-末位)续接准确 Session。超时、旧 lease 与探测失败不删除投影；移除资格只沿[Session 恢复 owner](session-recovery.md#工作面持久恢复与启动边界)，unknown／unavailable 不冒终局。投递与 typed 回答不得串到替换后的 Run。
- 此次收敛以现有状态、interaction、delivery queue、continuous-progress scheduler 与持久化接口为起点；消除重复 owner 和重复判断，不要求将所有状态改成事件溯源，不新增自演化引擎、通用 Job/Workflow/插件平台或平行兼容实现。已有 loop 复用统一观察与投递边界，任务完成真值仍归任务来源。

- 架构可发现性也是本次分层收敛的约束：公共文档与 API 入口应能引导维护者找到既有能力的唯一 owner、真实消费者与行为证据，区分已有实现、可选 Provider 能力和待实现需求；分析遗漏须先核对来源，不以未经查证的“能力缺失”新增平行实现。

## Steer 与 Provider 输入能力

普通当前终端输入保持其原目标合同；显式寻址原生对话的意图必须携带准确原来源，并由 Provider 核对的原生输入通道、轮次及请求合同接纳。已保存历史可读不代表读取它的进程拥有原 actor 写资格，原生 client correlation 也不代表可重放。无原通道、错来源或失效目标只拒绝该次定向操作，保留原操作及健康终端输入。共同信箱、采用关系及接入方边界分别见[输入与邮箱](conversation-input.md#统一发送信箱与原生采用)和[Conversation 协议](../../specs/conversation-protocol.md#mailbox-consumption)，不由各客户端重定义。

用户反馈工作中的 steer 被“composer readiness epoch already consumed”拒绝。Provider 负责具体 CLI 的可用输入方式及就绪证据，Core 负责同一 Run 的并发提交、去重和交付。不能把 turn 完成信号当成所有输入的唯一机会，使本可接受 steer 的健康 Agent 被内部纪元卡住；也不能绕过尚未完成的提交或把未知输入状态猜成安全。已入队未投出的消息必须保留；提示准确说清当前等待对象，不能承诺永远等不到的自动恢复，也不能建议结束健康 Session 来修复流程。

人工明确发送允许复用原 Session／Run 的当前终端输入，由原生 CLI 按其当前草稿、附件、界面和执行状态处理输入；不要求启动时未保证存在的外部 Native 接口，也不承诺只提交 Message Tool 这一条正文。直接发送和对应快捷键立即提交到这条原输入通路，不添加 interrupt、ESC、清草稿或刷新动作；原生 CLI 决定开始、steer 或排队，平台不能由字节 ACK 宣称已经按立即意图接纳。Provider 只在自己的边界编码受支持终端协议，Core 复用同一逻辑 submission、输入 phase、原 Run、作者与去重 owner，Client 不增加厂商按键或独立检测器。持久保存、终端字节确认、原生接纳和业务完成分别表达；字节已经确认时结束本次写入等待并明确说明，不能冒充原生消费，也不能因为未取得原生接纳继续显示发送中。用户操作、快捷键及单条授权范围只见[《Composer 静息形态与主操作》](conversation-input.md#composer-静息形态与主操作)。

同一条人工显式发送在原 Agent 空闲或 working 时都可提交到当前终端，不以回合结束、空输入框或展示识别为通用许可闸。已知准确 pending interaction 仍由原请求 owner 守住，普通消息不冒充权限或问题回答；人工在原 Terminal 的输入能力保持。若某机制另有可证明的原生开始或追加回执，保留其准确层次，不能由缺少该回执否定已经完成的终端写入。自动续行与定时消息仍守各自准确的空闲／完成条件，不借用人工发送授权。 同一完成边界已被先前输入消费后，新的到期消息只可沿准确原生目标的原子 idle queue 接纳；原终端画面、提示符或颜色不能重新授予空闲资格。缺少这项协议时原意图保持待处理，普通人工输入继续可用。

输入资格消费绑定当前原生输入目标的协议事实及真实控制状态；已完成任务的名称和结果正文不能因含有状态词而阻断新输入，也不能反过来授权中断或冒充当前回合已完成。真实草稿、待答交互、原生临时状态及未知输入回执仍由各自 owner 核验。

运行中的人工消息沿原当前终端输入提交，不要求所有 Agent 先空闲。模型、effort、状态栏、提示语或历史阅读方式属于展示，不能作为发送资格的合同；压缩上下文等状态由原生 CLI 自己处理，平台只按准确已知协议事实说明暂时阻塞，不从画面猜测。写入后真实接纳仍未知时保留这一说明，不能冒充原生接纳或业务完成。

### 输入环境判定与复用边界

项目级控制事实规则归 [AGENTS《通用机制与 Provider 适配》](../../../AGENTS.md#通用机制与-provider-适配)。Message Tool、公共 SDK／RPC／CLI、Mobile、人工直接发送、普通队列与自动消费使用同一 Core 输入业务 owner；相同原消息、目标与执行意图不得因入口不同得到另一套资格、权限或去重事实。

输入的承载范围由本次实际 Provider／Runtime 通道和原持久记录合同决定。Core 与客户端不能把统一的正文长度、终端观察行数或可选上下文预算当成所有输入的容量上限；检查对象是实际冻结的完整 UTF-8 输入与所选计划，以及承载层编码后的完整帧。原记录必须在认领和外发前沿既有解析 owner 确认可持久读取；既有记录上限与协议明确拒绝仍如实保留，不另造重复校验或绕过实际承载限制。

可选启动上下文可以在有界预算内按完整来源选择，并保留未载入来源及其读取方式；必需的平台说明、用户原文和已冻结的对话 quote 不因此裁剪、摘要或改写。终端回扫与滚动历史各守有界观察成本，观察窗口不足不证明输入未发生、原生未接纳或 Agent 已坏。编码前明确拒绝只说明本次未发出，不改写同一原操作的历史未知结果；失败保留原输入、quote、key、Session／Run、回执及健康的独立输入，显式继续沿原身份核对，不自动换目标或重发。SDK、RPC、CLI、Composer、队列与外部消息入口复用上述边界，不新增 Provider 字段、引用协议或第二套消息存储来绕开它。

- **Provider 提供高阶原生输入环境语义。** 判定基于受支持原生协议或 Provider 对该协议的实现，说明当前原生主体／会话／回合、可接收的操作及机制、真实 pending interaction、暂时阻塞或明确不支持，并保留来源、原对象绑定和观察／回执边界。结果必须区分已确认可接收、已确认暂不能接收、明确不支持和未知；缺失字段不能补成空闲、无草稿、无权限请求或已完成。不将终端 cells、footer、提示文案、颜色或模型输出封装为一个 boolean 后冒充这些语义。
- **当前终端输入不要求独立消息接口。** 人工已明确接受当前终端语义时，资格以原 Session／Run、当前授权和真实输入 owner 为边界；不能再以 Native socket、句柄尚未发现、草稿未知或画面识别失败挡住本来可用的终端输入。原生草稿和当前界面的处理归原 TUI，平台不额外清理或导航。旧 Native／TTY 已尝试 unknown 或 partial 仍沿原 key 和冻结计划核对，不跨机制自动重放；新的独立意图不继承无关历史观察作为永久前提。
- **目录声明不代签当前 Run 的输入机制。** Provider 能力目录与可执行文件探测用于发现适配器及候选机制，不证明当前 Run 已具有对应的原生输入入口。Provider 基于准确运行进程、原生会话与真实协议确认原主体已有的通道；某一种受管启动形式或平台私有 actor 不是所有原生输入的共同前置，缺少它不等于原生主体没有相应能力。Core 按 Provider 核准的原后端、原 Session／Run 与操作合同选择通道，不能据目录标签把所有已运行 Run 强制改用尚未确认的通道。新启动、合法恢复与已有健康 Run 分别验证；缺少通道事实保持未知，不改原配置、另起 writer 或热换健康 Run 来补造能力，也不承诺等待会自行产生输入入口。
- **原生输入适配沿真实版本合同维护。** 当前 CLI 版本的原生输入资格由 Provider 沿实际启动、认证、准确原生对象、操作及回执确认；已核旧版本的目录声明或版本白名单不能代替当前版本适配，也不能仅因版本号相近就承诺兼容。可选受管准备尚未资格化时保留原先可用的启动形式，不因此拒绝创建；一种机制的资格不能外推到另一种。磁盘当前可执行文件的版本不证明已有 Run 启动时加载的版本或原协议；新建、合法恢复和原健康 Run 分别沿自己的身份与能力核对，不为升级适配重启、热换或替换已有 writer。原生立即开始／追加与耐久排队分别依原协议表达，排队接纳不冒充立即执行、原生采用或完成；定向原生意图不可静默降为另一种机制，已有当前终端输入继续按原意图使用。可信原输入的采用关联与普通 Terminal 手动发言的公开来源资格分别成立，不为当前版本的受管输入适配新增平行 Store、队列或客户端厂商分支。
- **新入口保原启动语义，队列与直接输入分别确认。** 为原 Run 增加机器输入入口须保留原生主体完整已解析的配置、权限、信任、认证、网络、工作目录及恢复语义；参数近似、换启动模式或另解析配置不能代签等价。同一进程不单独证明同一 backend，另一个协议客户端进程也不单独证明新增了模型 writer，均核实际原生主体及消费者。持久会话队列只按明确队列意图及其保存、消费、去重、取消和恢复合同使用，不能把入队 ACK、空闲后执行或跨恢复消费冒充原 Run 的直接接纳与忙时 steer。
- **Core 负责统一准入与继续。** ctxmux 的 Run、PTY、输入 owner、字节与 ACK 事实和 Provider 的原生语义各守用途；Core 核对原 Session／Run、本次机制所需的来源身份、权限、意图、前驱条件与冻结投递，再决定该次操作是否能开始、继续、等待或具名拒绝。原生接纳、输入字节 ACK、消息持久保存和任务完成分别记录，不能互相代签。工具底层的可复用实现属于这条 Core／Provider 边界，不属于某个面板、按钮、宿主包装或客户端专用 parser。
- **展示观察只服务呈现与诊断。** 终端画面、标题、提示和输入回显可用于显示及解释现场，不能证明当前输入 owner、原生权限、回合状态、原消息接纳或允许提交。窗口大小、主题、语言、自定义状态栏和阅读位置变化，不改变原协议已确认的输入能力。终端控制序列与有序字节可确认其明确协议所保证的传输事实，不能由同步重绘、光标位置或新输出猜测 Prompt 接纳。
- **未知保全能力，真实边界仍成立。** 目标、授权、当前协议机制或原请求条件无法确认时，说明准确缺失事实和本次操作结果；保留原消息、草稿、pending interaction、原身份、已确认回执、可用终端与可达恢复动作。原生不支持某一语义输入通道不等于 Agent 已坏；不能自动接另一原生 writer、重放 unknown 输入、代答权限／问题、清空草稿或添加中断、额外 Enter、刷新动作来绕过未确认环境。普通手动 Terminal 输入与该次语义投递的资格分别表达。
- **声明须接实际消费者并可证伪。** Provider 合同、Core 判定及 SDK／RPC／CLI／各客户端复用关系按[公共能力贡献约定](../../guides/public-capability-contributions.md)交付；只改检测函数名、声明接口或 help 不算实现。验证绑定协议事实与真实输入回执，并证明展示文案、样式、尺寸或阅读位置变化不会改变授权决定。保护原权限、草稿、身份、未知与部分输入，不能通过删除护栏获得成功；代码、测试、fixture 与真实产品接纳分别说明，不把本合同写入文档视为现有实现已符合。

原生协议如需准备动作或刷新终端观察，只能由 Provider 声明其用途与协议保证，并证明不提交、清空或重排草稿与既有待处理输入；授权限定在这次显式立即执行及原 Run。Core 沿原持久投递保留该准备阶段的唯一身份与实际回执，丢回执或重启不重复执行。刷新和保真恢复仅产生对应终端展示／诊断证据；resize、重新接入、来源变化、旧完成帧、checkpoint 合成绘制或随后重绘，都不能补造原生输入环境或证明语义准备完成。

原生恢复后的输入证据必须属于当前 Run。历史创建版本不能代替当前原生进程的能力，已结束或丢失 Run 的 working 尾部也不能直接成为新 Run 的当前回合；Core 持有准确的恢复与 Run 关联，Provider 在该边界内解释原生来源。新的 working、待答交互或草稿仍按当前事实处理，缺失或变化的来源保持未知，不从时间、正文或画面猜空闲。无法读取恢复边界不阻断健康原生恢复，保留可用输入并持续说明未确认步骤；同一消息的投递身份与未知结果不因恢复而重置。

当前输入能力与可执行文件路径或版本读取分别确认。运行进程的原程序文件更新、移除或暂不可读，不单独推翻该 Run 已正向确认的输入能力；Provider 按本次受支持机制所需的原对象、进程身份及准确输入目标核验，并在首次输入前重核原 Run 和意图；字节、输出或尺寸栅栏只消费其协议实际保证的事实，不成为所有输入的通用前提。实际能力或目标无法确认时只拒绝该次操作，明确缺失事实并保留原请求和健康终端；不能由路径名、另一可读副本、相同版本字符串或历史创建信息补造当前能力，不重放既有未知输入，也不增加另一份身份或能力 owner。

准备或观察被取消时，当次错误和 logid 保留实际取消来源：原调用取消、客户端断连、人类终端输入、语义交互回答或终端协议让行。保留调用者原取消原因与协议让行身份；日志不把来源缺失猜成用户取消，不为补诊断改变既有取消、并发或输入权限。

准备总期限用尽时，原错误与 logid 保留已实际进入的等待阶段及其进入、最近完成时刻；只消费同次调用与原屏幕 owner 已有的有限游标、几何、完整性和判据结果。阶段未进入、尚未返回或观察缺失如实保留未知，不把等待位置当作根因，不记录正文、cells 或低熵摘要，也不为诊断增加探测、输入、期限或重试。

首次输入认领前的只读准备须让终端自动协议回复及时结算，再沿同一原请求核验；直接输入与中断后输入均复用这一并发边界。只对原观察确认的协议让行、同 Run 连续准确 ACK 在原总期限内继续，不重建意图、期限或发送；已开始认领、真实人类或调用取消、断连、身份变化及未知输入回执不得据此续做。 终端鼠标控制报告仍保留其真实输入来源，不能仅凭 source=user 就当成人工取消；首次认领前，完整已知控制报告只在同 Run 连续准确 ACK 后允许重新核验当前输入目标。夹杂正文、截断、未知或未确认字节不享有这一让行；已开始认领和真实取消仍保持原边界。

同一当前 Run 的只读终端观察因已知几何变化或同 Run 证据重建而作废时，只作废旧展示／诊断观察，不取消原人工输入意图。只要原调用的总期限尚未结束，沿同一 Session／Run、来源、operation、condition 和输入进度恢复对应观察；输入资格重新核对原生协议环境与 Core 原条件，不由新画面授予。不重置期限，不要求新的回合或额外刷新，不增加或重复正文、提交键、准备动作与输入 claim。取消原因须保留准确出处和当次 logid；原调用取消、人类输入、断连、Run 替换、输出 Gap、权威性缺失、真实错误或未知原因不能被当作几何作废吞掉。已确认或未知的输入仍按原持久回执处理，读取继续不构成重放授权。

投递问题必须表达原调用停在哪一步：输入前的只读准备未完成、原输入已尝试但回执未确认，或原字节与原生接纳已经确认。输入前拒绝只按 Core 该次调用没有触发原输入的权威事实说明；它不证明同一消息从未由另一次调用输入，也不把既有未知投递改成未发送、可编辑或可重放。API 已发起、缺少记录、只读失败与终端仍可工作分别表达，不能互相代签。客户端与公共命令消费同一 Core 错误／受据事实，保留准确的原消息、操作和 Run 绑定，并说明健康终端仍可使用；缺少阶段事实时继续明确未知。

原消息冻结的发送前置条件与当前已知提交冲突时，明确说明本次在写入前拒绝、原条件已失效，以及原消息此前的投递仍需核对；前一提交缺少身份时仍表达未知。不能把反复重试同一失效条件作为恢复动作，也不能自动更换条件或操作身份重放。用户可显式把原文移至同一 Session 的草稿：保留已有草稿和原条目的完整归档记录，移交不发送、不继承原自动执行授权，也不撤回已输入内容。核对 Agent 回复后，用户通过普通发送明确创建新消息；健康终端与其他消息继续可用。

Readiness 是 Provider 协议提供并绑定原对象和用途的输入环境事实，不是输入框显示识别或健康 Run 的永久发送许可证。一次未取得、超时、已消费的旧事实不得封闭后续人工发送或 steer 路径；事务冲突、未完成投递、错 Run 和待回答交互仍由各自权威 owner 处理。缺少所需协议事实时说明未知与可达动作，只在同一原边界取得真实事实后清除不确定性。

自动续跑以当前 Run 的实际 turn 完成事实作为触发机会，每个完成事实最多推进一次；working、待回答交互、未知完成状态仍不自动发送。其去重必须由持久化调度 owner 持有，不靠屏幕 readiness 恰好成功或被消费来间接阻止重复。

自动推进的领域调度由独立 Host 持有，客户端连接与桌面退出不改变原已保存的执行意图；实际投递仍经过同一 Core 的原 Session／Run、授权、完成事实、输入认领和暂停边界。客户端开始编辑时，以 `agent.automation.pause` 取消准确 Session／Run／owner instance 上的自动推进，并以原 operation 查询确认；该操作不发送输入、不清空或上传草稿，也不授予后续输入资格。缺少桌面观察不能推断草稿为空；取消结果未知时保原意图、操作和健康人工输入，不自动重放。原普通进度通过 `agent.progress` 消费同一 manager；动作只核原目标和调度领域快照，不以标签、解释文案或观察展示字段决定资格，也不增加第二份持久版本事实。普通进度的新建、配置更新、恢复和立即检查需要原认证的人或设备；受管 Agent 可在原准确目标授权内读取、暂停或停止，不能借普通进度安排绕过原有署名消息输入边界。

人工输入取消自动推进时，查找成本随准确 Host／Session 的相关安排增长，不扫描无关 Session；同一批安排的暂停由原调度 owner 合并保存。内存暂停不代表持久化已确认，保存失败须保留原未知结果及明确的补保存路径，不能靠持续按键反复制造事务或自动重试。普通输入仍应及时可用。

自动推进的认领和发送确认必须分开：在认领之后、确认之前重启，显示结果未知并保留原投递标识供显式继续；不得伪装为已完成，也不得默默重复投递。暂停、停止、新一轮开始或 Run 更换后，旧完成事实不得再触发发送。通知已读记录不能因重启过程尚未载入 Session 事实而丢失。

人工消息先于 Provider 的开始工作事件被接收时，旧 done 事实也已经被该次输入使用，不能让自动推进再借它发送一条；这个事实由 Core 在输入认领时原子记录，适用于单阶段和两阶段 Provider。人工 steer 不受已使用完成事实的限制；同一已认领操作仍可取回原回执。

## Executor 标识的归属

- 用户明确：固定 Icon 直接在 Executor／Execution 配置里，这不算显示配置，而是为了标识 Executor。颜色叠加与左上 Icon 和该 Executor 一起编辑、保存；外观设置不再另放一份入口或配置。
- 所有代表具体 Agent 的图标都显示其 Executor 标识，不再只显示 Provider 标识；同 Provider 不同 Executor 可区分。Provider 图形作为未自定义时的默认底图。纯 Provider 能力目录仍表示 Provider，不凭空关联 Executor。
- 菜单、Tab／Region、Topic、列表、消息工具与设置预览消费同一 Executor 标识；状态角标与身份保持独立。此约束取代此前放在显示设置下的方案，视觉轮廓仍遵循密度 SSOT。

## 插件扩展边界

- Provider、Skill 和命令通过 `packages/core` 暴露的类型化插件合同发现和注册。宿主先读取清单，再按用户选择激活；编辑器只消费统一目录和能力，不为某个厂商写分支。
- 插件拥有自己的声明和生命周期投影，但 Run、PTY、ordered bytes、Replay、Gap 与 Session 权威事实仍归 Core/ctxmux；插件不能复制一套进程或终端状态。流程探测失败作为服务窗提示，不阻断健康 Agent。

## 状态投影、Browser 页面与 Scratch Topic 工作面

- Agent 的进程、活动、错误与观察缺口沿[全局状态事实](#agent-全局状态唯一事实与投影)；左侧 Project 树的数量与提醒不改写事实。
- Browser 的控制权提示只是页面旁边的辅助信息。`Browser ready`、`You have control` 之类的提示不能替代、覆盖或把真实页面变成空白控制面；没有进行中的操作或控制权交接时不显示占位提示，页面仍由 Main-owned Browser surface 承载。
- Topic 是 Space 导航的一等内容，按[《Space、Folder 与 Topic》](spaces-and-layout.md#spacefolder-与-topic)的 Topics 分类进入；Scratch 保留底层共享布局含义，不再作为另一份产品父行。Topic 与既有知识目录、原工作面和 Session 的关系可追踪，重启后仍保持；选中、hover、空列表、新建和恢复状态沿同一合同给出一致反馈，不能依赖一张已经失效的装饰卡片。

## Executor 身份组件与信息面板

- 所有显示 Executor/Provider 身份的地方，包括顶部 Tab、Project/Topic 列表、Session、Board 和 Browser 操作条，都必须使用同一个可复用 Executor identity 组件。Provider 图标、较小的 Executor 自定义图标、珐琅式外轮廓和状态标记只能由这一组件组合，不能在调用方各自画点、描边或叠加。
- Executor 面板在 hover 或键盘 focus 时以统一的 tooltip 信息面板出现，展示可读名称、Provider、当前状态和可用的上下文；不要求先点击才能看见。面板的字号、内边距、颜色和动作区与其他信息面板一致，不能因为来源不同出现另一套密度。
- 自定义头像属于 Executor 配置，不属于 Appearance。面板只提供一个小型设置入口；点击后进入该 Executor 对应的模板设置，不能跳到 Appearance，也不能在信息面板内复制一套配置表单。身份 ID、Session 绑定和工作区事实保持稳定。
- 头像编辑归属 Executor 模板；移动设置入口不能改变已有身份外观、丢弃已存头像，或因头像问题阻断应用启动。仍存在的 Appearance 头像按原 Executor ID 继续显示，新的 Executor 编辑写入其稳定配置；未匹配的旧记录保留原样，不猜测新身份。

## 工作状态与 Executor 叠加标记

- `working` 必须有一个明确的活动字形，表达 Agent 正在产出；普通 `running`／idle 只表示进程仍可用，不在头像右上角放常驻标记。
- 等待用户、阻塞、断联和真实错误属于需要用户知道的特殊事实，保留各自的提醒形状；错误行优先显示 Runtime 提供的具体原因，无法取得详情时才使用短的事实说明。
- Executor 自定义图标与 Provider 图标先合成一个身份图，再应用共享的珐琅外轮廓。Executor 图标应小而紧，叠在 Provider 图标内部，不得成为围在外面的第二圈。
- 状态语义只通过右上角的小型标记或活动字形表达；普通身份不使用外描边制造状态。
- 活动菜单必须保留可读的原因、项目和 Provider 信息；长内容在有界菜单内换行或滚动，不能被固定宽度裁成看不懂的尾巴。

## Agents 全局层级与拓扑图

Focus 与 Space、Goals 位于同一组全局工作面。Focus 打开时 Project Rail 被遮挡，Project 作为 Agent 的归属事实，不再在左侧重复出现。Agents 保留可用的分组／详情表面；按工作区域组织的关系观察归[A2A 协作图](a2a-collaboration.md#工作区域与-agent-协作图)，作为 Space／Focus 的附属视图。图的范围、入口与事实归属由该专题定义，不另立独立全局引力图或第二套 Agent registry。

## Claude Prompt 提交

从 Message Tool 发送给 Claude 的文字必须沿 Provider 已确认的当前输入机制完成一次真实 Prompt 提交。输入模式与接纳从原生协议事实及对应回执确认，不以输入框显示、回显文本消失或终端继续输出猜测已离开编辑态、接纳或执行。需要提交键的原机制保留 payload／submit 各自已确认进度；字节 ACK 不代签原生接纳。发送失败或所需输入环境仍未知时保留原消息、草稿和可诊断提示，不静默清空或假装执行。

## P0 的共同交付边界

零输入字节只能证明当前失败尝试没有写入，不能证明更早一轮已结束。原 operationId 的恢复继续走幂等路径；换成另一条消息且回合仍未知时，必须有这条消息自己的明确继续选择，不能借用上一条消息的批准。

用户要求完成当前六项 P0 的设计与实现，包括此前只规划的可读 A2A 协议。各项约束仍归其所属章节；“代码已有”不能代表交付，必须证明真实入口、失败分支和重启后的恢复。发送与恢复的检查失败不能拿走健康 Agent 的工作能力；无法确认的事实保持未知，并在原工作面持续说明恢复动作。Browser 批准只授权被确认的目标和操作；Demand 详情保留原需求身份与编辑能力。

## 跨重启的 Prompt 投递凭据

- Prompt 两阶段投递的持久化 claim 是去重与恢复记录，不是把下一条 Prompt 永久挡在门外的许可闸。应用重启后重新接入同一个仍为 `running` 的 Run 时，旧 claim 未确认本身不得触发 Resume、Retire 或删除健康 Session。
- 两个公开 `AgentMuxClient` 实例共享同一受支持 Session Store/Run，以及两个 Control/Renderer 经同一 Core owner 发送，都必须保有唯一在途 Prompt 投递 owner。另一 Client 看不到本实例内存记录，不代表旧 owner 已结束；活跃 claim 不能被替换。投递前须重新读取当前 Session/Run 与待答边界，普通 Prompt 不冒充交互回答。精确绑定当前 Session/Run/request 的人类回答不等待可选的 Prompt 渲染观察；结束该观察不取消已派发的 Native Input，也不替请求补完成或批准。
- Core 投递 scope 释放或进程退出，不代表 Native Input 已终结；游标仍在旧 claim 起点也不能证明旧输入将来不会写入。首次投递前须在现 admission 保存原始 bytes、key、range、daemon incarnation 与两阶段意图，冷恢复只按原 tuple 接续既有 recoverableInput，不能从 digest 或变化后的 Provider 计划重建输入。unknown/partial 保留原 operation、内容、工作面与原生输入能力，并说明待核实原因；缺 tuple 如实 unknown。不同消息接管同一两阶段写入范围须有真实 not_applied 或其他终局事实，证明旧请求已无未来写资格；不能猜 TTL、PID 或语义状态，不能留下无法自行恢复的永久 BUSY。
- 两阶段 Prompt 的正文已接受、提交未派发时，人工输入可能占用旧提交范围。恢复须核对原提交的终局；不能把正文已接受改成整条消息未投递，也不能因为已终结的提交阶段让后续消息永久卡住。无法确认的部分仍保留原消息与原生输入能力。
- 新的两阶段提交建立自己的字节范围与 readiness 观察；同一 `submissionId` 和相同内容按原冻结输入幂等续做，冲突内容拒绝。旧 ACK 只属于原 Session/Run/operation，不清新 claim、请求或草稿；Host accepted 不冒充 Provider consumed。任何恢复流程失败都要保留可见工作面和健康 Session。
- **整条输入确证未应用后，原逻辑输入可以继续。** Core 须从准确原 operation 的完整回执确认整条输入 `not_applied`、前序已终局且无未来写资格。保留其冻结目标、参数与回执；同 ID 仍返回原结果，不覆写旧事实。原意图、当前作者授权与显式条件仍成立时，原输入 owner 可建立唯一后继物理尝试，取得当前准确目标与字节范围，保留可核对的前序关系。后继推进等待代次，保留上一 `waitRef`、派发 gate 与 delivery key；原逻辑 key、正文、作者、队列成员和顺序不变。并发、重启和重复请求只能取得同一后继；重复旧 `waitRef` 只返回当前事实，后继再次失败也不能借旧请求继续创建尝试，旧停止动作不取消新代次。后继不替换用户已冻结的显式条件，也不建立第二队列或让客户端私下重发。仅本次准备失败／零字节、独立刷新拒绝、缺少 admission 或部分正文已接受均不足以证明整条未应用；unknown、partial、accepted 只沿原 operation 核对。公共 API、JSON-RPC 与 CLI 消费同一 Core 合同。
- Run 终局可以清除当前 Prompt readiness 与临时提交投影；已确认输入仍按原 Session/Run/operation 的持久受据表达。验收不得要求已退出 Run 保有可再次提交的 readiness，也不得因其缺席抹掉已确认交付。
- 人工在上一回合结束尚未确认时明确继续的事实属于这次持久投递；只有首次准入确实遇到回合边界未知才保留这项事实，不能把每次显式允许继续都说成未知回合。丢回执、重试或冷恢复不能遗失这次选择与回合说明，也不能借给另一条消息。恢复原 Input 回执只确认投递，不确认此前回合已经结束：投递得到确认后消除投递未知，仍保留同一消息尚未确认的回合风险；只有对应的真实边界或新的明确当前事实才能更新说明。可选的说明持久化失败不阻断仍能接受输入的 Agent，并明确保留失败步骤与当前状态。
- **显式条件与直接发送意图分别保留。** 调用者明确提供的 admission 条件与 operationId、原正文和原 Run 一起先保存；重试、丢 ACK、冷恢复和跨客户端都不改 `afterSubmissionId` 或 Run，Main 不能每次补最新值。条件中的 `null` 仅表示已确认没有 admission，缺字段、不可读事实或现记录缺逻辑身份均是 unknown。新的 `manual-actor` 意图明确授权这条人工输入的当前终端执行语义，在空闲或 working 时均可提交，仍保留原正文、作者与逻辑输入身份；Core 已接纳人工等待的首次实际 Run 选择及其 gate 冻结仅沿[Composer 队列合同](conversation-input.md#composer-消息队列与紧凑状态)，不改原 key 或显式条件。Core 为协调并发读取的 predecessor 不成为调用者的发送条件，不能让多条合法消息冻结同一个协调值而互相误拒。旧条件不能因标为 human 或恰好等于当前值被解释成协调信息；Goal、completion、future、input fence、初始输入与待答交互不借此升级为 manual。
- 首次条件读取只刷新精确目标 Session 的持久事实，不以进程状态代替 admission，不顺带探测、投影或恢复其它 Session。Mote 浮窗和任务入口的消息复用现发件列表；入队表示保留意图，不能把它称为 Agent 已经收到或执行。 浮窗交接被拒时保留未交接文字及原因，只报告一次，不因重渲染反复交接或修改焦点。 目标事实读取的等待不得占住全局消息写通道，阻挡其它 Session 的消息；两个客户端准备同一显式条件消息时，只有首次保存的条件有效。
- 消息回执只有已成立的状态转换才能写入 durable journal；被拒的转换不得留下无法重放的记录，也不得覆盖该消息已有的投递事实。
- 控制链路报错或丢回执只说明该次投递无法确认，不据此把消息标为终局 failed。消息保留最后已确认的状态及未确认原因；取得真实回执后消除该提醒。迟到的报错不能降低另一客户端已确认的投递事实。 未确认原因是普通文本，保留换行；诊断时间必须有效，不能改写最后已确认状态的时间。同状态回执保持原值，不因重试刷新时间或原因。
- Core 在同 Session 独占 scope 中核对原输入记录、意图与当前资格，再认领一次派发。显式前驱条件只允许沿原条件准入或核对原操作；条件已被后来输入改变时拒绝本次新派发，保原结果与后续事实，不能无限重试或自动更换条件。timeout、丢 ACK、unknown 和零游标不证明原输入尚未 admission。原 Native 输入 unknown 时，同一 `inputKey` 只核对原回执，不重新准备或重播；合法不同 key 的独立 manual 输入仍可在准确原 actor、当前授权与本次协议资格下接纳，不能因旧观察丢回执永久禁用健康能力。旧 claim、TTY partial 与缺来源记录完整保留，不覆盖或冒充 Native 未应用；不同协议输入面是否独立须有 Provider 的机器合同与真实证据，未确认时保留未知及原可用通路。
- 一个仍能接受输入的 Agent 必须有明确可达的发送路径。回合结束回执缺失不能把 readiness 变成永久许可闸；无法确认回合边界时说明风险，人工显式发送按「Cmd+Enter 直接 steer」执行；自动消费仍不能猜测空输入框等于回合已结束。已被接受但未确认的 Prompt 使用原 operation identity 续做，不重新发送正文；排队消息不因无关 Runtime 事件反复提交。
- Message Tool「先前能发，长运行后又发不进」的复发必须单独核对：消息进入 mailbox 只说明意图已保留，点「直接发送」也不等于 Agent 已收到。手动 Terminal 打字正常时，不能把消息投递流程失败说成整个 Run 或共享 owner 已停止；必须就原消息说明卡在哪一步、哪些字节已确认、哪些送达仍未知，保留原消息、草稿与工作面。已绑定当前 Run 的显式发送不能因为展示工作面的保存未确认而被挡，保存失败仍持续说明；发送受据与界面保存分别确认，不因此放开后台队尾、未绑定恢复或退出／更新的保存资格。运行时长或相邻 OUTPUT_GAP 不证明根因；恢复原投递仍遵守原身份与受据边界，不能用新 operation 重发未知正文，也不能把这条消息的未知变成健康 Session 永久无法显式发送。

- **每次失败仍可手动重试并可追查。** Desktop 与 Mobile 中未确认发送的原消息必须持续保留“发送”动作，不能因失败过一次、观测未知或旧回执而永久置灰、收起或静默跳过。只有该条实际发送正在进行时短暂显示忙碌；完成或失败后恢复动作。用户再次点击沿原消息身份、原目标和已确认输入进度核对并续做；上述整条输入确证未应用后，沿同一逻辑输入继续唯一后继物理尝试并保留前序诊断；不能把旧物理 operation 的稳定拒绝解释为原消息永久不可重试。自动继续仍限于原意图有效且当前资格成立的等待或确证未应用，不重新写入已确认字节；错误目标或授权仍明确拒绝这一尝试，健康 Agent 与原消息保留。
- **输入身份、等待代次与控制动作分开。** 不可变 `inputKey` 保留接收时的原 Session／Run 与原 SDK operationId 或 A2A messageId，A2A 原 Control operationId 仍只标识 ingress；逻辑 key 与首次或后继物理尝试的实际派发 Run 的关系只由[Composer 队列合同](conversation-input.md#composer-消息队列与紧凑状态)定义，不以当前 Run 改写旧 key。首次保存 ACK 丢失时，按原输入 key 或原 Control key 读取 owner 保存的原目标与结果，不要求尚未返回的等待代次，也不重新解析 Tab／Region 或生成新消息。`waitRef` 在原 key 上绑定准确等待代次；停止动作有自己的幂等身份和不可变回执，迟到停止不能作用于下一代，同动作重读仍返回原结果。key、设备信息与 envelope 不授予权限。
- **历史回执与当前投影属于同一 admission owner。** 同 Session 的原 admission owner 保留各输入的原 claim、计划、来源及真实结果，latest 仅为该 owner 当前投影；推进新输入前保全旧占位事实，迟到回执只结算原 key，不覆盖后来输入。消息 journal 保留保存意图与等待控制，不另存 Native outcome 真值。旧值缺身份、来源或派发事实继续未知，不回填资格；缺 journal gate、当前 claim 或结果记录不能推导原输入从未派发。 Session 投影保存失败不撤销准确原 inputKey、正文和消息内容对应的已确认回执；只读核对原 owner，分别表达输入已确认与投影保存未确认，不因此重发。
- **当前占用不从历史记录推导。** 已确认并归档的输入历史不占用当前输入面；草稿、实际在途写入及相关活跃意图分别按原 owner 判断。归档不证明 unknown 已终结，接纳不证明任务完成。客户端保留旧未知消息的原正文、身份、条件与回执，同时允许用户建立明确的新独立意图到 Core 核验；不能把一次旧观察失败变成整个 Session 的客户端锁，也不能借新意图重放同一未知消息。
- **观察取消释放其原等待，不授予后续操作。** 准确停止先于派发 gate 胜出后，旧只读授权检查即使迟迟不返回，也不得继续占住后续输入准备；迟到结果只结束旧观察，不恢复旧派发。新输入仍重新取得当前作者、准确目标与原派发资格。派发已授权后的真实受据仍沿原操作核对，取消观察不承诺撤回。
- **原输入恢复按准确对象查证。** 原 owner、输入 key/ref 与权限能够精确核实时，inspect、停止等待及持久 Inbox 消费不以无关 Session 全目录投影、活跃展示或 Native 输送连接正常为前提。真实缺记录、未知 owner、错误作者与过期代次仍拒绝；停止旧等待不发送、不重建 Session。持久 Inbox 继续由原 journal 在短事务中核对当前作者、readerRun、generation 与消费游标。
- **接收方继续处理不取得原作者身份。** 对已保存的外部 message，准确接收 Agent 可通过公共原输入入口继续仍获授权的原请求；用户无需记住来源、重发消息或切到另一界面代办。Core 必须核对本次继续入口的准确调用者资格（接收 Agent 入口为其当前 capability）、原作者 owner 的当前权限、准确 `waitRef`、原逻辑目标与冻结内容，并核对准确原代次的控制事实。首次派发须确认原代次仍 `enabled`、既无 admission、也未授权派发；已有 claim 的原请求只有满足上述整条输入确证未应用合同，才可建立唯一后继物理尝试。检查不可读不等于尚未派发或未应用。原 Run 改变时，原接收 Agent 显式继续，或[原收件 owner 自动继续](conversation-mode.md#共同来源与双向交付)的外部 `manual-actor` 请求，可沿[首次实际投递目标合同](conversation-input.md#composer-消息队列与紧凑状态)核验准确语义恢复；两者都只继续当前仍获授权的原等待，不能改写旧 key 或用当前 Run 替代原环境证据。原作者 owner 仍验证原 envelope／Run／意图与当前权限，实际恢复目标由 Core 单独裁决。尚未派发的原等待在准确语义恢复后的首次派发仍保留同一 `waitRef`；整条输入确证未应用后的后继尝试才按上述合同推进代次并保留准确前序。继续不重新开启已停止输入，也不以旧 `waitRef` 采纳并发出现的新代次。停止、未经确认的目标变更，以及尚未确证整条未应用的已有派发、未知／部分效果仍沿原回执核对，不能因先前 inspect 合格而越过随后变化；真实 claim 继续由原 journal 与 Session owner 裁决。原作者、operation、message、quote 与 wire 均保留，接收方 capability 只证明调用者，不改成作者或扩大记录读取权限。此能力复用 Core 原等待链及 SDK／JSON-RPC／CLI，不由连接器私下代发、不新增授权库或 Provider 分支；本机 prompt 与其他作者类型仍守各自原权限合同。
- **连接与句柄不冒充持久主体。** 同一原生主体的当前连接、FD 别名及本次观察代次，只用于核对这次准确原对象；它们改变不能单独推导原 actor、thread 或来源已换。新的独立输入按当前原对象重新资格化，旧 unknown 不跨连接重放；真实 peer、process birth、来源或 thread 改变仍拒绝本次错误目标。
- **准备等待保留原意图，并由 Core 统一继续。** 原消息先保存；暂不能接纳或所需协议事实未知时，说明正在等待哪项事实，保留原消息与停止等待动作。只读准备的一次超时不把消息判成终局失败。Core 根据准确原对象的相关事实变化或用户明确重试重新核验；客户端不另建投递循环，不将诊断中的零输入、错误码或“可取消”字样当成重试或取消回执。Provider 已确认的暂时状态可以沿原操作有界退避观察；没有可推进事实的明确不支持保留具名说明与可达动作，不反复探测或承诺自行恢复。输入环境取得后仍须在 claim 与实际派发前核验原目标、意图条件、来源、pending interaction 与当前作者授权。旧 unknown／部分输入先取回原回执，不能重新准备或派发；保存接纳与等待不冒充原生接纳或 delivered。
- **停止等待必须有原 owner 的真实回执。** 原消息 journal 对准确 `waitRef` 的停止与派发授权用短事务裁决，派发 gate 先于新输入 claim：停止先胜只确认该代不会派发，保原消息供有授权的新明确等待；gate 先胜则只能停止观察，即使物理输入尚未写出也不承诺撤回或零派发。跨 journal／Session 保存或回执未知时保原事实，不从缺记录补未应用。草稿取消、关闭读连接或本地停止计时不代替 Core 停止回执；已派发、回执丢失或旧结果未知不改成“未发送”或“已撤回”。取消保正文、原回执与健康 Terminal，不中断、stop 或恢复 Agent。重启不从旧 envelope、标签或新 Run 的 capability 恢复旧自动发送授权；重新等待仍核原 author 与目标，不重播已授权派发或 unknown 输入。
- **正常请求收尾不取消持久等待。** 首次保存已由 Core 受理后，发送请求正常回复、一次性 RPC reader 释放或连接正常收尾，不撤销该原输入的持续等待，也不要求用户再次发送才能继续。首次受理前的真实调用取消、同进程 Core SDK 的显式 `input.signal` 观察取消、原 owner 退出、准确代次停止与授权撤销分别处理；不能靠忽略全部取消修复正常收尾。Hosted SDK 的 signal 只取消当次 RPC reader；已收到保存回执后，停止后台等待使用原准确 `waitRef` 的 Core Stop，不将已结束 reader 的 signal 暗中转换为跨连接取消。持续准备及派发前仍核原作者当前权限，设备归因或已释放 reader 的旧授权观察不代签这一权限，缺少来源则保原输入等待并说明缺项。冷恢复只沿[Composer 队列合同](conversation-input.md#composer-消息队列与紧凑状态)确认的原本机人工授权来源恢复等待，不把持久作者归因升级成当前设备或外部授权。
- **准备超时诊断保留真实观察位置。** 输入面观察已结束的超时保持当时阶段与原观察事实，后续锁释放或收尾不能改写成等待进入另一阶段；这一要求也适用于未识别出暂时原因的输入面。解释当前画面时，尺寸、字节游标与尺寸修订必须绑定原 Run 的同一观察，不能用后来尺寸或另一幅画面补造原因；原尺寸不可读则明确未知。相同错误码不证明正在整理上下文，准确的普通输入面仍未确认也不授权自动重试。旧 ACK 按上述原 operation 边界保留，不能借给新消息。
- **失败提示给具体原因与 logid。** 每次失败，包括进入 Core 前的恢复、存储或连接失败，都返回本次原因和可复制的唯一 logid；用户提供该 ID 后应能通过公共查询找到原尝试。记录保留准确目标、Run、原操作身份、实际步骤、原始错误链、已确认输入与回执及其来源和观察时刻。客户端报告、Core 控制事实、Runtime 受据、未知和观测不可用分别表达；不得以后来快照猜当时是否发送。日志独立于队列移除、归档与会话变化，保留旧 ID 的原记录；正常持久记录跨重启仍可读。日志存储失败单独说明持久未确认，保留可查询的当前记录和发送能力，不能因此拿走健康输入。
- 资源压力下的草稿、消息、诊断与健康发送能力遵循[低资源下的正确性与可恢复性](shared-rules.md#低资源下的正确性与可恢复性)；恢复后的显式重试仍遵守本节原身份、已确认进度与受据边界。

## Hook 配置隔离与非 AgentMux 会话

Hook 观察区分解析、排队、owner 执行、持久完成与回执读取。入内存待绑定只表示 memory acceptance，成功完成回执才代表 owner 完成；sender 的协议期限须包含排队与执行。未执行的排队请求过期后不得稍后落地；同 receipt 的在途重试合并、识别内容冲突，并在 sender 观察窗口内保留去重事实。owner 提交未知仍是未知，用原 receipt 和原生事实核对，不重放 Agent 输入。背压、超时或单条内容越界不得关闭原 Session／Run／终端；对应 binding 沿既有 SDK／Hosted runtime events 服务窗说明受理阶段、未知事实与恢复动作，不承诺跨任意 Core 重启的 exactly-once。

原生恢复身份与会话记录必须属于当前 Agent Session。下属 Agent 的普通工具、权限与生命周期事件及其记录位置不能覆盖主 Agent 的原生会话句柄，也不能把主身份与下属记录路径拼成一个貌似有效的句柄。Provider 已声明的下属事件继续提供状态、活动和在途事实；记录归属不清时如实保留未知，不阻断主 Agent 的工作。合法主会话事件仍可建立或更新主会话句柄，不靠目录扫描、标题或最近文件猜测身份。

Hook 对原生主会话的解释同时使用当前已校验的 Session／Run／Provider 关联和已持久原生身份；这些已知事实只来自 Core，事件正文不能自称可信身份。恢复后仍沿同一事实识别主会话，不能靠上一次内存中的归属替代持久身份，也不能因生成恢复命令就改变关联。Provider 解释原生 Session 的明确父系与主／子事实；主身份未知或父系事实不足时，保留原始 trace 和未知，不能将同目录、Message 的引用父级或界面选择猜成主 Session。

- AgentMux Hook 的安装、读取、更新和卸载必须只作用于 AgentMux 自己的受管配置作用域；Provider 的共享配置文件仍保留用户和项目已有条目，不能把 AgentMux Hook 当成共享默认值。
- Hook 事件必须携带并校验 AgentMux Session/Run 关联身份。没有该关联、关联不匹配或无法确认来源的 Provider 事件不得触发 AgentMux ingress；应记录可诊断的降级事实，不影响外部 Provider 会话继续工作。
- Hook 探测、合并或安装失败属于流程问题时，健康 Agent 继续可用；服务窗说明哪一步未完成、当前按什么能力运行和恢复动作。只有 Agent/进程本身明确终止才允许阻断。
- Doctor 必须逐 Provider 如实报告 Hook 安装策略，包括不受管与无 Hook 的情况；Runtime 不可达也不能把这些策略改成全局默认值。策略声明不代表磁盘配置已安装，实际磁盘安装状态是另一项事实，不能混在同一字段中。
- **Hook 安装状态按这次实际检查判定**。公开 Core 在明确 Provider、Workspace 和执行环境作用域内新读受管配置，报告 installed、not_installed、partial、error 或 skipped，以及检查时刻、范围、原因和恢复动作。文件存在、过去回执、安装策略、整文件格式差异或未核实的原生 enabled 都不能代替完整且当前的受管定义及必要加载/信任事实；已写入受管配置与原生入口已加载分别表达；只有文件或恢复参数事实时不能宣称已激活，明确禁用保持禁用，加载未确认如实说明未知。未查成不能叫未安装。检查不注册安装 intent、不修配置、不执行 Hook，不复制 Provider 的路径/事件/所有权事实。
- **Doctor 不能先修好再冒充原本已安装**。其真实 CLI 入口先做连接前的只读点时检查，再保留普通连接及明确执行环境下的启动／恢复修复；明确标注检查阶段，后续修复不能倒填结果。Runtime 不可达或一家 Provider 失败仍保留其他逐 Provider 检查，健康 Session 和输入继续可用；输出不含配置原文、完整命令或凭证。

- **Hook 认证与原生主体归属分开。** 受管 token 证明事件入口属于某个 Session／Run，不证明 payload 所述原生线程就是该 Run 的主线程。Provider 根据原生协议和本 Run 的可信进程／记录依据解释主、下属、旧会话及归属未知；共享父系 session ID 或字段存在不能冒充主身份。下属活动可在已证当前任务归属时贡献整体工作状态，但不能覆盖主 native locator、用量、权限或重开主轮次。
- **原生定位的用途和证据明确。** 当前 Run 的可信主线程观察与显式语义恢复目标各守用途；确证进程身份失配时不得将新观察伪装成原 Session 已恢复。旧字段缺来源保持未知，不补造历史；校正必须有本 Run 可复核证据和明确可校正的来源，未知或错误目标只影响该次无法确认的操作，不关闭健康 Run。所有 Provider 的既存定位变化须有明确主体或转移资格；缺少见证不是允许偷换的证据，显式 Level B 目标不由 Hook 改换。
- **被接受的事件仍可解释未应用。** 公开 Hook receipt 保留有限、非秘密的原始事件名、主体归属依据、活动／生命周期是否应用及原因；不保存完整工具正文来替代事实。原生记录发现只随相关 Run 和身份需要发生，不扫全 Session，也不靠增大 TTL 或输出增长猜工作状态。

## 按 amux id 搜索 Agent

- 用户原话：「加个功能快速合入 main: 支持按 amux id 搜索 agent」。快速切换的既有搜索应能找到当前入口已提供的 Agent，按 Core 权威 Agent Session ID 检索；Run ID、Provider 原生会话 ID 和普通 Terminal 的身份不是 amux Agent ID。Focus 的对象链接、其他身份和历史正文范围沿[同一搜索合同](focus-context.md#搜索上下文对象身份与历史正文)，不把其他对象 ID 改称 Agent SID。
- ID 输入去除首尾空白后按原大小写连续匹配，支持完整 ID、前缀和中间连续片段；不把散落字符的模糊匹配用于 ID。前缀或片段命中多个 Agent 时展示全部匹配，由用户明确选择，不静默猜一个；这是一组现有行的搜索结果，不改变 CLI 唯一前缀寻址的合同。
- 原名称、上下文、Provider 等已有文本搜索规则与排序保持；快速切换的 ID-only 命中使用中性匹配权重，原注意力、文本质量与观察时间排序不另设 ID 优先级。快速切换只添加已有可见 Agent 行的 ID 匹配，不扩展候选集合；Focus 的筛选和对象结果沿同一搜索合同。
- 选中结果沿原 Focus 或快速切换动作进入同一 Agent 工作面；搜索本身不创建或恢复 Session，不改变原焦点、布局或健康 Run。匹配依现有已加载事实完成，不另建 Core 索引、轮询或第二份身份。

## Hook 事件与原生记录的生命周期

原生 Hook 的事件名来源声明必须在实际投递和消费中生效。经认证的显式事件名优先；负载来源只读取 Provider 声明的字段，即使其他合法字段同时带着不同值也不能覆盖它。指定字段缺席、空白或类型不符时如实保持 unknown，不从另一字段猜名。投递、状态、生命周期、授权与提问以及诊断消费同一已确认原始名；重新启动或恢复时不得带入另一 Provider 的旧来源声明。未知事实保留 trace，但不能凭别名制造完成、交互或提交资格，也不能停止或替换仍健康的 Agent。

工具开始与结束只有在同一 Run、Provider、已核原生会话和同一次工具调用身份都成立时，才合并为同一 trace 项。不同原生会话即使复用工具 ID，也必须独立可读，不能冲突、互相覆盖或造成 Hook 投递失败；缺少主体事实时按原回执保留观察，不从主 Session 句柄、子 Agent 名字／类型或相近时间猜归属。工具关联身份与可恢复记录路径分别表达，记录尚未落盘不能否定已经明确的原生 ID。

原生会话记录在活跃追加、半行尾部和一条记录包含多条消息时，向前分页仍须按同一读取快照连续返回，不重不漏。Provider 只解释原生语义，物理字节位置、文件身份、快照边界和重复读取同一记录由共享读取 owner 持有；不能在 Provider 外侧另设成本统计或改写不透明游标。原生协议所需的辅助身份／元数据验证仍沿其语义 owner，来源自身的格式上限不能替代页预算。游标只携带定位该读取快照所需的事实，不能随历史长度累积。同一逻辑页即使需要多个物理来源，全部实际读取也共用一份字节预算与截止时间，包括辅助身份／元数据来源、预读、打开时的来源验证和下一页游标指纹；并行在途读取在分配与 I/O 前占用同一余额，不能等读取完成后再扣或按逻辑区间估算。取消在真正分配与读取前生效，不能因为此前的元数据检查已开始就继续新的读取。余额不足时如实给出有界结果或诊断，不输出未经验证的 continuation，不影响同一健康 Agent 的输入与原工作面。

原生会话已提交的旁写日志属于同一会话来源，读取快照必须包含所需日志，并验证主记录与日志仍属于同一来源；不能只读主文件而遗漏已提交内容。读取不得写入、截断、删除或锁住原生记录，也不得影响原生 writer 或健康 Run。全部实际读取继续共用上述页预算、截止时间与取消边界；来源在读取中变化、必要日志缺失或不能安全解释时如实诊断，保留已读内容与正常输入，不输出未经验证的 continuation。

原生协议已确认本轮结束或取消后，用户可在同一健康 Session 开始下一轮；取消不能被画成成功完成，也不能因成功 completion 身份缺席而被提交门禁挡住。自动投递仍只消费真实成功完成身份。结束事实必须属于当前 Run、晚于已消费边界，并在下一次提交后被消费；普通通知、旧回执、未结束的工作和未回答交互都不能放开提交。重启后沿同一持久事实恢复这些边界，不增加第二份状态账本。

主轮已明确结束但成功与否未知时，界面与持久状态必须一致地结束“工作中”，如实保留结果未知；普通未知通知不能清除正在进行的工作。子 Agent 自身的事件不能单独改变主轮状态、主会话身份、主轮结束或提交资格，也不能伪造主轮成功；子主体的对话与 trace 仍保留。父轮明确等待子任务结束的收口只消费既有、真实的父轮与子任务事实，不能把带有子主体的任意 Stop 当成主轮结束，也不能为此补造子任务名单。重启后这些身份、状态与提交边界继续保持一致。

主轮已经真实结束、后台子任务尚未结束时，不能拿走用户在健康 Session 开始下一轮的手动操作；整体自动继续仍等待真实成功收口。新主轮开始后，旧主轮等待子任务的成功不能兑现到新主轮，旧子任务的结束继续作为其自身 trace 保留。 子任务收口不能清掉主轮已经上报的真实用量；完整主轮用量只随新的主轮事实更新或清空，不能拿子任务缺少主轮用量当成主轮读取失败。

原生 Stop 若仍可能被其他 Hook 否决并继续执行，就只是一个步骤的观察事件，不能据名字宣布主轮结束。Provider 必须能明确声明此负载没有主轮生命周期；重启后仍保留这个事实，不能再次从名字补成完成或可提交。

Hook 修复必须使用当前操作明确提供的 Executor 执行环境，作用于该 Agent 实际读取的配置目录。普通连接只恢复既有 Hook 绑定，不得在没有执行环境时向默认用户目录重新生成配置；具有明确执行环境的启动与会话恢复承担受管定义的校正。两个 Executor 即使使用同一 Provider 和 Workspace，其不同配置作用域也不能被合并。修复失败保留健康 Run、原工作面和输入，并持续说明失败步骤、运行状态与恢复动作；未知作用域不能被当成默认作用域。自动化验收的 Runtime、配置目录、消息队列与 Session 存储必须隔离，并核对其实际子进程边界。认证与配置只消费明确的测试作用域；在途操作未收口前保持该私有环境，未知或清理失败保留私有证据，不能以扫描宿主进程、恢复全局默认路径或先删除目录掩盖失败。
