## 主题切换与样式真值

- App chrome 的主题由一个根运行时控制器统一投影：它解析已保存的主题身份、dark／light／system 明度、系统偏好与临时预览，写入根文档的 `data-theme`、`data-appearance` 与语义 custom properties（`packages/client-ui/src/theme/runtime.ts`）。设置、系统偏好与启动恢复都经同一控制器生效；选择 system 时随系统外观变化更新；启动首帧由 preload 从同步主题快照写入同一组根属性（`apps/desktop/src/preload/theme-bootstrap.ts`），不先闪回默认主题。组件不得各自保存一份主题真值。
- 投影的属性、主题值与语义映射属于 Surface SSOT，见[Surface 与密度合同《主题与样式 SSOT 规范》](../presentation/shared-rules.md#主题与样式-ssot-规范)。
- Monaco 编辑器跟随已解析的 App 主题与明度；Terminal 继续使用独立的 Terminal palette。切换 App 外观不得改变 Session、Run、Layout 或 Terminal palette 的持久化事实。
- utility 样式与共享 primitives 只消费语义 token，不引入构建期 CSS 工具（见呈现合同[《非目标》](../presentation/shared-rules.md#非目标)）；切换主题不能改变 Session、Run、Layout 或其他产品事实，也不能为同一事实创建第二套状态。

## 设计哲学

- AgentMux 是 Agent-first、terminal-first 的桌面 Client。Agent 状态、用户输入、终端输出和恢复动作必须靠近它们影响的 View。
- 同一信息只在最合适的位置显示一次。Tab 保留工作面上下文，Region 标明其中 Agent 的身份；低频 ID、Host 和时间进入 tooltip 或 context menu；Activity 拥有最近消息。
- 对话模式遵守[连续统一的对话列表](conversation-mode.md#连续统一的对话列表)原则，完整要求由该专题唯一维护。
- 界面层级由 Surface、明度、局部高光和紧凑密度建立，不靠连续边框、重复标题或极小字号制造“专业感”。
- 选择、键盘、拖拽、菜单和可访问性交互使用维护中的成熟依赖与平台模式。
- Desktop 只组合 Core 的公共能力；ctxmux、Core 与 Desktop 的分层和事实归属唯一见 [AGENTS《分层与身份》](../../../AGENTS.md#分层与身份)。
- Renderer 等无 Node client 消费 Core 的纯投影时，公开入口的运行期依赖必须保持环境无关，不能把 Provider、Runtime 或 Node 内置模块带入 client 构建；同一投影继续由 Core 持有，不在 client 复制逻辑或替换 Node API 来掩盖边界错误。

## Agent 主观审美的端到端验证

视觉审美由独立 Agent 看图判断，不以像素距离等工程阈值代替，也不为此建设过度防御的流程。视觉交付必须能沿真实产品的端到端场景留下可重复的截图，并由独立 Agent 看见截图、结合当前任务和两份设计 SSOT 作出可解释的判断。已有产品 probe 承担场景与截图采集；合成展厅、源码字符串或局部几何检查不能替代真实工作面。

截图及评审必须能关联实际场景、产物身份和观察状态；独立 Agent 明确哪些画面已经看到、哪些情况仍缺证据，并给出具体问题、影响和修正建议。未看到画面、目标未显示或采集不清楚时诚实标为未知；采集或评审流程失败不能关闭健康 Agent、清空用户工作面或把流程问题写成产品已经坏了。机制只组合既有 probe、两份设计 SSOT 和 Agent 的看图判断，不增设通用测试框架、自动审美评分或另一份设计真相。判断所用的视觉语言与工程测量边界只定义在密度 SSOT[《Agent 主观审美的判断边界》](../presentation/shared-rules.md#agent-主观审美的判断边界)。

所有界面设计改动的交付约束：独立 Agent 按成熟产品的高审美标准实际看本批完整界面与关键状态；若结论为 needs_changes，修正具体问题、重新采集受影响场景并复审，直到独立评审明确 approved／满意、可交付。原图、未通过意见与修正后候选身份均保留，判断须说明具体画面与理由，不用主观数字评分。未知、未看或仍需修改不能判 done；测试全绿、几何达标、采图成功、高评分或旧批次满意不能代替本批候选的独立满意结论。范围、真实反馈与健康工作面的保护不因审美迭代而放松。

视觉审计须实际执行，且不违背需求 SSOT。每个 UI 改动任务的验收必须有本批候选的实际场景执行、截图与独立 Agent 看图证据；发现问题并修正后，须有同场景复核。有流程说明、采图入口或旧批次报告，不能代替本次已执行。证据缺失时明确缺项，不宣称视觉已验收，审美判断仍由 Agent 完成。

fixture 只定义场景数据、操作、观察点与模拟边界，并引用当前需求 SSOT；不复制设计预期或在 fixture 内另定审美规则。需求 SSOT 变化后，Agent 必须检查受影响场景是否仍对应当前约束，调整已过时的场景并明确未覆盖或未执行的部分；旧截图和旧判断不能因 fixture 仍能运行而被当作当前验收。执行保证沿 UI 任务的验收与证据责任成立，不凭流程说明宣称已有每次自动执行的保证。

## 组件化的独立评估边界

组件化单独评估，以公开 API、服务的定义与实现及消费关系、贡献的注册与释放、真实调用者和替换成本为依据。比较项目仅作为证据，不能成为本项目的实现分支，也不自动形成 all-plugin 或 RSI 要求。评估与后续改进必须保护 Core 与 ctxmux 的既有职责和权威事实，不复制运行时 owner，不阻断健康 Run，不丢失现有工作面。

Provider 的 managed Hook 安装由同一注册对象完整贡献、插件注册先整体校验再进入目录，这两条约束见[《插件扩展边界》](agent-capabilities-and-messaging.md#插件扩展边界)。

## Owner 边界

ctxmux、AgentMux Core 与 Desktop／client 三层的事实归属唯一见 [AGENTS《分层与身份》](../../../AGENTS.md#分层与身份)。Desktop 只经 Core 公共 API 消费 ctxmux 事实；Agent 语义状态由 Core 持有，Desktop 只投影。下表细化 Desktop 内部（Main、Renderer）与 Scratch 文件系统的 owner：

| 事实或动作 | 唯一 Owner | Desktop 的职责 |
| --- | --- | --- |
| Space／Zone／Tab／Group／Region 身份、拓扑、布局、选择与全部绑定 | Core Spatial owner | 消费同一持久图，投影屏幕与发起原操作 |
| 屏幕几何、可见性、DOM 挂载与输入焦点 | Desktop／client | 不从屏幕观察改写空间或执行身份 |
| Workspace Root、revision、写入、观察、move、Git、Browser WebContents 与原生系统能力 | Desktop Main | 提供 typed IPC 和最终磁盘事实 |
| File tree、buffer、dirty、generation、冲突、路径映射与交互 | Desktop Renderer | 消费 Main 事实并原子投影视图状态 |
| Topic 内容与协作者身份 | Scratch 文件系统 | 枚举、导航和绑定 View |

任何一层都不得为方便 UI 再持有第二份 Runtime、Session、Topic、Layout 或磁盘真相。

## 按操作判断强弱依赖

强弱依赖是**某项事实与某次操作所承诺结果之间的关系**，不是给组件贴的永久标签。判断前先说明操作、准确目标、承诺结果、权威 Owner 及其事实来源：缺少这项事实，是否仍能合法、安全、如实地完成该结果？准确目标、授权、真正必要的执行条件及业务必需的持久 admission／commit 可以阻断该次操作；不能因为启动慢或用户急需就跳过。

辅助观察、增强、展示与辅助记账的迟缓或失败，不得拿走已确认且仍可执行的高优能力。同一 Provider、Hook 或存储步骤对不同操作可能有不同必要性：续接原生上下文需要原 Provider 身份；接回仍健康的准确 PTY 不应等待无关 Session 的语义恢复。不能把必要业务提交改称“记账”后跳过，也不能因为多个步骤被同一个函数等待，就把整组步骤变成所有操作的强依赖。具体恢复前提由[Durable Runtime 健康](session-recovery.md#durable-runtime-健康)按操作说明。

启动与恢复应按相关消费者逐级、按需加载：先呈现原持久工作面，准确健康 Run 具备接回条件时先接回；无关的全局目录、历史、名称补充和辅助观察继续独立推进。某个目标缺少自身必要事实时，只将该目标的相应结果保留为未知或明确拒绝，不让低优加载拖住其他已可用能力。沿完整真实调用及回执交付链判断依赖，不能入口放行后又在结果投影等待同一无关全局恢复；工作量不因无关 Session 放大。

非阻塞不等于隐去失败或虚报成功。沿[原服务窗](session-recovery.md#我们的流程坏了不等于-agent-坏了)持续保留失败步骤、最后确认事实、未知范围和可执行恢复动作；恢复后由准确原事实收口。原身份、请求和已确认进度保留，未确认结果不猜成功或死亡，不自动重放未知操作。新增拦截的审查方法沿[RED-LINES](../../../RED-LINES.md#写拦截前回答四个问题)。

## 低资源下的正确性与可恢复性

**原 Session 的持久身份与原生上下文可恢复性是 P00 基础。** 长程任务跨磁盘满、内存高压、挂起、进程丢失与系统断电，须保全各 Owner 已确认持久的原 SID、Provider 上下文来源、工作面及原操作／未知投递，按原身份继续核对和恢复；不能靠新 PID、空白会话或重建工作面宣称完成。物理进程存活时保原 Run；失电后不承诺原 PTY 仍存在，原上下文恢复的准确资格与 Level B 边界归[Session 恢复](session-recovery.md#durable-runtime-健康)。这是设计底线，不代表所有故障场景已验收。

- 磁盘满或不可写、CPU 与内存高压时，身份、授权、已确认进度与 Owner 边界仍须正确。资源不足允许变慢；观测超时或诊断失败不证明 Agent 已死亡，不能因此关闭健康 Agent 尚可使用的能力。
- 草稿、消息、工作面与最后已确认的持久记录不得因资源故障被静默清空、覆盖或移除。进程仍存活时保留未保存的当前内容并明确提示；内存保留不等于磁盘保存，写入或替换未确认也不等于保存、入队或投递成功。需要持久确认而无法完成的动作如实失败，不能先返回成功再丢弃内容。
- 失败说明实际受阻步骤、已确认事实、未知范围与恢复动作。资源恢复后仍可显式重试原操作，沿原消息、operation、条件、执行方式、授权与已确认进度续做；不能自动重投未知输入、改换操作身份绕过去重，或让旧失败永久占住未来尝试。该次目标或授权有误仍应拒绝，不扩大为禁用整个健康 Session。
- 诊断沿原故障 Owner 保留失败阶段、原始原因、已暴露的 code、关联 logid、观察时刻、已确认写入与未知进度。诊断保存、上传、采样或回执也受资源限制时，明确哪些记录只在当前进程可读、哪些已持久、哪些缺失；持续展示尚可取得的事实与恢复动作，不以空日志证明无故障，也不把后来的恢复状态代作失败当时的事实。诊断自身失败不能掩盖原错误，或再次阻断仍可执行的发送、取消与后续重试。
- 保全承诺以实际持久确认与进程存活为界。物理不可写不能保证新增内容落盘；OOM、强杀或系统崩溃前未完成持久确认的内容，不能承诺跨进程必然恢复。重启只按最后已确认的记录恢复，缺失与未知如实说明，不伪造内容、受据或成功状态。

## 验收原则

- 行为验证优先于 CSS 声明：Production Electron 要检查真实尺寸、DPR、overflow、焦点、拖拽落点和恢复结果。
- 安全与状态一致性不能由截图替代，须由对应 owner 的测试与真实产品调用链证明；命令选择见[测试策略《Gate》](../../testing/strategy.md#gate)，验收分层见[《任务验收与假绿防护》](../../testing/strategy.md#任务验收与假绿防护)。
- 文件保存覆盖继续输入、外部修改、删除、读取失败、写入失败和替换失败；草稿不被静默覆盖，原文件不被失败写入截断。
- 文件移动覆盖目标碰撞、外部竞争、Workspace Root／父目录换代、source／destination 被无关对象替换、helper 缺失和 syscall 后回执失败；磁盘未确认成功时 Renderer 状态保持不变。Explorer 的移动入口（指针拖放、Move 子菜单、`Shift+F10`）只移动单项选择；非法 drop 不施效；悬停展开在离开或取消后清理；Explorer 拖放与 Workbench 的 Tab／Region 拖放互不接收；Workspace 回访时已满足的状态不再触发 Explorer 投影通知；旧 Workspace 留下的 parent refresh 在 Renderer admission 被拒绝，不到达 Main，也不污染当前 Workspace 的缓存。真实 Electron 的验证方法见[测试策略](../../testing/strategy.md)。
- 资源收益只用同一场景的 before/after 数据声明，不强制 GC，不卸载仍使用的 Surface，不增加全局 Cache 框架。
- Unsupported 能力明确失败关闭；不加兼容层、migration、fallback、第二 Runtime Owner 或隐藏 Registry。

## 非目标

- 不把 AgentMux 做成另一个 Run Runtime。
- 不把 Desktop 布局、Topic、Provider 或 Agent 语义下沉到 ctxmux。
- 不为命令对称、未来平台或未出现的规模证据预建功能。

## 语义图标体系

- 具有产品语义的状态、对象、动作、导航和层级图标统一经过 semantic icon 目录；调用者传入语义枚举，不直接在业务 JSX 中选择 lucide glyph 或写状态字符串。
- 编辑器、终端和第三方内容内部的图标不强行迁移；只有跨表面共享、需要无障碍名称、状态表达或动画策略的图标进入该体系。
- 动态图标、动画图标和组合图标都必须通过同一 renderer contract，支持 `prefers-reduced-motion`、`aria-hidden`/可访问名称、稳定尺寸和低成本重渲染；动画不能由业务组件各自实现。
- 不保留向后兼容、migration 或 fallback；旧的 icon 语义直接删除或明确替换，不能让两套语义长期并存。
- 同一功能含义使用稳定语义 ID，跨客户端沿同一身份引用；不同含义保留独立身份与主题覆盖入口。几何与辨识要求沿[语义图标密度与性能](../presentation/shared-rules.md#语义图标密度与性能)。图标映射测试必须钉死完整集合而不是只断言“有图标”，验收方法沿[任务验收与假绿防护](../../testing/strategy.md#任务验收与假绿防护)。
- 动态选择只消费原 owner 对准确对象的当前活动或已应用回执，不从图标、文案或点击推断运行、权限或成功。默认静止、具体动作与 reduced-motion 统一沿[同一呈现合同](../presentation/shared-rules.md#语义图标密度与性能)，不在行为层另定义动作样式。

## 共享控件的选择与键盘行为

动作菜单执行命令。单选字段沿 Listbox 表达候选和已选值。需要查询或额外操作时，具名对话框在同一浮层中提供原生输入和 Listbox。长本地选项列表在原选择字段内提供按名称与说明查找、清除和无匹配反馈；查询只缩小当前可选项的呈现，不改变已保存值、未知原值或禁用事实。键盘高亮与已选值分开，显式确认才调用原选择动作；IME 组字、方向移动和关闭返焦保持。少量选项保持简明，已有真实远程搜索和分页不替换为本地全量过滤。

Note 与截图标注的原工具栏按组提供键盘进入与离开：Tab 进入一个可用项，方向键／首尾键只移动当前组焦点，Tab 离开；显式激活才执行原动作，跳过不可用项，原选中事实与编辑器选区保持。编辑器、IME 与 Terminal 自己的方向键不被组外处理器截获；沿维护库或既有 owner，不另建全局键盘系统。

## UI 架构实施原则

- 先分层和确定事实 owner，再写组件；设计、需求、状态和验证保持在项目知识 SSOT 内，避免无意义的平行抽象。
- 共享动态视觉的组件 owner 同时负责浏览器渲染成本边界，宿主提供真实槽位和可见性；组件复用、独立调度与隐藏停活之外，还须保护同文档内的 Terminal、编辑和阅读响应。具体边界见[《动态视觉的渲染边界》](../presentation/shared-rules.md#动态视觉的渲染边界)，证据方法见[浏览器成本验证](../../testing/strategy.md#动态视觉的浏览器成本验证)。
- 实现选择（满足当前需求的最简单实现、复用已有依赖与成熟模式、先跑通最小端到端、不留「以后再换」的临时兼容层）唯一见 [AGENTS《实现选择》](../../../AGENTS.md#实现选择)；测试范围与执行成本沿[测试策略](../../testing/strategy.md)。

## 产品表面设计审核与参考层级

- 新的桌面工作面、浮层和工具栏在实现前必须先找同类成熟产品作为参考；参考必须匹配对象和交互，而不是只借颜色或圆角。浮动终端/工作面优先参考成熟桌面终端的浮动面板形态：一行紧凑工具栏直接承载 Tab、分屏和新建动作（高度预算见[《密度预算》](../presentation/shared-rules.md#密度预算)），工作面不再另造一条大标题。
- 设计默认采用内容优先、工具条优先和单一 chrome。标题是身份元信息，不是首屏主视觉；如果去掉标题仍能从 Tab、头像、状态和工具提示识别工作面，就不要保留大字标题、副标题或欢迎式说明。
- 一个表面只能有一套窗口边界、一套标题/Tab 层级和一套关闭语义。把完整 Workbench 放进弹窗时，必须复用 Workbench 的顶层 Tab/工具栏，不得再套一个同义标题栏、第二个空壳或重复的 PMO 入口。
- 评审第一眼必须能回答三个问题：当前工作面是什么、第一交互是什么、内容从哪里开始。不能回答时先删减层级和装饰，再考虑增加说明。大标题、宽 padding、持续副标题、重复边框和无操作的品牌卡片属于默认拒绝项。
- 参考证据、反例和最终截图／运行态核验随该任务的验收证据保留（留存边界见[过程资料规则](../../process-directories.md)）；「看起来更现代」不能只作为口头判断。验收至少包含正常宽度、窄宽度、打开后第一帧和拖动中的状态。
