## Ticket 的身份与地址

Ticket 是 Goal 计划中有明确产物、成功标准和检查的工作节点。同一 Ticket 保持稳定身份，认领记录某位执行者承担本次工作，派工确定执行尝试和实际输入。要求修改时，同一 Ticket 用新尝试交付，旧报告、评审和前置来源仍可读。一次性的约束作用于本次认领和尝试，历史依原记录保留。

Ticket ID 使用版本化、可复算的记录摘要。该记录至少绑定原 Goal、经认证的创建者和原创建操作，由系统签发。接收方可用原记录复算 ID 并核验签名，检测 ID 与内容不符、内容损坏或凭证被替换。各集群独立生成，发布顺序与共享计数器均不参与。

计划发布时就为 Ticket 签发完整 SHA-256 摘要作为正式 ID，创建记录绑定直接前置的 Ticket ID。摘要采用 Base64url 编码，签名沿原 Runtime 的 Ed25519 密钥。同一修订内可先按依赖拓扑签发上游身份，再签发后继身份。原创建记录保持可复算，变更后的状态与后续尝试沿自己的凭证核对。Agent 继续使用原计划发布、认领、派工和评审入口，系统在相应操作中生成和校验凭证。

`amux://goal/<GoalID>#T-<nodeId>` 直接引用同一个节点，原 Goal ID 也完整保留。已发布的节点以取消结束，重排、改名、改派和返工沿同一身份，取消后仍可追溯。删除 Goal 时，原 owner 保留身份终局记录，旧地址不会打开重用同 ID 的新任务。未拆分 Goal 使用原 Goal 链接。认领回执和派工上下文给出可直接使用的地址。使用 Git 的 Agent 可将地址放入 commit 的 `Goal-Node` trailer。交付、合入和评审采用各自的原回执。

短式地址的签发和解析须使用该链接到原 Runtime、存储命名空间与 Goal 的可信绑定。缺少绑定时，签发原限定 Goal 地址加同一个节点片段。Goal 根 ID 的签发见[原 Goal 地址](goals.md#清单详情与当前下一步)。打开短链时，以原 owner 的创建记录和地址重算完整 ID。当前仅发现一个同 ID 的 Goal 时，解析仍核对原绑定。来源或节点待确认时保原链接、目标和工作面。地址只负责阅读定位，权限沿原 Goal owner 核对。 [Goal 阅读地址](goals.md#清单详情与当前下一步)

## 活跃任务与认领

Agent 可以从公共 CLI 和 JSON-RPC 获取当前有用的工作。可认领查询返回已开放、前置条件成立且调用者具备资格的节点。管理查询也能读取正在执行、待评审、待修改和需要对账的节点。已结束的工作留在原记录，按准确 Ticket、尝试或回执读取。查询只读取事实。

人在 **Goals → Tickets** 可以跨 Goal 查看当前工作，并通过 Ticket 回到原节点、执行尝试和交付。CLI 对应 `amux goal plan active --view manage`；用 `--goal ID` 限定原 Goal。Supervisor 的查询按原身份只读其负责的 Goal。日期、历史评审和待前置节点均沿原计划阅读。未拆分成计划的工作继续从 Goal 本身进入。

Host 以相关 Goal、活跃节点和核对资格所需的前置事实限定读取和投影范围。活跃查询的成本须随实际相关的节点与引用增长，包含存储读取和状态推导。跨 Host 或来源不可读时，原工作仍可沿已知身份继续检查。

认领由原 owner 原子核对准确节点、开放状态、当前执行资格及相关前置，然后绑定一个实际执行者。竞争同一节点的其他调用可读回现有分工。认领独立节点时，无关节点的认领、交付或展示变化无需令这次操作重新提交。涉及本节点目标或依赖的变化时，核对实际受影响的事实。丢失回执沿同一 operation 对账。

## 前置交付与血缘

后继只有在直接前置的交付通过声明的节点评审后才能认领或派工。原 owner 在认领时冻结每个直接前置的节点、具体交付及对应通过回执。直接派工无单独认领时，在准备原派工时冻结。实际派工核对所依赖的交付仍符合本次资格。后继提交沿同一次尝试自动保留这些引用。多个后继可并行引用同一份通过的产物，各有自己的认领与执行尝试。

有通过结论但缺少原签名完成回执时，原节点状态为未知，依赖该成果的后继继续等待。保留原评审、尝试和产物，读取原 owner 的回执确认后再推进。

前置引用保留当时的版本。相关标准或前置交付变更时，新认领核对当前有效事实，已发生的工作继续可追溯到实际使用的版本。当前尝试依据不足时表达待核对及受影响的依赖，原产物、原回执和健康工作面继续可读。追溯沿直接前置逐层打开原记录。

认领时，系统签发凭证，绑定本次 Ticket、执行者和各直接前置已通过的具体完成回执摘要。直接派工在冻结尝试时签入同样的血缘。完成凭证由独立评审通过触发，绑定此次执行的血缘凭证、具体交付摘要和评审事实。认领和完成各保留自己的摘要与签名。同一操作重试读取原凭证，新的尝试引用当时有效的前置完成凭证，已发出的 Ticket ID 保持稳定。

接收方凭原记录、签名和对本次用途获准的签发者公钥，可以核验下游所引用的确切 Ticket、尝试与产物版本。签名证明谁签发了这些事实，接收方按已有验收合同判断该结果是否可合入。

## 交付、核验与自动接续

Agent 可以沿用户原有工具完成工作，交付时引用准确产物版本、检查结果及原证据。报告、文件、研究实验、工单和代码合入都可以提供节点所声明的证据。外部工具保有原业务记录，Goal 通过实际来源核对所需事实。只有节点把合入列为完成条件时才需要原仓库、目标分支、实际落地提交和匹配的检查回执。用户已有合入和审批入口可直接使用。

使用现有工单时，在 Goal 正文链接原工单；报告按所对应的 Ticket 和标准提交成果链接。代码交付可引用落地提交及对应检查，文件或研究交付可引用固定版本和复验材料。原工单或 PR 的状态可供评审查证，后继接续仍取决于本 Ticket 的通过回执。

原 Goal owner 按已认证作者计算交付哈希。输入包含准确的原 Goal、节点和尝试、作者的 Runtime 与 AgentSession、冻结的直接前置回执，以及原报告内容和产物版本。采用明确版本的规范编码，同一次提交重读或重试保持相同哈希。评审绑定具体交付哈希及实际检查；新的交付与验收各沿自己的原操作。

原 owner 确认当前 Ticket 的交付后，按本 Goal 已授权的工作流安排独立复核。复核任务绑定准确 Ticket、尝试、交付哈希、检查和独立评审者。评审者实际运行本节点声明的检查，并沿原节点评审保存结论、证据与作者。重复的触发或未知投递沿同一原操作对账。同一尝试的较晚回报以及已被取代的交付保留原记录，当前结论继续由原 owner 核对。缺少准确评审者、授权或检查资源时，当前交付保持可读并显示待处理依据，人工独立复核仍可用。

复核通过后，原 owner 根据签名完成回执推导下游就绪，已有明确派工资格时继续派工。要求修改时沿原 Ticket 及 thread 交代实际原因，返工沿原尝试规则推进。权威检查回执可作为独立复核的证据，执行者自报、外部标签和来源无法读取各保原事实。所有相关节点通过后，准备目标核验材料并等待人的 [结果接受](goals.md#目标确认与结果接受)。

## 可信集群的发起与完成回执

Ticket 的工作回执以可信集群为首版前提。Goal 根保存原 owner 的 Runtime、存储命名空间和 Goal ID。同一 Runtime 内的作者可引用准确 Session，跨 Runtime 的作者须保留该作者的原 Runtime 与 Session。Core 或 Host 从已认证调用中取得作者身份和权限，Agent 沿自己的身份调用 CLI，系统按原操作记录署名。

- **发起回执**记当前创建者、Ticket 和原创建操作，以及能核实的触发操作。由 A 提议、B 有权采纳时，两次操作分别记录。一个 Agent 手上有多项工作时，触发操作沿实际指明并核对的尝试追溯。
- **完成回执**关联该次交付和独立评审。它能回答谁交付、哪次尝试、哪份产物通过了谁的检查。发起者、执行者和评审者可来自不同 Session，资格由各自操作核对。

例如 A 执行一个 Ticket 时提出后继，由有权限的 B 把后继加进计划。发起记录指向 A 的实际提议与 B 的计划修订。后继如果依赖 A 的产物，认领时另外绑定该产物的通过回执。C 交付后继后，D 的评审核对该份交付。创建来源和依赖来源各自可追溯。

已存在的跨 Runtime 通信继续遵守 [原消息签名与目的信任](a2a-collaboration.md#跨-runtime-原消息与回报)。Ticket 回执保存准确的签发者、作者、对象与前置引用，供原 owner 核对。签发、实际产物与业务通过各有证据。

## Goal 计划：节点、评审与盯盘

公开指南从同一 Goal 的计划、当次交付和评审进入，标明可分派与须返工的节点。命令帮助持有准确参数，评审回执不明时回读原节点与原委派。

### 工作流模板与计划修订指引

系统提供可复用的 Goal 工作流模板，描述方法所需的职责、依赖、交付、检查和结束条件。工作流从 [Settings → Goals → Workflows](settings-and-observation.md#设置页的信息架构) 配置，也可由 Agent 从 Goal 模块 skill 发现。同一份模板由人或当前 Supervisor 对照本 Goal 的成功标准实例化，经原计划修订发布为 Ticket。查看、选用模板和发布计划各有明确时机，实际执行仍沿原分工、派工与授权。设置变化作用于未来使用，已保存的计划、当前尝试和回执沿原来源读取。

Goal skill 为计划修订提供增量复查指引。以当前成功标准正文、产物版本、实际检查和冻结的前置完成回执核对受影响节点，保留未受影响的原评审，指明哪些证据需要复查。操作结果未知时以原派工或评审操作对账。指引消费原计划和回执，复用同一修订、评审与恢复入口。

### 计划发布与推进

一个 Goal 是一个完整目标；目标较大时，在 Goal 内拆成计划，而不是拆成多个零碎 Goal。计划是一组节点及其依赖构成的有向无环图。每个节点写明要达成的结果、依赖哪些节点、覆盖当前目标提案中的哪些成功标准，以及可由他人复核的检查。计划是同一 Goal owner 内的业务记录，不创建分支、不要求提交，也不依赖任何仓库状态；代码在各项目中如何合入仍按项目自己的方式。

Goal 详情中始终可读[推进图](#详情工作台的原记录)。「拆分计划」沿原制定入口经同一 Supervisor 请求机制向该 Goal 当前合法 Supervisor 发出明确的制定计划请求：围绕当前目标提出节点、依赖与检查，并将结构化计划保存到同一 Goal owner；仅打开讨论、返回一段拆分文字或准备了请求，都不算计划已建立。保存后的计划在原 Goal 详情可见，不要求用户另开隐藏视图或先学习 CLI。计划写入仍由当前合法 Supervisor 或人完成；专属讨论的存在不自动授予管理权，没有 Supervisor 时，客户端保留原请求并沿原关系入口明确选择；保存选择本身不发送，之后一次明确点击才发送同一请求。Agent 作为当前 Supervisor 应直接读取和修订计划，不能请求自己。不暗改负责人或冒用人的身份。阅读 Goal 不写入计划修订、节点、依赖、执行委派或持续推进。

制定计划、目标确认、节点派工、人的结果接受分别成立。已有真实目标提案时可以据其当前标准编制计划，不因尚未确认目标而隐藏计划入口；缺少目标定义或可引用标准时，在原讨论说明具体缺口并先整理同一 Goal 的提案，不虚构标准、人的确认或依赖关系。请求沿原 Host 的同一持久准备与输入机制冻结准确 Supervisor Host、Session、Run、请求者及当前提案与计划版本，和 PMO 巡查按用途隔离；忙、有草稿或观察未知时保留准备，可投递时只尝试一次，未知只对账。Supervisor 变更保留原请求为陈旧，新明确请求才指向新负责人；同一 Session 恢复后仅从未尝试且原 claim 确认不存在的请求可显式接续。计划请求不接受巡查回报、不进入巡查告警；保存新的计划版本才是完成事实。已冻结或已 claim 的旧专属讨论请求沿其原接收者只对账，不重发计划正文、不改投，也不妨碍向当前 Supervisor 发出独立新请求。请求准备、实际送达、计划保存与派工分别反馈；失败或回执未知保留原 Goal、计划请求与讨论身份，先核对原操作，不重复投递或新建替代目标。

计划由 Supervisor（通常是 Mote）在目标提案之后提出并维护，人可以随时修改。每次修订带计划版本并按版本比较写入，两个调用方同时修订时后到者被拒绝并先读取当前计划，不能静默覆盖。同一操作的重读须核对原作者、预期计划版本、提案版本与节点正文；该操作之后已有新修订时说明原操作生效的版本和当前版本，先读当前计划，不把新计划冒称原操作的重放。新节点或无执行记录节点本次改写的成功标准集合须非空且属于当前提案；未改动的既有集合保留，陈旧引用沿原节点明确对账。依赖必须指向同一计划内已有节点且不能成环。已有执行记录的节点保留原结果、检查与成功标准集合，换成另一项任务须取消原节点并新增节点；标题与执行者仍可明确修订。目标提案换版后，节点引用的成功标准按当前原文与原委派冻结的标准核对，缺失或正文改变的标准如实标出，旧评审仍可读但不代签当前完成、不解锁依赖；未变化的标准成果继续有效，不因无关提案换版作废。

已关联 Goal 的范围内，衍生工作和拆解由当前 Supervisor 或人写回原计划。会话引用保存回执中的原 Ticket。新增工作可以依赖已完成的 Ticket，保留它的原交付、评审与签名。追加只提交新节点及依赖，原 owner 用当前计划检查引用和成功标准。并行追加独立分支可以共用同一标准版本，无需提供读取时的计划版本。改动已有节点继续按原计划版本比较。人负责目标验收，已关闭的 Goal 须明确重开才可追加工作。

节点只持有业务关联，执行仍沿[委派回报与责任接续](goal-execution-and-supervision.md#委派回报与责任接续)：Supervisor 把一个依赖已全部完成的节点委派给一个准确的 AgentSession，沿 Core 原 thread 发送冻结任务；委派记录保存所属节点和冻结的直接前置回执，原输入、报告与评审沿同一尝试核对。执行 Agent 可以在本机、在远端 Host，或通过远端执行绑定在远端项目中工作；节点以 Host 与 AgentSession 精确指向执行者，Project 与执行 cwd 分别成立，不从名称或显示位置推断位置。委派与回报沿 Core 原通信，跨 Host 的来源与反向回报沿[跨 Runtime 原消息与回报](a2a-collaboration.md#跨-runtime-原消息与回报)的独立目的信任与原签名成立；不转发受管 Agent 凭据。原 Goal 只在监督者的 owner 中保存，委派分别冻结 owner 与 worker Host、双方 Session/Run、标准版本和原消息。执行者从本机已核验的原 source 与严格结构化 Goal 载荷回报，不解析可见正文确定权限、不复制 Goal Store；回执明确区分远端报告已持久准备与原监督者已收集。原监督者沿现有连接取回已签原回报，再按原委派核对并收集评审。信任或观察不足时保留原计划、执行者和消息引用，明确未确认的阶段及恢复入口，不改派、不降为无来源的消息。节点可在计划中写明执行者（Host 与 AgentSession），委派必须指向该执行者；一个节点同一时刻只有一个当前执行委派。换人通过计划修订改写执行者完成，原委派、报告与 thread 保留。明确写入不同的非空执行者时，最新且尚无评审结论的尝试被取代，不再驱动节点状态；依赖已满足时可派给新执行者。清空执行者不取代原尝试，已通过的节点不因换人重开，要求修改的节点沿原返工规则明确改派。在新执行者尚未收到委派前改回原执行者，原尝试仍可恢复为当前尝试；新执行者已收到委派后，旧尝试只作历史。被取代尝试的迟到报告保留在原委派并标为前一次尝试，不能作为当前尝试接受节点评审。

人或当前 Supervisor 可直接指派执行者，也可把已有计划中依赖已满足、尚无执行者和当前委派的工作节点开放认领。既有计划默认维持原分工，缺少开放记录不产生认领资格。该 Goal 当前的负责人或 Supervisor 可通过公开 CLI／JSON-RPC 以经过认证的自身身份认领。仅被列为相关 Session 的 Agent 可读取计划。原 Goal owner 沿[活跃任务与认领](#活跃任务与认领)原子保存一位执行者；竞争者可以读回最新分工，同一操作可对账。认领只建立责任关系，真实派工、交付、节点评审与人的结果接受分别沿原流程。对身份、版本或授权的拒绝只作用于本次写入。分工请求在本地准备阶段确认尚未发出时，保留原选择并允许修改。写入已尝试且回执未知时，先核对原操作与准确计划版本。

执行 Agent 按节点的成功标准逐项回报，相当于一次待评审的交付。节点完成需要一次评审：评审方必须是执行者以外的 Agent 或人，实际运行节点声明的检查，并把检查命令、结果与证据位置记在评审结论里，结论只有「通过」或「要求修改」。要求修改时，Supervisor 在同一 thread 上向执行者发出返工委派，原委派、报告与评审保留。评审通过的节点才算完成，其依赖者才可开工。评审节点的结论不代签 Goal 的结果接受；所有节点完成后，Goal 的结果仍沿[目标确认与结果接受](goals.md#目标确认与结果接受)由人接受。

Goal 内的交付入口指向原计划节点和准确的当前委派。要求修改后的新交付与先前结论在同一节点可追溯。界面保存人的节点评审时沿原公开 `goal.plan.review` 与相同依赖推导；焦点、按钮操作、已保存的报告和独立复核各有明确回执。回执未知时，Desktop 持久保留该次冻结请求和草稿。用户可在原交付回读 Goal，回读只查询原记录。以原 owner 保存的评审核对同一次请求正文，确认后只收起对应评审草稿。评审作者、记录时间和完成签名随原回执保留。单次直接执行沿原结果接受入口。

节点状态不单独保存，由依赖是否完成、当前委派与报告事实、最新评审结论推出：等待依赖、可开工、执行中、待评审、要求修改、已完成、已取消，以及委派或观察事实未知时的未知。Agent 退出、idle、投递或 ack 都不推出完成。依赖未完成的节点不能委派；节点之间可以并行的就并行推进，不要求逐个排队。

盯盘复用已有的持续推进：Goal 的 Supervisor 以该 Goal 为任务来源开启持续推进时，每次检查同时读取计划。有可开工、执行中、待评审或要求修改的节点时继续推进，并把这些节点和各自的原 thread 交给 Supervisor 核对；全部节点完成时暂停，等待人接受结果；剩余节点都在等待已取消的依赖时暂停，说明需要修订计划；计划不可读时暂停并说明原因。节点处于未知时继续推进，并要求 Supervisor 先按原回执对账，不因观察缺口停掉盯盘。不为计划另起第二套调度或轮询。

公开能力：计划的读取、修订、节点委派与评审都经同一 Goal owner 的公开 JSON-RPC 与 `amux goal` 命令提供，帮助说明节点、依赖、评审与盯盘的关系，管理者与执行者的上岗指引引用本节。Desktop 与 CLI 读同一份计划和推导状态，不各自另算。推导由 Goal owner 随每份返回的计划一并给出，当前尝试只引用原委派的 `delegationOperationId` 与 `reported`；source、thread 和 worker 从同一响应的原委派唯一事实读取，不复制参与者身份。owner 未附推导、推导结构失效或与所附计划／委派对不上时，只隔离这份非控制推导，在该 Goal 显示节点状态不可用、具体原因及重读原 Goal／更新原 Host 的恢复入口；原计划、委派、列表其他 Goal、写入原 operation 与回执仍完整可读，不重复已保存的写入、不自行补算节点状态。控制写入仍由原 owner 核对权限、版本、依赖与原消息。若计划状态推导失效，只读投影附 `planStateIssue`；旧严格读者须与 Host 同时升级，不保留旧尝试镜像字段兼容层。

### 详情工作台的原记录

看板负责跨 Goal 的扫描与选择，详情围绕同一 Goal 阅读分工、依赖、当前交付和执行记录。分工、图、执行记录与协调入口定位同一原节点、当次委派及其检查；旧尝试保留原证据，不能用它评审新交付。Goal 默认就是图中的唯一工作节点，包含原目标、目标当前结论、成功标准与原执行。拆分后同一位置读取原 owner 保存的节点和依赖。图的 Start 和 Finish 只解释同一流程的首尾，不参与任务计数、委派或评审。完成标记同时依据 Goal 完成与当前结果接受事实，保留带差距接受、旧完成未验证和取消的区别。单次尝试失败继续归该尝试。默认节点直接读取 Goal 本身，既有 Goal 无需补写。

打开详情默认阅读推进计划，返回清单保留原筛选、视图和焦点。首个当前待评审交付可直接阅读，查看交付只定位原节点和当次委派，不提交评审。分工、图、执行记录和 Supervisor 的准确协调入口共用同一节点读取，显式选择保留在此次详情内。详情页头的当前结论可以定位到同一原委派、一次性任务或 Supervisor 栏中的原巡查。巡查的核对、选择 Supervisor 和显式续接使用原请求与原执行关系。从计划图进入 Supervisor 栏的编排入口，只改变阅读位置与焦点；发送或续接编排另行显式操作。提交、回收和确认仍在原记录操作。协调记录的作者按原身份及 Host 读取已确认的名字，来源不完整时保留原作者引用。

执行记录以原操作与确切时间事实为准。派发关联、结果回报及评审等只证明各自事件。可证实的执行时间区间才画成执行条；仅能确认当前语义活动时，区间止于原观测并标明尚未结束。Goal 的明确计划起止另画为排期，单侧日期仅标该日期。缺起止的历史保持为事件，输入未确认不推断开始，计划依赖不生成预计时长。

甘特图的标题和执行条打开准确的 Ticket 或尝试。单个时间点在悬停和键盘聚焦时预览发生时间、作者、动作和结果，缺失事实显示为未知。鼠标、键盘和触控都可打开持续阅读的详情。详情按原引用进入 Goal 下的事件、Ticket 或该次尝试，历史报告和评审随原尝试保留。关闭详情或从尝试返回时，焦点回到触发的时间点。时间点消失时回到它所在的原行。重叠点和紧凑记录也可逐个阅读。

Supervisor 的待办和协调记录消费原负责人与已有派工、计划修订、评审、巡查及决定。作者按各自原记录展示，导航仅定位已确认的节点与尝试。交接读取同次委派的原任务负责人与执行者。只有原负责人身份与当前 Supervisor 绑定一致时显示 Supervisor 角色。回报来自原执行者时才可展示返回方向，提交回报和回收报告各自以原回执为准。阅读和联动不授予输入或验收权限，目标确认与人的结果接受仍沿原入口。
