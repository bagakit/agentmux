# 事故案例写作指南

本文规定整理为长期知识的事故案例（postmortem）应保留哪些证据，适用于 `docs/casestudy/`。逐轮排查、候选评审和现场草稿遵循[过程资料边界](../process-directories.md)，留在本机，不提交。健康能力的判据归 [AGENTS《健康能力与未知状态》](../../AGENTS.md#健康能力与未知状态) 和 [RED-LINES](../../RED-LINES.md)，Task 的验证方法归[测试策略](../testing/strategy.md#任务验收与假绿防护)。

## 存放位置与命名

- 案例放 `docs/casestudy/`，**按用户看到的现象命名**，kebab-case。
  例：`stale-package-feature-disappearance.md`。
- 同一根因的第二种形态，**追加到同一文件**里的 `## 复发：<新现象>` 小节，
  不新建文件。见 `docs/casestudy/stale-package-feature-disappearance.md` 的复发段。
- 前瞻性的计划、评审、交接、状态和想法属于本机过程资料，目录与留存规则唯一见[过程资料边界](../process-directories.md)；整理后的案例本身放 `docs/casestudy/`。
- 不带 meta 注释块。开头是 `# 现象式标题`，紧跟 `## 定性`；定性段开头说明本案的范围（哪类用户、哪条路径、哪个候选），承担[文档维护规范](document-truth-and-maintenance.md#先说清范围再写结论)要求的开头范围说明。

## 证据的提交绑定与时态

- 复盘里的 file:line、`git log -L` 命令、包身份和遗留状态，都写明它们所在的提交。行号和代码会随后续提交漂移，没有提交锚的引用无法复核。
- 引用的提交须能从 main 追溯；历史改写后的处理见第 5 节[《历史改写后的 SHA》](#历史改写后的-sha)。
- 遗留一节以「以下按本复盘时（`<SHA>`）的状态记录」开头；之后的变化逐条注明修复提交。
- 仍开放的项指向 Tracker 或 owning 设计里登记的缺口，不写「正在修」「仍须」这类没有时间锚的状态。

## 日期、身份与隐私

- 时间线中的提交写 SHA 和 commit message。日期可写可不写：写就取 main 上的作者日期；不写也不需要说明理由，已有复盘不必补日期。
- 不复制用户发给 Agent 的 Prompt、终端正文、环境变量值和机器上的绝对路径。用户对现象的描述仍按第 2 节逐字引用。
- 原始报错和诊断字段原样贴，只把其中的 Session、Run 和 Provider 原生会话 UUID 换成 `<sessionId>`、`<runId>`、`<nativeId>` 这类占位；错误码和字段名照留。第 2 节的「原样贴」按这条执行。

## 历史清理与改写的语义授权

清理仓库历史（例如隐私扫描后改写提交）时，复盘证据和其他引用按下列规则处理：

- 隐私扫描只能发现候选；扫到不等于可以改写业务值。
- 改写前按 token、引用类型和表达式边界分类；Agent URI、相对材料引用和 skill 引用保留原始字面量。
- 验收靠实际表达式、真实消费者和打包结果；「扫描无命中」「能解析」「整树一致」都不能代替验收。
- 证据绑定精确版本，变化后只补验受影响的范围；保全原始 blob、失败候选和未保存工作。

## 必备章节与验收线

下面九节**全部必须有**。每节除了「在场」，还给了一条**验收线**——判断这节是真写了还是水过去了。
写的人要能通过验收线，审的人照验收线打回。

### 1. 定性 / 事故等级

- 本节的 P0 / P1 / P2 是「事故等级」，只给已发生的事故定性。评审意见与失败检查用测试策略的[评审严重度](../testing/strategy.md#任务验收与假绿防护)，AGENTS 中的 P0／P00 是[产品优先级](../../AGENTS.md#目标与优先级)；三者不互相换算。
- 写清是哪一档，并写**为什么**是这一档。
- P0 的判据（任一即 P0）：触犯 AGENTS 的[健康能力](../../AGENTS.md#健康能力与未知状态)或[工作面恢复](../../AGENTS.md#工作面恢复与终端阅读)底线；我们的防御拿走了已跑通的能力；用户当前无法工作且没有 in-band 恢复路径。不满足这些判据时，按实际影响写 P1 或 P2 并给出理由。
- **验收线**：等级后面必须跟一句可证伪的理由，指向具体后果，不是「很严重」。

### 2. 用户可见症状

- 用**用户自己的话**记录，尽量逐字，保持已确认约束与原观察范围。报错文案原样贴，包括诊断字段；其中的会话与 Run 身份按[《日期、身份与隐私》](#日期身份与隐私)换成占位。
- 一个事故有几个症状就列几个，并说清哪些症状**属于同一个机制、哪些不是**——
  把两个机制的症状混成一个，会让整篇复盘变得可被一条反例推翻。
- **验收线**：至少有一句是引号里的用户原话或原始报错文本；多症状时每个症状后面注明归属哪个机制。

### 3. 影响面：坏了什么，**没坏**什么

- 两侧都要写。只写「坏了什么」不写「没坏什么」不合格——夸大爆炸半径会摧毁整篇报告的可信度。
- 必须收敛到最小真实范围：哪个 Provider、哪种 run、哪条路径受影响；哪些同类路径**不受影响**、为什么。
  有能力清单时逐能力标 STOPS / KEEPS WORKING。
- **验收线**：有一段明确写「以下不受影响」并给出证据（绑定提交 SHA 的 file:line，或可复现的命令），而不是留白；提交绑定规则见[《证据的提交绑定与时态》](#证据的提交绑定与时态)。

### 4. 止血措施

- 回答一件事：**现在**有个用户正卡着，他怎么立刻脱困。
- 与「改进措施」区分：止血是让**当前这个用户**马上能干活（in-band 恢复、或明确的 out-of-band 操作
  如 stop+resume）；改进是防**下一次**。没有 in-band 恢复就如实写「除了 X 之外无法在带内恢复」。
- **验收线**：给出一条现在就能执行的动作，或诚实声明「无带内恢复」——不能空着。

### 5. 引入时间线（必须来自 git，不来自记忆）

- 用命令查，不靠脑补。至少跑这几条并把结果写进来：
  - `git log -S '<关键符号或字面量>' --oneline -- <路径>`（pickaxe：定位**引入**该字符串的提交）
  - `git log -L <起>,<止>:<文件>`（看某段代码逐次怎么被改）
  - `git log --follow --pretty='%h %s' -- <文件>`（该文件的完整改动史）
- 必须点名**引入提交**（缺陷是哪一次带进来的），并引用它的 commit message——
  引入提交的自述常常正是反讽所在（例：一次「放宽过严的门」的修复，放开了 turn 0 却把 turn 1..n
  留在同一类因上）。
- **最锋利的一条**：列出引入之后**每一个改动过同一段代码、却没发现缺陷的提交**，
  并逐条写**它当时在优化什么**（措辞、测试严格度、类型投影、重构……）。这些提交揭示缺陷为什么能存活。
- **验收线**：时间线里的每个 commit 都有能从 main 追溯的真实 SHA + commit message + 一句「它在优化什么/为什么没抓到」（日期可选，规则见[《日期、身份与隐私》](#日期身份与隐私)）；
  「引入之后没有别的提交碰过这段」这种结论必须有 `git log -L` 输出支撑，不能默认。

#### 历史改写后的 SHA

- 复盘引用的 SHA 必须能从 main 追溯。main 历史被改写后，按 commit message 和作者时间映射到 main 上的新提交。
- 改动在历史清理中被并入其他提交时，用 `git log -S`、`--grep` 或改动文件找到承载它的提交，并注明「在历史清理中并入 `<SHA>`」；找不到就改写为文件或符号描述，不留一个查不到的 SHA。
- 外部仓库的 SHA 和 tree 哈希保留原样并注明其性质；描述改写本身的候选 SHA 保留，并注明当前仓库已不可达。
- 包内记录的 tree 与 main 上对应提交现在的 tree 不同时要注明，但不必逐处写「改写前为 X」。

### 6. 根因分析

分三层写，**不许停在最表层的那个 bug**：

- **直接原因**：代码层面直接触发现象的那一步。
- **根因**：一直追问「为什么」，直到答案**不再是关于某行代码，而是关于流程或判断**才停。
  例：不是「native-stop 分支在掉线时没写 readiness」（这仍是代码），而是「续期这件事被设计成
  依赖一个可能永不到达的 hook receipt，且没人问过『Agent 还能干活吗』」。
- **为什么没被更早发现**：测试为什么没红、评审为什么放行、监控为什么没响。
- **已有成文规则却被违反时**：根因**绝不是「我们不知道」**。必须点名**规则为什么没能约束住**
  ——它只是一句话没有机械执行？三次改到这段代码的提交都没触发它？——因为一条存在却被反复
  绕过的规则，需要的是机械化的强制手段，不是把规则再抄一遍。
- **验收线**：根因那一层的句子主语是流程/判断/机制，不是某个函数名或某一行；
  涉及已有规则时，明确写出「规则 X 存在但没绑定住，因为 Y」。

### 7. 改进措施

编号列出。**每一条**都必须自带下面三个字段，缺任一字段的改进动作不合格：

- **是否足够 root**：修的是这一类还是这一个实例？点名这个**类**，并说清同类还有几个实例
  （precedent scan 的结果要在这里落地）。只修了 N 个已知实例中的 1 个，必须如实说「另 N-1 个未动」。
- **能否彻底避免**：这条措施是**本可以阻止**这次事故，还是只是让它**更快被发现/被缓解**？
  要诚实。「无法阻止，只能更早发现」是可接受的答案；把「更早发现」伪装成「彻底避免」不可接受。
- **是否降低系统熵**：它是**去掉**一个概念/分支/特例，还是**加**一个？
  加 flag、加配置、加重试层、加兼容路径都是**增熵**，必须对照一个「更简单但被否掉的方案」来论证
  为什么仍然选它（见 [AGENTS《实现选择》](../../AGENTS.md#实现选择)）。
- **验收线**：每条改进动作下面都能看到这三个字段的答案；「是否足够 root」里出现具体的实例计数；
  任何增熵的改动都附了「考虑过并否掉的更简方案」。

### 8. 验证

- 每条改进措施怎么被证明有效，逐条写。
- 实现改进按[测试策略《任务验收与假绿防护》](../testing/strategy.md#任务验收与假绿防护)证明；以下要求针对实现，纯文档整理使用来源、链接和语义保全 review，不编造代码变异或调用者：
- 指出每条实现措施实际承重的变异、单独变红的结果和真实产品消费调用链。源码扫描或文本匹配不能替行为证明；扫描及空集合的假绿防护统一消费测试策略，不在案例指南复制另一套规则。
- 测试从仓库根跑，剥掉 ambient env（写清命令）。
- **验收线**：每条改进措施旁边有一条**可复现的命令，或绑定提交 SHA 的 file:line**；只写「已验证」不给命令的不合格。

### 9. 遗留

- 以「以下按本复盘时（`<SHA>`）的状态记录」开头，之后的变化逐条注明修复提交（见[《证据的提交绑定与时态》](#证据的提交绑定与时态)）。
- **有意识没修的东西**，逐条写清「是什么」和「为什么现在不修」。
- 未证实、只做了静态判断的结论，如实标 PARTIAL 并说明缺哪一步验证。
- **验收线**：这一节非空；如果真的什么都没留，写「无遗留」并说明为什么这次是闭合的。

## 反作弊：一篇「通过但没用」的复盘长什么样

审的人重点抓这几种水过去的写法：

- 时间线只有引入提交，没有「后续没抓到」的提交——缺了缺陷为什么存活的解释。
- 根因停在某个函数/某一行，主语还是代码——没往上追到流程或判断。
- 改进措施三个字段有形无实：类没点名、实例没计数、增熵的改动没有「更简方案」对照。
- 「能否彻底避免」全填「是」——现实里检测类措施占多数，全「是」多半是没想。
- 影响面只有「坏了什么」，没有「没坏什么」，范围写得比实际大。
- 验证只有「已通过」三个字，没有命令、没有承重变异。

## 骨架模板（可直接复制）

```markdown
# <用户看到的现象，一句话>

## 定性
P0 / P1 / P2 —— 因为 <可证伪的理由，指向具体后果>。

## 用户可见症状
> <用户原话或原始报错文本，逐字>

- 症状 A（机制一）：…
- 症状 B（机制二，与 A 不同源）：…

## 影响面
坏了什么：<Provider / run / 路径，逐能力 STOPS>。
没坏什么：<不受影响的同类路径 + 证据 <SHA> file:line>。

## 止血措施
现在卡住的用户：<一条立即可执行的动作，或「除 X 外无带内恢复」>。

## 引入时间线
命令：`git log -S '…' -- <路径>` / `git log -L …` / `git log --follow …`
- <SHA> 引入提交：<message 摘要>，反讽在于 <…>。（日期可选，写就用 main 上的作者日期）
- <SHA> <message 摘要>：只优化了 <措辞/测试/重构>，没问「Agent 还能干活吗」，故没抓到。
- <SHA> <message 摘要>：…

## 根因分析
- 直接原因：<触发现象的那一步>。
- 根因：<主语是流程/判断/机制，不是某行代码>。
- 为什么没更早发现：<测试/评审/监控为什么没响>。
- 已有规则为什么没绑住：规则 <X> 存在，但 <只是一句话没机械执行 / …>。

## 改进措施
1. <动作>
   - 是否足够 root：<修的是「<类>」；同类已知 N 个实例，本条覆盖 M 个，其余未动>。
   - 能否彻底避免：<本可阻止 / 只能更早发现——诚实>。
   - 是否降低系统熵：<去掉了 X / 加了 X；否掉的更简方案是 Y，因为 Z>。
2. …

## 验证
- 动作 1：命令 `env -u … pnpm exec vitest run <paths>`；承重变异 <…> 单独打红；
  生产消费调用链 <owning 入口到真实消费者>，方法与假绿防护见测试策略。
- …

## 遗留
以下按本复盘时（`<SHA>`）的状态记录。
- <有意识没修的 + 为什么>；<标 PARTIAL 的未证结论 + 缺哪步验证>；<仍开放项指向的 Tracker 或设计缺口>。
```
