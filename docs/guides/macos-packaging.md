# macOS 打包与安装

本页面向并行开发中的一次打包交付，唯一持有打包的步骤、可复用的结果与补查条件；打包原则见 [AGENTS](../../AGENTS.md#打包)。构建、更新路由及进程机制见 [Desktop 更新架构](../architecture/desktop-updates.md)，数据与恢复要求见 [Session 恢复](../design/behavior/session-recovery.md#更新安装与恢复验收)。本页不增加发布门禁，也不把某轮临时安装脚本当成正式入口。

## 最短交付路径

影响当前操作的修复（例如 Terminal／TUI 的使用问题）在自身验证通过后及时打包安装，不等待无关功能收口；安装仍保留原工作面和健康 Run，安装成功与用户问题已解决分别验收。

1. **锁定开包时最新的 committed main。** 记录 commit 与 tree；共享工作区有并行修改时，在该提交的独立干净 worktree 构建。可复用一份明确由打包流程持有的专用 worktree，其可选的本机记录位于 `.local/package-delivery/reusable-worktree.json`（仅本机，不随仓库分发；仓库中没有脚本读写它，由执行打包的 Agent 自行维护）：先确认它仍为本仓库注册的 worktree，且没有在途构建、未提交或未跟踪工作，再只在该 worktree 更新到锁定的提交；记录缺失或状态不明时保留原内容并新建隔离 worktree。保留他人的修改，不用 stash、切共享分支或清场换取干净目录。构建中 main 继续前进不触发自动重打；交付时说明本包锁定提交，不能称其包含开包后的提交。
2. **准备锁定依赖，选择一个入口。** 复用专用 worktree 中与锁定依赖相符的 `node_modules` 和原路径的原生构建缓存；依赖输入变化时按锁文件重新安装。本地 `file:` 归档内容变化也属于依赖输入变化；pnpm 的重复安装优化可能漏刷同路径归档，此时用 `--config.optimistic-repeat-install=false` 更新受影响依赖。缓存齐全时可用 `pnpm install --offline --frozen-lockfile`；缓存缺项则由正常锁定依赖安装补齐。运行时同样沿锁定依赖的官方安装入口准备，不依赖开发目录残留，不另造下载器，也不借用其他 App。然后按下文[《入口、产物与安装位置》](#入口产物与安装位置)选一个入口。打包入口本身已执行依赖构建、组包、签名和产物检查，外层不再先跑一遍完整 build、typecheck 或测试套件。整条打包命令每次都要求干净源码树并重新构建，所以已有签名候选的安装续做不重新调用它；当前没有命令行续做入口，续做方式见下文「失败后从准确阶段续做」。
3. **复用同一候选与已有结果。** App、DMG 和安装副本来自同次构建；按已完成阶段核对准确身份，复用功能任务已有验收。DMG 压缩和 App 复制会争用磁盘，不默认同时启动多个重 I/O 任务；同机其他 Agent 正在工作时优先控制并发和重复副本。只在阶段转换或具体失败时读取相关日志，不高频扫描全局进程、目录、工作面或重算整包散列。DMG 的输入副本在镜像创建、准确卸载和验证均成功后应立即释放，再创建核验副本；失败沿原诊断与暂存保全路径处理，不提前删除输入或改变已签源。
4. **安装后核对实际加载，再清理。** 从 `~/Applications/AgentMux.app` 经 LaunchServices 正常启动并通过就绪检查，核对实际 Main、Renderer、必要持久保存、原工作面和相关 Runtime／Run 事实；磁盘身份或版本号不能代替已加载身份，核对方法见[《安装后的身份核对》](#安装后的身份核对)。然后清理本次不用的中间产物与 worktree；可保留一份明确供后续打包复用的专用 worktree 和构建缓存，并保留在用映像、未保存工作和必要原始回执。清理不能成为安装前置条件。

## 入口、产物与安装位置

先按[打包协作约定](../../AGENTS.md#打包)确认本次允许的操作。整包从开包时锁定的干净提交构建，Desktop 自己的 prebuild 负责工作区依赖、原生组件与资源。

| 本次要交付什么 | 入口 | 结果与后续动作 |
| --- | --- | --- |
| 更新本机，允许按需重启 GUI | `pnpm update:local` | 构建一次。候选与已装 App 的 `shell`、`ctxmux` 指纹都匹配时热更 Renderer；`ctxmux` 匹配而 `shell` 不匹配或缺失时，用同一次构建签出并安装完整 App。已装 App 缺少前端 release 清单也走 App 安装，由安装器核对实际 Runtime。 |
| 仅允许热更 | `pnpm update:renderer` | 匹配时只切换 Renderer，Main 与 Run 继续运行。需要安装 App 或评审 Runtime 时，命令返回原因与后续入口，负责人按本次委派范围处理。 |
| 本机直接安装完整 App | `pnpm package:mac:install --app-only` | 签名、核验并安装到 `~/Applications/AgentMux.app`。原 GUI 正在运行时先确认保存并正常退出，再启动候选；已有旧 App 移入 Trash。 |
| 暂缓 Native 升级，明确要安装 App | `pnpm update:local --ui-only` | 直接选择 App 安装并启动候选 GUI，已有 Runtime 服务时核对候选能否接入，无 listener 时由正常启动创建 Runtime。安装器按需重载 semantic Host，分别报告 UI 与 Native 的结果。 |
| 构建分发件 | `pnpm package:mac` | 生成 `apps/desktop/release/mac/AgentMux.app` 与包含该已签 App 的同批 DMG（未公证）。选择 `pnpm package:mac:install` 会同时安装该候选。 |

已有清单的 `ctxmux` 指纹变化或缺失时，普通更新返回 `runtime-review` 并保留原工作面。要升级 Native，先按[分层更新与回切](../design/behavior/session-recovery.md#分层更新与回切)评审原 Run 兼容性及 Provider resume，然后运行 `pnpm package:mac:install --app-only --runtime-reviewed=<评审记录路径>`。安装器读取非空记录，核对实际 Runtime，并验证交接结果。保存被拒或资格未知时沿[失败续做](#失败后从准确阶段续做)处理。

`--app-only` 选择产物，本机 App 路线省去 DMG 的创建、挂载核验与发布，保留 App 的签名、Runtime 核验和启动验证，回执为 `dmg=not-requested`。`--ui-only` 选择安装意图，在直接安装入口也可与 `--app-only` 合用。两者可以独立选择。

回切前端用 `pnpm update:renderer:rollback` 或应用菜单 View > Revert frontend update。排查同名 App 用 `pnpm package:mac:report` 核对候选、canonical 安装、系统 Applications、开发缓存与运行实例。报告在候选缺失或输出不完整时给出缺少的路径，仅作诊断。

`apps/desktop/out`、DMG 挂载目录和任意临时或旧的 `.app` 都不能安装；只有同一次 clean build 产生的 `release/mac/AgentMux.app` 能进入安装动作。远端机器安装可以传输这份同批已签候选及准确安装源码／运行依赖闭包，保持 `release/mac/AgentMux.app` 的构建来源、签名与传输完整性，再调用原 `installApplication`；传输不产生第二候选或第二安装器，也不能把任意 DMG 提取副本当作已核候选。候选在签名、身份核对或安装前启动验证的任一步失败时，入口保留现有 canonical 安装并报告失败阶段，不能把旧包或半成品报告为新版本。已安装的旧副本只移入 Trash 或经用户确认清理；可再生的私有暂存沿下文 owner 自动收尾，不删除 Application Support、Session、Run 或工作区数据。

### 产物的自动收尾

创建副本的流程负责释放它，不另设后台清理器：

- 安装器创建的私有暂存，在复制、验签或安装前资格检查失败、尚未开始目录切换且原已签源仍能确认同一候选时自动移除。唯一候选、明确采用的原暂存、已经进入切换或回滚的候选继续保留供续做。清理失败附在原错误上，不覆盖原失败，也不触发重放安装。
- Mac DMG 与 Linux 命令行分发入口将归档发布到同一仓库的共享 `.local/package-delivery/artifacts/<target>/`，打印准确路径、摘要和清理结果。直接交付该路径，不再自行复制日期目录或额外 App。`--app-only` 不发布归档；可复用的 Linux 构建函数仍只写调用者指定的输出。
- 每个 target 尽力保留最近两次完整发布；新包完整写入并核对身份后才清理更旧的归档。挂载、打开或占用观察不明的包保留，后续发布再尝试。并发发布可暂时多留，不为严格数量引入锁或守护进程。只处理此 writer 的完整回执与原对象，不扫描旧历史目录、未完成发布、worktree 或 Trash。
- 发布或清理失败单独提示，原构建输出、安装结果和可用能力保留；不为此重构、重签或重新安装。小回执保留，构建缓存与专用 worktree 沿原归属规则复用。

### 签名身份

- 正式签名：把 `AGENTMUX_MACOS_SIGN_IDENTITY` 设为可用 Developer ID Application 证书的准确 SHA1；未设置时读取本机记录 `~/.agentmux/signing/identity.json`。
- 本机签名身份：先运行一次 `node apps/desktop/scripts/macos-local-signing.mjs --setup` 建立身份，再运行 `--trust`，由本人认证当前用户的代码签名信任策略。
- 开发打包须显式加 `--ad-hoc`。它与环境变量中的证书互斥，也不能与 `--install` 一起使用（每次构建都会改变隐私授权身份）；不确认授权连续性，并跳过 LaunchServices 检查。

### 安装后的身份核对

- 候选携带来源身份 `package-identity.json`：源码 commit、tree、应用版本、平台与架构。安装前后核对同一身份；版本号相同不等于产物相同，排障不能只看 `CFBundleVersion`。
- 重启从 `~/Applications/AgentMux.app` 发起，把运行进程的真实 executable path 与 bundle 内的 `package-identity.json` 对上；对不上时报告「启动了其他副本」，不能解释成代码回滚。
- 当前 UI 的身份和完整工作面经 `connectAgentMuxRpc()` 的只读 `app.inspect` 确认，观察连接在成功与失败后都释放。观察失败只说明这一步未确认，不代表健康 Main、Session 或 Run 已失效，也不授权停止它们。
- 交付说明里的关键用户能力沿用任务验收已有的「设计约束 → 生产实现 → 测试调用者」三段证据。删除了实现文件时，指出替代实现与仍在生产路径上的调用者，或标为待人工复核；单元测试本身不能证明能力没有被并发改动从产品路径上去掉。

## 必要核对与触发式补查

| 阶段 | 本次应消费的证据 | 何时才补查 |
| --- | --- | --- |
| 源码与构建 | 锁定的 commit／tree、准确构建结果 | 源码身份漂移或具体编译失败 |
| 候选与 DMG | 原入口产生的签名、来源身份、组装结果 | 候选字节变化、签名失败或容器身份不符 |
| 安装与重启 | 原安装动作结果、实际加载的包和 Renderer、工作面及相关 Runtime 事实 | 退出、加载或保全出现具体失败／差异 |
| 清理 | 本次准确目录的提交、未保存内容与占用事实 | 目录存在独有工作、在用引用或归属未知 |

这不是让操作者再手工执行一遍同名检查。入口已有准确结果时直接复用；缺口只补该项。打包复用各任务已完成的功能与视觉验收：除用户明确要求，不把全量回归、功能 E2E、重复图审、深度签名核验、多轮全文件比对、全仓资源盘点、无关验收或等待后续提交加成前置条件；候选未变且没有具体失败依据时，不以「多验一次总没错」重复构建、扫描或校验。安装不重新证明全部功能、打开隐藏 Browser 页面、等待所有页面联网或要求同事停止开发。原安装入口对新复制目标的签名与身份核对仍有自己的范围。

## 失败后从准确阶段续做

以下各条的共同原则：只修复失败的那个阶段，复用仍有效的构建、签名候选和暂存副本；时限只约束它准确保护的对象，观察未知不授权停止进程、重放操作或重构未变化的候选。

- **先保留原 operation 与结果。** 区分未开始、暂存完成、已替换、已启动和观察未知。确认原进程及实际副作用后再决定下一步；未知不自动重放，后续成功不覆盖原失败。只修复失败阶段，复用仍有效的构建、签名候选和暂存副本。当前没有命令行续做入口：[package-macos.mjs](../../apps/desktop/scripts/package-macos.mjs) 导出的 `installApplication` 接受 `preparedApplicationPath`，可显式采用原暂存目录，核对它与选定签名源的包身份、主程序和签名封印，继续原验签与后续检查；此路不删除或重新复制暂存，不把 canonical App 当作暂存。`package:mac*` 命令不暴露这个参数，调用它需要直接调用该函数。
- **复制慢不等于 App 故障。** 不给额外包装器随意套一个比真实复制更短的总超时；原安装入口的复制并未使用 GUI 就绪时窗。超时后先确认复制进程已结束、canonical App 是否变化，再处理该次不完整暂存目录。不要因复制失败重编译或重签未变化的候选，也不要改大 GUI／Runtime 时窗来处理磁盘复制问题。
- **启动烟测等待原消费者的真实就绪。** Hosted consumer 初次连接尚未确认时，保留原诊断并等待其既有后台重连；恢复通知只唤醒同一消费者的完整 bootstrap 确认，不直接代签 ready。父级原总时窗继续约束烟测，不另加重连循环、预算或 Runtime；准确终局与取消仍释放本次观察。
- **Host 身份与 UI 读取不另套固定子进程总时窗。** 续做原安装时，消费原 fenced bootstrap／`app.inspect` 的真实回复或失败，不提前杀掉仍可完成的查询。保留原 UI activation 的轮次等待范围，不把它宣称为已实现的在途取消。原 Runtime、PID、UID、出生时间与映像归属核对继续有效；观察未知不授权停止未知进程，也不要求重构未变化的已签候选。
- **Runtime 声明查询等待原进程实际退出。** 已签候选复制后的 `--version` 读取不另加固定取消时窗；完整输出仍须通过版本、protocol、handoff 及前后 inode／digest 核对。等待期间立即报告准确候选、查询 PID 和已等待时长，并每五秒更新；SIGINT／SIGTERM 只结束这一个声明查询子进程，等待其真实关闭后沿原安装失败回执说明中断，保留同一已签候选。原已签源仍在时可释放可再生暂存；唯一或明确采用的原暂存继续保留。查询中断不能证明 Runtime 故障；原 App、运行中的 Runtime 和用户数据保持原样，复用同一已签候选从准确阶段续做，不因此重构或重签 App。
- **签名深度核验等待真实结果。** `codesign --verify --deep` 的耗时随候选内容增长，正式入口显示当前核验阶段，不以固定短时窗杀掉仍在进行的核验；终端可沿原方式中断本次打包。证书、身份和签名失败仍按原结果拒绝，其他原生查询的时窗不变。
- **GUI 与 Node 模式分开。** GUI 启动沿原入口从环境副本移除 `ELECTRON_RUN_AS_NODE`；CLI 和 semantic Host 的有意 Node 模式保留。这里只调整 Electron 启动模式，不移除、改写或伪造 Agent 凭据与权限身份。
- **退出检查只判断真实当前对象。** 进程 `admissions` 是历史，当前 `serving` 与准确 UID/PID/birth、实际映像和执行模式才参与当前归属判断；展示 title 或 argv 变化不撤销同一对象的模式读取，也不授予 GUI 身份。历史条目仍在不等于进程仍活；未知模式也不能猜成 GUI 或后台。semantic namespace、GUI worker 和独立 Run 的范围沿原机制确认，不能从脚本名或命令行外观猜测后强杀。旧 GUI 在切换前重开时，刷新它的准确保存／退出观察，复用已准备好的候选。
- **首次升级 Desktop 用户数据存储 owner。** 旧运行版本缺少 native 保存观察时，热安装会在退出前拒绝；Chromium 目录存在和 void flush 都不能补成写入回执。先经原 App 的正常退出保留其数据，再沿同一安装入口走已有 cold 路径，不强杀 GUI 或另开数据根。[安装事务](../../apps/desktop/scripts/package-macos.mjs)只切换应用目录；新 Renderer 读取原根中的旧数据，并由 Main 的一次性导入取得真实写入确认。缺少 outgoing 工作面观察的 cold 收据保持 `unknown`，不能证明原布局、草稿或 Session 已完整连续恢复；实际恢复仍按[持久化合同](../design/behavior/persistence.md#退出更新与恢复)核对。
- **接口拒绝只解释该次操作。** Core `runtime.*` 的身份拒绝不等于 macOS 文件安装也被拒绝；但不能通过去掉凭据、换终端或代按确认来重做同一个被拒操作。依据用户已有安装授权和准确操作范围继续可执行步骤，不额外制造人工确认门。仅完成 App／Renderer 替换、保留旧 semantic Host 时，应分别报告这些结果，不能宣称 Core 服务已重载或 Native 已升级；正式安装器的 Host reload 路径仍以实际源码与回执为准。

## 记录耗时，不把经验变成额外验收

使用现有阶段时间、失败回执和必要日志区分编译、签名、复制、容器压缩、退出观察与清理。签名和复制本身可能耗时，不能据此虚构“校验很多”；重复构建、过短超时导致的重复制、把历史当存活进程而循环等待，则属于应消除的操作负担。没有具体异常时不另跑资源 benchmark 或全局采样来证明打包足够轻。

安装调用方须完整保留返回或异常中的 `transaction`，包括 `ui.continuity.before/after`，沿原诊断规则写入本机回执；只摘录 status／error 会丢失正式保存与恢复的比较依据。包装器较早的 inspect 不能代替安装器实际退出前的观察。正式原件缺失时，该次连续性保持 `unknown`；当前已装版本的独立重启验证是新操作，不能追认旧次成功，也不能据跨越正常操作的两次快照差异直接重写用户布局。

每次打包的原始时间线、具体提交、PID、临时脚本与重试证据只留本机过程目录；后续可复用做法保留在本页，不能从文档更新推断打包工具已获得新的实现能力。
