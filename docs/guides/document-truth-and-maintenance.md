# 文档事实与维护规范

本文定义 AgentMux 文档的职责、写法与更新方式，供人和 Agent 阅读、修改项目文档时使用。产品行为归设计 SSOT，协作底线归 AGENTS；本规范不增设发布 gate、运行时元数据或第二份事实库。

## 每份文档只回答一类问题

| 文档 | 回答的问题 | 不在这里重复定义 |
| --- | --- | --- |
| README / 文档导航 | 项目做什么、从哪里开始、去哪里找规则 | 全部设计、状态快照和验收清单 |
| AGENTS.md | Agent 工作时必须遵守哪些目标、边界和责任 | 事故推演、测试技巧与工具实现细节 |
| design | 产品必须满足什么行为或视觉约束 | 聊天时间线、实现步骤、Task 进展 |
| architecture | 当前机制如何工作、谁持有什么事实 | 未落地方案或无来源的当前能力 |
| specs | 一个接口或协议的准确合同、适用范围 | 另一层的生命周期或同一合同的副本 |
| guides | 对某个任务怎样操作、前提和失败怎样处理 | 新产品要求或并行命令词典 |
| testing / benchmarks | 怎样验证、oracle 能证明什么、成本怎样测 | 本批候选已通过或竞品排名 |
| casestudy | 某次事故发生了什么、证据与教训是什么 | 当前缺陷清单或今天的执行授权 |
| 本机过程资料 | 本轮计划、评审、交接、状态与证据 | 新的长期规则或 Tracker 状态镜像 |

目录的跟踪与保留规则只由 [过程目录](../process-directories.md) 定义；入口只由 [文档导航](../README.md) 组织。小主题先合入现有 owning 专题，有独立读者问题和边界时才新增文件，不为每次讨论拆一页。两份设计 SSOT 的原路径是专题导航入口，完整行为及视觉要求在各自专题中；新增约束写进 owning 专题，入口只维护可发现性。

## 沿对象找事实，沿读者意图选入口

读者要理解某个对象时，先找它的已确认约束，再到机制、公共接口、操作和验证来源。导航连接这些层，不把所有内容复制到一份巨型合同。查看事实、执行操作和管理配置的读者意图必须可辨；接口及 CLI 的精确合同指向实际类型、export、parser、help 和业务 owner，同一能力不会因为换入口拥有第二份定义。当前来源与目标设计分开说明，目录中有文档或源码有 symbol 都不自动代表实现或安装已交付。

## 先说清范围，再写结论

开头用一至三句话说明本文负责什么、适用范围及主要依据。只有在容易误读时才补充状态，例如「提案，尚未实施」「历史验证结果」「当前源码机制」；不强制统一 front matter、更新时间字段或固定模板。

一段落只推进一个问题：先给结论或必须成立的约束，再给必要的原因、边界或动作。表格用于可比较的对象、owner 或接口；步骤用于真实执行顺序。技术名词使用 [交互 SSOT 的概念词典](../design/behavior/spaces-and-layout.md#统一概念与空间寻址)，不因换表面另铸名词。

规范使用明确的主体、条件、动作和结果。必要的「必须」说明它保护什么；提示和建议写成提示和建议，不借措辞升级为门禁。不同领域规则冲突时，在确认的 owning SSOT 中修正，再让引用者跟进；不要靠后追加一句相反规则让读者自己选。

## 区分四种事实

1. **已确认约束**：写进 owning 设计合同。它描述必须成立的结果，不自动证明实现已满足。
2. **当前实现**：给出能核对的源码文件和关键 symbol；源码、构建、安装副本与实际运行实例分别表达。
3. **已验证结果**：绑定实际候选、场景、命令、结果和未覆盖范围。旧 receipt 只证明旧候选，不因文档改了版本号而获得新资格。
4. **提案或历史**：明确其未实施或当时范围。方案被替代后保留必要历史证据并指向现规则，不继续作为当前操作入口。

未知就写未知。测试全绿、进程 running、字节写入、保存请求与安装成功，不能彼此提升成任务完成、用户接受、磁盘确认或原工作面已恢复。

## 一个事实只在一个地方定义

- 产品交互和行为在交互 SSOT，视觉和密度在密度 SSOT；相邻文档链接到 owning 章节，不复制规则全文。
- 当前版本、平台、协议、依赖和 artifact identity 引用 manifest、package 或 lockfile，不在多份正文手抄一套。历史证据中的原版本、SHA 和测量值保留，注明范围。
- 当前命令以实际执行版本的 `--help` / `--skill` 为准；源码目标命令树明确为目标，不冒充已安装能力。操作指南给原入口和前提，不成为第二份 parser 合同。
- 源码引用优先用 repo-relative 文件链接加 symbol，避免易漂移的当前行号。复盘可保留绑定提交的原 file:line 证据。
- 过程性文档不提交，包含 raw 调研、计划、评审、状态、原型和验收输出；长期结论经过提炼再归原 owner，完整记录和证据留本机。忽略与已有跟踪文件的处理唯一见[过程资料边界](../process-directories.md)。长期说明不依赖本机资料；可选证据注明范围与缺口，不能伪造永久链接或当前验收结论。

## 用新的约束替换旧的表达

用户讨论后，先提取已确认约束与未决问题，再原位合并到相关章节；保留必要的用户原话，删除重复叙述。不持续追加「用户进一步反馈……」形成聊天日志。旧细则被取代时合并或删除，旧现场与推导移到对应复盘或本机过程资料。

章节按稳定读者问题组织，标题描述内容，不把日期、状态和内部 Task ID 当正文导航主轴。已有公开引用的标题有真实变更需要时才改，修改时同步入口；不为了统一外观全仓机械重命名。

新增架构事实先核源码，新增验收结论先核实际证据。发现实现与已确认约束不一致，分别说明要求和现状，并登记实际缺口；文档修订不替实现宣布完成。

## 完成一次文档修改

检查范围限本次改动及直接受影响的引用：

- 内容是否属于该文档、同一规则是否已有 owner、旧表达是否已收敛。
- 当前事实是否有来源，历史身份是否保留，未实施与未知是否明确。
- 新增或修改的本地链接与章节是否可达；扫描式检查必须证明扫描集合非空。
- 比较修改前后，确认目标、权限、恢复、健康 Run、用户工作面、成本和验收责任没有被精简掉。实质规则重组由独立 Agent 做一次语义保全 review。
- 运行限定文件的 `git diff --check`，阅读最终 diff 与提交清单，保全同事的 staged / unstaged 工作，按过程资料边界排除本机文件。

纯文档改动采用来源核对、链接和语义评审；不构造不存在的代码调用者或代码变异证据。实际改了产品、脚本、协议或功能验收标准时，仍执行该实现任务原有的行为验证。复用有效证据，不为排版改动新增全量回归、UI 图审或打包前置流程。

收尾报告写清本次修正了什么、以什么依据核对，以及仍未核实的范围。规范可随实际问题修正，但新的检查必须有具体保护对象，不能靠多一层流程证明文档质量。
