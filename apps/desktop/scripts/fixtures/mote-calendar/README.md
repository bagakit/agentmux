Run `node apps/desktop/scripts/fixtures/mote-calendar/capture.mjs` from this worktree after the product Calendar source is ready. It bundles current product source privately, mounts the original `MoteFilesTool`, `MoteProfilePopover`, `MoteDetailsPanel`, `AgentSessionComposer`, `DesktopClientUiProvider`, CSS and theme/icon runtime, then operates real controls with native Electron mouse/keyboard events.

Only the outer Space shell, static discussion prose, two exact synthetic Session references, a Goal, filesystem replies and typed schedule API replies are controlled. A responsive wide Space pane, narrow viewport and original constrained popover do not replace product component CSS. Profile exercises a compact employee card, all four confirmed personality axes, partial and unconfirmed behavior reads, original work, saved memory, private-chat settings, upcoming-arrangement navigation, preferences, long names and an expanded long introduction on a short narrow surface. Ideas exercises request input, local filtering, selected-file reading, same-file unknown recovery and wide/narrow navigation. Calendar exercises month/week/agenda, date selection, creation, unknown original receipts, explicit same-operation reconciliation, confirmed-save feedback and exact-item navigation. Schedule list checks exact Mote physical scope; all create/mutation/inspect replies stay in memory. This proves Renderer presentation/interaction against controlled data, not Main/RPC persistence, actual scheduler timing, Provider/model behavior, installed Desktop, or runtime recovery.

The same native Renderer records visible geometry, body/prose font sizes, local horizontal overflow and original header control hit tests. For the short-name `Mote` with the default fine pointer, the wide Profile places a finite identity card, at most 241px wide, beside the work area with visible spacing below and starts personality content within 72px. A compact identity header occupies at most 45% of the available height, leaving the first useful content within 55%; the long-introduction scene checks the same rule after expansion. The first populated Calendar date starts within 180px when its toolbar is wider than 600px, or 250px when that toolbar wraps. The Calendar's own scroll offset is included so scrolling cannot make an oversized toolbar pass. Long names continue through the independent readability, hit-test and close-control overlap checks without either short-name height budget. Coarse-pointer scenes instead protect 44px targets, readable content and unobstructed controls; their larger hit areas are not constrained to the fine-pointer height budgets. Each geometry record names its applicable pointer policy and records the exact name. Body text remains at least 12px and saved-file prose at least 13px. An intermediate 620px pane exercises the compact header and Calendar wrap points. A 1120px synthetic outer pane crosses the production Calendar's wide breakpoint and checks that the initial month fills the space available to its canvas.

Three `insertCSS` mutations stretch the original identity card to full height or add excess height to the original navigation bar and Calendar toolbar. Each must trigger its own density assertion; `removeInsertedCSS` runs in `finally`, then the same budget must pass. Mutation geometry and assertion messages are retained in the Renderer result. Native touch emulation must actually match `(pointer: coarse)` before the original Mote tabs, Calendar toolbar controls, saved-note row and Back action are checked for 44px targets and center-point hit testing. These checks establish measured layout and operability, not aesthetic approval; the complete captured images still require independent review.

Every child starts after clearing inherited `AGENTMUX_*`, `CTXMUX_*` and `ELECTRON_RUN_AS_NODE`; its Runtime, state, store, queue and Electron userData paths are unique to that capture. No preload, user journal, user schedule, real Session/Run or model is opened. Compiled output is removed after source/PNG/log/operation hashes are written. Receipts are `captureOnly: true`; capture success is not aesthetic approval. Another agent must open every complete PNG and review the exact candidate.
